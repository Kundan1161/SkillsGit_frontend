# Rate Limiting Strategy Designer

## When to use

Use this skill when an engineering team needs to pick a rate-limit approach for a workload and turn the choice into an implementable design. The output covers algorithm selection, the key by which limits are scoped, coordination across nodes, the response contract a client sees when limited, and abuse-handling escalation. The skill is opinionated about which approach fits which problem; it does not commit to a specific product or library.

The skill applies to:

- Public APIs that need fair, predictable limits per customer or per API key.
- Internal RPC fabrics where one caller can accidentally saturate a shared dependency.
- Authentication endpoints under brute-force pressure that need graduated response.
- Billing-sensitive endpoints where each call carries cost and quota matters more than throughput.
- Background-job systems that must throttle work hitting a fragile downstream.

Do not use this skill for:

- Capacity planning of the underlying service (sizing CPU, memory, connections) — rate limiting is a guardrail, not a substitute for capacity.
- DDoS mitigation at the network or transport layer — that lives in a different layer and uses different signals.
- Fairness-only schedulers where the goal is interleaving rather than blocking — weighted-fair-queueing has different primitives.

## Inputs

- `workload_profile` (required) — Drives algorithm choice. Bursty interactive traffic, smooth steady traffic, and write-amplifying work each prefer different shapes.
- `tenancy_model` — Drives key scope and the hierarchy of limits.
- `deployment_topology` — Drives the coordination model — local-only is fine for a single node, distributed enforcement is needed when N nodes share one quota.
- `fairness_goals` — Drives whether per-key limits, per-tenant caps, or both are required, and how strictly limits must be honored.
- `abuse_signals` — Drives graduated response and the attribution choice (IP vs auth vs fingerprint).

## How to apply

The design proceeds in layers: the algorithm, the key, the coordination, the response, the abuse handling, the rollout.

### 1. Frame the goal precisely

1.1. State what the limit protects. Three common purposes lead to different designs:

- **Resource protection** — the downstream cannot survive the rate. The limit must be enforced strictly.
- **Fairness** — one caller must not starve another. Approximate enforcement is acceptable as long as the busy caller is slowed.
- **Cost or quota** — each call has a price; the limit is a billing primitive that must be accurate.

1.2. State the time horizon that matters — burst (a few seconds), sustained (per minute), aggregate (per day). Many designs combine two horizons.

1.3. State the failure mode when the limit-store is unavailable — fail open (allow), fail closed (deny), fail degraded (fall back to a coarser local limit). Pick one and stick with it.

### 2. Choose the algorithm

2.1. **Fixed window** — count requests in `[t, t+W)`; reset at boundaries. Simplest, lowest cost, easiest to explain. Pathology: a client can double-spend across a boundary (full quota at second 59, full quota again at second 60). Acceptable when the limit is loose or the boundary effect is irrelevant.

2.2. **Sliding window log** — store a timestamp per request; count those inside `[now - W, now]`. Exact, but storage is proportional to traffic. Use only when limits are tight and traffic is modest.

2.3. **Sliding window counter** — weighted blend of the current and previous fixed windows by overlap fraction. Approximates the log within a few percent, with the cost of a fixed window. Strong default for HTTP request rate limiting.

2.4. **Token bucket** — tokens refill at a steady rate up to a cap; each request consumes one. Burst-friendly: a client can spend the bucket then pay only at the refill rate. The mental model most APIs want to expose to customers.

2.5. **Leaky bucket** — outgoing rate is fixed; requests queue or are rejected when the bucket is full. Smooths bursts before they reach the downstream. Right when the downstream cares about pacing, not just count.

2.6. **GCRA (generic cell rate algorithm)** — store a single timestamp per key (theoretical arrival time) and accept or reject based on whether the new arrival lies within tolerance. Mathematically equivalent to a leaky bucket but storage is O(1) per key. Excellent fit for distributed enforcement with a single round-trip per check.

2.7. **Concurrency limit** — limit the number of in-flight requests, not the rate. Right when the bottleneck is a resource pool (connections, threads, memory). Often combined with one of the rate algorithms above.

2.8. **Quota / budget** — a counter consumed over a long window (per day, per month). Used for billing-tier enforcement. Pair with a separate burst limit; quota alone does not protect against per-second floods.

2.9. **Heuristic for first pass:**

- Burst-friendly public API: token bucket.
- Smooth-pacing requirement for a fragile downstream: leaky bucket or GCRA.
- HTTP request rate with low storage budget: sliding window counter.
- Strict billing accounting: quota plus a token-bucket burst gate.
- Login or other abuse-prone endpoint: fixed window plus graduated response (Section 7).

### 3. Pick the key (scope of the limit)

3.1. The key determines who is being limited. Common keys, ranked from least to most trustworthy:

- **IP address** — easy to assign, but cheap to evade (proxies, CGNAT, mobile carrier pools). Use only when no authentication exists or as a coarse first gate.
- **Device fingerprint** — passive client-side signals (TLS, header order, JS profile). Useful for unauthenticated endpoints; not bulletproof.
- **API key or token** — strong attribution; the right key for authenticated APIs.
- **Account or tenant id** — the unit a customer cares about; use it for billing-tier limits.
- **User id within a tenant** — for per-seat limits inside a multi-user tenant.
- **Endpoint or operation** — for write-heavy endpoints where rate matters more for that operation than overall traffic.
- **Composite key** — `(tenant, user, endpoint, ...)` — the right shape when limits are hierarchical.

3.2. Design the **hierarchy** explicitly when more than one applies. A typical multi-tier shape:

- Per user — protects the user from their own bug.
- Per tenant — caps a tenant by their plan.
- Per IP — gates anonymous floods.
- Per endpoint — extra cap on a costly route.
- Global — last-resort gate to protect the service.

3.3. The check evaluates limits in order; the first that says no wins, the others still consume tokens for accounting. Stop at the first denial.

3.4. Make the key **non-spoofable**. Authenticated keys are read from the validated token, not from headers a client controls.

3.5. **Pre-auth limits** are unavoidable for anonymous endpoints. Use IP plus a low ceiling; raise it only after authentication promotes the request to an authenticated key.

### 4. Pick the coordination model

4.1. The choice depends on how strict the limit must be and how many nodes share enforcement.

- **Local-only** — each node tracks its own counters. Effective limit is approximately N × per-node limit. Cheapest. Use when N is small or the limit is a soft fairness target.
- **Local with periodic sync** — nodes share periodic snapshots; each node enforces against an aggregated view. Tighter than local-only with bounded coordination cost. Tolerates brief overshoot during sync intervals.
- **Central store (Redis-style)** — every check hits a shared store; the store is the source of truth. Strict enforcement, but every request pays a round-trip and the store is on the critical path.
- **Sharded store** — partition keys across multiple store instances. Scales beyond a single store. Each key still talks to one shard; cross-shard limits are not supported.
- **Token-leasing** — nodes request a batch of tokens from a central authority and spend locally. Hybrid between local and central: most checks are local, occasional refills hit central. Cuts coordination cost dramatically with bounded inaccuracy.

4.2. Pick by what the limit protects (Section 1.1):

- Resource protection — central or sharded store; strict.
- Fairness — local-only or token-leasing; approximate.
- Cost or quota — central with strong durability; reconcile asynchronously if billing requires.

4.3. Plan the store's failure mode. If the store is down, the rate-limit check must still produce an answer. Common choices:

- Fail open — log and allow; safer for revenue, riskier for the downstream.
- Fail closed — deny; safer for the downstream, painful for users.
- Fail degraded — fall back to per-node local counters with a reduced limit; the typical default.

4.4. Cache the limit lookup result aggressively where it can't be the limit itself. A 1ms cache of "this key is currently limited" cuts store load by an order of magnitude on the slow path.

### 5. Design the response contract

5.1. The HTTP response that a limited client receives is a contract. It must be unambiguous, machine-readable, and stable.

5.2. **Status code** — 429 Too Many Requests for rate exceeded; 403 if the client is forbidden for other reasons (do not confuse the two); 503 with Retry-After if the limit is a circuit-breaker response.

5.3. **Headers** — emit a standard set on both allowed and limited responses so well-behaved clients can self-pace:

- `RateLimit-Limit: <max>; window=<seconds>` or `X-RateLimit-Limit`.
- `RateLimit-Remaining: <count>`.
- `RateLimit-Reset: <seconds-until-reset>` or `<unix-seconds>`.
- `Retry-After: <seconds>` on 429 responses; required for client backoff.
- The IETF `RateLimit` headers (draft) are the converging standard; `X-RateLimit-*` is the historical de-facto. Pick one and document.

5.4. **Body** — a small JSON object with `error.code = "rate_limited"`, `error.message`, and the same `retry_after_seconds`. Avoid leaking the limit's internal mechanics (the exact algorithm, the cluster topology).

5.5. **Idempotency interaction** — if the client retries the same idempotency key after a 429, the server must not double-charge nor double-act when the retry eventually succeeds.

5.6. **Documentation** — publish the limits, the keys they apply to, the response contract, and the recommended client behavior (exponential backoff with jitter, honoring Retry-After exactly). A documented limit is a contract; an undocumented one is a trap.

### 6. Design distributed-quota semantics (when applicable)

6.1. When a quota must be exact (paid call counts, billing aggregation), the design must handle three risks:

- **Concurrent decrement** — many nodes decrement at once; the store must be atomic (a single Redis Lua script or equivalent).
- **Out-of-order reconciliation** — when the store is asynchronous from billing, reconcile windows after the fact.
- **Hot keys** — a single tenant with extreme traffic concentrates on one shard. Shard by sub-key (`tenant:bucket`) when traffic is uneven.

6.2. Choose **strict** versus **approximate** consumption. Strict requires synchronous decrement before allowing the operation. Approximate allows the operation and decrements asynchronously, accepting brief over-allowance.

6.3. **Refunds** — failed operations should refund the consumed tokens or quota. Decide whether the refund is server-driven (the worker refunds after a downstream 5xx) or client-driven (the client signals a no-op).

### 7. Design abuse handling

7.1. Rate limits are the floor; abuse handling is the escalation. Build a graduated response so a benign spike is treated differently from a clearly malicious one.

7.2. **Tiers** — typical four-tier shape:

- Tier 0 — normal traffic, no action.
- Tier 1 — soft limit hit; standard 429 with Retry-After.
- Tier 2 — repeated hits within a window; longer Retry-After, optional CAPTCHA or proof-of-work challenge.
- Tier 3 — sustained abuse signal; temporary block on the key or its parent (e.g., the IP of an offending API key), alert raised, manual review trigger.

7.3. **Attribution model** — choose what unit to escalate against:

- IP — easy but blunt; one shared IP can lock out many users.
- Authenticated key — precise; ineffective against unauthenticated abuse.
- Fingerprint — useful for anonymous endpoints but contestable.
- Composite — escalate on IP for anonymous traffic, on key for authenticated, and on tenant for paid-tier exploitation. Document which case picks which.

7.4. **Decay** — escalations must decay automatically. A blocked IP from an hour ago is rarely useful information; a never-decaying block list becomes a tarpit for legitimate users.

7.5. **Allow-listing** — partners and known-good clients have a documented path to higher limits. Without one, support tickets become the limit-management interface.

7.6. **Login endpoints** specifically — use a fixed window with a tight per-IP and per-account limit (e.g., 5 attempts per minute per `(IP, username)`). On exceed, escalate to a slower regime; lock the account briefly; require a fresh challenge. Never reveal whether the username exists.

7.7. **Write-amplifying endpoints** (signup, invite, comment) need lower per-key limits than read endpoints. They are favored attack surfaces.

### 8. Design observability

8.1. Per-key metrics: requests allowed, requests limited, near-limit ratio (requests within 90% of the cap). The near-limit ratio is the early-warning signal that a customer is about to be limited.

8.2. Per-rule metrics: hit rate, rejection rate, tail key concentration. A rule firing 99% on one key indicates either an attack or a misconfigured customer.

8.3. Per-store metrics: latency, error rate, fallback rate (how often local-fallback fired). The rate-limiter store is on the hot path; its latency must be tracked.

8.4. Logs: structured per-decision logs at sample rate, enough to retrospectively audit a customer's claim that they were unfairly limited.

8.5. Alerts:

- Sustained denial rate above a baseline for a tenant — possible bug or attack.
- Store fallback fraction above a threshold — limiter is degraded.
- Single key holding more than X% of denials — investigate attribution.

### 9. Design rollout and changes

9.1. **Shadow mode first** — log decisions without enforcing. Verify the rule's selectivity matches expectation before turning it on.

9.2. **Phased enforcement** — enable at 1% of keys, then 10%, then 100%. Watch denial rate and customer signal at each step.

9.3. **Per-key overrides** — keep a documented override mechanism so a single misconfigured customer can be unblocked without redeploying.

9.4. **Change as data** — limits change in a config store, not in code. New limits go through review and are reversible.

9.5. **Customer communication** — limits visible in the developer dashboard, with current usage, recent throttle events, and contact path for raises. Surprise is the source of most rate-limit complaints.

### 10. Emit the design

10.1. Lead with the algorithm and the rationale tied to Section 1.1.

10.2. Include the policy table: per route or key class, the limit, burst, key formula, scope, action.

10.3. Include the response contract: status, headers, body, and example.

10.4. Include the abuse-handling tiers and attribution rules.

10.5. Include the coordination model, the failure mode, and the store's role.

10.6. Include the rollout sequence and the override path.

### Decision rules and heuristics

- **Pick the simplest algorithm that fits.** Fixed and sliding-window counter solve most problems.
- **Token bucket if customers expect bursts.** GCRA if the downstream demands pacing.
- **Strictness costs round-trips.** Approximate enforcement is cheaper and usually enough.
- **The key is the contract.** Pick a key that survives the abuse model you expect.
- **The response is part of the API.** Document the headers and the retry semantics.
- **Escalate, do not just deny.** Repeat offenders deserve a different regime than first-time offenders.
- **Plan the store's failure.** Fail open, closed, or degraded — pick one and write it down.
- **Hierarchical limits cap the worst case.** A per-user limit plus a per-tenant cap is more robust than either alone.
- **Document the limits.** An undocumented limit is a trust bug.

### Edge cases

- **Clock skew across nodes** — for sliding windows and quota windows, clock skew can over-or-undercount. Use monotonic clocks on the limiter store, not node clocks.
- **Bursty long-tail keys** — a few keys generate most traffic; uniform limits over-constrain the median. Tier limits by historical usage.
- **WebSocket and long-lived streams** — request-count is the wrong measure; switch to message-count or bytes-per-second.
- **Webhooks and outbound calls** — the system is the client; rate limits live on the outbound side. Treat each destination as a key.
- **Mobile retries** — flaky networks cause client retries that look like abuse. The 429 contract must make Retry-After authoritative.
- **CGNAT** — many users share an IP. Avoid IP-only limits for anything user-visible.
- **Datacenter ranges** — automated traffic from cloud IPs is often legitimate (CI, integrations). Allow-list known partner ranges.

## Examples

### Worked example

Input excerpt:

> Public REST API for a B2B SaaS. Customers authenticate with API keys; each customer is a tenant with one or more users. Anonymous traffic is rare. We have 12 edge nodes in 3 regions and Redis is available. We want fair per-tenant limits with bursts allowed, a strict global cap to protect the database, and a graduated response to brute-force on `/auth/token`. Plan tiers: starter (60 req/min), pro (600 req/min), enterprise (3000 req/min).

Expected output sketch:

- Algorithms: token bucket per tenant (refills at the plan rate, burst = 2× per-second rate). Sliding-window counter per IP for `/auth/token`. Concurrency cap of 200 in-flight per tenant against the database.
- Key hierarchy: `(tenant, user, endpoint)` for general traffic; `(IP, username)` for `/auth/token`. Tenant key takes precedence; user key adds intra-tenant fairness; endpoint key adds extra cap on write-heavy routes.
- Coordination: central Redis with atomic Lua scripts for the token-bucket decrement. GCRA-style storage (one timestamp per key) for compactness. Local 200ms cache of "this key is currently limited" to absorb the slow path.
- Failure mode: degraded fallback to per-node local counters at 1/12 of the configured limit when Redis is unreachable.
- Response: 429 with `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, `Retry-After`. JSON body `{ error: { code: "rate_limited", message, retry_after_seconds } }`. Limits also surfaced as headers on 200 responses so well-behaved clients can self-pace.
- Abuse handling on `/auth/token`: 5 failed attempts per `(IP, username)` per minute → 429 with 60s Retry-After. 20 attempts in 5 minutes → 15-minute soft block. Sustained signal → 24-hour block plus alert. All attribution generic ("invalid credentials") to avoid username enumeration.
- Observability: per-tenant denial rate, near-limit ratio, store latency, fallback fraction. Alerts on per-tenant denial rate spikes, store fallback fraction above 1%, and per-key denial concentration above 50%.
- Rollout: shadow mode for one week; 1% → 10% → 100% over three days; per-tenant override mechanism in the admin console.

## Limitations

- The skill produces a design from the inputs supplied; the specific limit numbers (refill rates, burst sizes, escalation thresholds) require measurement and tuning under the real workload.
- It does not recommend a specific product or library; the algorithm and coordination choices apply across substrates.
- It does not protect against network-layer floods; DDoS mitigation lives below this layer.
- It does not solve fairness within a single window when no priority signal exists; weighted-fair scheduling is a different design.
- The response-contract recommendations follow the IETF draft and the prevailing de-facto conventions, both of which evolve; lock the chosen variant in the API documentation.
