# Dependency Review Policy Author

## When to use

Use this skill when an organization needs a written, defensible policy for how third-party dependencies enter the codebase and how they are maintained. Typical situations:

- A new compliance regime (security audit, customer questionnaire, internal governance) asks "what is your dependency policy?"
- The team has a thousand transitive dependencies of unknown provenance and wants to stop the growth.
- A recent supply-chain incident in a peer org motivates leadership to act.
- License risk has become a problem (a copyleft dep slipped into a proprietary build).
- Developer friction is high because the existing policy blocks too much; or alternatively, anything-goes is producing too much risk.

This skill writes the policy and the gates. Implementation belongs to platform / appsec / engineering-leadership teams.

**Scope guardrail.** Methodology guidance only. License classification has legal implications; have counsel review the license-class rules before adopting. Security posture criteria do not eliminate supply-chain risk — they reduce it.

## How to apply

Walk the eight phases. The hardest part is not writing rules; it is deciding what the policy *will not* require. A policy that demands deep review of every dependency is ignored within a quarter.

### Phase 1 — Tier the policy by risk

Apply different scrutiny to different uses. A single policy that treats every dependency identically produces either bureaucracy or rubber-stamping.

Define dependency tiers — for example:

- **Tier A — Production runtime.** Dependencies that execute in customer-facing services. Strictest review.
- **Tier B — Build & test.** Dependencies that run only at build time or in test environments. Moderate review. (Note: build-time deps still execute on your build infrastructure; they are not "free.")
- **Tier C — Dev tooling.** Local-developer-only tools, linters, formatters. Light review.
- **Tier D — Research / experimentation.** Sandboxed environments, never reaches production. Very light review.

Movement between tiers requires re-review. A research dep being promoted to production is a *new* adoption event.

### Phase 2 — License policy

Group licenses into classes; gate on the class, not on the license name.

Suggested classes (have legal review the final mapping):

- **Class 1 — Permissive.** MIT, Apache-2.0, BSD-2/3-Clause, ISC, Unlicense, 0BSD. Auto-approved for all tiers.
- **Class 2 — Weak copyleft.** LGPL-2.1, LGPL-3.0, MPL-2.0, EPL-2.0. Auto-approved with linking-mode guidance; review if statically linked into proprietary binary distribution.
- **Class 3 — Strong copyleft.** GPL-2.0, GPL-3.0, AGPL-3.0. Allowed for internal tooling; blocked for proprietary distribution unless explicit legal sign-off.
- **Class 4 — Non-commercial / source-available / "fair-source" / shared-source.** BSL, SSPL, Elastic License, Commons Clause, PolyForm variants. Case-by-case legal review.
- **Class 5 — Unknown / missing / non-OSI-approved custom.** Block by default; legal review required.

Operational rules:

- Use SPDX license expressions everywhere. Plain-string license fields ("Apache 2.0") are noise.
- The license decision is on the *artifact you ship*, considering the linking model of the language. Static vs dynamic linking changes copyleft obligations.
- License classification of transitive dependencies matters as much as direct ones. Surface them via SBOM tooling.
- "Multi-license" components — pick the license you can comply with and document the choice in writing.

### Phase 3 — Security posture criteria

For each candidate dependency at Tier A or B, evaluate against an explicit checklist. The checklist matters because a checked box is auditable; a vibe is not.

Objective signals (machine-readable, fast):

- **Known vulnerabilities.** No unpatched critical CVE in the candidate version. Use OSV-style scanning. Out-of-the-box high or critical findings block adoption pending fix.
- **Provenance.** Does the package's release process produce signed artifacts / attestations? Some ecosystems do, some don't. Track and prefer the ones that do.
- **Scorecard signals.** Use an OpenSSF-Scorecard-style automated check: presence of code review, dependency-update tooling, signed releases, CI testing, branch protection. Set a minimum score threshold by tier.
- **Maintainer count.** Single-maintainer packages are higher risk. Two-plus is preferred; one is acceptable only for small, well-scoped packages with a clear alternative.
- **Release recency.** A package with no releases in 24+ months is either stable-perfect or abandoned. Investigate before adopting.
- **Issue / PR responsiveness.** Median time-to-respond on security issues over the last year. >90 days suggests no active maintainer.
- **Typosquat / confusion check.** Run a name-similarity check against popular packages in the ecosystem. Block obvious typosquats; flag suspicious near-matches for human review.

Subjective signals (slower, used at Tier A):

- **Code quality.** A short manual look at the package source — is it readable, tested, structured? Obfuscation, suspicious post-install scripts, network-fetching install steps are red flags.
- **Reputation.** Maintainer history, governance (foundation-backed vs solo), public statements about security policy.
- **Alternatives.** Is there a more popular, better-maintained equivalent? Adoption inertia is cheap to avoid before adoption; expensive after.

### Phase 4 — Supply-chain attack surface

Independent of the package's intrinsic quality, evaluate how it could be compromised.

- **Install-time code execution.** npm `postinstall`, Python build scripts (`setup.py`), Maven plugins. These run during install with developer / builder privileges. Prefer ecosystems and configurations that disable arbitrary install-time code, or sandboxes that limit its scope.
- **Network access at install or build.** If the package's install/build reaches the network for additional content, you have a dependency you cannot pin. Flag and prefer alternatives.
- **Binary blobs.** Packages that ship pre-built binaries (especially native extensions) cannot be source-reviewed easily. Require build-from-source where feasible; otherwise, require signed publisher provenance.
- **Namespace risk.** Internal package names that overlap with public registries create dependency-confusion risk. Use scope-locked namespaces (e.g., npm scopes, Maven groupIds your org owns) for internal packages; configure package managers to reject public fall-through.
- **Registry trust.** Pin to a curated internal registry that mirrors approved versions of public packages. Public-registry fall-through is a supply-chain back door.

### Phase 5 — Automated gates

Encode the policy in CI so it runs on every dependency change.

Gates to enforce on a PR that adds or changes a dependency:

- **License gate.** Lookup license class; block if Class 4 or 5 without exception; auto-comment with the license summary.
- **Vulnerability gate.** Scan the new resolved lockfile with an OSV-style scanner; block on new high/critical findings unless an exception is on file.
- **Scorecard gate.** Compute a scorecard score for the candidate package; block at Tier A if below threshold.
- **Typosquat gate.** Block obvious near-name collisions to popular packages.
- **New-direct-dep gate.** Adding a *new direct* dependency triggers a richer review path: scorecard, maintainer count, release recency, alternatives mention. Transitive-only changes use the lighter check.
- **Lockfile-integrity gate.** Refuse PRs that change `package-lock.json` / `requirements.txt` / equivalent without a corresponding source-of-change in the PR (catches accidental lockfile drift).

Gates to enforce continuously (not just on PRs):

- **Daily re-scan of lockfiles.** New CVEs against old deps surface here.
- **Quarterly maintainership re-check.** Surface deps whose maintainership signals have decayed (no release in 24 months, maintainer count dropped to one, issue backlog grown).
- **Removal candidates.** Surface deps with zero usage in code (after dead-code elimination); a dep no one uses is pure risk.

### Phase 6 — Exceptions process

Policies without exceptions get bypassed. Design the exception path before someone needs it.

Components of a good exception process:

- **Documented request form.** Dependency, version, requesting team, business justification, alternatives considered, mitigations applied.
- **Defined reviewers.** Per gate type — license exceptions go to legal; security exceptions go to security; maintainership exceptions go to engineering leadership.
- **Time-boxed.** Every exception has an expiry. Forever-exceptions become invisible. Default 90 days; renewal requires re-justification.
- **Compensating controls.** An exception is granted *because* of specific mitigations: pinning a specific version, isolating the dep behind a sandbox, planning migration off the dep, etc. Record the mitigations.
- **Visible registry.** All active exceptions visible to the team in a queryable form. Surprise exceptions in audit are a leadership problem.

### Phase 7 — Lifecycle obligations

Adoption is the beginning, not the end.

- **Patch SLA.** Critical CVE → patched within N days at Tier A; high → N weeks; medium → next regular update.
- **Abandonment trigger.** If a dep loses its maintainer, hits zero recent releases for X months, or fails scorecard re-check, it enters a *deprecation track*: migration plan within Y months, sunset deadline.
- **Major-version policy.** Dependencies stay within a supported major version. EOL upstream major versions are aged out within Z months of EOL.
- **Pin updates, don't auto-merge them.** Automated dependency-update PRs (renovate / dependabot) are valuable but must run through human review for Tier A. Auto-merge is acceptable at Tier C/D with passing CI.

### Phase 8 — Communicate and measure

A policy nobody reads is ineffective.

- **Publish the policy.** A single document, versioned, with a changelog.
- **Train developers.** A short onboarding module on the policy. Updates on major changes.
- **Measure adoption.**
  - Coverage: % of dependencies with a current license class assignment, scorecard, and CVE scan.
  - Friction: median time from "I want to add this dep" to merge for in-policy adoptions. Should be hours, not days.
  - Exception rate: % of new deps requiring an exception. > 20% suggests the policy is too strict; near zero suggests it is rubber-stamping.
  - Patch SLA adherence: % of CVEs patched within tier SLA.
  - Abandonment surfacing: # of newly-flagged abandoned deps per quarter; # successfully migrated.

## Inputs

- **Org context.** Size, regulatory posture, product distribution.
- **Ecosystems.** Languages and registries in scope.
- **Risk appetite.** By domain.

- **Pain points.** What failures the policy must address.

## Outputs

A markdown policy document with:

1. **Tier definitions.** With examples of what falls into each.
2. **License-class table.** With the auto-approve / review / block rules.
3. **Security-posture checklist.** Objective and subjective signals.
4. **Supply-chain attack-surface rules.** Install-time code, binary blobs, namespace, registry.
5. **Automated gates.** PR-time and continuous.
6. **Exceptions process.** Form, reviewers, time-boxing, registry.
7. **Lifecycle obligations.** Patch SLA, abandonment, major-version, auto-merge rules.
8. **Communication and metrics.** With initial targets.
9. **Rollout plan.** Phase 1 = visibility, Phase 2 = soft gates, Phase 3 = enforce.

## Examples

**Example A — Mid-size SaaS, mixed Node and Python.**

Three tiers (production / build / dev). License classes auto-approved through Class 2; Class 3 blocked from production but allowed in internal CLI tooling. Scorecard threshold of 6.0 for Tier A direct deps. OSV-based scanning on every PR; critical CVEs block, high CVEs require an exception with 30-day fix plan. Renovate runs daily; Tier C/D auto-merge on green; Tier A requires a human approval. Quarterly review surfacing of abandoned deps. Patch SLA: critical 7 days, high 30, medium next cycle.

**Example B — Regulated on-prem product, conservative.**

Two tiers (shipping / internal). All Class 3+ blocked from shipping without legal review; even Class 2 statically linked into shipping binaries requires legal sign-off. Scorecard threshold raised to 7.5. All new direct deps require a written justification and security-team review; transitive changes pass through automated gates only. Quarterly mandatory abandonment review with a published deprecation list. No auto-merge anywhere.

## Limitations

- License classification involves legal interpretation. The classes proposed here are common industry practice but must be reviewed by counsel before adoption in your organization. Jurisdiction and product context affect classification.
- Scorecard signals are heuristics, not guarantees. A high-scoring package can still be compromised; a low-scoring package can still be safe. Use signals to focus attention, not as a final verdict.
- This skill does not address the special case of fork-and-vendor. Forking puts maintenance burden on you; it can be the right answer when no acceptable upstream exists, but it is a different decision than "adopt the dep."
- Some ecosystems (older Java, niche embedded toolchains) have weak metadata and limited tooling. Policy enforcement in those ecosystems is partly manual.
- The policy assumes the org has the capacity to run it. A two-person team adopting a 50-page policy will fail. Calibrate scrutiny to organizational capacity; expand as capacity grows.
