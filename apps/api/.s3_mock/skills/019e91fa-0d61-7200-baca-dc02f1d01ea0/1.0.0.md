# ROS 2 Behavior Tree Designer

## When to use

Use this skill when an engineer needs to design (or redesign) a behavior tree to orchestrate an autonomous robot task. Triggers include: starting an autonomy project and choosing between a state machine, a planner, and a BT (the BT is often the right answer for missions composed of reusable skills); the team's Nav2 BT has accreted recovery branches that no one understands and is looping on a corner case; a mission needs human-in-the-loop confirmation and the current state machine cannot express the wait-and-resume semantics cleanly; a new robot has a rich set of action servers and the team needs an orchestration layer; or a research demo is being productized and ad-hoc Python orchestration is being replaced.

The skill applies whether the target library is BehaviorTree.CPP (v3 or v4), the Nav2 fork of BT.CPP, py_trees on the Python side, or a custom implementation that follows the same semantics. The design output is library-agnostic at the conceptual level; the XML rendering targets BT.CPP-style conventions, which most ROS 2 BT libraries can adapt.

It does not apply to: low-level motion control (BTs do not replace controllers — they sequence skills that themselves use controllers); planning algorithms (BTs invoke planners as actions; they are not planners); or single-step request/response problems that a service call would handle.

**This skill produces methodology guidance for robot software architecture. Outputs must be reviewed by qualified robotics engineers and validated in simulation and bench tests before any deployment on hardware that interacts with people or property. Bad robot software causes physical harm — treat all advice as a starting point, not a deployment-ready specification.**

The bar the skill applies is "can a competent operator read the tree top-to-bottom and predict what the robot will do, including in failure modes, without reading C++?"

## How to apply

The designer proceeds in stages. Each stage produces a concrete artifact; the final stage assembles them into a coherent tree.

### Stage 1 — Mission decomposition

1. Parse the task description into a sequence of *phases*. A delivery mission has roughly: undock, navigate to pickup, await load, navigate to dropoff, await unload, navigate to home, dock. A manipulator pick-place has: home, perceive, plan grasp, pick, plan place, place, retreat.
2. For each phase, list the *normal flow* (what happens when everything works), the *expected branches* (e.g., dropoff has two options based on payload type), and the *expected interruptions* (low battery, operator stop, geofence breach).
3. Identify the *idempotent vs non-idempotent* phases. Re-navigating to a pose is idempotent and cheap; re-grasping an object is non-idempotent and may damage the payload. The recovery strategy differs.
4. Identify *commit points* — phases after which the robot cannot simply abort and return home (e.g., the gripper has the payload mid-air, the door is open, the package has been delivered). Commit points constrain the recovery tree.
5. Identify *human-in-the-loop* moments. Anywhere a human must confirm, accept, or override is a deliberate wait in the tree, not an implicit assumption.

### Stage 2 — Skill inventory

6. For every action server the robot exposes, record: action name, goal type, feedback type, result type, typical duration, cancellation semantics, idempotence, side effects on failure.
7. For every condition, record: condition name, what it reads, latency (cheap synchronous read vs. expensive sensor query), staleness tolerance (how recent must the reading be to be trusted).
8. Identify *missing skills*. If the mission needs a skill the robot does not have (a `WaitForOperator` action, a `CheckPayloadPresent` condition, a `BeepAndWait` cosmetic action), name it now. The BT design assumes these exist; the implementation team will fill them in.
9. Identify *skills that should be split*. A monolithic `DoTheMission` action defeats the BT — there is nothing for the BT to compose. Push the team to expose small, named, reusable skills.

### Stage 3 — Control flow nodes

10. The designer prefers a small, predictable vocabulary of control nodes.
    - **Sequence**: runs children in order; succeeds when all succeed; fails on the first failure. Use for ordered phases.
    - **ReactiveSequence**: like Sequence, but re-ticks earlier children every tick. Use when an earlier condition (battery, e-stop) must abort a later running action.
    - **Fallback (Selector)**: tries children in order; succeeds on the first success. Use for "try A; if not A, try B; if not B, fail."
    - **ReactiveFallback**: like Fallback with re-ticking. Use for recovery branches whose triggering condition can clear mid-execution.
    - **Parallel**: runs children concurrently; succeeds when N succeed. Use sparingly — concurrency in autonomy is hazardous and most "parallel" intents are really "sequence with a watchdog."
11. Avoid bespoke control nodes unless the library does not support a needed semantic. Custom control nodes are a maintenance trap because they redefine BT semantics.
12. Prefer *ReactiveSequence at the root* with a `IsBatteryOK?` and `IsEStopReleased?` check as the leftmost children. Every tick re-checks them; failure aborts the running mission deterministically.

### Stage 4 — Recovery design

13. Identify the *recovery scope* — a single skill, a phase, or the whole mission. Recovery at the wrong scope either re-tries forever at the wrong level (the planner re-plans when the issue is that the map is stale) or escalates too quickly (a transient localization wobble aborts a 10-minute delivery).
14. The standard pattern is *RecoveryNode*-equivalent: a control node that runs `[action, recovery]` — if the action fails, run the recovery, then re-tick the action up to N times. The Nav2 stack popularized this idiom.
15. For each phase, design a *recovery sub-tree* that is layered:
    - **Local recoveries** — clear costmap, spin in place, back up a short distance. Cheap and safe.
    - **Mid-level recoveries** — re-plan with a different planner, escalate timeout, narrow the search radius.
    - **High-level recoveries** — request operator help, return to a known safe pose, abort the mission.
16. Each recovery sub-tree has a *budget*. Recoveries that retry indefinitely are the most common cause of confusing BT behavior. Cap retries explicitly; surface budget exhaustion as a failure that the parent must handle.
17. Recovery sub-trees should be *named* and *reusable* across phases. A library of named sub-trees — `RecoverFromLocalizationLoss`, `RecoverFromObstacle`, `RecoverFromActionTimeout` — makes the root tree readable.
18. Commit-point recoveries are *different*. Once the gripper has the payload, the recovery is not "return home" — it is "place the payload at the nearest safe location and then return home." Design commit-point recoveries explicitly.

### Stage 5 — Conditions and decorators

19. Conditions are *fast*. A condition that takes 200 ms to evaluate freezes the tick loop. If a check needs a slow query, run it as an action whose result is cached on the blackboard, and let the condition read the cached value.
20. Conditions are *side-effect free*. A condition that publishes a topic or commands a motor as a side effect breaks the predictability of the tree.
21. Decorators wrap a single child to modify behavior. Useful decorators:
    - **Inverter** — flip success and failure.
    - **Retry(N)** — re-tick a failing child up to N times.
    - **Timeout(ms)** — fail the child if it does not finish in time.
    - **Repeat(N)** or **RepeatUntilFailure** — loops; use sparingly.
    - **ForceSuccess** / **ForceFailure** — typically a smell; if you need to ignore a failure, document why.
22. Avoid *nested decorators* more than two deep — `Timeout(Retry(Timeout(action)))` becomes unreadable. Flatten by giving the child a clearer semantic.

### Stage 6 — Blackboard discipline

23. The blackboard is the BT's shared memory. Treat it as a typed dictionary, not a junk drawer.
24. *Name the keys consistently*. `goal_pose`, `current_goal_pose`, `target_pose`, `nav_goal` for the same value is a real bug — different sub-trees read different keys.
25. *Type the keys*. Document each key's type, units, and frame_id where applicable. A `goal_pose` that is sometimes in `map` and sometimes in `odom` causes drift bugs.
26. *Scope the keys*. Some keys are mission-scoped (`mission_id`, `payload_kind`); some are phase-scoped (`current_waypoint_index`); some are tick-scoped (`last_battery_voltage`). Sub-trees should declare which keys they read and write. BehaviorTree.CPP supports port remapping for sub-tree scope — use it.
27. *Initialize the blackboard explicitly* at mission start. Tree behavior that depends on uninitialized blackboard keys is non-deterministic.
28. *Persist nothing the robot cannot afford to lose*. The blackboard is in-process memory; it does not survive a node crash. Long-lived state lives elsewhere (a mission server, a database, a parameter file) and is loaded into the blackboard at start.

### Stage 7 — Ticking strategy

29. Decide the *tick rate*. Mobile robots typically tick at 5-20 Hz. Manipulators with fast reactive needs tick faster. Faster tick rates burn CPU and can race with action-server feedback.
30. Decide *whether to tick at all when no event has occurred*. Pure periodic ticking is simple. Event-driven ticking (wake on a topic, a service call, a timer) saves CPU but introduces missed-event bugs. Most teams should start with periodic ticking and only optimize when measured.
31. Decide *what blocks a tick*. Synchronous actions inside a tick that take longer than `1 / tick_rate` cause backlog. All long-running actions must be asynchronous and return RUNNING until done.
32. Decide *what happens during a halt*. When the tree halts a running action, the action server must respect cancellation. Audit each action for cancellation correctness — an unstoppable navigation action makes the BT a liar.

### Stage 8 — ROS 2 integration

33. The BT executor is a node in the ROS 2 graph. Decide its *lifecycle status* — for a production robot, the BT executor should be a lifecycle node so the operator can deactivate it cleanly.
34. The BT publishes *status*. A `mission_status` topic with the current phase, current node, and a recent transitions trail is the minimum operator-visible signal.
35. The BT publishes *logging* for analysis. Each tick's transitions can be Groot-compatible logged for offline visualization. Volume can be high; sample at a fraction in production.
36. Action clients inside BT leaves *share executors* with the rest of the node. Audit for executor-deadlock patterns from the architecture-review skill — calling synchronous services from BT condition nodes is a classic deadlock source.
37. *Parameters* configurable per mission (waypoints, payload type, geofence) load into the blackboard at BT start. Do not hard-code mission specifics in the XML.
38. *Sim and real share the same tree*. Differences live in parameters and in mocked vs. real action servers. A divergent tree per environment is a major debt.

### Stage 9 — Testing and validation

39. Each sub-tree should be *testable in isolation*. Recovery sub-trees in particular should have unit tests with mocked action clients.
40. *Failure-injection tests* are mandatory. Force each leaf action to fail and verify the recovery path is what the design intends.
41. *Hang tests* — confirm that no infinite loop is possible. Each loop has either a counter or a budget that terminates.
42. *Soak tests* — run the mission for N hours in simulation and look for slow blackboard growth, recovery-budget exhaustion that does not surface, or tick-rate degradation.

### Stage 10 — Render the design

43. Render the *root tree* in pseudo-XML with named sub-trees referenced rather than inlined. Inlining a 100-line root tree is unreadable.
44. Render each *named sub-tree* with its purpose, its blackboard reads and writes, its expected duration, and its failure semantics.
45. Render the *blackboard schema* as a table: key, type, units/frame, scope, initial value, writers, readers.
46. Render the *recovery matrix* as a table: failure mode, detecting condition, local recovery, mid recovery, high recovery, commit-point handling.
47. Render the *tick strategy* as a short note: rate, executor, blocking semantics, halt behavior.
48. Provide an *adaptation note* if the chosen library is not BT.CPP — name the equivalent control nodes and decorators in that library.

## Reference sub-tree library

The designer reaches for a small library of named, reusable sub-trees. Each sub-tree has a documented purpose, blackboard contract, and failure semantics.

- **NavigateWithRecovery(goal_pose)**: ReactiveSequence wrapping `IsGoalReachable?`, `NavigateToPose(goal_pose)` paired with `RecoverFromNavFailure` as a RecoveryNode, with a Retry(3) cap. Reads `goal_pose`; writes `last_nav_result`.
- **RecoverFromNavFailure**: Fallback over `ClearAllCostmaps`, `BackUpShort+Spin`, `RequestOperatorHelp`. Reads nothing required; may write `operator_intervention_requested`.
- **RecoverFromLocalizationLoss**: Sequence of `StopMotion`, `WaitForLocalizationConfidence` (with a budget timeout), then a final `RequestOperatorHelp` if the budget expires. Reads `localization_confidence`; writes `motion_halted`.
- **AwaitOperatorConfirmation(prompt)**: publishes a UI prompt, sets `awaiting_operator=true`, ticks RUNNING until a UI service or topic clears the flag or times out. Reads `prompt`; writes `awaiting_operator`, `operator_confirmation_value`.
- **PowerSafetyWatchdog**: a ReactiveSequence with `IsBatteryAboveThreshold?` (warning) and `IsBatteryAboveCriticalThreshold?` (critical). Used as a parallel watchdog or as the leftmost child of the mission ReactiveSequence.
- **GeofenceWatchdog**: a parallel child that aborts the mission if `IsInsideGeofence?` returns false. Should never be omitted on robots that operate near restricted areas.
- **DockOrReturnHome**: a Fallback — try `Dock`; if dock fails, navigate to a known safe pose. Used as the final cleanup of every mission.

The agent assembles missions from this library where possible. When a needed sub-tree is absent, the agent flags the gap and names the new sub-tree explicitly so the engineering team can implement it.

## Control flow rules-of-thumb

- *Sequence is the default*. When in doubt, sequence.
- *ReactiveSequence at root*. The mission always re-checks safety preconditions.
- *Fallback for "try plan A, then plan B"*. Fallbacks are for choices the robot makes between alternatives.
- *Parallel is rare*. Most "parallel" intents are really "sequence with a watchdog" and should be written that way. True parallelism in autonomy is hard to reason about.
- *Decorators wrap one thing*. Stacking decorators is a smell; if you stack more than two, push the logic into a named sub-tree.
- *Conditions are O(microseconds)*. If a check is slow, run it as an action that caches its result.
- *Every loop has a budget*. Either a Retry(N), a Timeout, or a counter on the blackboard. Unbounded loops are bugs.

## Worked walkthrough

A worked design pass for a hospital-corridor delivery robot. Mission: pick up a tray from the supply room, deliver to a nurses' station, return for the next request, dock at end of shift.

**Stage 1 mission decomposition.** Phases: Undock → NavigateToSupplyRoom → AwaitTrayLoad (human-in-the-loop) → NavigateToNurseStation → AwaitTrayUnload (human-in-the-loop) → CheckQueue → loop or Dock. Commit points: after `AwaitTrayLoad` succeeds, the robot owns a tray and cannot simply return home without delivering it somewhere appropriate.

**Stage 2 skill inventory.** Required actions: `Undock`, `NavigateToPose`, `AwaitOperatorConfirmation`, `Dock`. Required conditions: `IsBatteryAboveThreshold?`, `IsInsideGeofence?`, `IsTrayPresent?`, `IsCorridorClear?` (a coarse safety check). Missing skills the design will assume: `IsTrayPresent?` (the robot needs a way to confirm the tray is on the bay before leaving the supply room — flag for the hardware team if absent).

**Stage 3 control flow.** Root is a ReactiveSequence:
- IsBatteryAboveCriticalThreshold? (abort if not)
- IsEStopReleased? (abort if not)
- IsInsideGeofence? (abort if not)
- The mission Sequence.

The mission Sequence wraps:
- Undock with Retry(2) and a RecoveryNode pairing it with `RecoverFromDockFailure`.
- A RepeatUntilFailure loop (capped at the shift duration) containing:
  - NavigateWithRecovery(supply_room_pose)
  - AwaitOperatorConfirmation("Load tray and confirm")
  - IsTrayPresent? (commit-point check)
  - NavigateWithRecovery(current_nurse_station_pose)
  - AwaitOperatorConfirmation("Unload tray and confirm")
  - CheckQueue (a service call that updates the blackboard with the next request)
- A final DockOrReturnHome.

**Stage 4 recovery design.** `RecoverFromNavFailure`: Fallback(ClearCostmaps, BackUpShort+Spin, RequestOperatorHelp). Budget: 3 retries per phase. Commit-point recovery for the post-load state: if the robot cannot reach the nurses' station after exhausting retries, it does NOT return to the supply room (the tray would arrive at the wrong destination); instead it parks safely and pages the operator.

**Stage 5 conditions and decorators.** `IsTrayPresent?` is a fast condition wrapping a cached sensor read updated by a separate node at 5 Hz. `IsCorridorClear?` is a 200ms vision query — flag as too slow for a tight tick; run it as an action whose result is cached.

**Stage 6 blackboard.** Keys: `current_nurse_station_pose`, `current_request_id`, `tray_present`, `mission_start_time`, `last_recovery_used`, `operator_intervention_requested`. Schema documented in the cookbook table.

**Stage 7 ticking.** 10 Hz. The longest synchronous action is a service call to the queue (target sub-100 ms) — well under the tick budget.

**Stage 8 ROS 2 integration.** BT executor is a lifecycle node. Mission status published at 1 Hz to `/mission_status`. Tick log recorded to rosbag at 10 Hz during commissioning, 1 Hz in production. Action clients for navigation share a multi-threaded executor with reentrant callback groups to avoid deadlock on cancel.

**Stage 9 testing.** Failure-injection tests for each leaf (fail Undock, fail NavigateToPose, fail AwaitOperatorConfirmation by never confirming, fail IsTrayPresent). Soak: 8-hour simulated shift with random nurse-station goals. Hang test: confirm no infinite path exists by exercising the budget exhaustion of every loop.

**Stage 10 render.** XML rendering of the root tree using `<SubTree>` references for each named sub-tree, port remappings for blackboard scoping, decorators with explicit parameters.

## Examples

A trimmed example for an outdoor delivery robot. The root is a ReactiveSequence with `IsBatteryAboveThreshold?`, `IsOperatorRunRequest?`, and the mission Sequence: `Undock`, `NavigateToPickup`, `AwaitOperatorConfirmation`, `NavigateToDropoff`, `AwaitDropoffConfirmation`, `ReturnHome`, `Dock`. Each navigation is wrapped in a Retry(3) decorator over a RecoveryNode that pairs the navigation with a `RecoverFromNavFailure` sub-tree, which itself is a Fallback over `ClearCostmapsAndRetry`, `BackUpAndReplan`, and `RequestOperatorHelp`. A separate watchdog sub-tree at the root, in a Parallel with the mission, ticks `IsGeofenceBreached?` and halts the mission on breach.

## XML rendering conventions

The reference XML follows BehaviorTree.CPP v4 conventions. The agent uses these consistently so adaptation to other libraries is mechanical.

- Root is `<BehaviorTree ID="MainTree">` with a single child (typically a ReactiveSequence or Sequence).
- Sub-trees are top-level `<BehaviorTree ID="...">` blocks referenced via `<SubTree ID="...">`.
- Port remappings are explicit on each `<SubTree>` invocation: `<SubTree ID="NavigateWithRecovery" goal_pose="{goal_pose}"/>`.
- Action nodes use the `<Action ID="..." param="value"/>` form, with parameters either literal or `{blackboard_key}` references.
- Condition nodes use `<Condition ID="..."/>`.
- Decorators wrap a single child: `<Retry num_attempts="3"><Action .../></Retry>`.
- Comments in XML are sparse — the design document carries the rationale; the XML carries the structure.

For py_trees, the conceptual mapping is direct but the Python object model replaces XML. For Nav2's fork of BT.CPP, the XML is mostly compatible but Nav2 ships additional control and decorator nodes (`PipelineSequence`, `RoundRobin`, `RateController`) that the designer mentions where they help.

## Sizing and complexity guidance

A healthy mission tree is small enough for one engineer to read and explain. Practical sizing:

- *Root tree*: 5-20 visible elements (children of the root, including SubTree references). More than 20 is a smell — extract sub-trees.
- *Each named sub-tree*: 3-12 elements. More than 12 is a smell.
- *Total tree depth* (nesting): 5-8 is normal. More than 10 is a smell — flatten by extracting named sub-trees.
- *Total sub-tree count*: 5-20 named sub-trees for a typical mission. Hundreds is a smell — the design has not extracted reusable abstractions, or the mission is genuinely huge and a different orchestration paradigm may fit better.

When the design exceeds these bounds, the agent flags it and proposes either extraction (more sub-trees) or a higher-level orchestrator that calls multiple smaller BTs.

## Outputs

The skill emits two artifacts. The first is `bt_design`, a complete narrative design with the root tree, named sub-trees, blackboard schema, recovery matrix, ticking strategy, ROS 2 integration notes, and adaptation notes for the chosen library. The second is `bt_xml`, a reference XML rendering ready for adaptation — node names follow BehaviorTree.CPP v4 conventions and can be mapped to v3, Nav2's fork, or py_trees by the implementer.

The design document is the canonical artifact; the XML is a starting point that an implementer adapts to the team's specific action and condition node names.

## Anti-patterns the designer warns against

- **Decorators inverting failure into success without rationale**. `ForceSuccess` over a critical action means a real failure is swallowed; the operator never knows.
- **Unbounded retries**. `Retry(-1)` or no retry cap on a recovery path; the robot loops forever on a failure that needs operator attention.
- **State machines wearing BT clothes**. A "tree" that is really a state machine implemented as a deeply-nested switch of conditions is harder to reason about than a state machine. If the problem is fundamentally state-machine-shaped (a small set of named states with explicit transitions), use a state machine.
- **Side-effect conditions**. A condition that publishes a topic or sends a command as part of its evaluation breaks the predictability of the tree and makes failure modes opaque.
- **The blackboard as global memory**. Sub-trees that read keys not declared in their port list make composition unsafe. Tighten with port remapping.
- **Tick rates that exceed action-server feedback rates**. Ticking a goal_handle every 1 ms when the action server publishes feedback at 10 Hz wastes CPU and risks racing on partially-updated handles.
- **Conditional logic inside action goal construction**. The action goal sent to a server should be a function of blackboard values, not a computation done inline in the XML. Compute on the blackboard; consume cleanly.
- **Recovery sub-trees that re-enter the same failure**. A recovery that calls the failing action again as its first step is a loop in disguise.

## Operator visibility

The behavior tree is the closest thing the robot has to a readable plan, and the operator should see it. The designer recommends:

- A `/mission_status` topic publishing the current phase, the currently-RUNNING leaf, the last transition, and the last recovery used.
- A *tree-state log* persisted alongside rosbags so post-incident analysis can replay the tick-by-tick decisions of the tree.
- A *tree visualization* (Groot or equivalent) available to the operator UI in development environments; on production robots it may be disabled to save bandwidth, but the underlying telemetry should still be recorded.
- A *deliberate-failure surface*. When the BT exhausts its recovery budget and gives up, the operator gets a structured alert with the mission ID, the failed phase, the last recovery attempted, and the blackboard state. Silent give-up is a Major design flaw.

## Limitations

The designer produces a methodology and a starting design. It cannot:
- Verify the action servers the design assumes actually exist and behave as claimed.
- Tune tick rates or timeouts for a specific robot — those are measured, not designed.
- Replace simulation-based and hardware-in-the-loop validation of the recovery behaviors. Recovery sub-trees that look sensible on paper routinely surprise on hardware.
- Substitute for safety review. Anything that commands motion under uncertainty is a safety case and must be reviewed by qualified engineers.

Behavior trees centralize the orchestration in a readable artifact, but they do not make autonomy safe by themselves. The kill switch, the geofence, and the human supervisor remain mandatory until proven otherwise.

A well-designed tree is one a new engineer can read on their first day and predict, within a margin, what the robot will do in any of the documented failure modes. If the team's existing tree fails that test, the rewrite is worth the cost.

## Integration with the broader autonomy stack

The behavior tree is the orchestration layer. It sits above the action and service layer (planners, controllers, perception pipelines) and below the mission-management layer (queue of jobs, fleet manager, operator UI). The designer captures the interfaces at both seams:

- *Above the BT*: how does a new mission start? A service call, a topic, a parameter load, a UI button? The BT consumes that and writes the relevant blackboard keys at start.
- *Below the BT*: how does a leaf action wait for completion? Action client send_goal with a feedback callback that updates the blackboard, with a goal handle stored so cancellation works.
- *Across the BT*: how do parallel watchdogs interact with the main mission? The leftmost children of a ReactiveSequence are re-evaluated every tick; their failure halts the mission RUNNING children deterministically.

The designer also captures *what the BT does NOT own*: the low-level control loop runs at its own rate inside the controller node, not as a BT tick; the planner runs as an action server, not as a BT computation; the safety monitor runs as an independent node (or microcontroller) that can preempt motion regardless of BT state. The BT orchestrates; it does not implement.

## Compatibility notes per library

- *BehaviorTree.CPP v4*: the reference target. All node names map directly.
- *BehaviorTree.CPP v3*: most node names are the same. A few control nodes were renamed; the `Subtree` semantics differ slightly. The agent flags v3 idioms when the user picks v3.
- *Nav2 BT*: based on BT.CPP but extended with Nav2-specific actions and decorators. The agent uses Nav2 node names when the user is integrating with Nav2.
- *py_trees*: Python-native. The control flow vocabulary is similar; idioms differ. The agent emits Python skeleton in addition to XML when py_trees is chosen.
- *Custom*: the agent emits the design as library-agnostic pseudocode and asks the implementer to map to the team's BT engine.
