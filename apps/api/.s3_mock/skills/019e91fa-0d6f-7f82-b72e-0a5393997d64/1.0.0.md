# ROS 2 Navigation Stack Tuner

## When to use

Use this skill when a team is bringing up Nav2 for the first time on a new robot, retuning Nav2 after moving from one environment to another, or chasing specific navigation symptoms (oscillation, stuck at doorways, recovery loops, slow plans, drift). Triggers include: a new mobile robot is moving from simulation to a real warehouse and the default Nav2 params produce timid or erratic motion; a team is switching planner or controller and needs a rationale-driven baseline; a robot that worked in one facility is being deployed to a new one with different aisle widths and obstacle density; or a fleet has accumulated a copy-paste Nav2 config no one understands and a clean redo is needed.

The skill applies to Nav2 deployments running on ROS 2 (Humble, Iron, Jazzy, Rolling, or compatible). It covers the costmap stack, the planner server, the controller server, the behavior server, the smoother server, the BT navigator, and the supporting lifecycle manager.

It does not apply to: SLAM tuning (mapping is upstream of navigation; this skill assumes a usable map exists); localization tuning (AMCL or SLAM-Toolbox localization mode is its own playbook); low-level motor controller tuning (the wheel-level PID is below Nav2's controller). It also does not replace empirical testing — every recommendation here is a starting point that must be validated.

**This skill produces methodology guidance for robot software architecture. Outputs must be reviewed by qualified robotics engineers and validated in simulation and bench tests before any deployment on hardware that interacts with people or property. Bad robot software causes physical harm — treat all advice as a starting point, not a deployment-ready specification.**

The bar the skill applies is "in the target environment, does the robot move smoothly toward goals, avoid obstacles with appropriate margin, recover from realistic failures, and surface to the operator when it cannot?"

## How to apply

The tuner walks through Nav2 layer by layer. Each stage produces concrete parameter recommendations and rationale. The final stage assembles them into a YAML overlay.

### Stage 1 — Robot footprint and kinematics baseline

1. Define the *footprint*. A circular footprint with a single radius is the simplest and is appropriate for robots that are roughly round and that can in-place rotate without sweeping. For rectangular robots, especially with overhangs, define a polygon footprint with explicit vertices in `base_link`.
2. Define the *inflated footprint margin*. The inscribed radius is what the controller respects for hard clearance; the inflation radius is what the planner uses to bias paths away from walls. A 10-15 cm inflation radius for typical indoor robots is a baseline; tight environments shrink it, fast or fragile payloads widen it.
3. Define *kinematic limits*. `max_vel_x`, `min_vel_x`, `max_vel_theta`, `acc_lim_x`, `acc_lim_theta`. These should reflect what the *robot can safely do*, not what the actuators can mechanically achieve. Start at 60-70% of mechanical limits for safety, tune up.
4. Define *control modes*. Differential-drive cannot strafe; setting `max_vel_y` non-zero is a footgun. Ackermann needs `min_turning_radius`. Omnidirectional is the most permissive. Mismatches between declared kinematics and controller selection break navigation silently.
5. Define the *control frequency* (typically 20 Hz indoor, 30+ Hz for fast outdoor). The controller's `controller_frequency` must be achievable on the compute platform under load — measure, don't assume.

### Stage 2 — Costmap common parameters

6. Both global and local costmap share several parameters. `robot_radius` or `footprint` must match the robot definition; mismatches between them cause asymmetric clearance.
7. `transform_tolerance` defaults around 0.3 s. Tighter is more responsive but breaks easily when TF is occasionally late. Loose is forgiving but lets stale data drive decisions. Tune to the worst observed TF latency plus 50% headroom.
8. `update_frequency` (how often the costmap rebuilds) and `publish_frequency` (how often it is republished). Local costmap typically 5 Hz update / 2 Hz publish; global typically 1 Hz update / 1 Hz publish or on-demand. Higher rates cost CPU.
9. `rolling_window` is `true` for local costmap (follows the robot), `false` for global (fixed to the map).
10. `global_frame` is typically `map` for global costmap, `odom` for local costmap. Using `map` for the local costmap couples local obstacle avoidance to localization quality — a bad trade in most setups.
11. `track_unknown_space` matters in semi-known environments. For a warehouse with a complete map, false is fine; for outdoor or partial maps, true so the planner does not naively path through unmapped regions.

### Stage 3 — Costmap layers

12. The standard layer stack is *static layer*, *obstacle (or voxel) layer*, *inflation layer*, in that order. Other layers (range_sensor, denoise, keepout, speed_filter) layer in as needed.
13. **Static layer** reads the static map. Confirm the map topic and frame match the map server. A misaligned static layer causes the robot to plan through walls or refuse to plan through doorways.
14. **Obstacle / Voxel layer** reads live sensor data.
    - List every observation source (lidar scan, depth camera, ultrasonic) with topic, data type, marking and clearing flags, min and max obstacle height, obstacle range, raytrace range.
    - For 2D lidar, the simpler obstacle layer suffices. For 3D sensors (depth camera, 3D lidar), a voxel layer with a meaningful `z_resolution`, `z_voxels`, and `mark_threshold` discriminates real obstacles from floor noise and ceiling fixtures.
    - `obstacle_max_range` should exceed the planner's lookahead and the controller's stopping distance plus a margin. `raytrace_max_range` should equal or exceed `obstacle_max_range`, otherwise stale obstacles persist.
    - `observation_persistence` greater than zero is dangerous — phantom obstacles linger. Default zero unless there is a specific reason.
15. **Inflation layer** turns hard obstacles into a gradient.
    - `inflation_radius` controls how far the gradient extends. Equal to the robot's longest dimension is a starting baseline.
    - `cost_scaling_factor` controls the steepness of the gradient. Higher values produce a sharper cliff and tighter paths; lower values produce gentler bias toward open space. Typical 2.5-5.0 for indoor; tune empirically.
    - The inflation must be the *last* layer for the cost-summing semantics to work.
16. Special-purpose layers:
    - **Keepout zones** (filter mask) define areas the robot must not enter regardless of sensors. Use for charging cradles, human-only zones, drop-offs.
    - **Speed limit zones** define areas with a maximum speed. Use for hospital corridors, near humans, in narrow aisles.
    - **Range sensor layer** for cheap sonar/IR sensors that are not modeled by the lidar-driven obstacle layer.
17. Different stacks for global vs local. The global costmap may use fewer or simpler layers (static + inflation is often enough); the local costmap layers in live sensor data.
18. Flag any layered cost mistake: marking-only without clearing (obstacles stick forever), clearing-only without marking (the robot drives into a real obstacle), or sensor obstacle height that excludes real obstacles.

### Stage 4 — Planner selection and tuning

19. Pick the planner based on kinematics and map character:
    - **NavFn (Dijkstra/A***): fast, simple, ignores kinematics. Good for holonomic and differential robots in open spaces with frequent replan.
    - **SMAC 2D A***: optimized 2D A* for differential and omnidirectional robots, faster than NavFn at higher quality.
    - **SMAC Hybrid-A***: kinematically feasible paths for Ackermann or constrained differential robots. Use whenever turning radius matters.
    - **SMAC State Lattice**: motion primitives over a lattice. Use for nuanced kinematic constraints when the team is willing to invest in primitive generation.
    - **Theta***: any-angle paths over a grid. Use when smoother global paths matter and downstream smoothing is undesirable.
20. Plan rate and tolerance:
    - `expected_planner_frequency` is informational; the planner runs on demand. Setting it too high in BT replan loops floods compute.
    - `tolerance` (planner) controls how close to the goal the plan must reach. Higher tolerance in cluttered goals avoids "impossible to plan exactly" failures. Match to robot radius plus inflation.
21. For SMAC Hybrid-A* and Lattice, tune `minimum_turning_radius` (must match the robot), `motion_model_for_search` (DUBIN for forward-only, REEDS_SHEPP for reverse-capable), `cost_penalty`, `smooth_path`. Defaults are reasonable; the turning radius is the most common mismatch.
22. Plan-time guarantees: every planner has worst-case search time. Configure timeouts in the BT or in the planner so that an impossible goal does not lock the planner thread.

### Stage 5 — Controller selection and tuning

23. Pick the controller:
    - **DWB**: trajectory rollout with pluggable critics. Tunable but the critic weights are non-obvious. Use when fine control over trajectory selection is needed.
    - **Regulated Pure Pursuit (RPP)**: path-following with regulation for curvature, proximity to obstacles, and collision lookahead. Simple, intuitive parameters, well-suited to differential and Ackermann robots in structured environments.
    - **MPPI**: model-predictive sampling-based controller. Powerful for complex dynamics but compute-hungry — confirm the platform can run it at the configured frequency.
    - **Rotation Shim + RPP**: rotate in place toward the path heading before engaging RPP. Good when the robot starts at an awkward heading.
24. DWB tuning (when DWB is selected): the critic weights are the heart of it. `BaseObstacle.scale` (avoid obstacles), `PathAlign.scale` (follow planned path), `GoalAlign.scale` (orient toward goal), `PathDist.scale` (stay near path), `GoalDist.scale` (reach goal). Start with stock weights; raise `BaseObstacle.scale` for tight environments, `PathAlign.scale` for cluttered maps where path quality matters.
25. RPP tuning: `desired_linear_vel`, `lookahead_dist`, `min_lookahead_dist`, `max_lookahead_dist`, `use_velocity_scaled_lookahead_dist`. Velocity-scaled lookahead is usually the right default. `regulated_linear_scaling_min_radius` controls how aggressively the robot slows in tight turns; lower for nimble, higher for safer.
26. MPPI tuning: `time_steps`, `model_dt`, `batch_size`, `temperature`, critics (`GoalCritic`, `PathFollowCritic`, `ObstaclesCritic`, etc.). MPPI is sensitive to compute — confirm the batch size and time steps run within the control period budget.
27. Goal checker: `xy_goal_tolerance`, `yaw_goal_tolerance`, `stateful`. Stateful goal checker prevents oscillation near goal. Tolerances must exceed the controller's steady-state error or the robot dithers forever.
28. Progress checker: distance and time thresholds. If the robot moves less than X meters in Y seconds, declare progress failure. Without a progress checker, a robot pinned against an obstacle never gives up.

### Stage 6 — Behavior (recovery) server

29. The behavior server hosts recovery actions: `Spin`, `BackUp`, `Wait`, `AssistedTeleop`, `DriveOnHeading`. Each is parameterized.
30. `Spin`: `max_rotational_vel`, `min_rotational_vel`, `rotational_acc_lim`. Confirm the robot can rotate in place in the available space — for a long robot in a tight aisle, spin is not safe.
31. `BackUp`: `simulate_ahead_time` for collision check, max distance, speed. Backing up blind into a previously-cleared area is hazardous; the simulate-ahead time gates safety.
32. `Wait`: pure timer. Use sparingly — waiting only helps if the obstacle is dynamic.
33. Recovery behavior choice belongs to the *behavior tree*, not to the navigation server. Audit the BT (or the default Nav2 BT) for recovery composition; see the BT designer skill for tree-level recovery design.

### Stage 7 — Smoother and post-processing

34. Optional but valuable on jerky paths. `SimpleSmoother`, `ConstrainedSmoother`, `SavitzkyGolaySmoother`.
35. `ConstrainedSmoother` respects kinematic constraints and produces drivable paths; recommended for Ackermann.
36. Smoothing adds latency. Confirm the BT triggers smoothing only after planning, not in the controller loop.

### Stage 8 — BT navigator integration

37. Nav2 ships default BTs that handle replanning, recovery, and goal cancellation. Confirm the team uses the right default for their use case or has a custom BT.
38. The BT's recovery branches should match the behaviors enabled in the behavior server — referencing a `Spin` recovery when spin is not configured produces a runtime failure on first need.
39. Replan rate is BT-controlled. Replanning every controller tick is wasteful; replanning on path-stale conditions (obstacle on path, goal reached criteria changed) is the pattern.

### Stage 9 — Observability

40. Confirm RViz2 visualizations are configured for `/global_costmap`, `/local_costmap`, the planned path, the controller's trajectory rollout (DWB) or path candidate (MPPI), and the inflation overlay.
41. Diagnostics: each Nav2 lifecycle node should publish status. The lifecycle manager surfaces aggregate status — confirm the operator UI displays it.
42. Metrics: plan time, control loop duration, costmap update time. Recording these in rosbags during commissioning is the single best preparation for tuning later.
43. Logs: at INFO, Nav2 should be readable. Replan storms, frequent recovery triggers, and goal-checker timeouts all surface as log patterns worth grepping.

### Stage 10 — Symptom-driven adjustments

Each common symptom maps to a concrete adjustment. Walk through the reported symptoms.

44. *Oscillation near goal*: tighten `xy_goal_tolerance` to exceed steady-state error; enable stateful goal checker; for DWB raise `GoalAlign.scale` or reduce `vx_samples` to discourage over-correction.
45. *Stuck at doorway*: shrink `inflation_radius` slightly; verify the door width exceeds robot width plus inscribed inflation; consider a narrower footprint in known doorway regions via cost-shaping; verify the planner is generating a path through the doorway at all (visualize the global plan).
46. *Drift into walls during motion*: check controller lookahead — too long a lookahead cuts corners; check sensor coverage — a blind spot at the corner of the robot causes wall contact; raise inflation cost_scaling_factor.
47. *Replan storms*: confirm the BT replans on triggers, not every tick; check that the planner is not failing repeatedly (which forces replan); investigate sensor noise injecting phantom obstacles on the path.
48. *Recovery loops*: cap recovery attempts in the BT; investigate whether the recovery itself is failing or just not addressing the root cause; check for a transient localization wobble that triggers recovery and then clears.
49. *Slow plans on long goals*: switch from NavFn to SMAC 2D, or tune SMAC's heuristic and cost weights; verify the global costmap resolution is not unnecessarily fine (5 cm vs 10 cm changes plan time by 4x).
50. *Jerky controller output*: lower acceleration limits, add smoothing, verify the controller frequency is actually met (check controller_diagnostics or measure with rqt_plot).
51. *Phantom obstacles*: tune voxel layer `mark_threshold` and `unknown_threshold`; verify sensor frame and orientation; check for reflections on shiny floors (lidar) or sunlight blooming (depth camera).
52. *Misses goal entirely*: confirm `xy_goal_tolerance` is greater than typical controller steady-state error; confirm the goal is reachable on the inflated costmap.

### Stage 11 — Verification checklist

53. *Footprint vs door*: pick the narrowest passage in the environment and confirm robot footprint + inscribed inflation fits with margin.
54. *Speed sanity*: at max speed, stopping distance (using `acc_lim_x`) is less than the controller's `obstacle_max_range` minus inflation. If not, the robot can hit something before it sees it.
55. *Replanning loop*: place a temporary obstacle in the original plan and confirm the robot replans, navigates around, and converges to the goal in bounded time.
56. *Recovery exercises*: simulate localization drop, sensor brownout, and full path-blocked scenarios. Confirm the BT reaches a deliberate failure (operator alert) rather than an infinite loop.
57. *Soak test*: a 60-minute random-goal mission in the target environment, with rosbag recording. Inspect for slow degradations — costmap memory growth, increasing plan times, accumulating phantom obstacles.

### Stage 12 — Render

58. Produce a `tuning_report` with: an executive summary of the recommended profile; a parameter rationale section (costmap, planner, controller, behavior, smoother); a symptom-to-fix table; a verification checklist with pass criteria; and the YAML overlay.
59. Produce a `nav2_param_overlay` with only the deltas from a sensible default, each non-trivial change annotated with a brief comment.

## Environment-specific guidance

The tuner adjusts its baselines based on the declared environment. The same robot tuned for one environment will not work in another.

**Cluttered warehouse with 1.2 m aisles, dynamic forklifts**: prioritize tight inflation (0.10-0.15 m), high `cost_scaling_factor` (4-6) for sharp gradient, voxel layer with `observation_persistence=0` (forklifts move), aggressive `progress_checker` to give up on stuck states quickly, RPP controller with short lookahead (0.4-0.8 m). Recovery emphasizes operator escalation over `Spin` (a spin in a forklift aisle is dangerous).

**Hospital corridors with humans**: prioritize a generous inflation (0.25-0.35 m), `speed_filter` mask for human-only zones (slow to walking speed), keepout zones for stretcher bays, `Spin` recovery disabled in narrow halls, `BackUp` recovery limited to 0.10 m. Controller prefers smooth velocity profiles over aggressive convergence.

**Outdoor unstructured terrain**: prioritize a 3D obstacle representation (voxel layer with z-binning), GPS fusion in the localization (not Nav2's concern but interacts via the global frame), Hybrid-A* or Lattice planner for Ackermann robots, longer planner lookahead, costmap update at lower rate (terrain does not change tick-to-tick).

**Hospital pharmacy / lab indoor**: prioritize precision near goals (tight `xy_goal_tolerance`, stateful checker), low max speed (0.4-0.6 m/s), generous timeouts (false alarms in a tight precision environment are worse than slow execution). `track_unknown_space=false` because the map is complete.

**Open factory floor with mixed traffic**: balanced inflation (0.15-0.20 m), velocity-scaled lookahead, `speed_filter` for known-busy zones, full voxel layer for forklift detection at standing-person height, MPPI controller if compute permits (handles dynamics well).

**Outdoor parking lot / wide spaces**: longer lookahead, larger costmap (10-20 m local, full-map global), lower update rate, planner is the dominant cost not the controller.

## Sensor-specific tuning notes

The costmap depends on what the sensors actually deliver. Audit each sensor:

- *2D lidar*: standard obstacle layer with the lidar topic. Confirm the lidar's published frame matches the URDF; misalignment is a common source of "the robot avoids phantom walls."
- *3D lidar*: voxel layer with z-binning. Set `z_resolution` to ~10 cm for indoor, ~20 cm for outdoor. `z_voxels` = `(robot_height + headroom) / z_resolution`. Set `min_obstacle_height` above floor noise; `max_obstacle_height` to robot top + clearance.
- *Depth camera*: voxel layer, but consider noise filtering upstream. Depth cameras hallucinate obstacles under sunlight, reflective floors, and at range limits. A separate denoise node ahead of the voxel layer is often necessary.
- *Sonar / IR / range sensors*: use the `range_sensor_layer`. These are noisy and slow; treat them as supplementary, not primary.
- *Bumpers and contact sensors*: not directly a costmap input — they should drive an immediate stop via the controller's safety pathway, not via the costmap (which has too much latency).
- *Stereo cameras*: treat output as a point cloud and route through the voxel layer; expect lower quality than depth or lidar at range.

For multi-sensor fusion, list every observation source on the voxel/obstacle layer. Misconfigured sources are a top cause of mysterious navigation failure — confirm each source is marking and clearing as expected.

## Tuning workflow on a real robot

Once the parameters are written down, the tuning is empirical. The agent recommends:

1. Bring up the stack in simulation first. Confirm the robot can navigate to a series of goals in an open environment. If sim fails, real will fail more.
2. Move to an empty bench-rig or a closed test cell. Run the same goals. Diff trajectories and timings against sim.
3. Add obstacles incrementally. Watch the costmap visualization in RViz2 while the robot moves; misalignment surfaces visually before it surfaces as a failure.
4. Tune in this order: footprint → costmap layers → planner → controller → recovery. Each stage stabilizes before the next is touched.
5. When a symptom appears, hypothesize the layer most likely responsible from the symptom-driven adjustments table, change one parameter, observe. Do not change multiple parameters at once.
6. Record every successful run as a rosbag. The library of rosbags becomes the regression test set when later changes are evaluated.
7. Lock the tuned values into version control with rationale comments. Future engineers should never wonder why `cost_scaling_factor=3.5`.

## Examples

A representative example: a 40 cm differential-drive warehouse robot, 1.2 m aisles, 2D lidar, indoor-flat, max 0.8 m/s. The tuner would likely recommend a circular footprint of 0.22 m radius, inflation 0.20 m at scaling factor 3.0, SMAC 2D A* global planner, Regulated Pure Pursuit controller with velocity-scaled lookahead 0.3-0.9 m, stateful goal checker at 0.10 m xy / 0.20 rad yaw, behavior server with Spin (max 1.0 rad/s) and BackUp (0.10 m, simulate-ahead 1.0 s), and a custom BT with capped recovery retries. Specific values are starting points to validate in simulation and on a bench rig before any production use.

## Common interactions to watch

Parameter choices interact. The tuner highlights these:

- *Inflation radius and tolerance*: a planner tolerance smaller than the inflation radius can produce "impossible to plan" failures near goals.
- *Controller lookahead and obstacle range*: lookahead beyond the sensor's reliable range means the controller plans paths through unobserved space.
- *Costmap update rate and controller rate*: a controller at 20 Hz reading a costmap updated at 1 Hz is reacting to stale obstacle data.
- *Acceleration limits and progress checker*: a slow-accelerating robot triggers progress-stuck checks too easily; widen the budget.
- *Voxel observation_persistence and dynamic obstacles*: any persistence > 0 with moving obstacles creates ghosts. Default zero except for special cases.
- *Goal tolerance and controller damping*: tight tolerance with a fast oscillating controller produces dither; either widen tolerance or damp the controller.
- *Inflation cost_scaling_factor and aisle width*: too steep a gradient in a narrow aisle puts the entire aisle in high-cost space and the planner avoids it.

## Outputs

The skill emits two artifacts. The first is a markdown `tuning_report` covering rationale, parameters, symptom adjustments, and verification. The second is `nav2_param_overlay`, a commented YAML delta ready to merge into the team's Nav2 params and lifecycle-bringup.

The report opens with the recommended profile in one paragraph (planner choice, controller choice, key parameter values) so an engineer who needs only the punchline can act in five minutes. The detail follows for the engineer doing the actual tuning.

## Symptom-to-fix quick reference

For a hurried engineer chasing a specific symptom, the tuner provides this compressed table. Each entry expands into a detailed adjustment in the full report.

| Symptom | First check | Second check | Third check |
| --- | --- | --- | --- |
| Oscillation near goal | xy_goal_tolerance vs steady-state error | stateful goal checker | controller damping (DWB GoalAlign.scale, RPP lookahead) |
| Stuck at doorway | aisle width vs footprint + inflation | global plan visualization | obstacle layer sensor coverage |
| Drift into walls | controller lookahead | sensor blind spots | inflation cost_scaling_factor |
| Replan storms | BT replan triggers | planner failure rate | sensor noise on plan path |
| Recovery loops | BT recovery cap | recovery effectiveness | localization stability |
| Slow plans | planner choice (NavFn vs SMAC) | costmap resolution | planner heuristic |
| Jerky controller | acceleration limits | smoother enabled | controller frequency actually met |
| Phantom obstacles | voxel mark_threshold | sensor orientation | floor/ceiling reflections |
| Misses goal | goal tolerance vs error | goal in inflated obstacle | progress checker firing |
| Refuses to plan | start in inflated obstacle | goal in inflated obstacle | costmap layers stacked correctly |
| Costmap shows wrong walls | static map alignment | TF tree | map_server topic and frame |
| Controller laggy | controller_frequency vs achievable | executor configuration | composition with costmap |

## Lifecycle and bring-up sanity

Nav2 is a lifecycle-managed stack. The tuner verifies:

- *Lifecycle manager* is in the launch and brings nodes up in dependency order: map_server → amcl → costmap nodes → planner → controller → behavior server → BT navigator.
- *Bond timeouts* on the lifecycle manager are calibrated; the default works in sim and fails under load on real hardware.
- *Recovery from a node death*: when an individual Nav2 node crashes, the lifecycle manager surfaces the failure rather than letting the stack appear half-up.
- *Map server* loads the correct map at activation. Mismatched maps between planning and localization are a common bring-up bug.
- *Initial pose* is set after activation, before the first goal. AMCL without an initial pose drifts unpredictably.
- *Costmap initial state* — the first goal arrives after the costmaps have stabilized (give it 1-2 seconds after activation).

## Limitations

The tuner produces a methodology and a starting parameter set. It cannot:
- Measure real costmap update times, control loop jitter, or plan latencies on the target hardware.
- Substitute for an empirical tuning pass in the target environment.
- Catch hardware-level issues (loose lidar mount, sensor mis-calibration, wheel slip) that masquerade as tuning bugs.
- Replace simulation, bench testing, or staged on-floor commissioning by qualified engineers.

Navigation parameters interact in subtle ways. A change that improves doorway behavior can degrade open-space behavior. Tune one layer at a time, verify in simulation, then in a controlled physical space with kill-switch coverage, then in production.

The tuner is calibrated to the publicly-documented Nav2 patterns and parameter conventions; a team running a heavily-customized Nav2 fork or a non-Nav2 navigation stack should use the methodology and translate the parameter names to their stack. The structure of the audit — footprint, costmap, planner, controller, recovery, BT, observability — applies broadly.

Finally, do not tune in production. A robot that is being tuned should be on a bench rig or in a closed test cell. Tuning in front of a customer or in a live operating environment is a category mistake.

## Deliverable acceptance criteria

A tuning engagement is complete when:

- The team can articulate, for every recommended parameter, why the value was chosen and what symptom or principle drove it.
- A canonical mission runs end-to-end in simulation, then on the bench rig, then in the target environment, with rosbags captured at each stage.
- The verification checklist (Stage 11) passes in the target environment.
- The parameter file is in version control with rationale comments and a link to the tuning report.
- The team has identified and documented at least three symptom-to-fix levers they will use for in-field adjustments.
- A regression baseline (rosbag set) is captured so future changes can be diffed against the tuned state.
