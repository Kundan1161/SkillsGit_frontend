# DAG Architect

## When to use

Use this skill when a user needs to **design or redesign an orchestration DAG** in Apache Airflow, Dagster, or Prefect, and the design must be **defensible** for production: idempotent, retry-safe, observable, and SLA-aware. Typical signals:

- "Design me an Airflow DAG for X."
- "Our Dagster asset graph keeps half-finishing — fix the design."
- "We need a Prefect flow with sensors and proper retries."
- "Help me decide schedule vs sensor for this trigger."
- "What's the right idempotency strategy for this pipeline?"

Do **not** use this skill for:
- Writing the implementation code without a design step (use a coding skill instead).
- Choosing *between* orchestrators at the platform level (use the `orchestrator-migration-planner` skill).
- Authoring inter-stage data contracts (use the `pipeline-data-contract-author` skill).
- Planning a historical backfill (use the `pipeline-backfill-conductor` skill, if available).

## Inputs

| Input            | Required | Notes |
|------------------|----------|-------|
| `orchestrator`   | yes      | Pick one. If `undecided`, the skill will produce designs in pseudo-DAG form plus a short decision matrix and stop. |
| `pipeline_brief` | yes      | Free-form. Should answer: what sources, what sinks, what cadence, what freshness SLA, what scale (rows/day, MB/day), who owns it, who consumes it. |
| `existing_dag`   | no       | Paste current code; the skill will diff its recommendations against it. |
| `constraints`    | no       | E.g. "must run on Airflow 2.7, no KubernetesExecutor", "Dagster Cloud Serverless", "Prefect 3 on ECS Fargate", "cost cap $200/mo". |

If `pipeline_brief` is fewer than 40 words or omits the schedule and freshness SLA, **stop and ask** before designing — a vague brief produces a useless design.

## Outputs

A single markdown document with these sections, in this order:

1. **One-paragraph design summary** — what you are building and why this shape.
2. **Topology** — ASCII or mermaid graph of tasks/assets and dependencies.
3. **Trigger strategy** — schedule expression, sensor(s), or event source, with the *reason* for the choice.
4. **Idempotency contract** — the partition or idempotency key used by every write, and the read pattern that pairs with it.
5. **Retry & failure policy** — per-task retry counts, delays, exponential backoff, retry-condition logic, dead-letter behavior, alert routing.
6. **Branching & dynamic generation** — where the DAG branches, where it expands dynamically, and how the parser cost is bounded.
7. **Observability** — logs, metrics, lineage hooks, SLA misses, on-call routing.
8. **Sketch implementation** — a runnable but skeletal code block in the target orchestrator (≤120 lines), with `# TODO` markers for business logic.
9. **Open questions** — anything the brief did not answer.

## How to apply

### Step 1 — Restate the pipeline in one paragraph

Restate the pipeline back to the user in your own words, including: sources, sinks, schedule cadence, freshness SLA, expected volume, criticality (tier), and downstream consumers. **Surface every assumption** you had to make. If three or more assumptions were required, stop and ask.

### Step 2 — Decide the unit of execution

The orchestrators disagree on the right unit; pick deliberately:

- **Airflow**: the unit is the **task** inside a DAG. Each task = one atomic operation (extract, transform, load, validate). Tasks communicate via XCom for small values (<48 KB) and via remote storage (S3, GCS, blob) for everything else.
- **Dagster**: the unit is the **asset** — a named, persisted data artifact. Wire assets by declaring upstream `deps=` rather than wiring ops. The graph emerges from the asset definitions.
- **Prefect**: the unit is the **task** inside a flow, but flows can call subflows. Use subflows for reusable subgraphs; use tasks for atomic steps. `@task` decorators add retries, caching, and concurrency limits.

State explicitly: **"the unit here is X because Y"**. If the user is undecided, default to:
- Asset-shaped (Dagster) when the pipeline is data-product-centric and lineage matters more than orchestration.
- Task-shaped (Airflow) when the pipeline is operation-centric (move, transform, deliver) and the team already has Airflow infra.
- Task-with-subflows (Prefect) when the team is small, Python-native, and wants minimal infra.

### Step 3 — Atomize tasks for idempotency

Every task **must** be re-runnable without corrupting state. Apply these rules:

1. **One side effect per task.** Extract, transform, load, validate are separate tasks.
2. **No INSERT to data sinks.** Use one of: `MERGE`/`UPSERT` keyed on a business + partition key; `DELETE WHERE partition = X; INSERT`; `INSERT OVERWRITE PARTITION`; or write to a partition path and atomically swap a symlink/manifest.
3. **No "read latest" inside a task.** Read a specific partition or watermark passed in by the orchestrator (`logical_date` in Airflow, `partition_key` in Dagster, parameter in Prefect). The same task with the same input must produce the same output.
4. **Externalize state.** If a task needs counters, sequence numbers, or cursors, store them in a deterministic location keyed by the run's partition, not in memory.
5. **Side effects last.** Within a task, perform the network/IO write as the **final** statement so a crash mid-computation leaves no half-written rows.

### Step 4 — Pick the idempotency key

Every write needs an explicit idempotency key. Choose one shape and document it:

- **Time partition**: `event_date = {logical_date}` or `hour = {logical_date:%Y%m%dT%H}`. Best for time-series and batch ingestion.
- **Natural key**: `MERGE ... ON target.id = source.id`. Best for slowly-changing reference data.
- **Composite**: `(source_system, batch_id)`. Best for event-sourced ingestion where batches are explicit.
- **Hash of content**: `sha256(payload)`. Best for API ingestion where the source emits the same payload on retry.

Record the key in the design under **Idempotency contract** with a one-line proof: *"if this task runs twice with the same partition, the sink ends in the same state because writes are keyed on (X, Y) and use MERGE."*

### Step 5 — Choose trigger: schedule vs sensor vs event

- **Schedule (cron / cron preset)**: use when the source is reliably available on a clock. Cheapest, most predictable. Almost always the default.
- **Sensor**: use when the source's arrival time varies. In Airflow, prefer **deferrable sensors** (triggerer-based) over reschedule-mode sensors over poke-mode — they free the worker slot. In Dagster, use a `@sensor` that polls the source and yields `RunRequest`s. In Prefect, use an event-driven deployment or a sensor flow that polls and triggers a child flow.
- **Event**: use when a producer can emit a webhook, SNS, EventBridge, Kafka, or Prefect-event. Pair with a small dedupe table keyed by event id so duplicate events don't cause duplicate runs.

Hybrid pattern: schedule a "guardrail" run daily even when the primary trigger is event-driven. This catches missed events and gives a known-good recovery point.

### Step 6 — Set retry policy per task

Per task, specify:

- `retries`: default **2** for most tasks; **0** for tasks whose side effects are not safely retriable (e.g. an external API that charges per call without an idempotency key on its side); **5+** for flaky external services that you cannot improve.
- `retry_delay`: minimum **30 seconds** to avoid thundering-herd against a recovering service.
- `retry_exponential_backoff`: **on** for any external call. Cap at `max_retry_delay` ~10 minutes.
- `retry_condition` (Prefect) / `on_failure_callback` (Airflow): inspect the exception. *Do not retry* validation failures, schema errors, or auth errors — those are deterministic. *Do retry* timeouts, 5xx, and transient connection errors.
- `execution_timeout`: every task. A hanging task without a timeout blocks the entire DAG.
- **Dead-letter behavior**: on terminal failure, write the failed record's id to a dead-letter table or path. Do not lose the input.

### Step 7 — Branching and dynamic generation

- **Static branching**: `BranchPythonOperator` (Airflow), conditional `@op`/`@asset` outputs (Dagster), `if/else` in flow (Prefect). Use when the branch count is fixed and known at DAG-parse time.
- **Dynamic task mapping** (Airflow 2.3+): use `.expand()` over a list produced by an upstream task. Bound the fan-out — never expand over an unbounded source. Set `max_active_tis_per_dag` to protect downstream systems.
- **Dynamic partitions** (Dagster): use `DynamicPartitionsDefinition` and add partition keys as new data sources appear. Pair with a sensor that adds the partition then triggers materialization.
- **Subflows** (Prefect): call `child_flow()` from within a parent flow; each invocation is a separate flow run with its own retries.

**Parser-cost rule**: any code that runs at DAG-parse time (top-level imports, top-level DB calls, top-level loops generating tasks) is paid by the scheduler on **every parse**, often every 30 seconds. Move expensive logic into task bodies. If a list of dynamic tasks must be known at parse time, cache it on disk with a short TTL.

### Step 8 — SLA and observability

- **SLA**: declare freshness and runtime SLAs in code. Airflow: `sla=timedelta(...)` on task or use `SLAMiss` callbacks (note: deprecated in some versions — confirm). Dagster: `FreshnessPolicy(maximum_lag_minutes=...)`. Prefect: deployment-level expected runtime + alerts.
- **Logs**: structured (JSON) where possible. Include `run_id`, `partition`, `attempt`, `task_id`. Ship to your aggregator (CloudWatch, Datadog, Loki).
- **Metrics**: per-task duration, retry count, rows in/out, bytes in/out. Emit as StatsD/OTel from inside the task.
- **Lineage**: enable OpenLineage in Airflow (`openlineage-airflow`) or use Dagster's built-in asset lineage. Prefect 3 emits events that can be forwarded to OpenLineage.
- **Alerting**: route SLA misses and terminal failures to the on-call channel with the run URL and the partition. Do not send retries to on-call — that's noise.

### Step 9 — Produce the sketch implementation

Write a ≤120-line skeleton in the target orchestrator that compiles (imports resolve, decorators valid) but contains `# TODO` for business logic. The skeleton must show:
- The trigger.
- All retry / timeout / sla settings on at least one representative task.
- The idempotency key passed in via the partition or run context.
- One sensor or branching example if relevant.
- An on-failure hook.

### Step 10 — List open questions

End every output with **Open questions** — every assumption you made that the user did not explicitly confirm. Number them; the user should be able to answer them inline.

## Examples

### Example A — Airflow daily ingestion with deferrable sensor

User: *"I need a DAG that waits for a daily file in S3 at `s3://corp-raw/orders/dt={ds}/`, loads it into Snowflake, validates row counts, and notifies #data-ops on failure. Freshness SLA is 09:00 local."*

Design summary (excerpt):
- Trigger: schedule `0 7 * * *` UTC (= 02:00 ET, gives 2h buffer to 09:00 ET SLA) plus a deferrable `S3KeySensor` on the partition path.
- Idempotency key: `dt = {logical_date_ds}` partition in Snowflake; load uses `COPY INTO ... FILE_FORMAT ... ON_ERROR = ABORT_STATEMENT` against a partitioned staging table, then `MERGE` into target keyed on `(order_id)`.
- Tasks: `wait_for_file` (deferrable sensor) → `load_stage` → `validate_row_count` (BranchPythonOperator: ok / quarantine) → `merge_to_target` → `emit_lineage`.
- Retries: `load_stage` retries=3, exponential backoff 60s→10m; `validate_row_count` retries=0 (deterministic); `merge_to_target` retries=2.
- SLA: `sla=timedelta(hours=2)` on `merge_to_target`. SLA miss callback posts to #data-ops.

Sketch:

```python
from airflow.decorators import dag, task
from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor
from datetime import datetime, timedelta

default_args = {
    "retries": 2,
    "retry_delay": timedelta(seconds=60),
    "retry_exponential_backoff": True,
    "max_retry_delay": timedelta(minutes=10),
    "execution_timeout": timedelta(minutes=30),
}

@dag(
    schedule="0 7 * * *",
    start_date=datetime(2026, 5, 1),
    catchup=False,
    default_args=default_args,
    tags=["orders", "ingestion"],
)
def orders_daily():
    wait = S3KeySensor(
        task_id="wait_for_file",
        bucket_key="s3://corp-raw/orders/dt={{ ds }}/_SUCCESS",
        deferrable=True,
        timeout=60 * 60 * 2,
    )

    @task(retries=3)
    def load_stage(ds=None):
        # TODO: COPY INTO staging.orders_{ds} from s3://corp-raw/orders/dt={ds}/
        ...

    @task(retries=0)
    def validate(ds=None):
        # TODO: assert row_count >= last_partition_row_count * 0.5
        ...

    @task(retries=2, sla=timedelta(hours=2))
    def merge(ds=None):
        # TODO: MERGE INTO prod.orders USING staging.orders_{ds} ON order_id
        ...

    wait >> load_stage() >> validate() >> merge()

orders_daily()
```

### Example B — Dagster asset with dynamic partitions

User: *"Each new tenant gets a daily report. Tenants are added by Sales in our CRM, sometimes 0/day sometimes 10/day. I want one asset per tenant per day."*

Design summary (excerpt):
- Unit: asset (`@asset`) with two-dimensional partitioning: `tenant` (dynamic) × `date` (daily).
- Trigger: a `@sensor` polls the CRM hourly; on new tenant, `instance.add_dynamic_partitions("tenants", [new_tenant])` and yields a `RunRequest` for today's partition.
- Idempotency: write target is `s3://reports/{tenant}/dt={date}/report.parquet`. Overwrite the partition path; never append.
- Retries: asset `retry_policy=RetryPolicy(max_retries=3, delay=60, backoff=Backoff.EXPONENTIAL)`.
- Freshness: `FreshnessPolicy(maximum_lag_minutes=24*60)`.

## Limitations

- This skill produces a **design**, not production-ready code. The sketches compile but require business logic, secrets, and connection configuration before they run.
- Airflow 1.x is not supported. Designs assume Airflow ≥ 2.6 (TaskFlow API, deferrable operators). Dagster designs assume 1.5+. Prefect designs assume 3.x.
- The skill does not size infrastructure (worker count, executor choice, DB sizing). Pair with an infra-planning skill.
- The skill does not author SQL or business logic — only the orchestration shape around it.
- Streaming-first systems (Kafka Streams, Flink) are out of scope. Use a streaming-oriented skill instead.
- If the brief implies a streaming-grade freshness SLA (< 5 minutes), the skill will warn that batch orchestration is the wrong tool.
