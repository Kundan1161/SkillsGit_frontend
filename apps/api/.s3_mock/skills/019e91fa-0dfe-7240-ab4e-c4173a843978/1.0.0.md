# SLAM Evaluation Rig Designer

## When to use

Use this skill when a team needs to **design or upgrade a SLAM evaluation rig**, meaning the set of datasets, metrics, infrastructure, automation, and human processes that together answer the question "is our SLAM stack good enough to ship today?". Common triggers:

- A SLAM stack is moving from research code into a product and ad-hoc evaluation no longer suffices.
- Public-dataset performance is good but field performance is poor; the team needs an evaluation that catches the gap before release.
- An incident has shown that a regression slipped through; the team must add a regression suite that would have caught it.
- A safety review demands written evidence that performance is being measured against the deployment envelope.
- A new platform variant is being introduced and the evaluation must extend to cover it.

The skill produces an **evaluation rig design**: a set of artefacts (datasets, metrics, harnesses, dashboards), a set of processes (cadence, ownership, gating), and a set of policies (what triggers a hold, what triggers an investigation). It does not implement the rig.

**Safety disclaimer (mandatory):** This skill produces methodology guidance for SLAM evaluation rig design. SLAM failures cause physical harm in autonomous systems. Every recommendation must be reviewed by qualified robotics engineers, validated in simulation, and bench-tested in a safe enclosure before any deployment near people or property. The evaluation rig itself is a safety-critical artefact; gaps in it propagate to gaps in field safety. Treat all advice below as a starting point that must be augmented by hazard analysis and third-party review.

## How to apply

Work the steps in order. The rig design is constrained at the top by the deployment envelope and at the bottom by available infrastructure; both must be honest inputs.

### Step 1 — Specify what "good" means for this stack

Before designing metrics, write down what the platform actually needs.

Ask:

- **Whose decisions does the SLAM output feed?** A planner with a fixed-rate control loop has different requirements than a once-per-mission re-localization step. The consumer's error tolerance is the upstream constraint.
- **What error metric does the consumer care about?** Sometimes it is absolute trajectory error end-to-end. Sometimes it is relative pose error over a short horizon. Sometimes it is loop-closure latency. Sometimes it is the probability of catastrophic failure per kilometre travelled. The rig must measure what matters.
- **How rare can catastrophic failure be?** "Once per shift" is a different rig than "once per fleet-month".
- **What is the operational envelope?** The rig must cover all of it. A rig that demonstrates accuracy in environment A while environment B remains uncovered is not a rig, it is a sales demo.

The output of Step 1 is a one-page rubric: a list of performance properties, each with a numeric target and the consumer whose decision it bounds.

### Step 2 — Choose the metric set

The metric set must be small enough to communicate but rich enough to surface every important failure. The conventional baseline metric pair for SLAM is the absolute trajectory error and the relative pose error.

**Absolute trajectory error.** The aggregate deviation of the estimated trajectory from a ground-truth trajectory, after a rigid alignment in the appropriate frame. Useful for whole-run accuracy. Sensitive to scale errors. Report root-mean-square, median, and tail percentiles separately — the mean alone hides catastrophic excursions.

**Relative pose error.** The error in the relative transform between two states at a chosen time horizon (e.g. one second, ten seconds, one minute). Useful for surfacing drift growth independent of overall alignment. Sensitive to local dynamics. Report at multiple horizons so that short-horizon and long-horizon behaviour can be inspected separately.

Beyond these two, build out a layered metric set:

- **Drift rate** along axes the platform cares about (often vertical drift on aerial platforms, scale drift on monocular systems).
- **Re-localization metrics.** Time to first lock on startup, success rate, false-lock rate against a known set of similar locations.
- **Loop-closure metrics.** Acceptance rate, false-acceptance rate against deliberately introduced look-alike negatives, latency from query to integrated constraint.
- **Tracking robustness metrics.** Mean and minimum feature count, fraction of frames with track count below a threshold, mean track lifetime.
- **Health-monitor metrics.** False-alarm rate and miss rate of any internal degradation monitor, evaluated against labelled failure intervals.
- **Resource metrics.** End-to-end latency from sensor capture to pose output, CPU and memory budgets, energy per kilometre or per minute.
- **Failure-mode counts.** Frequency of "tracking lost", "session aborted", "re-localization failed" events.

Every metric needs a clear definition, a single owner, and a single source of truth.

### Step 3 — Decide on ground-truth sources and their honest error bounds

Ground truth is the foundation; if it is wrong, the whole rig is wrong. Most rigs combine several sources.

Common sources:

- **Optical motion capture.** Sub-millimetre accuracy indoors, but bounded by the capture volume and requires markers on the platform. Use for accuracy-of-record indoor evaluation.
- **Real-time-kinematic GNSS.** Centimetre-class accuracy outdoors with open sky, degraded near buildings or canopy. Use for outdoor evaluation; combine with inertial smoothing for short-duration accuracy.
- **Total-station tracking.** Survey-grade accuracy along a line of sight; useful for ground vehicles in semi-controlled environments.
- **Surveyed fiducials.** Static markers with known world-frame coordinates; the platform passes through them to anchor segments of a trajectory. Cheap, scalable, but only constrains the trajectory at fiducial locations.
- **Multi-modal cross-validation.** Two independent estimators (e.g. a high-end commercial unit and a structured engineering rig) compared on the same run. Confidence comes from agreement and from documented disagreement modes.
- **Simulation truth.** Perfect in principle, but only as faithful as the simulator's sensor models. Use for stress tests and parametric coverage, not for absolute accuracy claims.

For every ground-truth source, write down its expected error band. A motion-capture truth with one-millimetre error is fine for evaluating a centimetre-class stack and useless for evaluating a sub-millimetre stack. Do not report SLAM error tighter than the truth's own error.

### Step 4 — Construct the environment-and-motion matrix

The rig must cover the deployment envelope. Build a matrix with two axes:

- **Environment.** Indoor lab, indoor cluttered office, indoor warehouse with aisles, outdoor courtyard, outdoor urban canyon, indoor-outdoor transitions, tunnels, low-light, mixed-light, dynamic scenes, static scenes, repetitive scenes, textureless scenes, glass-and-mirror scenes.
- **Motion regime.** Low-speed manoeuvring, high-speed straight-line, aggressive yaw, sustained hover, sudden acceleration, sustained vibration, intermittent occlusion of one or more sensors.

For each cell in the matrix, decide:

- **Required or optional.** A required cell must be covered before release; an optional cell is captured opportunistically.
- **Capture source.** Public dataset, in-house dataset, simulation, hardware-in-loop, or live deployment data with post-hoc annotation.
- **Ground-truth source.** From Step 3.
- **Pass criteria.** Specific numeric thresholds for the metrics defined in Step 2.

The matrix is the rig's contract with the deployment envelope. Coverage gaps are the deliverable to flag to leadership.

### Step 5 — Build the regression suite

A regression suite catches changes in stack performance from one release to the next. It must be:

- **Automated.** Run on every code change, or at least nightly on the head of the main branch.
- **Deterministic.** Same inputs, same outputs (within documented stochastic bounds). Eliminate or seed every randomized component.
- **Fast enough to gate releases.** A two-hour suite is acceptable; a two-day suite is not. Tier the suite into a fast smoke and a longer deep suite if necessary.
- **Layered.** Unit-level (e.g. front-end on a single image pair), integration-level (e.g. full stack on a short segment), and full-trajectory-level (e.g. complete benchmark replay).
- **Statistical.** Run multiple seeds for any stochastic component; report distributions, not single-run numbers. A single-seed regression is noise.

Each test in the suite has:

- A purpose stated in a single sentence.
- An input dataset (versioned, immutable, with documented provenance).
- A target metric and a pass threshold (with a documented rationale, not a number pulled from thin air).
- A failure-triage owner.

Tests that flake without action lose credibility; either fix them or remove them.

### Step 6 — Design the hardware-in-loop harness

Software-only replay is necessary but insufficient. The actual sensors and the actual compute have failure modes that replay does not surface (clock drift, thermal throttling, IMU temperature behaviour, exposure-control feedback loops). A hardware-in-loop harness reproduces these.

Design choices:

- **Fixture or platform.** A motorized gimbal with the real sensor head, or the actual platform driven through a repeatable course.
- **Repeatability mechanism.** Encoded turntables, robot arms, or rail systems for indoor; surveyed routes with timing gates for outdoor; AprilTag-style fiducials at known locations for re-localization tests.
- **Telemetry capture.** Record raw sensor streams and stack outputs every run so that any failure can be re-played offline.
- **Cadence.** Pre-release on every candidate; periodic regression on the head of main; full sweep before any externally-facing milestone.
- **Operator process.** Checklists, abort criteria, recovery procedures. The harness is a piece of equipment; it has its own operating procedures.

The hardware-in-loop harness is expensive to build. The question is not whether to build it but when, and how to phase its capabilities. A common phasing is: turntable on a bench first, then short trolley course indoors, then full platform-on-rails outdoors.

### Step 7 — Define release gates and rollback triggers

The rig produces numbers. Numbers need rules to become decisions.

Define:

- **Release gates.** Specific metric thresholds that must be met before a release can be promoted from pre-release to release. State each gate in the form "metric X must be at most Y on dataset Z" with explicit dataset versioning.
- **Hold criteria.** Thresholds that, if exceeded on a candidate release, automatically pause the release pipeline pending investigation.
- **Rollback triggers.** Once a release is live, what observed-in-the-field metric crosses the line and triggers a rollback. Define these in advance; arguing over them mid-incident is too late.
- **Exception process.** When a release misses a gate, what is the explicit waiver process, who must sign, and what compensating controls are required.

The gates are policy, not data. They reflect what failure rate the organization is willing to tolerate. Make them explicit and review them on a known cadence.

### Step 8 — Build dashboards and review cadence

The rig outputs only become evaluation if humans actually look at them. Build dashboards that present:

- **Trend lines** for every primary metric, weekly and per-release.
- **Per-environment breakdowns** so a regression in one cell of the matrix is not hidden by aggregate stability.
- **Flake rates** for the regression suite.
- **Coverage gaps** in the matrix.
- **Open investigations** with the latest evidence and owner.

Define a review cadence: weekly tactical review, monthly trend review, quarterly strategy review. Without a review cadence, dashboards become wallpaper.

### Step 9 — Assign ownership and write the runbook

Every component of the rig must have a single named owner. Without ownership, rigs decay.

Owners exist for:

- Each dataset (provenance, versioning, retirement).
- Each metric (definition, computation, threshold review).
- The regression suite (flake budget, triage rotation).
- The hardware-in-loop harness (operating procedure, maintenance schedule).
- The release gates (policy, exception process).
- The dashboards (curation, retention).

Write a runbook describing how to add a new dataset, how to add a new metric, how to handle a regression, how to triage a hardware-in-loop fail, and how to walk a release through the gates. The runbook is the durable artefact; the people change, the runbook outlives them.

### Step 10 — Plan the rig's own evolution

The rig itself must evolve. Plan:

- **Periodic coverage audits.** Every quarter, re-examine the matrix against the deployment envelope. Add cells for new environments; retire cells that no longer reflect deployment.
- **Truth-source upgrades.** As accuracy targets tighten, the truth source must outpace the stack. Plan for the truth-source upgrade ahead of the stack improvement.
- **Suite curation.** Retire tests that no longer reflect deployment, add tests for any field-observed failure, deduplicate.
- **Tool refresh.** Trajectory analysis tooling, replay frameworks, simulation back-ends evolve quickly. Avoid lock-in; favour interchangeable data formats and versioned tooling.

The rig is never finished. The discipline is to keep it healthy with the same rigour as the stack itself.

## Inputs

The skill expects:

- A stack summary at the level of sensors, coupling, front-end and back-end classes.
- A deployment envelope description.
- Existing evaluation artefacts and gaps.
- Any infrastructure constraints (budget, lab space, available truth sources, team size).

When inputs are sparse, the skill must enumerate the missing items and refuse to commit to specific thresholds until they are filled in.

## Outputs

A markdown rig-design document organized as:

1. Rubric of performance properties with consumer-anchored targets.
2. Metric set with definitions and owners.
3. Ground-truth strategy with honest error bands.
4. Environment-and-motion matrix with capture sources and pass criteria.
5. Regression suite design with layers and statistical posture.
6. Hardware-in-loop harness design with phasing.
7. Release gates, hold criteria, rollback triggers.
8. Dashboarding and review cadence.
9. Ownership and runbook.
10. Rig-evolution plan.

A parallel JSON document with the same structure feeds downstream tooling.

## Examples

> **Indoor warehouse VI-SLAM, fleet of wheeled platforms, persistent multi-session map.**
>
> Truth strategy: motion capture in a dedicated cell for accuracy-of-record indoor runs, plus a surveyed-fiducial network throughout the operational warehouse for in-situ accuracy spot-checks. Matrix prioritizes long-corridor traversals, glass-walled aisles, dynamic forklift scenes, restart-and-relocalize scenarios, and overnight idle-to-resume cases. Regression suite gates every release on a fast suite covering single-shift replays plus a deep weekly suite covering week-long idle-and-resume cycles. Hardware-in-loop harness consists of a representative platform on a known indoor route with timing gates; runs nightly on the head of main. Release gates: end-of-shift absolute trajectory error below a centimetre-class target, re-localization success above a high probability target, zero "tracking lost" events on the deep suite.

> **Aerial inspection drone, outdoor, stereo + tactical IMU, single-session product.**
>
> Truth strategy: real-time-kinematic GNSS with inertial smoothing for accuracy, plus simulation-based stress tests for aggressive-motion regimes that cannot be reproduced safely in the field. Matrix prioritizes high-yaw-rate manoeuvres, low-light dusk and dawn, hover-to-cruise transitions, intermittent rotor occlusion of the lower camera. Regression suite gated on every release; deep suite includes simulation seeds covering ten variants per matrix cell. Hardware-in-loop harness is a motion gimbal with the real sensor head, running pre-release on every candidate. Release gates: relative pose error at the one-second horizon below a single-digit-millimetre target, no IMU-saturation-induced failures on the regression suite, end-to-end latency below a stated millisecond budget.

## Limitations

- The skill produces methodology and rig design, not implementation. Building the rig is a substantial engineering investment.
- Ground-truth accuracy is the hard physical constraint; the skill cannot recommend a truth source more accurate than the customer can procure.
- Some failure modes (e.g. extreme rare-event tail behaviour) require statistical sample sizes that no rig can reasonably produce. For those, the rig must be supplemented by field telemetry and incident review.
- The skill does not replace formal safety-case construction for any safety-critical deployment.
