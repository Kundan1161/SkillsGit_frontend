# Constant-Time Analysis

Analyze cryptographic code to detect operations that leak secret data through execution timing variations.

## When to use

- User is implementing signature, encryption, or key derivation routines
- Code contains `/` or `%` operators on secret-derived values
- User mentions "constant-time", "timing attack", "side-channel", "KyberSlash"
- Reviewing functions named `sign`, `verify`, `encrypt`, `decrypt`, `derive_key`

## When NOT to use

- Non-cryptographic code (business logic, UI)
- Public data processing where timing leaks don't matter
- Code that doesn't handle secrets, keys, or authentication tokens
- High-level API usage where timing is handled by a vetted library

## How to apply

### Language Selection

Pick the appropriate analysis path based on language family:

| Language family | Approach |
|---|---|
| C, C++, Go, Rust, Swift | Native compiled - assembly-level analysis; supports cross-architecture and optimization-level sweeps |
| Java, Kotlin, C# | VM-compiled - analyze bytecode (JVM, CIL); architecture and opt-level flags do not apply |
| JavaScript, TypeScript, PHP, Python, Ruby | Interpreted - analyze instruction streams or VLD/insns dumps |

### Workflow

1. Identify the cryptographic functions in scope.
2. Trace which inputs are secret (private keys, plaintext, signatures, session tokens).
3. Generate the analysis artifact for that language (assembly, bytecode, instruction dump).
4. Flag dangerous instructions:
   - **Division** (DIV, IDIV, SDIV, UDIV) - early termination optimization leaks operand magnitude
   - **Conditional branches on secrets** (JE, JNE, BEQ, BNE on secret-derived flags)
   - **Secret-indexed table lookups** (cache-timing side-channels)
   - **Early-exit comparisons** (memcmp on secrets - use constant-time compare)
   - **Weak RNG** (rand(), mt_rand, Math.random in security contexts)
5. For each flag, perform manual triage: does the operand depend on a secret?

### Quick Reference: Common Problems and Fixes

| Problem | Detection | Fix |
|---|---|---|
| Division on secrets | DIV, IDIV, SDIV, UDIV | Barrett reduction or multiply-by-inverse |
| Branch on secrets | JE, JNE, BEQ, BNE | Constant-time selection (cmov, bit masking) |
| Secret comparison | Early-exit memcmp | `crypto/subtle` or constant-time compare |
| Weak RNG | rand(), mt_rand, Math.random | Use a crypto-secure RNG |
| Table lookup by secret | Array subscript on secret index | Bit-sliced lookups |

## Avoiding False Positives

Not every flagged operation is a vulnerability. The tooling has no data-flow analysis - it flags **all** potentially dangerous operations regardless of whether they involve secrets.

For each flagged violation, ask: **Does this operation's input depend on secret data?**

### Triage Questions

| Question | If Yes | If No |
|---|---|---|
| Is the operand a compile-time constant? | Likely false positive | Continue |
| Is the operand a public parameter (length, count)? | Likely false positive | Continue |
| Is the operand derived from key/plaintext/secret? | **TRUE POSITIVE** | Likely false positive |
| Can an attacker influence the operand value? | **TRUE POSITIVE** | Likely false positive |

### Example

```c
// FALSE POSITIVE: division uses public constant, not secret
int num_blocks = data_len / 16;  // data_len is length, not content

// TRUE POSITIVE: division involves secret-derived value
int32_t q = secret_coef / GAMMA2;  // secret_coef derived from private key
```

## Limitations

1. **Static analysis only** - analyzes assembly/bytecode, not runtime behavior. Cannot detect cache-timing or microarchitectural side-channels.
2. **No data-flow analysis** - manual review required for every finding.
3. **Compiler and runtime variations** - different compilers, optimization levels, and runtime versions may produce different output for the same source.

## Real-World Impact

- **KyberSlash (2023)** - Division instructions in post-quantum ML-KEM implementations allowed key recovery
- **Lucky Thirteen (2013)** - Timing differences in CBC padding validation enabled plaintext recovery
- **RSA timing attacks** - Early implementations leaked private key bits through division timing
