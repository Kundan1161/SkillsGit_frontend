# Frontend Architecture Reviewer

## When to use

Use this skill when a developer or tech lead wants an outside-eyes pass over a React, Vue, or Svelte codebase that has grown organically and now feels harder to change than it should. Common triggers:

- A new hire is about to onboard and the team wants to know which sharp edges to warn them about.
- Page load or interaction latency has slipped, and the suspicion is structural rather than algorithmic.
- A migration is on the horizon (class components to hooks, Options API to Composition API, pages router to app router, Vue 2 to 3, Svelte 4 to 5) and the team wants to know the size of the lift.
- A weekly bug pattern keeps recurring in a particular feature area, and the patches feel cosmetic.
- The team is considering adopting a new state library, router, or data-fetching tool, and wants a baseline reading before committing.

The skill is **not** a bug hunt and not a security review. It looks at the shape of the code: how state is divided, how data flows, where re-renders fire, how the bundle is sliced, and how components compose. Defer to a security skill for auth, XSS, or supply-chain concerns. Defer to an accessibility skill for WCAG conformance. Defer to a refactor-spotter skill for line-level code smells that do not touch architecture.

The skill is calibrated to respect the app's stage. A pre-launch internal tool gets a different bar than a public-facing site with millions of sessions; the `app_shape` input pushes the agent toward the right calibration so it does not over-prescribe for small apps or under-prescribe for large ones.

## Inputs

| Input | Required | Purpose |
| --- | --- | --- |
| `codebase` | yes | Code to review. Whole files give much better signal than diffs; include router, store, and at least three page-level components. |
| `framework` | no | Steers idiom-specific checks (React server components vs. client, Vue ref vs. reactive, Svelte runes vs. stores). |
| `app_shape` | no | Sets the right bar — small marketing site vs. enterprise dashboard vs. consumer-scale app. |
| `scope` | no | Trades depth for breadth. Quick stays at the file level; thorough crosses files and reasons about dependency direction. |

## Outputs

- A markdown review with five sections: state, data, components, rendering, packaging.
- A JSON findings list with severity, file, and recommended move.
- A prioritized remediation backlog at the end, ranked by payoff over effort.

## How to apply

### Stage 1 — Map the codebase

Before any findings, the agent builds a working mental model. Skipping this step produces shallow reviews that miss cross-file problems.

1. List the entry points: the root component, the router file, and any provider tree wrapper. Note the order of providers and what each one injects.
2. For each route or top-level page, record: route path, the components mounted at that path, the data the route fetches, and the state it reads or writes.
3. Identify the state primitives in use. Catalog: framework state (`useState`, `useReducer`, `ref`, `reactive`, Svelte stores, runes), context or provide/inject, external stores (Redux, Zustand, Pinia, Jotai), server-state libraries (TanStack Query, SWR, RTK Query, Apollo, urql), URL state, form state, and persisted state (localStorage, cookies).
4. Identify the data-fetching layer. Is fetch logic in components, in hooks, in a service module, in route loaders, in server components, in a generated client? How are loading and error states represented?
5. Note the component vocabulary: how many leaf primitives, how many "smart" containers, whether headless patterns are in use, and whether components are colocated with their styles, stories, and tests.

The output of stage 1 is internal — do not surface it as a section. It informs every finding that follows.

### Stage 2 — Run the audit across five dimensions

The agent evaluates the code against five independent dimensions. Each dimension uses its own checklist. Findings are tagged with the dimension and an explicit severity.

#### Dimension A — State coherence

This dimension answers: do similar pieces of state live in similar places, and does each piece of state live where it is used?

Look for these patterns and flag the ones that fire:

- **State sprawl**: the same logical value is duplicated in component state, a global store, and a query cache, with no single source of truth. Flag with the three locations.
- **Wrong tier**: server state (data that exists on a backend, can go stale, and benefits from caching) handled by a Redux slice or `useState` chain instead of a server-state library. Flag with a pointer to the relevant component.
- **Global by default**: per-page or per-component state has been hoisted to a global store with no cross-page consumers. Flag with the consumer count.
- **Provider chains**: more than five context providers wrapping the root, or providers carrying values that change every render. Flag with the provider list.
- **URL state in memory**: state that should be in the URL (filters, tabs, sort order, search query, pagination) lives only in component state and is lost on refresh. Flag with the affected route.
- **Form state confusion**: form state mixed with submission state and with derived validation state in a single ad-hoc reducer. Flag with the form name.
- **Cache duplication**: server-state libraries side by side (e.g. TanStack Query and a Redux slice that holds the same entity). Flag both call sites.
- **Mutable global state**: shared singletons (a service object, an event bus, a globally exported `let`) that components read and write without any reactivity contract.

For each finding, name the relevant pattern, point to the file, and propose a single move (lift, lower, split, replace, remove). Do not propose a full library swap unless three or more findings in this dimension all point to the same wrong-tier problem.

#### Dimension B — Data fetching

This dimension answers: how does data enter the app, and does the same kind of data enter the same way?

Look for:

- **Fetch in render**: `fetch()` called directly inside a component body, render function, or `setup` function without a hook or library wrapper. Flag the file and explain why it triggers waterfalls and refetches.
- **Waterfall sequence**: a parent fetches A, then a child mounts and fetches B that depended on A's id, and so on for three or more steps, when one query could have batched. Flag with the request chain.
- **No cache key discipline**: same endpoint called with different cache keys across the app, or different endpoints sharing the same cache key. Flag with the affected hooks.
- **Manual loading state for cached calls**: `isLoading` booleans tracked by hand when the library already exposes them. Flag with line numbers.
- **Missing optimistic updates** on user-initiated mutations where the UX would visibly benefit (likes, toggles, adds to a list). Flag with the mutation name.
- **Error boundary gaps**: throws or rejected promises that bubble to a generic top-level error screen when a feature-scoped boundary would degrade more gracefully. Flag with the boundary that's missing.
- **Polling without backoff**: setInterval-driven polls that fire while the tab is hidden or while the user is offline. Flag with the poll interval and the affected hook.
- **Mismatched paradigms**: route-level data loaders co-existing with in-component fetches for the same data. Flag both.

Recommend a single fetching idiom per data shape (read, mutate, subscribe, paginate, infinite-scroll) and call out exceptions explicitly.

#### Dimension C — Component composition

This dimension answers: do components have one job, and do they compose without intermediate adapters?

Look for:

- **God components**: a single component over a few hundred lines, or with more than a dozen props, or that handles both data fetching and presentation and routing decisions. Flag with the line count and prop count.
- **Prop drilling**: the same prop passed through three or more intermediate components without being read. Flag the chain.
- **Wrapper hell**: a component that exists only to forward props to another component, with no added behavior. Flag with the wrapper name and the wrapped target.
- **Inversion-of-control gaps**: a component takes a `variant` enum that switches large branches of behavior, when accepting a slot or render prop would let callers compose the variants themselves. Flag with the variant enum.
- **Implicit shared state via refs**: components reaching into each other through refs to coordinate animations, focus, or scroll position. Flag with the refs in question.
- **Headless and styled mixed**: a single component owns both behavior and styles in a way that makes it hard to reskin. Flag if the team's design system requires reskinnability.
- **Missing key boundaries**: a list renders without stable keys, or keys are derived from the index when items can reorder. Flag with the list location.
- **Tight coupling to routing**: leaf components import the router and read params, when a parent could pass them down. Flag the import.

For each finding, propose a refactor move (extract, inline, split, hoist, expose as slot/render prop).

#### Dimension D — Rendering

This dimension answers: how often does each part of the tree re-render, and does that match how often its inputs change?

Look for:

- **Context fan-out**: a context value that changes every render and is consumed by many components. Flag the provider and the consumer count.
- **Reference-instability props**: parents pass freshly-allocated objects, arrays, or inline functions to memoized children, defeating memoization. Flag the parent and the child.
- **Effects that should be event handlers**: `useEffect` chains that respond to user events rather than to state changes. Flag with the effect body.
- **Effects that should be derived state**: `useEffect` that mirrors one state into another. Flag and propose the derived expression.
- **Over-memoization**: `useMemo`, `useCallback`, or `React.memo` wrapped around cheap pure expressions with no expensive child below. Flag and propose removal.
- **Reactive over-tracking** (Vue, Svelte, Solid): a single reactive object holds many properties and any change re-runs every consumer. Flag and propose splitting.
- **Hidden subscriptions**: store selectors that return new object identities each call, forcing re-renders even when nothing material changed. Flag with the selector.
- **Layout thrash**: components measure the DOM in a layout effect and then write back style changes in the same frame. Flag and propose a single read-then-write batch.

For each finding, point to a profiler signal the reviewer would expect to see (long task, commit duration, wasted renders) so the developer can validate the diagnosis before fixing.

#### Dimension E — Packaging

This dimension answers: does the bundle ship only what the route needs, and does the framework's route graph match the user's navigation graph?

Look for:

- **No route-level splitting**: every route's code lives in the main bundle. Flag and propose dynamic imports per route.
- **Heavy default imports**: a single named export drags in a whole library because of a barrel file. Flag the barrel and propose either deep imports or `sideEffects: false` config.
- **Eagerly imported icons or fonts**: an icon set loaded as one module when the app uses six icons. Flag with the import.
- **Polyfills shipped to modern browsers**: a polyfill bundle served to all browsers when modern targets do not need it. Flag the build config.
- **Vendor monolith**: `node_modules` resolved into one giant vendor chunk that invalidates whenever any dep updates. Flag with the chunk name.
- **Server-only code on the client**: imports that look server-only (Node built-ins, secret env vars, large schema validators) reachable from a client bundle entry. Flag the import path.
- **Image and font waste**: large hero images served at full resolution to small viewports, or webfont families loaded with eight weights when two are used. Flag the asset.
- **Third-party scripts injected synchronously**: analytics or chat scripts that block first paint when they could be deferred. Flag the script tag.

When relevant, suggest a measurement step (run the bundle analyzer, then re-run after the fix) before the developer invests engineering time.

### Stage 3 — Rank and write

After all five dimensions are scored, compile the findings into a single review document.

1. Open with a three-to-five-line executive summary. The first sentence states the headline judgment (the architecture is sound and needs surgical fixes; the architecture has one or two systemic issues; the architecture needs a planned reset). The remaining sentences name the top two or three risks.
2. List findings by dimension. Use H3 per dimension and bullets per finding. Each finding has: severity (low, medium, high, critical), file, brief description, and proposed move. Critical is reserved for issues likely to cause data loss, crashes, or user-visible regression at the next change.
3. End with a remediation backlog ordered by payoff over effort. Place the items the team can do in one sitting at the top; place planning-required items lower.
4. If the review is positive, say so plainly. Empty critical and high lists are valid outputs.

## Calibration heuristics

- For apps below approximately twenty routes or below approximately fifty components, prefer fewer global abstractions. Many findings that would matter at scale are noise at this size.
- For apps above approximately fifty routes, accept that some duplication is healthier than a leaky abstraction. Be skeptical of "one true way" recommendations.
- If a finding requires a multi-week migration to act on, mark it as "directional" rather than "actionable" so the team can plan it separately.
- If the codebase mixes paradigms (class and hooks, Options and Composition API, stores and runes), call out the inconsistency once at the top rather than once per file. The fix is a migration plan, not a hundred small edits.
- If `app_shape` describes a one-time internal tool, soften severities by one level across the board. If it describes a public consumer site, sharpen them.

## Examples

### Example 1 — React dashboard with growing pains

Input: a single page-level React component, the global Redux slice it consumes, and the data-fetching hook.

Selected output excerpt:

> **Executive summary**
> The architecture is sound but two patterns are leaking out of one feature into the rest of the app. Server-state has begun to accumulate inside Redux slices; component memoization is being applied as a reflex rather than where the profiler shows wasted work.
>
> **Findings**
>
> *State coherence (medium)* — `dashboardSlice.ts` stores fetched user records alongside UI state. Move user records to a TanStack Query (or equivalent) cache keyed by user id; keep only the selected user id and view mode in the slice.
>
> *Rendering (low)* — Twelve memo wrappers in `widgets/` with no measurable parent. Remove and re-measure; reintroduce only where a profile shows a wasted commit longer than approximately 4 milliseconds.
>
> **Backlog**
> 1. Lift user records out of Redux into the query cache (≈ 1 day).
> 2. Remove speculative memo wrappers (≈ 2 hours).
> 3. Hoist the date-range filter into the URL so refresh restores it (≈ 3 hours).

### Example 2 — Vue 3 marketing site

Input: a Nuxt project's `pages/` folder, a small Pinia store, and the layout.

Selected output excerpt:

> **Executive summary**
> The site is over-architected for its size. A central Pinia store carries values that no two pages share. Most pages would be simpler with route-level `useFetch` and per-page refs.
>
> **Findings**
>
> *State coherence (high)* — `usePageStore` holds `currentPageTitle`, `currentHero`, and `currentCta`. No two pages read these at the same time. Inline them per page.
>
> *Packaging (medium)* — The blog index imports the full `marked` module to render an excerpt. Replace with a small substring or move rendering to build time.

## Limitations

- Without seeing the network panel and a runtime profile, several findings are educated guesses; mark them as such.
- The skill cannot judge ergonomics: if a pattern feels awkward to the team but tests fine on every dimension, the agent will not flag it.
- For very large codebases, the input may not contain the global picture. Findings should be scoped to what was passed in and should say so.
- Framework-specific quirks (Svelte 5 runes, Vue 3.5 reactive transform, React server components in canary) move quickly; the agent should hedge when the question depends on canary behavior.
