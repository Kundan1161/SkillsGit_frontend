# QA E2E Test Suite Architect

## When to use

Use this skill when a team needs a maintainable end-to-end test suite — either greenfield, or a replacement for an existing suite that has become slow, flaky, or impenetrable. The output is a complete architecture: directory layout, conventions, fixture taxonomy, data strategy, parallelism plan, CI integration, and a set of starter files the team can drop in.

Good fit:

- A new product is about to launch and needs an e2e suite from scratch.
- An existing Selenium or WebdriverIO suite has grown to thousands of brittle tests and is being rebuilt.
- A team is migrating to a modern browser-automation framework and wants to do it right this time.
- A platform team is building shared test infrastructure for many product teams.

Poor fit:

- A team writing a single test (they need test-authoring help, not architecture).
- A team with a working suite asking for a marginal tweak.
- A team that should not have e2e tests at all (better served by integration or contract layers).

The architecture is opinionated. The skill picks one shape and justifies it. Teams may deviate; the document explains the trade-offs so deviation is informed.

## How to apply

1. **Restate the journeys to cover.** Before any architecture, list the user journeys the suite must protect. Each journey is one logical user goal: sign up, log in, place an order, refund an order, reset a password. Aim for under 30 journeys in v1; e2e suites that try to cover everything die.

2. **Define what e2e is for in this codebase.** Write a one-paragraph charter: "These tests exist to verify that the deployed system honors the top user journeys end-to-end. They are not for component behavior, edge-case logic, or non-functional checks — those live in lower layers." This document prevents scope creep.

3. **Pick the framework.** Default to a modern browser-automation framework that supports auto-wait, network interception, multiple browser engines, and parallel execution out of the box. Avoid frameworks where retry logic and waits must be hand-coded. Recommend one primary and one fallback with justification.

4. **Decide single-app vs. multi-app.** If the product is a single web app, one repo and one config. If it is a portfolio (marketing site, app, admin), one repo with per-app projects so they can share fixtures but run independently.

5. **Lay out the directory tree.** A clean layout:
   - `tests/` — one file per user journey, named for the journey (`checkout.spec.ts`, not `tc1234.spec.ts`).
   - `pages/` — page-objects, one per logical page or major component.
   - `fixtures/` — composable fixtures keyed by capability (`authedAs`, `withSeededOrders`, `mobileViewport`).
   - `data/` — factories and seed builders; no static JSON unless it is intentionally a golden artifact.
   - `support/` — shared helpers (assertions, accessors, custom matchers).
   - `config/` — environment-specific configs (`local.ts`, `ci.ts`, `prod-probe.ts`).

6. **Pick the page-object shape.** Use the action-oriented variant: a page-object exposes verbs (`checkout.addItem(sku)`, `checkout.submit()`), not raw selectors. Selectors are private fields inside the page-object. This keeps tests readable and concentrates breakage in one file when the UI changes.

7. **Make page-objects accept a page or context.** Inject the browser context rather than constructing it inside. This enables reuse across fixtures and parallel workers without surprises.

8. **Locate elements semantically.** Prefer accessible roles, labels, and text over CSS class names or auto-generated IDs. Selectors keyed to ARIA roles double as accessibility checks and survive CSS refactors. Reserve test-IDs (`data-testid`) for cases where there is no semantic anchor.

9. **Design the fixture taxonomy.** Fixtures are dependency-injected capabilities tests opt into. Categorize them:
   - **Account fixtures**: `anonymous`, `authedAsCustomer`, `authedAsAdmin`. Each yields a logged-in context.
   - **Data fixtures**: `withProduct`, `withOrder`, `withSubscription`. Each seeds the necessary entities and exposes their IDs to the test.
   - **Environment fixtures**: `mobileViewport`, `slowNetwork`, `darkMode`.
   - **Cleanup fixtures**: each data fixture also tears down what it created.

10. **Avoid shared mutable state across tests.** Every test starts from a known state. Either reset the test environment between tests (slow) or scope all data to per-test namespaces (fast). The latter is almost always the right choice.

11. **Decide the auth strategy.** The most expensive operation in most e2e suites is logging in via the UI. Cache an auth token or storage state once per worker per role and reuse it. Have a single sign-in test that exercises the real login UI; the rest of the suite uses the cached state.

12. **Plan the data strategy.** Choose one of three:
    - **Per-test seeding via API**: tests POST to a privileged seeding endpoint that creates the entities. Fast and isolated. Recommended.
    - **Database fixtures**: pre-baked rows. Couples tests to schema, brittle to changes.
    - **UI seeding**: walking the UI to create the data the test needs. Slow and flaky. Avoid.

13. **Tag tests for selection.** Use tags such as `@critical`, `@smoke`, `@flaky`, `@a11y`, `@visual`. CI pipelines select by tag: PRs run `@critical`, nightly runs everything, prod probes run `@smoke`.

14. **Decide the parallelism model.** Parallel by file (every spec runs on a worker, tests inside a file run serially) is the simplest. Parallel by test is faster but requires fully isolated data. Pick file-level by default; opt into test-level only when isolation is proven.

15. **Plan retries narrowly.** Retry the test once only when the underlying error is an infrastructure error (network reset, browser crash, container OOM). Never retry on assertion failure. Configure retries at the project level and surface retry counts in reports.

16. **Choose the network strategy.** Three options:
    - **Full live**: the suite hits real backends. Most fidelity, most flake risk.
    - **Selective stubs**: intercept only the volatile third-party calls (payment processor, analytics) and let everything else go live.
    - **Full mock backend**: every API call answered by a deterministic fixture. Faster and more stable, less coverage.
    Recommend selective stubs as the default for product apps.

17. **Plan the CI shard count.** Take total runtime serial, divide by the desired wall-clock target, that is the shard count. Round up. Hold shard count under 50 in most cases — coordination overhead dominates beyond that.

18. **Plan the artifacts.** Every failed test must produce: a video, a trace, console logs, network HAR, and the final screenshot. Store for 30 days. These artifacts cut debug time more than any other investment.

19. **Plan flake tracking.** Use a structured test report format (JUnit XML or CTRF). Feed the report to a dashboard that tracks each test's pass rate over time. Burn down anything below 99% pass rate.

20. **Decide on accessibility checks.** For every page-object, optionally run an accessibility scan. Surface violations as test failures with severity. Run on every critical-path journey.

21. **Decide on visual regression checks.** Visual regressions are noisy. Only adopt if the team will maintain the baselines. Use deterministic environments (fixed viewport, fixed fonts, animations disabled).

22. **Plan secrets handling.** Test credentials are real credentials. Store in the CI secret store. Inject as environment variables. Never check fixtures with passwords into source.

23. **Plan environments.** Local: run against a local stack with `--headed --debug`. CI: run against a deployed PR environment. Production: a small `@smoke` subset runs continuously against production as monitoring.

24. **Document the conventions.** A `CONTRIBUTING.md` in the test repo with: how to add a journey, how to add a page-object, how to add a fixture, how to debug a failure, the anti-patterns. Make this readable in under 10 minutes.

25. **Enumerate anti-patterns.** Surface and forbid: fixed sleeps, hardcoded user IDs, asserting on auto-generated copy that may change, multiple journeys per spec file, shared mutable globals, tests that depend on the order of earlier tests, raw selectors in tests.

26. **Produce starter files.** Emit a config file, a base page-object, a base fixture, an example test, and a CI workflow file. These are starting templates the team can immediately use.

27. **Estimate runtime and cost.** Give an expected wall-clock per PR run at the recommended shard count, and a monthly CI-minutes estimate at the team's expected merge rate.

28. **Plan the migration if replacing a suite.** Stage the rollout: stand up the new suite covering the top five journeys, run it in parallel with the old one for two weeks, then delete the old tests journey by journey as the new ones reach parity.

29. **Flag what the architecture cannot solve.** A maintainable e2e suite still cannot replace contract tests, integration tests, or human exploratory testing. State this clearly so the team does not over-rely on the suite.

30. **Provide a maintenance cadence.** Quarterly: review pass rates, prune dead journeys, rotate cached credentials, upgrade the framework. Without a cadence, suites rot.

## Examples

**Example: a multi-tenant SaaS dashboard**

Input: a React frontend, a REST backend, OAuth login, three personas (customer, admin, support agent), 18 critical journeys, GitHub Actions CI.

The agent produces:

- Charter: e2e exists to protect the 18 named journeys against deployed regressions.
- Directory layout with `tests/`, `pages/`, `fixtures/`, `data/`, `support/`, `config/`.
- Page-object pattern with action verbs and ARIA-role selectors.
- Three account fixtures (one per persona) caching storage state per worker.
- Data strategy: per-test seeding via a `/test-seed` privileged endpoint behind a CI-only token.
- Network strategy: intercept Stripe and Segment; pass everything else live.
- Parallelism: file-level, 12 shards on GitHub Actions hosted runners.
- Tags: `@critical` runs on PR, `@smoke` runs continuously against prod, `@a11y` runs nightly.
- Artifacts: video, trace, network HAR, screenshot on failure, retained 30 days.
- Estimated PR runtime: 8 minutes. Estimated monthly CI cost: 1100 minutes.
- Starter files: a config, a base `Page` class, a `withAuthedCustomer` fixture, an example checkout spec, a workflow that triggers on PR.

## Limitations

- Architecture is opinionated and assumes the team can use a modern browser-automation framework. Teams locked to legacy tools will need to adapt.
- The plan trades some coverage for stability (selective stubs, API seeding). Teams that require full-live tests against every third-party need to extend the plan.
- Visual regression and cross-browser at scale require dedicated infrastructure not covered here.
- The starter files are templates, not production-ready code; they need adaptation to the actual repo.
- The plan does not size the team that will maintain the suite. A suite this size typically needs a part-time owner; without one it will rot.
- Mobile-app e2e (native iOS, Android) is out of scope; the architecture targets web.
- Security testing, load testing, and chaos testing belong in adjacent test layers, not the e2e suite.
