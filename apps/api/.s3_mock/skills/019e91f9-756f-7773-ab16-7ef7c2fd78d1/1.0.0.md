# Vector Database Architecture Designer

## When to use

Use this skill when someone needs to choose how vectors will be stored, indexed, and served — not just which library to call, but how the deployment is shaped. The skill produces a written design, not running code. The design names the engine family, picks an index algorithm and its parameters, lays out shards and replicas, decides how metadata filters interact with the ANN structure, defines a tenant-isolation model, and sets the capacity numbers the operations team needs to provision against.

The skill is appropriate when the workload is large enough that defaults will not survive: more than roughly a million vectors, or a tight latency budget, or a filtered-search requirement, or a multi-tenant model where one tenant's traffic must not starve another. For toy projects with ten thousand vectors and one user, the skill should recommend the simplest reasonable engine and stop. It is not the right skill for embedding-model selection (use the embedding-model selector), nor for day-two operations of an existing index (use the operations runbook).

## How to apply

The skill walks a thirteen-stage pipeline. Each stage produces a decision that the next stage depends on. Do not skip ahead.

### Stage 1 — Restate the workload

1. Rewrite the `workload_description` as a single sentence in the form "Given <embedding type> over <corpus type>, serve <query pattern> within <latency budget> at <QPS> with <recall target>, while honouring <filter and tenancy constraints>." If any slot is empty, ask the user to fill it before continuing.
2. Classify the query pattern: pure k-nearest-neighbour, k-nearest-with-metadata-filter, hybrid dense-plus-sparse, range search by distance, recommendation (vector-to-vector with negative filter), or retrieval-augmented-generation context fetch. Each pattern stresses the engine differently.
3. Identify the write pattern: bulk ingest with occasional updates, steady streaming inserts, frequent deletes, in-place updates, or append-only logs with periodic full rebuilds. The write pattern drives the index choice as much as the read pattern does.
4. Identify freshness expectations. If "written now must be searchable within ten seconds" is required, the index must support live insert without a global rebuild; offline rebuild-friendly indexes are off the table.
5. Identify durability expectations. Most production deployments expect zero data loss on a single-node failure. If the user is fine with rebuilding from a source-of-truth lake on every restart, the design space widens significantly.

### Stage 2 — Compute the raw memory and storage budget

6. Calculate the bytes per raw vector: `dimensions * 4` for float32, `dimensions * 2` for float16 or bfloat16, `dimensions` for int8, `dimensions / 8` for binary quantised. State both the storage and the in-RAM footprint separately because some engines keep only quantised vectors in memory and rerank against full-precision from disk.
7. Calculate corpus total: `vectors * bytes_per_vector`. Add the graph overhead for a graph index (HNSW typically adds 1.5x to 2.5x of the raw vector size in graph edges) or the centroid plus posting-list overhead for an inverted-file index (IVF adds a small centroid table and minor per-list metadata).
8. Add payload overhead: average payload bytes per vector times vector count, plus the inverted index on filterable fields, plus the primary key index. Real corpora often double once payloads are counted.
9. Apply a 1.5x to 2.0x safety multiplier for buffer pools, write-ahead logs, compaction headroom, and replica overhead. The result is the raw hardware budget per replica.
10. Compare the result to commodity instance shapes. If a single replica fits in a single machine with two times the budget for spike headroom, the design can stay single-node-per-replica. If not, sharding is mandatory.

### Stage 3 — Decide between in-memory, hybrid, and disk-resident

11. **In-memory graph index** (HNSW family). Recommended when the working set fits in RAM with safety multiplier, when the QPS is high enough that disk latency would dominate, and when recall must be very high (>= 0.97 at small k). Memory cost is the limiting factor.
12. **Hybrid in-memory plus on-disk** (IVF with on-disk posting lists, or graph index with mmap and OS page cache). Recommended when the corpus is large enough that pure RAM is uneconomic, but the working set (hot partitions) does fit in RAM. Throughput is bounded by the cache hit rate on the hot set.
13. **Disk-resident graph index** (DiskANN-style: graph topology on disk, quantised vectors in RAM, full-precision rerank read from disk). Recommended when the corpus is hundreds of millions to billions of vectors and the latency budget is tens of milliseconds rather than single milliseconds.
14. **Quantisation strategy.** For any in-RAM index over more than ten million vectors, plan for quantisation: scalar quantisation (float to int8) is a small recall cost for a 4x memory win; product quantisation trades more recall for an 8x to 32x win; binary quantisation cuts memory by 32x but typically needs a full-precision rerank stage. Pick the quantisation level that lands inside the recall budget on a benchmark of the user's own data, not a public benchmark.
15. **Decision rule.** Pick the lightest-weight option that satisfies recall, latency, and freshness; only escalate to a heavier option when a budget number forces it. Document the next step up the stack so it is clear what changes if the workload grows.

### Stage 4 — Pick the index algorithm family

16. **HNSW** when (a) inserts and updates happen live, (b) recall must be very high, (c) the working set fits in RAM with headroom, and (d) filters are typically low-selectivity. HNSW is the default for most online retrieval workloads under a few hundred million vectors.
17. **IVF or IVF with product quantisation** when (a) the corpus is large and memory is constrained, (b) filters are highly selective (post-filter cost can be amortised across one or two probed lists), (c) inserts arrive in batches and a periodic re-clustering is acceptable, and (d) the latency budget is forgiving enough to accept multi-list probes.
18. **DiskANN-style graph on disk** when (a) the corpus is too large to keep in RAM at any reasonable cost, (b) p95 latency in the tens of milliseconds is acceptable, and (c) SSDs with random-read latency under 100 microseconds are available. Cold-cache start is slow; warmup must be planned.
19. **Brute-force flat** when the corpus is small (less than roughly 100k vectors) or when the use case requires exact recall on every query (compliance, replay-from-ground-truth). Always include brute force in the design as a fallback path for evaluation.
20. **Sparse plus dense hybrid index** (BM25-style sparse plus HNSW dense, joined by reciprocal rank fusion or learned fusion) when keyword precision matters alongside semantic recall. Hybrid is mandatory for product search, code search, and most enterprise retrieval-augmented generation use cases.
21. **Pin the index hyperparameters.** For HNSW: `M` (graph degree, typically 16-64), `ef_construction` (build-time exploration, typically 100-400), `ef_search` (query-time exploration, tuned per recall target). For IVF: `nlist` (centroid count, typically `sqrt(N)` to `4*sqrt(N)`), `nprobe` (lists probed per query, tuned per recall target). State the starting values and the calibration plan in the design, not just one number.

### Stage 5 — Plan filtering and hybrid search

22. **Filter strategy.** Classify each filter field by selectivity (fraction of vectors matching) and cardinality (number of distinct values). High-cardinality, high-selectivity filters (e.g. `tenant_id`) should be expressed as a pre-filter that prunes the graph traversal or the IVF probe set. Low-selectivity filters (e.g. `is_active`) can be post-filtered after the ANN stage with over-fetching.
23. **Over-fetch multiplier.** When post-filtering, fetch `k * (1 / expected_selectivity) * safety` candidates from the ANN stage and then filter. If the multiplier exceeds roughly 20x, post-filter is the wrong choice — fall back to pre-filter or to a partitioned index.
24. **Payload indexes.** Decide which fields need exact-match indexes (`tenant_id`, `language`, `region`), which need range indexes (`timestamp`, `price`), and which need full-text indexes (`title`, `body`). Each index costs memory and write throughput; do not enable defaults you do not need.
25. **Tenant-as-partition.** When `tenant_id` is the dominant filter, prefer a multi-collection design with one collection per tenant or a sharded design that routes by `tenant_id`. Filtered single-collection search wastes work scanning other tenants' graphs.
26. **Hybrid fusion.** If sparse plus dense, decide where fusion happens: in the engine if it has native fusion (reciprocal rank fusion or a learned scorer), or in the application after independent calls. Native fusion is cheaper and lower-latency; application-side fusion is more flexible and easier to A/B test.
27. **Reranker stage.** For most user-facing retrieval, plan a second-stage reranker after the ANN layer — a cross-encoder, a learned-to-rank model, or a small LLM judge. The ANN layer recalls; the reranker precisions. Separating responsibilities lets each be tuned independently.

### Stage 6 — Sharding plan

28. **Decide whether to shard.** If the single-replica memory budget exceeds about 60% of the largest reasonable instance, shard. If filters partition naturally (per-tenant, per-region, per-time-bucket), shard along that natural axis. If neither, shard by a hash of the primary key.
29. **Pick the shard key.** A good shard key satisfies (a) even distribution of vectors per shard, (b) routability — most queries can target one or a few shards, not all — and (c) stable over time. Avoid time-based shard keys for live-write workloads; they hot-spot.
30. **Shard count.** Start with at least twice the number of physical machines so rebalancing on node addition is incremental. Do not exceed a few hundred shards per cluster; coordinator overhead grows with shard count.
31. **Scatter-gather cost.** When a query has no shard predicate, every shard must be probed in parallel and the results merged. Latency is bounded by the slowest shard, not the average. Budget shard count and per-shard latency so tail latency stays inside the p95 budget.
32. **Replicas per shard.** Two replicas survive single-node failure for read traffic; three replicas survive single-node failure for write quorum and rolling restarts. Capacity-plan for at least the higher of "2x peak QPS divided by per-replica QPS" and "minimum-for-availability".

### Stage 7 — Replication and consistency

33. **Read consistency.** Most vector workloads tolerate eventual consistency between replicas — the corpus moves slowly compared to read traffic. Pin the staleness budget (e.g. "writes visible on all replicas within five seconds") and let the engine choose replication mode.
34. **Write quorum.** If durability is critical, configure write acks to require quorum (majority) of replicas. If throughput is critical and the source of truth lives elsewhere, single-replica ack with async replication is acceptable, with a documented recovery path on replica loss.
35. **Leader election and failover.** Confirm the engine has automatic leader failover for shards; if not, plan operator runbooks for manual failover. Document the steady-state time-to-recover.
36. **Cross-region replication.** For multi-region read traffic, prefer per-region read-only replicas fed by asynchronous replication. Cross-region synchronous replication is rarely worth its latency cost for vector workloads.

### Stage 8 — Multi-tenancy model

37. **Choose the isolation model.** Options ranked from heaviest to lightest: (a) cluster per tenant, (b) collection per tenant within a shared cluster, (c) partition per tenant within a shared collection, (d) tenant-as-filter within a shared collection.
38. **Cluster-per-tenant** for regulated or noisy-neighbour-intolerant tenants. Highest cost, strongest isolation, slowest provisioning.
39. **Collection-per-tenant** is the default for SaaS workloads with hundreds to thousands of tenants. Each collection has its own index parameters and quota. Engines vary in how cheaply they handle many collections; verify the engine supports the planned count.
40. **Partition-per-tenant** when tens of thousands to millions of tenants make collection-per-tenant impractical. The engine routes by tenant key inside a single collection. Filtered search is constant-time per tenant.
41. **Filter-only tenancy** is the cheapest but offers the weakest isolation. Use only for low-tenant-count internal use cases where one tenant's queries impacting another's latency is acceptable.
42. **Quota and rate-limit per tenant** must be planned at the application layer regardless of physical isolation. The engine rarely enforces tenant quotas natively.

### Stage 9 — Hardware sizing

43. **CPU.** ANN search is memory-bandwidth-bound and SIMD-friendly. Prefer CPUs with wide vector units (AVX-512 or ARM SVE); inverse hyperthreading often hurts. Size cores by `peak_qps / single_core_qps_at_recall_target`.
44. **RAM.** Sum the index footprint from Stage 2 plus working memory for query exploration (proportional to `ef_search` or `nprobe` and concurrent queries) plus OS page cache for any on-disk components.
45. **Storage.** SSDs only — never spinning disks for ANN. NVMe class for DiskANN-style workloads; SATA SSD is acceptable for cold replica storage. Plan three times the corpus size on disk for snapshots, write-ahead logs, and compaction.
46. **Network.** Sharded ANN is bandwidth-hungry on scatter-gather. Budget at least 10 Gbps inter-shard for medium clusters, 25 Gbps for large.
47. **GPU.** Most production ANN serving does not need GPUs. Index *build* may benefit from GPU for very large initial loads; query-time GPU pays off only for very high-dimensional embeddings at extreme QPS. Default to CPU-only unless the math forces otherwise.

### Stage 10 — Engine selection matrix

48. Match the requirements to the engine family without naming specific brands in the body — the matrix is by capability. Score each candidate on the following axes, each 0-3: ingest throughput, filtered-search performance, recall ceiling, operational simplicity, multi-tenant support, hybrid sparse-dense support, disk-resident support, backup and snapshot story, observability surface, and community activity. Engines under 22 points across these ten axes are rejected for production.
49. **Embedded versus server.** For sub-million-vector workloads where the application owns the index lifecycle, an embedded engine (library linked into the process) is simpler and faster. For shared, multi-tenant, or multi-team workloads, a server engine with a network API wins.
50. **Self-hosted versus managed.** Managed offerings remove operator load but constrain index parameters and topology. If the design needs unusual hyperparameters or a disk-resident topology not exposed by managed offerings, self-host. Otherwise, default to managed for small operations teams.
51. **Open-source license.** Verify the chosen engine is under a license the user can deploy with. Some engines have a permissive core and a separately-licensed enterprise add-on; the design must say which features rely on the add-on.

### Stage 11 — Ingestion and rebuild pipeline

52. **Ingestion path.** Specify whether vectors arrive via the engine's write API, via a CDC stream from a source-of-truth store, or via bulk batch loads. Each has different durability characteristics. The design must name the source of truth and the recovery path: "if the index is lost, rebuild from <source> by <process>".
53. **Backfill plan.** Initial loads for large corpora benefit from offline index building (FAISS-style train and add) followed by an import into the serving engine. State whether the engine supports bulk import; if not, plan ingestion throughput against the steady-state write API.
54. **Re-embedding plan.** If the embedding model is upgraded, the entire corpus must be re-embedded and reindexed. Plan this as a parallel-collection swap, not an in-place update. Reserve enough headroom to run two corpora simultaneously during cutover.
55. **Schema migration.** Adding a new filterable payload field, changing dimensionality, or swapping distance metric all require a rebuild. The design must say which schema changes are online versus require a rebuild.

### Stage 12 — Capacity plan

56. **Steady-state numbers.** Produce a sizing table: vectors today, vectors at twelve months, memory per replica, replicas per shard, shards per cluster, instance type, instance count, monthly cost order of magnitude.
57. **Burst headroom.** Reserve at least 2x peak QPS capacity. ANN search is more bursty than relational query — one slow tenant can quickly consume a replica's CPU.
58. **Scaling triggers.** State the metrics that should prompt scale-out: replica CPU above 60% at peak, memory utilisation above 75%, p95 latency above target, queue depth above zero for more than thirty seconds.
59. **Cost ceiling.** Pin a cost-per-million-queries budget. The design must show how the engine and topology choice arrive inside it.

### Stage 13 — Compose the deliverable

60. Open with a one-paragraph design intent: workload class, chosen engine family, index family, headline capacity, and the two or three risks that drove the choice.
61. Render the design as a markdown document with sections matching the stages above: workload, memory budget, in-memory vs disk, index, filtering, sharding, replication, tenancy, hardware, engine, ingestion, capacity.
62. Emit the structured JSON variant in `design_json` with stable keys so downstream tooling can consume it.
63. End with an explicit "alternatives considered and why rejected" section. Architecture decisions are judged on the rejected options as much as on the chosen one.

## Examples

**Input (placeholder):**

`workload_description`: "Semantic search across enterprise documents — about 40 million chunks today, growing to 200 million over twenty-four months, with strict per-tenant isolation across roughly 2000 customers."

`vector_dimensions`: 1024.

`latency_budget_ms`: "p50 30 ms, p95 80 ms, including a cross-encoder rerank on top-100 candidates."

`qps_profile`: "Peak 300 QPS, 95% reads, writes arrive in nightly batches."

`filter_requirements`: "Tenant ID is mandatory and highly selective. Document type and date range are common secondary filters."

`recall_budget`: "recall@10 >= 0.94 against brute-force flat reference."

**Design (abbreviated):**

- Memory budget: roughly 200 GB raw vectors at 24 months, plus graph overhead, plus payloads — 600 GB working set. Single-replica budget exceeds a single 256 GB box, so shard.
- In-memory HNSW with `M=32`, `ef_construction=200`, `ef_search` calibrated to hit recall@10 of 0.94.
- Scalar quantisation to int8 in RAM with full-precision rerank from disk for top-100.
- Tenant-as-collection: one collection per tenant for the 100 largest tenants; partition-per-tenant within a shared collection for the long tail.
- Sharded by hash of tenant ID, 16 shards across 8 machines, 2 replicas per shard.
- Filtering on date range and document type via payload indexes; tenant filter is handled by the partition routing layer.
- Hybrid: BM25 sparse index alongside dense, fused with reciprocal rank fusion, then cross-encoder rerank.
- Capacity: 8 machines of 256 GB RAM, 32 cores, NVMe storage. Burst headroom to 16 by adding replicas.
- Risks: HNSW recall under heavy filtering can collapse — calibration plan includes a filtered-recall benchmark at every shard scale step.

## Limitations

- The skill writes a design; it does not benchmark it. The user must run a recall-and-latency calibration against their own data before locking parameters.
- It assumes the embedding model has already been chosen; the embedding-model selector skill covers that decision separately.
- It does not address compliance specifics (HIPAA, FedRAMP, regional sovereignty) beyond noting where the design must consult a compliance officer.
- Engine-specific operational knobs (compaction tuning, WAL durability, snapshot scheduling) are covered in the operations runbook skill, not here.
- For corpora under one million vectors the recommendations may be over-engineered; the skill should detect this and suggest simpler defaults.
- Pricing claims about managed offerings are out of scope; cost-per-million-queries is a relative comparison, not an absolute number.
