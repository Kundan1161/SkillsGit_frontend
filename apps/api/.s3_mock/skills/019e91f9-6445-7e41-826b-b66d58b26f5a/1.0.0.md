# Data Quality Test Designer

## When to use

Use this skill to design the **data quality test suite** for a specific pipeline or dataset. The output is a tiered set of assertions plus an on-failure policy. The skill stops short of writing every individual SQL probe — but it produces enough specificity that an engineer can wire each test directly into dbt, Great Expectations, or an in-house runner in an afternoon.

Trigger phrases include:

- "data quality tests for..."
- "DQ suite / DQ rules"
- "dbt tests for..."
- "Great Expectations suite"
- "freshness check / volume check"
- "anomaly detection on this table"
- "what tests should I write?"

Do **not** use to author the dataset contract itself (route to `data-contract-author` — quality SLOs live there, this skill builds the probes that verify them). Do **not** use for ML-model quality (different beast entirely).

## How to apply

Design tests in **five layers**, then assign **severities** and **on-failure actions**. Tests without severity are noise; severity without an action is theatre.

### 1. Layer 1 — Column-level structural tests

The cheap, fast, deterministic tests. Run on every batch / every model run.

For each column, consider:

- **NOT NULL** where the contract says non-nullable. Always. Free.
- **Type / range**: `amount_cents BETWEEN 0 AND 10^11`. Reject impossible values; surface boundary values for review.
- **Enum**: `currency IN ('USD','EUR','GBP','JPY')`. List the allowed values explicitly; new currencies need a code change, not a silent appearance.
- **Regex / format**: `email REGEXP '^...$'`, `phone_e164` matches, `uuid` is a uuid.
- **Length bounds**: catches truncated strings and run-on garbage.
- **Cross-column constraints**: `refund_cents <= charge_cents`, `shipped_at >= ordered_at`.

Rule of thumb: every column whose **violation is unambiguously a bug** gets a structural test. Columns whose values are "fuzzy" (free-text descriptions) get length bounds only.

### 2. Layer 2 — Table-level structural tests

- **Primary-key uniqueness**: `count(distinct pk) = count(*)`. Always.
- **Foreign-key integrity**: `% rows whose fk resolves to parent table >= X%`. Set X based on tolerable late-arrival; in well-managed shops, 100%.
- **Row count bounds**: minimum and maximum row count per batch; catches "table is empty" and "we just ingested a duplicate file".
- **Schema match**: column set and types match the declared contract. Many teams skip this because the warehouse "would error" — but Snowflake's `select *` won't error if a column quietly got dropped upstream.

### 3. Layer 3 — Freshness tests

Freshness is the test most often forgotten because it can't be expressed as "WHERE clause on a SELECT".

- **Source freshness**: max age of the newest row's `event_time` (or load timestamp) is within the SLA. Run as a separate timed check (every N minutes), not piggybacked on the load.
- **Pipeline lag**: `now() - max(processed_at)` from the **target** table within budget.
- **Watermark stability**: the high-watermark column is monotonic (never decreases).

Express freshness in **two thresholds**: a `warn` at 1× SLA, a `fail` at 2× SLA. Some teams add a `page` at 4× SLA. Without thresholds, freshness alerts oscillate between "noisy" and "silent".

### 4. Layer 4 — Distribution / volume tests (statistical, not deterministic)

Catch the failures that pass schema and structural checks but break downstream models:

- **Volume anomaly**: today's row count vs trailing 7-day mean ± k σ; flag when |z| > 3.
- **Null-rate drift**: % null in a column vs trailing 7d; flag a step change.
- **Mean / median / quantile drift**: rolling stats on numeric columns; for revenue, flag if today's mean is > 10% off rolling p50.
- **Top-K mix drift**: for categoricals, JS divergence between today's distribution and a rolling baseline.
- **Cardinality drift**: distinct-count of a key column vs baseline.
- **Pairwise drift**: e.g., refund-to-charge ratio.

Calibration discipline:

- **Tune on history before you alert.** Run the tests against the last 90 days and ensure baseline false-positive rate is < 1/week.
- **Seasonality**: weekly cycle (Monday volumes ≠ Saturday) and monthly cycle (end-of-month finance bumps). Use a seasonality-aware baseline or exclude weekends/holidays explicitly.
- **Cold-start**: a brand-new table can't have anomaly checks for the first ~2 weeks. Add structural tests only and mark anomaly checks as `warming up`.

### 5. Layer 5 — Business-rule tests

Encode invariants the business *knows* to be true:

- **Identity / accounting**: sum of debits = sum of credits per period; recognized revenue + deferred revenue = billed revenue.
- **Domain rules**: a subscription cannot have `ended_at < started_at`; a refund cannot exceed the original charge.
- **Cross-table reconciliation**: revenue reported in `orders` reconciles with `payments` within ε.
- **Process compliance**: every order in `shipped` state has a corresponding row in `fulfillment_events`.

These are the most valuable tests; they're also the ones most likely to be wrong on first authorship. **Ground them in a business stakeholder's signoff**, and version them as the business rules evolve.

### 6. Severity tiers and on-failure actions

A test plan without a severity policy creates **alert fatigue** within two weeks. Adopt three tiers and a clear action for each:

| Severity | Trigger                                  | Action                                                       |
| -------- | ---------------------------------------- | ------------------------------------------------------------ |
| **P0 / block** | Schema breach, PK uniqueness fail, business-rule violation on financial data | **Fail the run.** Downstream blocked. Page producer immediately. Open incident. |
| **P1 / quarantine** | Freshness > 2× SLA, completeness SLO burned, volume anomaly with z > 5 | **Quarantine the batch** — write to a side path, keep last-good version visible to consumers. Page producer within business hours. |
| **P2 / warn** | Freshness > 1× SLA, distribution drift within absorbable range, soft enum violations | **Log and dashboard.** Email digest to owner. No paging. Triaged in weekly review. |

Choose severity per **test instance**, not per test type. Volume drift on the daily revenue table is P1; volume drift on the experimental sandbox table is P2.

### 7. Where to run each test

Tests live in three places. Plan the placement.

- **In-pipeline (assertions during transform)**: structural tests on the producing side. Catch garbage before it lands. Fast, but only sees what the pipeline wrote.
- **Post-load on the target**: table-level, freshness, distribution. Independent of producer code. Required if producers run an opaque tool you don't control.
- **Continuous monitoring (out-of-band)**: freshness and volume monitors that page even when the pipeline didn't run. Often the only thing that catches "the pipeline silently stopped scheduling".

Default placement matrix:

- Column-level structural: **in-pipeline**.
- Table-level structural: **post-load**.
- Freshness: **continuous monitoring**.
- Distribution / volume: **post-load** + a rolling baseline job.
- Business rules: **post-load**, optionally re-run nightly as a reconciliation.

### 8. The on-failure runbook

Every test ships with a one-page runbook stub:

- What this test checks, in plain English.
- The most likely root causes (ranked).
- The first 3 diagnostic queries to run.
- Escalation contacts.
- The "safe action" — pause downstream? rerun? wait?
- The "do not do" — never truncate, never edit raw, etc.

If you can't write the runbook, the test is premature; add it once you understand the failure modes.

### Worked plan (excerpt)

For an `orders_fact` daily table:

```yaml
# column-level (in-pipeline)
- col: order_id
  rules: [not_null, unique, regex '^ord_[a-z0-9]{16}$']
  severity: P0

- col: amount_cents
  rules: [not_null, between 0 and 100000000]
  severity: P0

- col: currency
  rules: [not_null, in [USD, EUR, GBP, JPY]]
  severity: P0

- col: shipped_at
  rules: [not_null, greater_than_eq ordered_at]
  severity: P1

# table-level (post-load)
- table: orders_fact
  rules:
    - pk_unique: [order_id]
      severity: P0
    - row_count_min: 10000
      severity: P1
    - row_count_within: { baseline: 7d_mean, sigma: 3 }
      severity: P1
    - schema_match: contract orders.line_items_v1
      severity: P0

# freshness (continuous)
- target: orders_fact
  rules:
    - max_age(loaded_at): 90m
      warn_at: 60m
      fail_at: 120m
      severity_warn: P2
      severity_fail: P1

# distribution (post-load, with baseline)
- target: orders_fact
  rules:
    - null_rate(promo_code): { baseline: 30d, threshold: 0.05 abs }
      severity: P2
    - mean(amount_cents): { baseline: 30d, sigma: 3 }
      severity: P1

# business rules (post-load + nightly reconcile)
- rule: refund_le_charge
  sql: |
    SELECT COUNT(*) FROM orders_fact
    WHERE refund_cents > amount_cents
  expect: 0
  severity: P0

- rule: revenue_reconcile_payments
  sql: |
    SELECT ABS(SUM(o.amount_cents) - SUM(p.amount_cents))
    FROM orders_fact o
    JOIN payments p USING (order_id)
    WHERE o.order_date = current_date - 1
  expect: less_than 100
  severity: P1
```

## Inputs

- **pipeline** (required): the dataset / pipeline under test — sources, transforms, target, downstream consumers.
- **business_rules** (optional but high-value): invariants the business knows.
- **known_failures** (optional): past incidents to encode as tests.
- **tooling** (optional): existing runner — affects syntax, not the design.

## Outputs

- A 5-layer test plan (column / table / freshness / distribution / business).
- Severity assignment for every test.
- On-failure action per severity tier.
- Placement matrix (in-pipeline / post-load / continuous).
- A baseline-calibration plan for the statistical tests.
- A runbook stub for the P0 and P1 tests.
- A 30-day "tuning" plan: which thresholds will likely need adjusting after observing real traffic.

## Examples

> "Daily revenue table, dbt-on-Snowflake, finance is the consumer, we got bitten by a duplicate-orders bug last quarter."

Structural: NOT NULL + range on `amount_cents`, enum on `currency`, regex on `order_id`. Table-level: PK uniqueness P0, row count within 3σ P1, schema-match P0. Freshness: 90m max age, warn 60m, fail 120m. Distribution: mean(amount_cents) 30d/3σ P1, null-rate on promo P2. Business rule: refund ≤ charge P0; daily reconcile with payments P1. Tools: dbt tests for structural, Great Expectations checkpoint after the dbt run for table-level and distribution, a separate cron probe for freshness.

> "Streaming event topic, 1M msgs/day, four downstream Flink jobs."

Schema enforcement at the registry (FULL compatibility) as the first line. Per-consumer: NOT NULL on critical fields P0, enum on `event_type` P1, freshness via consumer-lag metric (max-lag p95 < 60s) P1. Volume anomaly on the topic via rolling 1h baseline P2. Business rule: every `purchase` event has a matching `add_to_cart` within the prior 30 days — soft P2 (long-tail violations are real).

> "Vendor file feed, daily, schema sometimes changes silently."

Strict schema-match at file landing: P0. File-arrived-by-06:00 freshness: P1. Volume bounds: P1. Distribution on numeric columns: P2 (vendor data shifts seasonally — calibrate carefully). Quarantine on any P0 failure with a manual unblock; never auto-rerun.

## Limitations

- This skill designs the suite; it doesn't write production-grade SQL for every test. Hand to an engineer to translate into your runner's syntax.
- Statistical tests need real history to calibrate; the first 2 weeks of any pipeline are anomaly-blind.
- Anomaly detection beyond rolling z-score (e.g., Prophet, isolation forests) is out of scope; if the data is highly seasonal, plan for a separate spike.
- Tests are not a substitute for a **data contract** with a producer. If the producer can change schema without notice, no test suite will save you for long — author the contract first.
