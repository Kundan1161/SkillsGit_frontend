# Model Quantization Strategist

## When to use

Use this skill when someone needs to reduce a model's size, latency, or memory footprint by lowering the numerical precision of its weights or activations — and wants a plan that does not silently destroy accuracy. The deliverable is a written strategy: which precision to target, whether to do it post-training or during training, how granular the scales should be, what data to calibrate on, how to identify which layers are too sensitive to quantize aggressively, what accuracy regression is acceptable, and what to do if the first attempt fails.

The skill works for convolutional vision models, transformer-based language and vision models, audio models, recommender embeddings, and small generative models. It is opinionated about LLM-style transformer quantization (weights-mostly schemes, group-wise quantization, outlier handling) but applies to non-LLM models too.

It is not the right skill for designing a training run, for choosing a model architecture, for the end-to-end deployment pipeline (use the companion edge-inference pipeline-architect skill), or for sparse / pruning techniques. Quantization and pruning interact — the plan flags this — but the pruning plan itself is out of scope.

## How to apply

The skill walks a twelve-stage pipeline. Stages are sequential because precision choice gates granularity, granularity gates calibration design, calibration gates validation, and validation gates the fallback ladder.

### Stage 1 — Establish the why and the budget

1. Restate the goal in measurable terms. Quantization is rarely the goal; the goal is a smaller artifact, a faster inference, or a smaller memory footprint, of which one is primary. Ask which.
2. Record the size, latency, and memory budgets each as a single number. "Smaller" is not a budget. The plan will fail if these numbers are not in the deliverable.
3. Record the accuracy floor as a single number on a single metric on a single evaluation set. If the user has multiple metrics, pick one as the gating metric and treat the rest as guardrails.
4. Decide the accuracy regression budget: how much accuracy the quantized model is allowed to lose versus the original. A typical budget is 0.5 to 1.5 points on the primary metric; aggressive sub-byte quantization may stretch this. The budget must be pinned before any quantization is run, not chosen after the result is observed.
5. Pin the evaluation set: the same held-out data used in training-time evaluation, plus any production-style data the user has access to. The quantized model must clear the floor on the same set the source model cleared.

### Stage 2 — Pick the precision target

6. List the candidate precisions: FP32 baseline, FP16, BF16, INT8, INT4, INT2, and sub-1-bit binary schemes for special cases.
7. Anchor the precision to the deployment target. Some integer-only accelerators force INT8 or below. Some GPUs prefer FP16 or BF16. Mixed precision (INT8 most layers, FP16 outliers) is supported by many runtimes and is often the right answer for transformer models.
8. For language-model-style transformers with billions of parameters, the dominant pattern is "weights-mostly quantization": weights in low precision (INT4 group-wise is currently the practical sweet spot for memory-constrained on-device deployment, INT8 for less aggressive setups), activations kept in higher precision because their dynamic range is too wide to quantize cheaply.
9. For convolutional vision models, INT8 with per-channel weight scales and per-tensor activation scales is the well-trodden path. INT4 is reachable on these models but typically requires quantization-aware training.
10. For RNNs and models with recurrent state, additional care is needed: the recurrent activations accumulate error and per-step quantization can compound. The plan recommends a higher precision floor for recurrent paths.

### Stage 3 — Pick the method: PTQ vs QAT

11. Post-training quantization (PTQ) converts an existing trained model in place using a calibration pass to determine scales. PTQ is cheap and fast — minutes to hours — and is the default first choice.
12. Quantization-aware training (QAT) folds simulated quantization into the training graph and continues training, allowing the weights to adapt to the precision. QAT recovers accuracy that PTQ loses but costs a real training run and gradient signal.
13. The default ladder is: try PTQ first; if it clears the accuracy floor, ship it. If PTQ fails, try a static calibration with a larger or better calibration set; if still failing, try mixed precision (Stage 7); if still failing, fall back to QAT.
14. For very aggressive precisions (INT4 and below) on architectures more complex than vanilla convolutions, QAT is almost always required. Plan QAT capacity from the start; doing PTQ first and discovering QAT is needed has wasted no work because the PTQ result is the QAT starting point.
15. The training-capacity input gates this: `no_retraining` forces a PTQ-only plan, `light_finetune` allows a short calibration-plus-finetune, `full_qat` allows a complete training cycle. If the user's stated precision target cannot be reached with their training capacity, the plan flags the conflict and recommends either relaxing the precision or budgeting for QAT.

### Stage 4 — Pick the granularity

16. Per-tensor quantization assigns a single scale (and zero-point) to an entire weight tensor or activation tensor. It is cheap to compute and to store. It works well when the tensor's value distribution is reasonably uniform.
17. Per-channel quantization assigns one scale per output channel of a weight tensor. It costs a small overhead (a few floats per layer) and recovers a lot of accuracy when channels have different dynamic ranges, which is common in convolutional weights.
18. Group-wise quantization (the LLM weight pattern) assigns scales to fixed-size groups of consecutive weights within a row — group sizes of 32, 64, or 128 are typical. Smaller groups mean more accuracy at the cost of more overhead. The choice trades a few percent of disk size for a few percent of accuracy.
19. For activations, per-tensor is almost always the right choice on conv models; per-token (a scale per sequence position) is the right choice for transformer activations where the per-token dynamic range varies sharply.
20. The plan must explicitly say, for each layer kind, which granularity applies. A blanket "per-channel everywhere" is a smell — embeddings and biases typically do not benefit from per-channel.
21. Symmetric vs asymmetric quantization: symmetric (zero-point fixed at zero) is simpler and slightly faster; asymmetric (learned zero-point) recovers a little accuracy when distributions are skewed. Default to symmetric for weights and asymmetric for activations unless the runtime forbids it.

### Stage 5 — Design the calibration set

22. The calibration set is the data used to estimate the dynamic range of weights and activations. It is unlabelled — the model just does forward passes — and is typically a few hundred to a few thousand inputs.
23. The calibration set must be representative of production inputs. A model that will see camera frames in low light cannot be calibrated on stock photos. A model that will see code completions cannot be calibrated on prose.
24. Diversify across classes / categories the model serves. A calibration set that is 90% class A misses the activation distribution of the rare classes.
25. Diversify across input properties that affect activations: image size, lighting, language, code style, audio noise level. The plan must enumerate these axes for the user's domain.
26. For language models, the calibration set should be a mix of representative natural text and a small fraction of edge-case inputs (code, math, multilingual, very long sequences). Pure-Wikipedia calibration leaves the model fragile to other distributions.
27. Pin the size. Most PTQ algorithms plateau in accuracy gain between 256 and 4,096 samples; pick a size in that range and treat it as a parameter to tune only if accuracy is short.
28. Document the calibration set as an artifact with its own hash and version. The same calibration set must be reusable on re-quantization runs to get reproducible scales.

### Stage 6 — Run sensitivity analysis

29. Not all layers tolerate the same precision. A sensitivity analysis ranks layers by how much accuracy is lost when *only that layer* is quantized.
30. The protocol: hold the rest of the model at the source precision; quantize one layer at a time to the target precision; measure the metric on the evaluation set; record the delta from the baseline. Repeat for each layer. The result is a ranking from most sensitive to least sensitive.
31. The first and last layers are commonly the most sensitive — the first because input statistics have not been normalised by the network, the last because small errors at the head propagate directly to the output. The plan recommends keeping these in higher precision unless the sensitivity sweep shows otherwise.
32. In transformer blocks, the attention output projection and the layer-norm scales are common hotspots; in convolutional models, the very wide channel layers near the head are common hotspots. The sensitivity sweep should not just confirm these heuristics — it should measure them on the user's specific model.
33. For LLM weight-only quantization, a related diagnostic is per-channel weight outlier ratio. Channels with a few large outlier weights blow up the per-channel range and force coarser scales. The plan recommends an outlier-aware scheme (separate higher precision for outlier channels, or a smoothing transform that redistributes the magnitude) when the outlier ratio is high.
34. The sensitivity table goes into the deliverable. It is the basis for the mixed-precision ladder in Stage 7.

### Stage 7 — Build the mixed-precision ladder

35. The mixed-precision ladder is the ordered list of decisions the user takes if the uniform target precision fails the accuracy floor.
36. Step one of the ladder: keep the top-K most sensitive layers from Stage 6 at one precision higher than the target. K is typically 2 to 8 for most architectures. The plan must commit a starting K and a stopping rule (e.g. "K up to 10% of layers").
37. Step two: keep the model's first and last layers in FP16 or BF16 regardless of what the sweep says. This is a near-universal safety belt.
38. Step three: switch the granularity to a finer scheme — per-tensor to per-channel, group size 128 to group size 64 or 32. The cost is a small artifact-size increase.
39. Step four: switch the calibration method. Standard min-max calibration is often inferior to entropy-based, percentile-based, or distillation-based calibration on long-tailed activation distributions. The plan should test at least two calibration methods before declaring PTQ failed.
40. Step five: invoke QAT if available. If not, the ladder bottoms out and the plan recommends relaxing either the precision target or the accuracy floor.
41. Each step of the ladder has a measurable success criterion: clearing the accuracy floor. Do not climb the ladder further if the current step already clears it; do not stop early if it does not.

### Stage 8 — Plan validation gates

42. The quantized model must be validated against more than the headline metric. The plan must include:
    - Headline metric on the evaluation set.
    - Per-class or per-slice metrics. Quantization can collapse on rare classes while preserving overall accuracy.
    - Output similarity to the source model. For generative models, agreement-rate or KL divergence between source and quantized output distributions on the same inputs.
    - Calibration of probabilities: a quantized classifier may stay accurate but become overconfident.
    - Latency on the target accelerator, end-to-end. Quantization that requires runtime fallback for unsupported ops can actually be slower than the unquantized model.
    - Memory at inference. Quantization that does not actually reduce peak memory because activations remain in higher precision is a partial win.
43. Each gate has a numerical pass criterion. The plan rejects "looks fine" judgments.
44. The validation script is a reproducible artifact pinned to a specific evaluation-set version and a specific calibration-set version. Without pinning, re-runs are not comparable.
45. Add at least one adversarial validation case: a known-hard slice of inputs (corner-case images, low-frequency tokens, non-English text) where quantization is most likely to fail.

### Stage 9 — Handle outliers and dynamic-range hazards

46. Activations whose distribution has long tails (a few extreme values orders of magnitude larger than the median) are the principal source of quantization accuracy loss. The plan must include an outlier-handling strategy.
47. Common strategies: clip percentiles below the maximum to ignore the tail; smooth activations into weights via a per-channel rescaling transform; isolate outlier channels into a separate higher-precision path; switch the calibration method to be tail-aware.
48. For LLMs, the canonical hazard is a small number of "outlier features" in residual-stream activations that grow with model scale. The plan must call out that the chosen LLM quantization scheme handles these or risk silent quality collapse on long generations.
49. For convolutional vision models, batch-norm folding into preceding convolutions changes the weight distribution and may change which channels are outliers. The plan must require batch-norm folding *before* sensitivity analysis and calibration, not after.

### Stage 10 — Plan for retraining and recovery

50. If QAT is selected, plan its hyperparameters: which layers have simulated quantization inserted, what straight-through-estimator variant is used, what learning rate (typically 10x lower than original training), how many fine-tune steps (typically a small fraction of original training).
51. Decide whether to fine-tune all weights or only the quantization scales. Scale-only fine-tuning is much cheaper and often recovers most of the accuracy lost by PTQ; full QAT may be needed for very aggressive precisions.
52. For language-model fine-tuning, recommend a distillation objective using the source model's logits as a soft teacher signal — distillation often recovers more accuracy than next-token-prediction fine-tuning alone for the same compute.
53. Plan a stopping rule for QAT: a validation-metric patience window so that QAT does not over-fit to its fine-tune set and lose accuracy on held-out data.

### Stage 11 — Document the risk register

54. Enumerate the things that can make the quantization claim misleading:
    - Calibration set is unrepresentative — recommend a domain-shift probe.
    - Evaluation set has been seen during calibration — recommend strict separation.
    - The runtime silently falls back ops to higher precision, hiding accuracy losses — recommend dispatch validation.
    - The accelerator quantizes activations to a precision different from what the toolchain claims — recommend on-device numerical comparison.
    - Different platforms produce different quantization results from the same calibration data — recommend platform-specific validation.
    - Accuracy regression appears only on rare slices — recommend per-slice gating.
    - Memory or latency gains do not materialise because the bottleneck was elsewhere — recommend end-to-end profiling, not just inference profiling.

### Stage 12 — Compose the deliverable

55. Open with a one-paragraph quantization intent: precision target, method, expected accuracy regression, expected size and latency wins.
56. Render the plan as a stage-by-stage section. Include the sensitivity table from Stage 6 explicitly.
57. Render the mixed-precision ladder as an ordered list with a success criterion per step.
58. Emit the JSON in `plan_json` with stable keys for downstream tooling.
59. Close with the "what this plan does not cover" section: it does not run the quantization, it does not adjudicate accuracy-versus-cost trade-offs, and it does not encode platform-specific runtime quirks beyond a general checklist.

## Examples

**Input (placeholder):**

`model_description`: "A 7B-parameter transformer language model, decoder-only, fine-tuned for an in-house code-suggestion task. Source format is PyTorch."

`deployment_target`: "On-device on flagship phones; GPU accelerator with FP16 support, but memory budget is the binding constraint, so we want weights in 4-bit."

`accuracy_floor`: "Pass-rate on an internal eval set of 500 code-suggestion prompts must drop by no more than 2 percentage points relative to FP16."

`training_capacity`: "light_finetune."

`data_access`: "About 30k unlabelled code prompts from production logs and the 500-prompt eval set."

**Plan (abbreviated):**

- Precision target: 4-bit weights, FP16 activations, group-wise per-channel weight scales with group size 128.
- Method: PTQ first; if accuracy regression exceeds 2 points, fall back to a short scale-only fine-tune with a distillation objective using the FP16 source model as teacher.
- Calibration set: 2,048 prompts sampled from production logs, stratified by language and prompt length; held strictly disjoint from the 500-prompt eval set.
- Sensitivity sweep: quantize one transformer block at a time to 4-bit; rank by eval pass-rate delta. Pre-register a hypothesis that the first two blocks, the last block, and the attention output projections will be most sensitive.
- Mixed-precision ladder: (1) keep top-2 sensitive blocks at 8-bit; (2) keep first and last layers at FP16; (3) drop group size to 64 if pass-rate still short; (4) invoke distillation fine-tune.
- Validation gates: overall pass-rate, per-language pass-rate (Python, TypeScript, Go, Rust, others), generation-length distribution match against FP16, end-to-end latency on the target GPU, peak memory on the target device.
- Outliers: weight-magnitude outlier ratio measured per channel; channels above the 99.5th percentile kept at 8-bit; activation outlier handling via SmoothQuant-style migration as a fallback if pass-rate remains below the floor.
- Risk register: calibration may underrepresent multilingual prompts; runtime may silently re-dispatch some ops to CPU; group-size choice may conflict with the runtime's tile size.

## Limitations

- The skill produces a plan, not a quantized model. The user runs the toolchain.
- Sensitivity analysis is expensive; the plan recommends a layer-wise sweep but does not run it. For very large models, the user may need to bin layers (e.g. blocks of N consecutive layers) before sweeping.
- Recommendations on group sizes, K-most-sensitive thresholds, and learning rates are heuristic starting points. They must be tuned to the user's model and data.
- Accelerator behaviour is hardware-specific; some integer kernels behave subtly differently from the toolchain's reference implementation. The plan recommends on-device validation but cannot pre-empt every kernel-level surprise.
- Pruning interacts with quantization — a model pruned aggressively then quantized aggressively may collapse — and the plan flags this but does not encode pruning strategy.
- Distillation objectives are sketched, not fully specified. A user with no distillation tooling will need a separate plan to build it.
- Calibration ethics: production data used for calibration must respect data-handling policies. The plan flags this but does not adjudicate compliance.
