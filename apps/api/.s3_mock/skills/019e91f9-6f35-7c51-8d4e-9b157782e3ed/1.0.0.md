# ML Experiment Designer

## When to use

Use this skill when someone has a candidate machine-learning change — a new model, a different loss, a tweaked prompt, an added feature, a fine-tune of an open base model — and they want to know whether the change actually helps before they merge it. The skill produces a written plan, not a result; the plan tells the user exactly what to run, what to record, and how to decide whether the result is real.

The skill is appropriate for supervised learning (classification, regression, ranking), for LLM-powered features where the "model" is a prompt-plus-retriever-plus-generator stack, for recommender candidates, and for forecasting. It applies whether the underlying training stack is scikit-learn, PyTorch, an LLM fine-tuning pipeline, or a no-training prompt experiment.

It is not the right skill for greenfield "should we even build an ML system here?" framing — that belongs upstream of this step. It is also not a skill for running the experiment itself, just for designing it. The skill assumes the user has access to an experiment-tracking surface (a self-hosted tracker, a notebook with disciplined logging, or a cloud platform) — it does not depend on any specific one.

## How to apply

The skill walks a fourteen-stage pipeline. Stages are sequential because later stages depend on earlier decisions.

### Stage 1 — Restate the problem in operational language

1. Read the `problem_statement` and rewrite it as a single sentence in the form "Given <inputs>, predict <output>, optimised for <objective>, evaluated on <population>." If any of the four slots is empty or ambiguous, ask the user to fill it before continuing.
2. Identify whether the task is classification, regression, ranking, retrieval, generation, structured prediction, or hybrid. Different task types drive different default metric choices in Stage 4.
3. Identify the decision the prediction enables. "We predict X" is incomplete; the question is what action follows the prediction and what the cost of each kind of error is. If the user has not stated this, propose a default and flag it for confirmation.
4. Write a one-line null hypothesis: "the candidate change has no effect on <primary metric> versus the baseline on <evaluation population>." The whole plan exists to either reject or fail to reject this hypothesis.
5. Write a one-line alternative hypothesis with a direction and a minimal effect size that would be worth shipping (the "smallest improvement worth caring about", or SIWCA). If the user has not told you the SIWCA, propose one in plain language ("less than 0.5 F1 points is probably not worth the engineering cost") and flag it for confirmation. Without a SIWCA the whole experiment risks p-hacking after the fact.

### Stage 2 — Inventory the data

6. From `dataset_description` (or by asking) record: total rows, label provenance (human-annotated, click-derived, weak-supervised, synthetic), how recent the rows are, whether the data has temporal structure, what natural grouping units exist (user, account, session, document), whether there are known label-noise sources, and whether any leakage paths are suspected.
7. List the data slices you expect to report metrics on separately: at minimum the overall set and the slices defined by the most important categorical features (segment, language, geography, time bucket). The user often discovers a regression on a single slice that the headline metric hides.
8. Flag obvious leakage smells: features that are themselves derived from the label, features whose value is only known after the prediction event, sample IDs that span multiple splits, identifiers that uniquely identify a user across train and test, and label values that appear in feature text. If any are present, the experiment plan halts on a "fix leakage first" finding.
9. Identify the class balance (or value distribution for regression). If the imbalance is severe (rarer class < 5%), the metric plan in Stage 4 must include a metric that survives imbalance (e.g. PR-AUC instead of ROC-AUC) and the split plan in Stage 3 must stratify.
10. Identify duplicates and near-duplicates. If the dataset has them, hold-out evaluation will be optimistic; recommend dedup before splitting and pin a hash-based dedup rule in the plan.

### Stage 3 — Choose the data split strategy

11. Default split is **train / validation / test**: train for fitting, validation for hyperparameter selection and early stopping, test for the single end-of-experiment report. The test set is used exactly once.
12. If the dataset is small (<10k labelled rows or fewer than 100 per class), substitute **k-fold cross-validation** (typically 5-fold) for the train/validation split. The test set still stays sealed.
13. If the data has temporal structure, switch to a **time-based split**: train on rows before time T1, validate on rows between T1 and T2, test on rows after T2. Random splits across time leak future information into training and inflate metrics.
14. If the data has natural groups (multiple rows per user, per document, per session) where the model will at inference time see a *new* group, split *by group*, not by row. A user's rows must not appear in both train and test.
15. If the deployment is a recommender or any "next-item" task, prefer **leave-one-out per user** evaluation: hold out each user's most recent interaction, score the model on that, and aggregate.
16. If the data shifts seasonally, the test set should cover at least one full seasonal cycle; otherwise the report's external validity is weak.
17. Record the random seeds used for any random split. The plan must include the exact seed so the experiment is reproducible.
18. For LLM-driven features evaluated by prompts: the "training set" is the few-shot or fine-tuning examples; the "validation set" is the development set you iterate against; the "test set" is a held-out evaluation set that you do not look at the contents of during prompt iteration. Looking at the test set during prompt iteration is the LLM-era equivalent of training-on-test.

### Stage 4 — Pick metrics

19. **Primary metric.** Pick one number that the experiment will live or die by. It must be aligned with the decision the prediction enables (Stage 1, step 3). For balanced classification: accuracy. For imbalanced classification: F1, F-beta with the beta matched to the asymmetric cost, or PR-AUC. For regression: RMSE or MAE depending on whether outliers should be punished. For ranking: nDCG, MRR, or hit-rate-at-k matched to the surface. For generation tasks evaluated automatically: exact-match against gold or judge-scored win-rate. Do not use ROC-AUC as a sole metric on severely imbalanced data — it is misleading.
20. **Guardrail metrics.** List 2-5 secondary metrics that the candidate must not regress on by more than a stated tolerance: latency, cost per prediction, calibration error, worst-slice accuracy, fairness disparity, recall on the rare positive class. A model that "wins" overall while collapsing on a critical slice is a loss disguised as a win.
21. **Diagnostic metrics.** Add 2-3 metrics that help interpret the headline. Confusion matrix cells. Per-slice breakdowns. Reliability diagrams. Top-error examples. These are not gating but they tell the user what changed.
22. **Calibration.** If the downstream consumer uses the probability or score directly (e.g. ranking by score, thresholding for an action), include a calibration metric — Brier score, expected calibration error, reliability plot. A model can win on AUC while becoming uselessly overconfident.
23. **Cost-sensitive metric.** If false positives and false negatives have very different costs, the primary metric must reflect that. Recommend a weighted-cost metric whose weights come from the user's actual operational cost, not a textbook 50/50.
24. **Generation-task metric stack.** For LLM outputs: combine an automated metric (BLEU, ROUGE, exact match, structural validity) with an LLM-as-judge metric (covered separately in the eval-harness skill) and a small human-graded sample. Never rely on a single automated metric for free-text generation.

### Stage 5 — Choose baselines

25. Always include a **trivial baseline**: predict the majority class, predict the dataset mean, predict the last value seen. The trivial baseline tells you whether the problem has any signal at all and whether the candidate change beats nothing.
26. Always include a **simple baseline**: logistic regression on the obvious features, a one-rule heuristic, a zero-shot prompt with no examples. Many "improvements" disappear when compared to a careful simple baseline. If the user proposes a complex model without a simple baseline, push back.
27. Include the **current production system** if one exists. The candidate change must beat what is shipped today on the metric the business cares about — not just the simple baseline.
28. Include a **published reference** if one exists at task-appropriate scale (e.g. a known F1 from a public benchmark) so that absolute numbers can be sanity-checked.
29. Each baseline must run on the same data splits and report the same metrics as the candidate; otherwise the comparison is broken.

### Stage 6 — Plan ablations

30. List the ablations the user must run *if they observe a positive result*. The purpose of ablations is to attribute the gain to a specific change, not to a confound.
31. For each component the candidate adds (a new feature, a new layer, a new prompt instruction, a new retriever, a new loss term), define an ablation variant that removes that component and leaves the rest. If the candidate change is bundled with a refactor or a hyperparameter retune, propose a "controlled" variant that backs out the refactor.
32. For each hyperparameter that is being changed, propose at least one sweep value on each side of the chosen value, so the report can show whether the candidate is near a peak or on a hill.
33. If the candidate change uses a different random seed than the baseline, require *both* to be averaged over at least 3 seeds. Seed-variance can swamp a small claimed improvement.
34. If the change is data-side (a new feature, a new training subset, a new annotation), include a "candidate model trained on baseline data" or "baseline model trained on candidate data" cross-over ablation. This separates "the model is better" from "the data is different".
35. Cap the ablation plan at what the `time_budget` allows: a day-budget run gets the two highest-priority ablations only; a quarter-budget run gets the full grid. Always state which ablations are *required* to make the claim and which are *nice to have*.

### Stage 7 — Stopping criteria

36. State up front when the experiment ends. Without a stopping rule, the user keeps running variants until one wins by chance — the multiple-comparisons trap.
37. **Time-based stopping.** "We will spend at most N days; whatever we have at the end is the result." Honest but blunt.
38. **Metric-improvement stopping.** "We will stop when the validation primary metric exceeds the baseline by SIWCA for K consecutive evaluation steps with overlapping seed runs." Requires K and SIWCA pinned in advance.
39. **Compute-budget stopping.** For deep-learning runs, set a max FLOPs or GPU-hours budget per variant. Stops a single variant from monopolising the bake-off.
40. **Pre-registered freeze.** Before the user looks at the test set, the plan is frozen. Any change to metrics, splits, or candidate definition after looking at test results invalidates the test claim. Recommend writing the plan to a file and committing it.
41. **Early-stopping inside a single training run** (which is different from the experiment-level stopping above): use validation-set performance with a patience window; record the epoch at which the chosen model was saved. The hyperparameters of early stopping (patience, minimum delta) must be the same across candidate and baseline.

### Stage 8 — Statistical significance plan

42. State the test that will be applied to the primary metric on the test set. The test must match the metric:
    - For paired accuracy on a held-out set with binary outcomes: **McNemar's test** on the disagreement counts.
    - For paired regression error on a held-out set: **paired bootstrap** of the difference in MAE / RMSE.
    - For ranking or recommendation hit-rate over users: paired bootstrap across users.
    - For LLM judge win-rate: **binomial test** against the 0.5 null, paired by example.
    - For cross-validation averages: **5x2 cv paired t-test** or **Nadeau-Bengio corrected t-test**, not the naive paired t over fold means (the naive version under-estimates variance).
43. Pre-register the significance threshold (commonly p < 0.05) and the SIWCA. Significance is necessary but not sufficient: a statistically significant 0.1% improvement that costs 20% more compute is not worth shipping.
44. Report **effect size with confidence interval**, not just a p-value. The plan must require both. A 95% bootstrap CI of the metric difference is more informative than a binary "significant / not significant".
45. If multiple variants are being compared, apply a **multiple-comparisons correction**: Bonferroni for small numbers of comparisons, Benjamini-Hochberg for larger. The plan must enumerate which families of comparisons are corrected together.
46. For LLM-driven experiments where each evaluation is expensive: define a sample-size calculation in advance — given expected effect size and variance, how many test examples does the user need to detect the SIWCA at the chosen power? Reject "I'll just check 25 examples" as under-powered for almost any realistic claim.

### Stage 9 — Reproducibility plan

47. The plan must enumerate everything that must be logged for each run so a future reader can reproduce: data version (hash or tag of the dataset, including any preprocessing), code commit, library versions, random seed, full hyperparameters, GPU/CPU type, wall-clock time, peak memory, primary and guardrail metric values, model artifact path or hash.
48. Require that the run-tracker treat the experiment as an immutable record: re-runs make new entries; old entries are not edited. Tampering with history is the most common pre-publication mistake.
49. For data: any preprocessing step that is not deterministic given a seed (e.g. an LLM-based labelling step) must be recorded with the exact prompt and the exact model snapshot. Otherwise the data is unreproducible.
50. For models that download external assets at training time (a base model, a tokenizer, a retrieval corpus), pin the asset version. "Latest" is not a version.

### Stage 10 — Bias, safety, and fairness check

51. List the protected or sensitive attributes that apply to this domain (demographic, geographic, content-policy categories for generation). For each, the plan must report the primary metric *and* a fairness metric: equal opportunity, demographic parity, or a slice-accuracy gap, depending on the user's policy.
52. For generation tasks, list the safety categories the model must not regress on: refusal of policy-violating prompts, factual-hallucination rate on a probe set, toxic-output rate, prompt-injection susceptibility. Each gets its own held-out probe set and a "do not regress" guardrail.
53. The fairness and safety metrics are guardrails: the candidate must not regress on any of them by more than a stated tolerance, even if the headline metric wins. Flag candidates that gain on headline by trading safety as failed.

### Stage 11 — Productionization gate

54. The gate is a checklist the candidate must clear before being merged into a production path. The plan should list each item with a pass/fail criterion:
    - Primary metric beats baseline by at least SIWCA with statistical significance.
    - No guardrail metric regresses by more than the stated tolerance.
    - Latency p50 and p95 within `deployment_constraints` budget.
    - Cost per prediction within budget.
    - Memory and GPU footprint within budget.
    - Model artifact passes its serialisation round-trip test.
    - Inference path has at least one end-to-end smoke test that runs in CI.
    - Reproducibility checklist (Stage 9) is complete.
    - Fairness and safety guardrails clear.
    - For LLM-driven features: prompt or fine-tune is pinned to a specific base model version.
    - Rollback plan exists: how do we revert if a regression is detected in shadow or canary?
55. If any item is open, the recommendation is "not ready"; the plan lists the gaps to close, not a "ship it" verdict.

### Stage 12 — Tracking schema

56. Translate the plan into a schema the experiment tracker should record. Required fields: run_id, parent_run_id (for ablation lineage), config_hash, code_commit, dataset_version, seed, primary_metric, secondary_metric[*], slice_metric[*], fairness_metric[*], latency_p50_ms, latency_p95_ms, cost_per_prediction, gpu_hours, peak_mem_gb, status, artifacts.
57. Require parent-child run grouping so a candidate-vs-baseline pair can be retrieved as one comparison.
58. Require tagging by experiment hypothesis (a short slug) so the user can filter for all runs that share a goal.
59. Recommend that the tracker emit a Markdown summary per experiment so the report can be reviewed without opening a UI.

### Stage 13 — Risk register

60. Enumerate the things that could make the experiment misleading and what to do about each:
    - Label noise above 5% — recommend a labelling-audit sample before trusting metric gains within label noise.
    - Class imbalance shifts between splits — recommend stratification check.
    - Temporal drift between train and test — recommend a "fresh week" extra test slice.
    - Data leakage — recommend the leakage smell tests from Stage 2 step 8 as a CI check.
    - Reward-hacking the metric — recommend at least one orthogonal metric the optimisation cannot trivially game.
    - LLM-judge drift if the judge model is updated mid-experiment — recommend pinning the judge model.
    - Confounded ablations — recommend running one strict "single-variable-changed" ablation even if it costs extra.

### Stage 14 — Compose the deliverable

61. Open with a one-paragraph "design intent" summary: what the experiment is asking, what it would prove, what it would not prove.
62. Render the plan as a markdown checklist organised by the stages above so the user can tick items off as they go.
63. Emit the JSON variant in `plan_json` with a stable schema so a downstream tool can consume it.
64. End the plan with a "what this plan does not cover" section — the limitations of an experiment plan are themselves a contribution, because they tell the user what other work is needed.

## Outputs

The skill returns two artifacts:

1. `experiment_plan` (markdown) — the human-readable plan organised by stage.
2. `plan_json` (JSON) — structured plan with the keys listed under `outputs`.

## Examples

**Input (placeholder):**

`problem_statement`: "We auto-tag support tickets with a 12-class label. The current production model is a TF-IDF + logistic regression baseline. We want to evaluate replacing it with a fine-tuned encoder model."

`dataset_description`: "120k tickets, human-labelled, six months of history, distribution shifts slowly as product changes, one of the twelve classes is < 1% of rows."

`candidate_change`: "Fine-tune a small open encoder on the same labels."

`baseline_description`: "Production TF-IDF + logistic regression."

`deployment_constraints`: "p95 latency < 80ms per ticket on a single CPU core; we cannot add a GPU to the serving fleet."

`time_budget`: "week."

**Plan (abbreviated):**

- Hypothesis: fine-tuned encoder yields ≥ +2 F1 macro vs. baseline on held-out tickets, no slice regresses by more than 1 F1 point, latency stays within budget.
- Splits: time-based (oldest 80% train, next 10% validation, most-recent 10% test). Stratify on rare class within each split.
- Metrics: primary = macro F1; guardrails = p95 latency on CPU, recall on rare class, calibration ECE; diagnostics = per-class F1, confusion matrix.
- Baselines: majority class, current production logistic regression, zero-shot LLM prompt as a sanity check.
- Ablations (required this week): (a) encoder fine-tune vs. encoder frozen + linear head; (b) full feature text vs. subject-only text; (c) 3 seeds for both candidate and baseline.
- Stopping: 5 days of training and tuning; freeze the plan now.
- Significance: paired bootstrap of macro F1 difference with 1000 resamples per slice, 95% CI; multiple-comparisons correction across slices via Benjamini-Hochberg.
- Productionization gate: latency budget is the blocking item — recommend a CPU-only inference benchmark on a quantised version before claiming readiness.

**Output excerpt:** the markdown plan plus a JSON object whose `prod_gate` array lists each gate item with a pass/fail criterion and a current `unknown` status.

## Limitations

- The skill does not run the experiment; it only writes the plan. The user must execute it and feed the results back for a separate verdict.
- Significance test selection is heuristic — for unusual loss functions or non-i.i.d. dependencies, recommend that the user consult a statistician before trusting the test.
- The skill assumes labelled data of reasonable quality; if labels are themselves model-generated, the report must call this out and the user should plan a human-audit pass.
- The productionization gate is generic. Domain-specific gates (medical, financial, regulated) require domain expertise that this skill does not encode.
- The skill cannot detect data leakage by inspecting data — only by inspecting descriptions. The leakage smell tests must be executed by the user.
- LLM-as-judge calibration is covered only at a high level; the dedicated LLM eval harness skill goes deeper.
- For very small datasets (< 100 rows) classical significance tests are weak; recommend qualitative review and bootstrap CIs instead of p-values.
