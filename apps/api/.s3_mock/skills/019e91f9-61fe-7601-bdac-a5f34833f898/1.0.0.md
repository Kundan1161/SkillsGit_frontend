# 3D Render Farm Methodology

## When to use

Use this skill when a 3D production has grown past the point where one artist's workstation can render the work overnight. It is the right skill for a small studio standing up its first farm, for a technical director designing the submission workflow, for a producer who needs to know whether the schedule fits the farm, and for any project where a single shot's frame count multiplied by per-frame render time exceeds a single machine's available hours by a meaningful margin. It is also the right skill for an existing farm that has begun to fail in painful and irregular ways — jobs erroring on missing textures, license starvation blocking dailies, no one able to find last month's renders, frames silently re-rendering because the dependency capture missed something.

Skip it for one-machine work, for short turnarounds where a single workstation overnight is enough, and for cloud-only render services where the provider owns the queue management. Reach for it the moment two or more machines are rendering the same project, the moment a single shot's render time exceeds 12 hours on a workstation, or the moment a missed deliverable can be traced back to a farm problem rather than an art problem.

## How to apply

1. Decide whether the farm is **owned, rented, or hybrid**. Owned hardware (workstations and dedicated render nodes on premise) is cheapest per hour at high utilization and worst at burst. Rented hardware (cloud render services, on-demand burst providers) is expensive per hour but absorbs peak demand without idle cost. Hybrid is the typical mature answer: own a steady-state baseline, burst to cloud for crunch. The choice determines the rest of the workflow — owned farms care more about license budgeting, cloud farms care more about per-frame asset transfer time.
2. Pick a **render manager** that matches the team size. A two-to-five person team can run a small purpose-built scheduler with manual priority. A larger studio needs a render-management system with concurrent submission, dependency resolution, priority queues, license arbitration, retry policies, and historical reporting. Whatever the choice, every submission goes through the manager; no one ever copies a scene file to a node and starts the renderer directly. The manager is the only honest record of what was rendered, when, by whom, and from which inputs.
3. Define **submission as a pipeline action**, not a user action. A submission packages the scene, captures dependencies, validates inputs, assigns a priority class, and writes a manifest. The artist clicks one button and answers a small number of questions (frame range, priority class, comment); the pipeline does the rest. Encourage the use of a submission template per shot — a saved bundle of settings that the lighter modifies only when something is genuinely different.
4. Treat **dependency capture** as the single most important step. A render fails most often because something the scene referenced is missing or stale on the farm node — a texture path that points at a workstation drive, a cache that lives in a user's home directory, a reference to a publish version that has since been bumped. The submission scans the scene, resolves every external reference, copies or links the referenced files into the farm-visible storage, and rewrites paths to the resolved location. Anything that cannot be resolved fails the submission, not the render.
5. Use **content-addressed storage** for the resolved dependencies where possible. Storing dependencies keyed by content hash means a re-submission with no changes touches no new bytes; a re-submission with one texture changed touches only the changed texture; an archived job is reproducible from its manifest and the content-addressed store. The naming scheme makes it impossible to silently overwrite a dependency another job depends on.
6. Choose between **packaged scenes and referenced scenes**. A packaged scene is a self-contained directory containing every dependency the render needs; a referenced scene is a small scene description that pulls dependencies from network storage. Packaged scenes are robust against storage outages and cleaner for archival; referenced scenes save disk space and re-render faster after small changes. The typical pattern: referenced scenes for active production, packaged scenes for archival and for cloud burst where the farm cannot see the production storage.
7. Validate the scene before it leaves the submission step. Required checks: every external reference resolved; renderer matches the scene's required renderer version; output directory exists and is writable; chosen frame range falls within the scene's animated range; the scene's lighting AOV list matches the project's expected list; no in-scene errors that would block the renderer at start. Fail submission on validation errors and report them inline; do not let the artist submit a job that will fail in 90 seconds on the farm node.
8. Distribute **frames as the unit of work**, not scenes. Each frame is a separate task assigned to a separate node; nodes are interchangeable. This pattern parallelizes the render across the available pool and lets the manager re-assign individual frames on node failure. Long single-frame renders (stills, hero frames) can be split by tile if the renderer supports it; without tile support, single-frame stills sit on one machine and accept the parallelism limit.
9. Design **priority classes** before contention happens. A workable set: hero (highest priority, preempts other jobs), sequence (normal production priority), dailies (a daily deadline class that runs ahead of regular sequence work for a fixed window), R&D (low priority, runs when nothing else needs slots), and archive rebuild (lowest priority, runs only on idle slots). Each class has a fair-share allocation of the farm so that priority does not starve the lower classes entirely; without fair-share allocation, "everything is hero" devolves and the priority system loses meaning.
10. Budget **renderer and plugin licenses** explicitly. A farm with one hundred slots and twenty renderer licenses cannot run more than twenty render tasks concurrently regardless of slot availability. The render manager tracks license consumption and refuses to dispatch a task that would exceed the license count. Plugin licenses (procedural geometry, fur/hair, atmospherics) are usually the more constrained resource than the renderer itself; track each plugin's license budget separately. Build a dashboard that shows current license utilization so the producer can see whether the bottleneck is hardware or licensing.
11. Plan the **memory and core budget per task**. Some scenes need 64 GiB of RAM and 32 cores; others need 8 GiB and any free core. The submission step tags each task with memory and core requirements based on the scene's bounding profile; the manager dispatches tasks only to nodes that match. Mis-tagging is expensive: a heavy task dispatched to a small node OOMs and re-queues, taking the slot down for a recovery cycle.
12. Establish a **retry policy** that distinguishes transient from terminal failures. Transient failures (a node lost the network for 30 seconds, a license check timed out, the manager dropped a heartbeat) deserve automatic retry on a different node with exponential backoff. Terminal failures (a missing texture, a scene-validation error, a renderer crash with a known signature) deserve immediate task-fail and a notification to the artist. Re-trying a terminal failure forever burns farm hours and hides the underlying problem; retrying a transient failure once recovers the loss.
13. Detect **silent corruption** and **incomplete output**. A frame that wrote to disk but is half-black, NaN-laced, or under-sampled is worse than a frame that did not write at all — the manager thinks it succeeded. Add an output-verification step: a small process that reads the rendered file, checks dimensions, checks for stuck pixels, checks AOV completeness against the scene's expected AOV list, and fails the task if anything is wrong. The cost is a few seconds per frame; the alternative is the compositor discovering the problem in dailies.
14. Set up **alerting and dashboards** for the producer, not just the technical director. Producer-facing dashboards show: per-shot percent complete, estimated time to completion at current farm utilization, per-class fair-share consumption, license utilization, and the queue of jobs awaiting submission validation. The technical director sees node health, failure rates per node, network throughput, and storage I/O. Each role gets the view they need; no role has to dig through logs to answer a question they should be able to glance at a screen for.
15. Plan **dailies as a scheduled deadline**, not a hope. The dailies window is the fixed time before review at which all frames intended for review must be complete. The render manager pulls forward dailies-priority jobs into that window and runs them ahead of regular sequence work; the producer signs off on the dailies list the day before. A job that misses the dailies window does not delay review; it slips to the next day's review with an explicit note rather than holding the entire team while one shot finishes.
16. Build a **failure runbook**. The runbook lists the most common failure modes and the prescribed recovery action: missing texture (re-validate dependencies, re-submit); license starvation (raise license cap or lower fair-share for noncritical classes); node OOM (re-tag job memory requirements, re-submit); silent corruption (audit recent renderer or plugin upgrade, rebuild output verification rules); storage full (purge old caches by policy). The runbook is the artifact that lets a junior pipeline engineer keep the farm healthy without paging the technical director for every issue.
17. Archive **the manifest plus the content-addressed store** at sequence completion. The manifest names every job, its inputs by content hash, the renderer version, the plugin versions, the priority class, the slot/license consumption, the per-frame output paths, and the timestamps. With the manifest and the store, any frame can be rebuilt at any point in the future. Without the manifest, the archive is a pile of files that cannot be re-rendered. Treat the manifest as the index of record; back it up separately and verify the backup periodically.
18. Plan **archive cost and retention**. Hot storage (the live production NAS) is fast and expensive; warm storage (slower disk arrays, cheap NAS) is affordable; cold storage (tape, cloud cold tiers, deep archive) is cheap per gigabyte and slow to recover. A typical retention policy: hot for the duration of active production plus one month; warm for one year after delivery; cold for the legal retention period. Producer signs off on retention class per project; the pipeline executes the migration on schedule.
19. Verify the **archive is recoverable** before trusting it. Pick a randomly selected shot from a completed project, recover the manifest, restore the content-addressed dependencies, resubmit the job, render one frame, and compare to the archived frame pixel-by-pixel. If it matches, the archive works. If it does not, find the gap (missing plugin version, missing license, missing renderer version, missing dependency) and fix the archival process before the next project. An untested archive is folklore, not insurance.

- Scene complexity profile: heaviest expected memory/IO footprints.
- Priority class needs.
- Recovery tolerance.

## Outputs

- A farm workflow document covering submission, dependency capture, distribution, retry, and verification.
- A priority and license policy with class definitions and budgets.
- A failure-recovery runbook with thresholds and prescribed actions.
- An archival plan covering manifest, content-addressed store, retention class, and recovery verification.

## Examples

**Small studio, thirty workstations doubling as render nodes, owned hardware.** Manager: a small purpose-built scheduler running on the file server. Submission: a single-button submit from the DCC tools, with dependency-capture rewriting paths to a content-addressed store on the production NAS. Priority classes: hero, sequence, dailies (window from 06:00 to 09:00), R&D, archive. Licenses: ten renderer licenses, six fur-plugin licenses; manager refuses dispatches that would exceed. Retry policy: three transient retries with exponential backoff; one terminal retry only after artist sign-off. Output verification: dimensions, NaN check, AOV completeness. Archival: manifest plus content-addressed store committed to NAS at shot completion; one frame per shot re-rendered from the archive at sequence wrap to verify integrity.

**Mid-sized studio with hybrid owned-plus-cloud farm.** Manager: a render-management system with cloud burst integration. Submission packages scenes for cloud burst; references scenes for on-prem nodes. Priority classes: hero (preempts), sequence, dailies, R&D, burst-only (runs in cloud only when on-prem queue is saturated). Licenses: distinct license pools for on-prem and cloud, with cloud licenses metered hourly. Retry policy: cloud failures retry on a different cloud region; persistent cloud failure falls back to on-prem queue. Output verification: cloud frames re-validated on download to on-prem storage; a checksum mismatch fails the task and re-renders.

**Solo generalist managing one workstation plus three older machines.** Manager: a lightweight queue script — overkill on a full render-management product, but disciplined enough to fail cleanly. Submission: artist verifies dependencies are on a shared drive, hits submit, gets a job-id back. Priority classes: only two — current shot, everything else. Licenses: single seat of renderer; tasks dispatch one at a time to one machine, with the others running plugin-free shots when concurrent rendering is possible. Retry: one retry, then the job halts and notifies. Output verification: file-size sanity check plus NaN scan. Archival: at project end, the entire project directory (already small) is zipped, hashed, and committed to two physically separate backup locations.

## Limitations

- This skill assumes a render manager exists and can be operated; it does not prescribe a specific manager or guarantee any specific manager's feature set.
- License-budgeting strategies depend on the licensing model of the chosen renderer and plugins; floating-license pools, node-locked licenses, and per-machine-per-day licensing each require different policies.
- Cloud burst introduces network-transfer-time considerations that this skill names but does not enumerate in detail; transfer time can dominate render time for some scenes and must be measured per project.
- This skill does not address GPU-renderer specifics around VRAM constraints, driver lock-in, or out-of-core texture streaming, all of which can be the primary cost driver on GPU farms.
- Archive recoverability requires the renderer and plugin versions used at production time to remain runnable in the future. Vendor end-of-life for a renderer or plugin can break archival recoverability; track vendor lifecycles in the archival plan.
