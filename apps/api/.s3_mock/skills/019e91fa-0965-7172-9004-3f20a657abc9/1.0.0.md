# Firmware Architecture Reviewer

## When to use

Use this skill when an embedded engineer asks for a structured review of a firmware architecture — typically before tape-out of a hardware revision, before a safety-case submission, or in response to instability symptoms (random resets, missed deadlines, heap exhaustion, sporadic sensor dropouts).

Typical triggers:

- "We adopted FreeRTOS / Zephyr / NuttX / Mbed and want a second pair of eyes on the task layout."
- "Our product fails certification or stability testing intermittently — we suspect priority inversion or ISR overrun."
- "We're moving from bare-metal to RTOS and need to lock the design before writing code."
- "We need an audit checklist before a safety review under ISO 26262 / IEC 62304 / DO-178C / IEC 61508."

This skill produces a written architecture review — not code, not a patch. It surfaces risks, points to permissively licensed reference patterns, and proposes concrete remediations.

**Safety disclaimer (mandatory):** This skill produces methodology guidance. Embedded software defects can cause physical harm in safety-critical contexts. All outputs must be reviewed by qualified embedded engineers and, where applicable, validated against the safety standard governing the deployment (ISO 26262 automotive, IEC 62304 medical, DO-178C aerospace, IEC 61508 industrial). Treat this report as a starting point for human review — never as a release gate.

## How to apply

Follow the steps in order. Each step asks one question, names the failure mode it catches, and records a verdict (pass / caution / fail) with a citation to the input.

### Step 1 — Establish the timing envelope

Before judging the design, fix the numbers it is being judged against.

- **Hard deadlines.** List every periodic or sporadic task with its deadline. A deadline miss must produce a defined, safe behavior — never an undefined one. Mark each task: hard (deadline miss = hazard), firm (miss = degraded function), soft (miss = quality-of-service hit).
- **Worst-case execution time (WCET).** Demand a WCET number for every hard-deadline task. "We measured average" is not acceptable. WCET should be measured with caches/branch-predictors cold and interrupts allowed.
- **Tick rate.** RTOS tick should be the slowest rate that gives acceptable wake-jitter for the highest-frequency periodic task. Higher tick rates inflate context-switch overhead and power. Document the choice.
- **Interrupt budget.** Sum the per-event ISR cost times the worst-case event rate for every interrupt source. The total must leave at least 30–40 % CPU headroom on the slowest CPU bin variant you ship.

If any of these numbers are missing, stop and flag "untestable design" before continuing.

### Step 2 — Review RTOS configuration

Walk the RTOS configuration file (`FreeRTOSConfig.h`, `prj.conf` / Kconfig for Zephyr, `nuttx/.config` for NuttX, `mbed_app.json` for Mbed):

- **Preemption.** Confirm fully preemptive scheduling unless you have a documented reason for cooperative or tickless. Cooperative scheduling on hard real-time loads is a red flag.
- **Tickless / low-power idle.** Required for battery-powered designs. Verify the tickless implementation accounts for peripheral wake sources and that no task uses `busy-wait` polling.
- **Heap scheme (FreeRTOS).** `heap_4` is the safe default for most products; `heap_5` for multi-region SRAM; never `heap_3` (just wraps `malloc`); avoid `heap_2` (no coalescing → fragmentation). For Zephyr, prefer `k_heap` over `k_mem_pool`; for hard real-time paths, use `k_mem_slab` (fixed-block).
- **Static vs dynamic allocation.** Safety-critical tasks must be statically allocated (FreeRTOS `configSUPPORT_STATIC_ALLOCATION=1`, Zephyr static thread macros). Dynamic allocation after init must be banned by lint rule or static analyzer.
- **Stack overflow checking.** Enable runtime checking (`configCHECK_FOR_STACK_OVERFLOW=2`, Zephyr `CONFIG_STACK_SENTINEL` plus `CONFIG_HW_STACK_PROTECTION`). MPU-backed protection is mandatory for hard real-time or safety contexts.
- **Assertions.** Build with assertions enabled in development and at least with a fault-handler trap in production. A silently swallowed assert violates traceability requirements in every safety standard listed in the disclaimer.

Record each finding with the line of the config file and the failure mode it prevents.

### Step 3 — Audit task priorities and rate-monotonic ordering

Tabulate every task: name, period (or sporadic trigger), deadline, WCET, priority, stack size.

- **Rate-monotonic ordering.** For periodic tasks with deadlines equal to periods, higher rate → higher priority. Any deviation must be justified in writing.
- **Priority bands.** Reserve a priority band for the idle/diagnostics tasks, a band for soft-real-time work, a band for hard-real-time work, and the highest band for the watchdog kicker. Document the bands.
- **ISR-to-task signaling.** ISRs must defer work via task notifications, queues, or semaphores. ISRs must never call blocking APIs or take mutexes. Verify each ISR uses the FromISR variants or the equivalent in your RTOS.
- **Priority ceiling / inheritance.** Every mutex shared between tasks at different priorities must use priority inheritance (FreeRTOS mutexes, Zephyr `k_mutex`). Plain binary semaphores for mutual exclusion are a defect — flag them.
- **Avoid task explosion.** More than ~20 tasks on a small MCU usually indicates a missing event loop or state machine. Each extra task costs stack and increases scheduler overhead.

Forbidden patterns: priority shared between two periodic tasks with overlapping deadlines, ISR doing more than ~10 µs of work on a Cortex-M-class part, blocking call inside a critical section.

### Step 4 — Interrupt and latency budget

Build an interrupt table: vector, peak rate, ISR worst-case duration, deferred-work mechanism, priority (NVIC or equivalent).

- **ISR-to-ISR preemption.** Confirm NVIC priorities give DMA-completion and timing-critical sources preemption over slower peripherals (UART, I2C control). Document the priority grouping.
- **Critical sections.** Inventory every `taskENTER_CRITICAL` / `irq_lock` / `__disable_irq`. Each occurrence must be bounded in time and justified. The longest critical section bounds worst-case interrupt latency.
- **Worst-case latency.** Compute: (longest critical section) + (highest-priority pending ISR cost) + (context save). Compare with the deadline of the most time-critical event handler. Demand a margin.
- **Shared data with ISRs.** All shared variables must be `volatile`, accessed atomically (single instruction on the target), or protected by a queue/notification. Bit-banded peripherals on Cortex-M can sometimes give atomic single-bit writes — note when this is exploited.

### Step 5 — Memory discipline

- **Stack sizing.** Every task stack should have a "high-water mark" reading from a soak test, plus 25–40 % margin. Tasks that call libc, printf, sprintf, or floating-point need substantially more headroom; flag any such task with a small stack.
- **No dynamic allocation after init.** Confirm. Search for `malloc`, `calloc`, `new`, `pvPortMalloc`, `k_malloc` outside startup. Each occurrence is a finding.
- **Memory regions and MPU.** For Cortex-M with MPU or RISC-V with PMP, verify that code is in execute-only flash, stacks are non-executable, and task stacks are MPU-isolated from each other on safety builds (FreeRTOS-MPU, Zephyr userspace, NuttX `CONFIG_BUILD_PROTECTED`).
- **DMA buffers.** Must be in non-cached or coherent memory regions, aligned to cache-line boundaries on Cortex-M7/A-class, and lifetime-checked against the DMA transaction duration.
- **Cache coherency.** Wherever the CPU and a DMA-capable peripheral share a buffer, insert cache invalidate before peripheral-to-CPU transfer and cache clean before CPU-to-peripheral. Missing maintenance ops are a frequent silent corruption source.

### Step 6 — Watchdog and recovery discipline

The watchdog story is the single most reliable predictor of field stability.

- **Independent watchdog.** Use the silicon's independent watchdog (IWDG on STM32, WWDG-not-alone) running off a dedicated low-power oscillator. A software-only timer-based watchdog is not enough.
- **Single kicker task.** Exactly one task should kick the watchdog. Every other task must check in with the kicker by setting a per-task "alive" bit within its deadline window. The kicker refuses to pet the dog if any required task missed its window.
- **Window watchdog.** Where available, use a windowed watchdog so an over-eager kicker that's stuck in a tight loop also faults.
- **Brown-out detection.** Enable the silicon brown-out reset at a voltage above the lowest spec at which peripherals (especially Flash and external memory) misbehave. Logging brown-out events at boot is mandatory.
- **Reset-cause logging.** Read and log the reset-cause register on every boot. A device that resets and forgets why has no path to root-causing field failures.
- **Recovery behavior.** After watchdog reset, the firmware must come up in a known-safe state (outputs commanded off, motors freewheeling or short-braked per design, communication links re-established with sequence numbers reset). Define and review this state explicitly.

### Step 7 — Fault containment and degraded modes

- **Hard-fault handler.** Must capture the fault frame (R0–R3, R12, LR, PC, xPSR, plus configurable fault status registers on Cortex-M), persist it to non-volatile storage if possible, then reset. The handler itself must use the minimum stack and not call printf.
- **Assert handler.** Same constraint. Distinguish development assertions (halt, blink, debugger trap) from production assertions (log + reset).
- **Degraded operating modes.** For each major failure (sensor lost, comms lost, secondary CPU lost, battery low), define a degraded mode. Each mode has an entry condition, allowed actions, and an exit condition. Black-and-white "OK / dead" is a smell.
- **Health monitoring.** A background task should monitor task heartbeat, free heap (if any), CPU load, and key sensor sanity. Findings get logged and, on threshold breach, trigger the degraded mode.

### Step 8 — Coding-standard and tooling check

Verify the project enforces a relevant subset of:

- **MISRA C:2012** (automotive / safety-critical). Note that MISRA itself is not OSS; the rules can be enforced by tools like cppcheck (free, GPL) used for analysis only, or commercial linters. Document which subset is enforced and the deviation policy.
- **CERT C** for security-sensitive code paths.
- **Static analysis** in CI: cppcheck, clang-tidy with embedded rules, scan-build, or commercial equivalents.
- **Compiler hardening.** `-Wall -Wextra -Werror`, `-Wstack-usage`, `-fstack-protector-strong` where the runtime supports it, link-time stack-usage reporting.
- **No undefined behavior.** UBSan on host-side unit tests; structured cast and union audits in target code.

### Step 9 — Reference patterns from permissive sources

For each major risk area, point the reviewee at a permissively licensed reference. Verify license before adopting; the URL list at the bottom of this skill cites only MIT / Apache / BSD projects.

- Static-allocation patterns: FreeRTOS Kernel reference and Embedded-Artistry libraries.
- Tickless and low-power patterns: Zephyr power-management documentation.
- MPU-isolated tasks: FreeRTOS-MPU port and Zephyr userspace.
- Watchdog kicker pattern: Zephyr task watchdog subsystem.
- Hard-fault decoders: Embedded-Artistry fault frame helpers and Apache NuttX crash-dump.

### Step 10 — Produce the report

Output four sections:

1. **Findings table.** ID, severity (blocker / major / minor / info), area (config / scheduling / ISR / memory / watchdog / fault / standards), one-line description, evidence (file or input line), recommendation.
2. **Prioritized fix list.** Top 5 actions in order, each with effort estimate (hours / days / weeks).
3. **Open questions.** What you still need from the reviewee before another pass.
4. **Reference patterns.** Permissive-license URLs you'd point them at, paired to findings.

## Inputs

- **Target description.** MCU, core, clock, memory map, peripherals, power profile.
- **RTOS configuration.** Config file or summary, plus tick rate, heap scheme, IPC primitives.
- **Task inventory.** Name, purpose, period, priority, stack, blocking calls, shared resources.
- **Safety context.** Applicable standard and integrity level, or "none — commercial."

## Examples

> "Review our FreeRTOS layout: STM32H7, 8 tasks at priorities 1–7, 1 ms tick, heap_4, no MPU, software watchdog only, mixed mutex and semaphore use, occasional resets in 24 h soak."

Expected findings (abridged):

- **Blocker.** Software-only watchdog. Move to IWDG with single kicker task and per-task heartbeat bits.
- **Blocker.** Heap_4 with dynamic allocations during run-time (search results in input). Convert hot-path allocations to static or pool.
- **Major.** Two tasks at the same priority both periodic with overlapping periods → unbounded jitter. Re-rank rate-monotonically.
- **Major.** Mutex use mixed with binary-semaphore use for mutual exclusion. Replace exclusion semaphores with mutexes for priority inheritance.
- **Major.** No MPU. On H7 with 1 MB SRAM and 8 stacks, MPU isolation is cheap; enable FreeRTOS-MPU.
- **Minor.** Tick rate 1 ms unjustified; slowest periodic task is 20 Hz. Consider 100 Hz tick to halve scheduler overhead.
- **Info.** Soak test has no reset-cause logging; cannot tell whether resets are watchdog, brown-out, or hard fault. Add reset-cause capture as the first remediation so the next round of debugging is informed.

## Limitations

- This skill does not perform line-level code review. It reviews architecture and configuration.
- It cannot certify compliance with ISO 26262, IEC 62304, DO-178C, or IEC 61508 — only flag obvious gaps relative to those standards.
- It assumes a Cortex-M or comparable MCU. Cortex-A/Linux-class systems and AUTOSAR Classic ECUs require additional specialized review.
- Numerical guidance (e.g., 30–40 % CPU headroom) is rule-of-thumb; project-specific budgets supersede it.
- Always re-verify the license of any vendored reference code before shipping.
