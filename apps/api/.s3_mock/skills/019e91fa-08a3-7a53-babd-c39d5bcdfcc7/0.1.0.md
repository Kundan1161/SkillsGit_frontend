# ELN Instrument Integration Architect

> **Mandatory disclaimer.** This skill produces methodology guidance for
> integrating laboratory instruments and analysis software with an
> electronic lab notebook. Regulated environments (GLP, GMP, FDA 21
> CFR Part 11, EU Annex 11, ISO 17025) impose specific data-integrity,
> audit-trail, and electronic-signature requirements that apply to
> instrument data and its handling. Compliance for any regulated
> workflow must be reviewed by qualified Quality and Regulatory staff.
> Use the output as an architectural starting point, not as a validated
> design.

## When to use

Invoke this skill when a team needs instrument and analysis-tool data
to land in the lab notebook in a way that scientists, IT, and (later)
auditors can all live with. Typical situations:

- A notebook is in place but instrument files still live on shared
  drives, USB sticks, or vendor PCs, and the link back to an experiment
  is a copy-pasted file path.
- A new instrument fleet is being procured and the team wants the
  integration story decided before the boxes arrive.
- The current "integration" is a custom script per instrument that
  breaks on every vendor update.
- An audit observation has flagged that raw data and processed data
  cannot be distinguished or that lineage is unrecoverable.

This skill assumes the notebook itself exists and has at least a
minimum ingest API (create attachment, link to experiment). It does not
re-architect the notebook; it designs the integration layer that
surrounds it.

## How to apply

Work through the seven passes below in order. The final deliverable is
a phased plan, not a single design dump — instrument integrations are
almost always rolled out incrementally.

### 1. Inventory the instruments and their output shape

For each instrument or analysis software in scope, capture:

- **Output type** — single CSV, structured XML, vendor-proprietary
  binary, image, video, or a folder of files that must be treated as
  one unit.
- **Output location** — local disk on the instrument PC, network share,
  vendor-cloud bucket, or accessible only via a vendor SDK.
- **Volume** — files per day, average and peak size, retention on the
  instrument PC.
- **Naming convention** — how scientists or the instrument software
  encode experiment, sample, or run identifiers in filenames or paths.
- **Metadata richness** — what useful fields live inside the file
  (acquisition timestamp, operator, method, calibration id) versus
  what must be carried in alongside it.
- **Mutability** — whether the instrument software can modify a file
  after first write (post-acquisition reprocessing). This single
  question shapes the integrity model.

Classify each instrument into one of three integration tiers:

- **Tier A — Drop and link.** Files appear in a defined location; the
  integration moves them into managed storage and links them to an
  experiment. No deep parsing.
- **Tier B — Parse and surface.** Files are parsed into a structured
  measurement record (peak table, kinetic curve, plate readouts) that
  the notebook can display and query.
- **Tier C — SDK-driven.** Vendor SDK is required to extract data;
  files alone are insufficient.

Start with Tier A coverage for everything, then add Tier B for the
instruments whose data is queried often, then Tier C only where the
scientific case justifies the maintenance burden.

### 2. Choose the ingestion topology

Pick one topology, document why, and apply it consistently.

- **Watcher-at-instrument.** A small agent runs on the instrument PC,
  watches a defined output directory, and pushes new files to the
  ingestion service. Best when network shares are unreliable or
  vendor PCs are isolated. Cost is fleet management of the agent.
- **Watcher-at-share.** A central service watches a network share where
  instruments deposit data. Cheaper to deploy; weaker about catching
  files that never make it to the share.
- **Pull from vendor cloud.** A scheduled job pulls from the vendor's
  cloud API. Necessary for cloud-only instruments; introduces a
  vendor-availability dependency.
- **Manual upload with assist.** A scientist drops files into a web
  uploader that calls the same ingestion service. This is not a
  fallback; it is the always-on path for instruments that will never
  be automated. Treat it as first-class.

In all topologies, the ingestion service is one component with one
contract. Watchers and uploaders are clients of it. Do not let each
instrument grow its own end-to-end path.

### 3. Design the per-instrument adapter

Each instrument or analysis tool gets one adapter. An adapter has a
defined shape:

- **Detect** — identify that a file (or a folder) belongs to this
  instrument and is complete. Completeness checks include: a sentinel
  marker file, a stable file size for a defined idle period, or an
  explicit "run done" signal from the instrument software.
- **Stage** — copy or move the bytes into a staging area under a
  content-addressed name (sha-256). The staging area is on the same
  storage class as the eventual managed store, so promotion is a
  metadata operation, not a re-upload.
- **Identify** — extract the experiment, sample, or run identifier
  using the agreed naming convention and a structured rule. If
  identification fails, the file goes to a *quarantine* queue with a
  clear reason; it is never silently linked.
- **Parse** — for Tier B/C adapters, run the structured extractor and
  emit a measurement record alongside the raw file. Parsing never
  modifies the raw file.
- **Submit** — call the notebook's ingest API to register the
  attachment, link it to the target experiment or sample, attach the
  measurement record if any, and record provenance.

Adapters are stateless beyond their staging area. Crashes restart from
the queue. Adapters log their decisions to the integration service's
own audit log.

### 4. Separate raw and processed data, and preserve lineage

The integrity rule is non-negotiable: the raw file as it left the
instrument and the processed result derived from it are different
artefacts, stored separately, with a recorded relationship.

- **Raw layer.** Files exactly as the instrument produced them, stored
  by content hash, write-once at the storage layer where possible. The
  notebook reference to a raw file is via the hash, never the path.
- **Processed layer.** Re-analysed data, integrated peaks, gated
  populations, normalised plate values. Each processed artefact
  records: its parent raw artefact hash, the tool and version used to
  produce it, the parameter set, and the user or service account that
  ran the processing.
- **Re-processing is additive.** Re-integrating a chromatogram does not
  overwrite the previous processed artefact; it adds a new processed
  artefact pointing to the same raw parent, with a reason captured.
- **Lineage graph.** The notebook exposes the lineage as a graph:
  experiment -> sample -> raw artefact -> processed artefact(s) ->
  conclusion in the experiment body. The graph is queryable.

For instruments where the vendor software *does* modify files
post-acquisition (a common reality), capture the first-seen version on
ingestion and treat the vendor in-place edits as a separate processed
artefact, not as the raw file. Document this loudly; it is the most
common source of integrity surprises.

### 5. Handle failure modes explicitly

Instrument integrations fail. Plan for it.

- **File never arrives.** Watcher detects gap (the instrument ran but
  no file was deposited) and raises a ticket against the run, not just
  a system alert.
- **File arrives mangled.** Adapter cannot parse; raw file is preserved
  in quarantine with the error; scientist can review and request
  reprocessing once corrected.
- **Identifier cannot be resolved.** Run is unlinked; the file sits in
  the unlinked queue with a clear UI surface so scientists can attach
  it before it ages out. Aging out is a notification, not a deletion.
- **Vendor SDK breaks on upgrade.** Adapter version-pinned to the SDK
  it was tested against; upgrade is a change-controlled event with a
  test corpus replay.
- **Storage backend is unavailable.** Watcher buffers locally, with a
  bounded queue and a high-priority alert when the buffer crosses a
  threshold.
- **Wrong experiment linked.** Scientist can request a relink; the
  relink is an audited event, not a silent edit of the prior link.

Every failure mode has a named owner: the scientist, the integration
team, or the instrument vendor. Document the routing.

### 6. Define the contract with the notebook

The notebook needs only a small, stable API surface from the
integration layer:

- `register_artefact(hash, size, mime, source_instrument, captured_at,
  provenance) -> artefact_id`
- `link_artefact(artefact_id, experiment_id | sample_id, link_kind,
  by_user_or_service)`
- `add_measurement(artefact_id, structured_payload, parser_id,
  parser_version)`
- `add_processed(parent_artefact_id, hash, tool, tool_version, params,
  by_user)`
- `relink(artefact_id, new_target, reason, by_user)` — audited.

Every call is authenticated, every call writes audit events on the
notebook side, every call is idempotent on the artefact hash. The
ingestion service never writes to the experiment body text directly.

### 7. Phase the rollout

Trying to integrate everything at once almost always fails. Sequence:

1. **Phase 1 — Common path.** Ingestion service, manual uploader, audit
   plumbing, lineage graph, one Tier A adapter for the highest-volume
   instrument.
2. **Phase 2 — Tier A coverage.** Drop-and-link adapters for every
   remaining instrument that can deposit to a watched location.
3. **Phase 3 — Tier B selectively.** Parsers for the instruments whose
   data scientists query in the notebook (plate readers, chromatography
   systems, flow cytometers). Each parser ships with a frozen test
   corpus.
4. **Phase 4 — Tier C if warranted.** Vendor-SDK adapters for
   instruments where the scientific case justifies the maintenance
   burden, with a clear deprecation plan for SDK-version sunsets.

At each phase boundary, run an integrity drill: pick a recent run,
trace it from raw bytes on the instrument to the lineage graph in the
notebook, and confirm the path is complete.

## Inputs

- Instrument inventory with output shapes, volumes, locations, and
  naming conventions.
- A description of the existing notebook ingestion surface, if any.
- Constraints: which networks instruments live on, which vendors permit
  agents on their PCs, what storage classes are available, what the
  regulated trajectory looks like.

## Outputs

A markdown integration plan containing:

1. Instrument inventory with tier classification per device.
2. Chosen ingestion topology with rationale and explicit trade-offs.
3. Per-tier adapter design and a worked example for one device of each
   tier.
4. Raw / processed separation policy with the lineage graph shape.
5. Failure-mode register with owners and routing.
6. Contract with the notebook (ingest API shape, audit and idempotency
   expectations).
7. Phased rollout plan with the integrity drill at each phase boundary.

## Examples

**Prompt.** "Notebook is in. Two plate readers (CSV out, network share),
three HPLCs (vendor-proprietary, instrument-PC only), one flow
cytometer (folder of FCS files, network share). Need scientists to
stop emailing files."

**Expected output shape.** Plate readers and flow cytometer become Tier
B with watchers on the share; HPLCs start at Tier A via a small
on-PC agent because the vendor PC is air-gapped on a lab subnet; manual
uploader stays available for ad-hoc data. Identifiers are extracted
from filename templates with a quarantine queue for misnamed files.
Raw FCS folders ingested as immutable units; gated populations stored
as processed artefacts that reference the raw folder hash. The HPLC
in-place reprocessing case is called out as the highest integrity risk
and treated by capturing first-seen state and treating subsequent
in-place edits as a separate processed artefact with a reason.

## Limitations

- Vendor SDK behaviour, licensing, and stability change frequently.
  Tier C adapters require continuing investment that this plan can
  describe but cannot eliminate.
- This skill does not select specific parsing libraries. Parser
  selection depends on scientific accuracy requirements that must be
  validated against a per-instrument test corpus.
- For regulated work, instrument data integrity is itself subject to
  audit (ALCOA+ principles, audit-trail expectations on the instrument
  software). The integration architecture supports those expectations
  but does not by itself satisfy them. Qualified Quality and
  Regulatory review is required.
- The skill assumes a notebook with a usable ingest API. Where that
  API is missing, an earlier architecture step is needed; see the ELN
  System Architect skill in this niche.

## Sources reviewed

Methodology informed by a survey of widely deployed open-source ELN
systems and adjacent lab-data tooling. No prose, code, or schema was
copied; the systems below were read to triangulate the common
integration patterns.

- eLabFTW project repository (AGPL-3) — community integrations
  (instrument client libraries, language bindings) informed the
  adapter-as-client pattern.
- SciNote ELN repository (MPL-2.0) — informed the project / experiment
  / task hierarchy used as ingestion targets.
- Chemotion ELN repository (AGPL-3) — informed the analyses-attached-
  to-samples pattern and the raw-versus-derived distinction common in
  chemistry workflows.
- RSpace open-source platform repository (AGPL-3) — informed the
  notebook-plus-inventory coupling that ingestion must respect.
- Indigo ELN v2 repository (MIT) — informed the separation of a
  chemical registration service from the notebook core, which
  generalises to separating instrument adapters from the notebook.
- Public ALCOA+ data integrity guidance (regulatory) — used to frame
  the raw versus processed separation and the lineage requirement.
