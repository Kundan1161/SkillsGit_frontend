# Cloudflare Email Service

## When to use

Use this skill when sending transactional email or routing incoming messages from Cloudflare Workers, Agents SDK, or external applications. Not for marketing or bulk sends.

## How to apply

Prefer retrieval over pre-training — the service launched in 2025 and APIs are evolving. Use the binding shape for Worker-internal sends, and the REST API for external applications. Watch the naming differences (camelCase vs snake_case) between the two paths.

## Core Purpose

Cloudflare Email Service enables sending transactional emails and routing incoming messages directly within the Cloudflare platform, supporting integration with Workers, Agents SDK, and external applications.

## Quick Setup (Workers Binding)

Add to `wrangler.jsonc`:

```jsonc
{
  "send_email": [{ "name": "EMAIL" }]
}
```

Then in the Worker:

```typescript
await env.EMAIL.send({
  to: "user@example.com",
  from: { email: "noreply@yourdomain.com", name: "Your App" },
  subject: "Hello",
  html: "<p>Hello</p>",
  text: "Hello"
});
```

## Prerequisites

1. **Domain onboarding** — `npx wrangler email sending enable yourdomain.com`
2. **Binding configured** in `wrangler.jsonc`
3. **`postal-mime`** dependency only required for parsing *received* emails

## Workers Binding vs REST API

| | Workers binding | REST API |
|---|---|---|
| `from` shape | `{ email: "...", name: "..." }` | `{ address: "...", name: "..." }` |
| Reply-to field | `replyTo` | `reply_to` |
| Auth | bound automatically | Bearer token |
| Use case | Worker-internal | External apps |

## Common Pitfalls

- **Unverified domains** — sending fails silently or bounces.
- **Missing text alternative** — providing only `html` hurts deliverability; always include `text`.
- **Hardcoded API tokens** — use `wrangler secret put` instead.
- **Wrong field naming** between binding and REST API.
