# LLM Eval Harness Designer

## When to use

Use this skill when a developer is shipping or already running an LLM-powered feature and needs a real evaluation pipeline — not just spot-checking. The skill produces a written design for the eval harness, covering the test set, the metric stack, an LLM-as-judge with calibration, the human-review loop that keeps the judge honest, the regression thresholds, and how the whole thing plugs into CI.

The skill applies to a wide range of LLM features: chatbots, structured-output generators (SQL, JSON, code), summarisers, classifiers, agentic workflows, retrieval-augmented generation (RAG) systems, and assistant-style features where the output is free text. It assumes the user already has *something* deployed or close to it — the harness exists to keep that thing from quietly getting worse.

The skill is not for choosing between candidate models on a single benchmark — for that, a smaller bake-off plan from the experiment-design skill is more appropriate. Nor is the skill for safety red-teaming alone — it includes safety probes as one slice of the harness, but a dedicated red-team exercise is a separate practice.

The skill does not write the prompts that get evaluated and does not write the feature itself. It writes the *test* of the feature.

## How to apply

The skill executes a deterministic eleven-stage pipeline. Each stage produces a section of the deliverable.

### Stage 1 — Reframe the feature as an evaluatable contract

1. Read `feature_description` and rewrite it as a one-paragraph "evaluation contract": the inputs the feature accepts, the outputs it must produce, the things the output must always do, the things it must never do, and the user-visible criteria for "good". If any clause is fuzzy, ask before proceeding.
2. Decompose "good" into orthogonal sub-qualities. For a customer-support chatbot the sub-qualities might be: factual correctness, on-policy refusal of disallowed requests, format adherence (markdown, length, structure), tone alignment, and absence of PII leakage. For a SQL generator: query correctness, schema adherence, safety (no destructive statements), and runtime cost.
3. For each sub-quality, decide whether it is binary (passes / fails), graded (1-5 rubric), or continuous (a numeric score). Mixed-type harnesses are fine; the contract just has to be explicit.
4. Mark each sub-quality as either a **gate** (must pass for the output to be acceptable at all) or an **axis** (a quality dimension that trades against others). Gates are evaluated first; axes are aggregated into the overall score.
5. Write down what "the harness exists to detect" in one sentence. The most common honest answer is: "Detect when a prompt change, a model update, or a data update silently makes the feature worse." The plan downstream should make that detectable.

### Stage 2 — Construct the test set

6. The harness needs at least three test sets, not one:
    - **Smoke set** (~30 examples): runs on every commit. Catches catastrophic regressions in seconds. Covers the most common request shape and one example per declared gate.
    - **Regression set** (~200-1000 examples): runs on every merge to main and nightly. Covers all the slices in Stage 3. Includes every previously-fixed bug as a permanent test case.
    - **Frontier set** (~50-200 examples): edge cases, adversarial prompts, jailbreak attempts, malformed inputs, multilingual probes. Runs weekly or before a release. Catches "we got lucky on the regression set" regressions.
7. Source examples from at least three places: real production logs (sampled with PII redaction), red-team-style hand-written cases, and synthesised cases generated by another LLM with manual review. A test set drawn entirely from production logs will be blind to inputs you have never seen.
8. For each example, capture: input fields exactly as the model receives them, a reference output (or rubric, or no-reference flag), the slice tags, the sub-qualities being tested, the source of the example (production log, hand-written, synthetic), and a stable example ID.
9. Pin a "freeze date" on the test set and version it. New examples go into the next version; the current frozen version is what the regression baseline is computed against. Without versioning, "the eval changed" is indistinguishable from "the model changed".
10. Treat the test set like training data: hold it in a separate repository or storage path, gate write access, log every change to it. A leaked test set is uninformative; an unintentionally-updated test set is misleading.
11. For each gate, include at least one positive and one negative example. A "no PII leakage" gate that is only tested with PII-free inputs cannot fail.

### Stage 3 — Slice the test set

12. The headline score on the test set is a single number; it hides what changed. Slices are the antidote.
13. Define slices along the dimensions the user cares about: input language, input length bucket, user segment, request category, retrieval-document recency for RAG, model version, prompt version, tenant. Every example carries the tags for its slices.
14. Require a minimum sample-per-slice (default 25). Below that, slice-level metrics are too noisy to be actionable. The harness must either add examples to under-represented slices or hide that slice from the dashboard.
15. Include explicit **adversarial slices**: prompt-injection attempts, off-topic requests, requests in a language the feature was not trained for, requests for disallowed content. The harness should not aggregate adversarial slices into the headline score — they get their own panel.

### Stage 4 — Pick automated metrics per sub-quality

16. **Exact-match-friendly outputs** (SQL, JSON, code, math): exact match against canonical reference, or unit-test execution where the output runs against test inputs and the metric is "tests pass". For SQL, "result-set equivalence" beats string match — two correct SQLs can differ textually.
17. **Format adherence**: a deterministic parser that returns "valid / invalid" against the format spec. If the output must be JSON, parse it. If it must include certain fields, check each. This metric is dirt-cheap and catches a large fraction of regressions before any judge runs.
18. **Reference overlap for free text**: ROUGE, BLEU, BERTScore — useful as cheap canaries but not as primary metrics for nuanced quality. Use them as guardrail metrics that should not collapse suddenly.
19. **Semantic similarity** to reference, computed with a small embedding model: more robust than ROUGE for paraphrase. Still not a primary metric for fine-grained quality.
20. **Retrieval metrics for RAG**: separate retrieval quality (recall@k, mrr, ndcg against gold passages) from generation quality (faithfulness to retrieved context, answer correctness). Combining them masks which side is broken.
21. **Faithfulness / hallucination** for RAG: a metric that decomposes the answer into claims and checks each claim against the retrieved context. This is typically judge-driven; the metric design lives in Stage 5.
22. **Refusal correctness**: a deterministic classifier (or judge) that returns whether the model correctly refused a disallowed request and correctly answered an allowed one. Both false-refusal and missed-refusal rates are reported.
23. **Safety probes**: a separate batch of inputs designed to elicit policy violations; the metric is the violation rate. Treated as a guardrail, not part of the headline.
24. **Cost and latency**: every example records tokens-in, tokens-out, judge-cost-if-any, and wall-clock time. The harness reports the p50 and p95 of each. A "quality" win that doubles latency may not be a net win.
25. Reject any metric that does not have a documented failure mode. A metric without known limitations is one that has not been tested.

### Stage 5 — Design the LLM judge

26. The LLM judge is a model that scores other model outputs against a rubric. It is reliable only when the rubric is precise and the judge is calibrated.
27. **Rubric design.** For each sub-quality being judged, write a 3-5 sentence rubric that defines what 1, 3, and 5 look like with concrete behavioural anchors. "Helpful" is not a rubric; "Directly addresses the user's question without inventing details and asks for clarification when the question is ambiguous" is a rubric. Use a fixed scale (1-5 odd-numbered scales) and avoid 1-10 (judges cluster around the centre).
28. **Pairwise vs pointwise.** When comparing two candidate prompts or models, prefer pairwise judging (which is better, A or B?) over pointwise (rate A from 1-5). Pairwise judges are more reliable because the rubric is implicit in the comparison. Use a "tie" option to avoid forcing a winner.
29. **Position bias.** Pairwise judges favour the first option presented. Always run each pair in both orders and aggregate; flag pairs where the two orders disagree.
30. **Verbosity bias.** Judges over-reward longer outputs. Either include "length is not a quality" in the rubric and verify the judge respects it on a probe set, or normalise scores against length.
31. **Style bias.** Judges over-reward outputs that share the judge's own style. Use a different model family for the judge than for the candidate when possible.
32. **Chain-of-thought.** Require the judge to produce a short explanation before the score. Explanation-first judges are measurably more accurate. The explanation is also a useful audit trail.
33. **Judge model selection.** Pick the smallest model that achieves acceptable agreement with the human gold (Stage 6). A bigger judge costs more and is not always better. Pin the judge to a specific model version; do not let the judge auto-update.
34. **Prompt structure.** The judge prompt contains: role, rubric, scoring scale, instructions to refuse to score if the output is incomplete or out-of-scope, and a strict output schema (e.g. a JSON with `score` and `explanation` fields). Parse the output deterministically and treat unparseable judge outputs as test failures.
35. **No leakage.** The judge prompt must not include information the candidate did not have (e.g. the reference answer if the candidate did not see it). Otherwise the judge is grading "did the candidate guess the reference" not "is the output good".

### Stage 6 — Calibrate the judge against humans

36. The harness must include a **judge-calibration set**: 100-300 examples that are graded by humans against the same rubric. This is the ground truth for the judge.
37. For each calibration example, the judge runs and its score is compared against the human label. Compute Cohen's kappa or Krippendorff's alpha against the human-aggregate label. Targets: kappa > 0.6 for most production use; if kappa is below 0.4, the judge is not useful, and the rubric needs rewriting.
38. Compute agreement by slice. A judge that agrees overall but fails on a specific slice (e.g. multilingual outputs) must be flagged.
39. Use the calibration data to compute a confusion-matrix-style report: which scores does the judge confuse with which? Asymmetric confusion (judge says 5 when human says 3) is worse than symmetric noise.
40. Re-calibrate when the judge model is changed, when the rubric is changed, or quarterly. Drift in the judge model is a silent failure mode; treat the judge like a system component, not a fixed reference.
41. Maintain a **judge regression test**: a small set of pairs whose correct judgement is known. If the judge fails this set after a model upgrade, freeze the upgrade and investigate.

### Stage 7 — Human review loop

42. Automated scoring catches most regressions but cannot replace human judgement for the long tail. Plan a continuous-sampling human review:
    - **Continuous sample.** Randomly sample N production traces per day (default: 1% with a floor of 50). Surface them in a review UI with the original input, the model output, the automated scores, and the judge explanation.
    - **Disagreement queue.** Whenever the judge and a guardrail metric disagree (e.g. judge says 5 but format metric says invalid), the example goes to human review automatically.
    - **Low-confidence queue.** Whenever the judge's explanation indicates uncertainty or refuses to score, route to humans.
    - **Drift queue.** Whenever a slice's metric drops by more than the regression threshold, the affected examples go to human review.
43. Review outputs feed back into the test set: confirmed bugs become permanent regression cases; confirmed false alarms become judge calibration examples.
44. Track human-review SLA: median time-to-review per item, percentage of items reviewed within 48 hours. A human loop that nobody actually runs is theatre.
45. For sensitive content, set reviewer eligibility rules: trained moderators only, dual review on disagreements, anonymisation of inputs where feasible.

### Stage 8 — Regression thresholds and stop-the-line rules

46. For each metric in the headline, set a **regression threshold**: the maximum allowed drop versus the last green baseline. Defaults:
    - Gate metrics (correctness, refusal correctness, format adherence): zero tolerance for regression on the smoke set; small tolerance (1-2 percentage points) on the regression set.
    - Axis metrics (helpfulness, tone): regression of more than 5% relative or 0.2 absolute on a 1-5 rubric blocks merge.
    - Safety: zero tolerance for regression on the safety probe set.
    - Latency p95: 10% tolerance; cost per call: 15% tolerance.
47. Define a **stop-the-line rule**: if a gate metric regresses on the smoke set in CI, the change cannot merge. Override requires a written justification from a named approver, logged with the eval run.
48. For continuous monitoring of production (not CI), define an alerting threshold: e.g. a 7-day rolling judge score that drops below the baseline by more than the regression tolerance triggers an on-call alert.
49. Confidence intervals around the metric difference, not just the point estimate, must drive the threshold check. A 0.1-point drop with a wide CI is noise; with a tight CI it is a real regression.

### Stage 9 — CI and rollout wiring

50. The harness must run in three contexts: developer laptop (a `make eval` or `pytest` invocation that runs the smoke set), CI on every PR (smoke set as a required check; regression set as a non-blocking nightly), and shadow mode in production (the new prompt is invoked on a copy of live traffic and scored against the current production prompt).
51. PR-time eval results must be posted to the PR as a comment with: pass/fail headline, per-slice metric deltas, links to failing examples, and a link to the full report. The PR author should see the answer to "is this going to break anything?" without leaving the diff.
52. For prompt or model changes, recommend a canary rollout sequence: 1% → 5% → 25% → 100%, with the eval harness running on each canary slice and the next step gated on no regression.
53. Recommend an A/B routing layer so the harness can compare candidate versus baseline on live traffic with statistical-significance accounting. Wire shadow-mode metrics back into the same dashboard the offline eval feeds.
54. The harness writes a JSON record per eval run with run_id, code_commit, prompt_hash, model_id, test_set_version, judge_model_id, judge_prompt_hash, headline metrics, slice metrics, and the regression threshold check result. This is the artifact the team reviews in incident response.

### Stage 10 — Observability and dashboards

55. The harness produces a dashboard with: headline metric over time, per-slice metric over time, latency p50/p95, cost per call, judge-human agreement, human-review backlog, and an "examples that regressed" panel.
56. Each panel links to the underlying examples so a developer can click from a metric drop to the failing input within two clicks.
57. Long-running judges and humans introduce a delay; the dashboard must show the freshness of each metric (e.g. "judge data current as of 2 hours ago"). Stale metrics are worse than no metrics if presented without freshness.
58. Add a "champion vs challenger" comparison view: the current production prompt vs a candidate, scored on the same regression set, with significance and confidence intervals.

### Stage 11 — Compose the deliverable

59. Open with a one-paragraph "harness intent": what this harness will catch and what it will not.
60. Lay out the plan with one section per stage so the user can implement incrementally. A team that can only do Stages 1-4 today still gets value; the plan is not all-or-nothing.
61. Emit `harness_spec` (JSON) so a downstream code-generation step or a config-driven harness can pick it up.
62. End with a "What to build first" sequencing: smoke set + format checks + ten judge examples is enough to ship a v1; everything else iterates.

## Examples

**Input (placeholder):**

`feature_description`: "Customer-support chatbot that answers product questions, refuses to discuss pricing, and routes complaints to a human agent."

`failure_modes`: "Hallucinated product specs, refusing valid product questions, replying in the wrong language."

`ground_truth_availability`: "rubric_only" — there is no single canonical answer per question.

`production_volume_per_day`: 50000.

`latency_budget_ms`: 2500.

`stack_constraints`: "self-hosted only; cannot call external judge APIs."

**Plan (abbreviated):**

- Evaluation contract: input is a customer message + product context; output must answer product questions accurately, refuse pricing discussions, route complaints. Sub-qualities: correctness (axis), refusal-of-pricing (gate), complaint-detection (gate), language match (gate), helpfulness (axis), faithfulness to product docs (axis).
- Test sets: smoke 30 examples; regression 600 examples covering 8 slices (language × intent type); frontier 80 examples including prompt-injection attempts and edge-case product questions.
- Slices: language (en/es/fr/de/ja), intent (info / refusal / complaint / off-topic), product category (5 categories).
- Automated metrics: format (must be JSON with `text` and `route`), language-detection match, refusal correctness (rule-based classifier on output), retrieval recall@3 against product-doc gold passages.
- LLM judge: pairwise for the "helpfulness" axis, pointwise 1-5 for "faithfulness". Self-hosted judge model (since external is disallowed); pinned to a specific snapshot.
- Calibration set: 200 examples graded by two human reviewers each; target kappa 0.6.
- Human loop: 1% of production sampled daily for review; disagreement queue for judge-vs-format disagreements.
- Regression thresholds: zero tolerance on the three gate metrics; 5% relative drop on helpfulness or faithfulness blocks merge.
- CI wiring: smoke set on every PR; regression set nightly; shadow mode on 5% canary before broad rollout.
- Dashboard: 7-day rolling metrics per slice; judge-human agreement panel; backlog of unreviewed samples.

**Output excerpt:** the markdown plan plus a JSON `harness_spec` whose `regression_thresholds` array enumerates each metric with its allowed tolerance and severity.

## Limitations

- The skill writes the plan; it does not run the eval. The user must build the harness from the spec and operate it.
- LLM-judge calibration shifts as the underlying judge model changes; the skill cannot continuously revalidate. The plan must include the human re-calibration cadence the user actually executes.
- For tasks where "correctness" is itself contested (creative writing, opinion-laden output), the judge approach has a fundamental ceiling; recommend more human review and less judge weight.
- The skill does not enumerate every safety category for every domain; safety probe construction draws on domain knowledge the user must supply.
- Cost estimates for judge calls are heuristic; the user should benchmark against their actual provider pricing before committing.
- The skill assumes the team has at least one engineer who can implement a JSON-driven test runner; teams without that capability should start from a smaller smoke-only harness.
