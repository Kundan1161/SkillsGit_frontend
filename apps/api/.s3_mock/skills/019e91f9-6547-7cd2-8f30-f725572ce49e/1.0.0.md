# Distributed Tracing Stack Architect

## When to use

Use this skill when a team is designing or rebuilding the backend that stores distributed traces and the pipeline that delivers them. Common triggers:

- A team has just rolled out instrumentation and needs to decide what to retain and at what cost.
- Tail-based sampling is on the roadmap because head sampling at a low rate misses every error trace anyone wants to look at.
- A platform team is consolidating per-team tracing pipelines into a multi-tenant central one.
- Trace queries are too slow during incidents and the team needs to redesign the query path, not just buy a bigger backend.

Do not use this skill to instrument an application — pair it with an instrumentation-discipline skill, which produces the span structure this stack will store. Do not use it as a replacement for application performance profiling — traces explain what called what, profiling explains what burned the CPU; they coexist.

## How to apply

The design moves through six stages. Each produces a concrete artifact.

### Stage 1 — Quantify the trace workload

Ask for these numbers and refuse to proceed without at least an order-of-magnitude estimate for each:

| Quantity | Why it matters |
| --- | --- |
| Spans per second across the fleet at steady state | Drives collector and ingestion sizing. |
| Peak spans per second over the worst minute | Drives collector buffer sizing and tail-sampling decision window. |
| Average spans per trace | Drives storage per trace and tail-sampling buffer footprint. |
| Distribution of trace duration | Drives the tail-sampling decision window. A pipeline with 30-second traces needs a 60-second buffer; a pipeline with 30-second timeouts needs longer. |
| Number of services emitting spans | Drives attribute cardinality and the relevance of per-service retention. |
| Fraction of spans carrying an error status | Drives the value of tail sampling relative to head sampling. |
| Number of distinct teams who investigate | Drives tenancy. |

A useful framing for the user: head sampling decides whether a trace survives before its outcome is known; tail sampling decides after. Most teams want some of both.

### Stage 2 — Design the two-stage sampling policy

Choose the policy at three points: the edge (the producing service), the collector tier, and the storage gate. Most production stacks need decisions at all three.

**At the edge — head sampling:**

- Default to a probabilistic head sample of single-digit percent of root spans, with the sampling decision propagated downstream so every service in the same trace makes a consistent decision. Without propagation, traces are mutilated into useless fragments.
- Override to 100% sampling for explicitly marked "debug" requests, identified by an inbound header. Debug headers should be ACL-protected so they cannot be turned on by external callers.
- Override to 100% sampling for traces tagged as health-checks if you ever want to investigate them — but most teams should instead drop health-check traces entirely at the edge.

**At the collector tier — tail-based sampling:**

- Always keep traces that contain at least one error-status span. The whole point of tail sampling is that the edge does not yet know.
- Always keep traces whose total duration exceeds a per-route latency threshold. Calibrate the threshold per route, not globally; the same threshold across a fleet either keeps nothing or keeps everything.
- Probabilistically keep a small fraction of the remaining "normal" traces so the corpus has a baseline for comparison and the dashboards have non-error data to chart.
- Constrain the decision window to two to three times the longest expected trace duration. Longer windows balloon collector memory and turn the collector into the slowest part of the path.

**At the storage gate — per-tenant and per-service-tier policies:**

- Cap each tenant's ingest rate so a runaway service cannot starve other tenants.
- Apply a per-service-tier downsample on entry: a low-priority service can have its kept-traces rate further reduced at the gate, after tail sampling has already done the interesting selection.

Two principles:

- **Sampling decisions propagate; sampling does not.** If service A keeps a trace, service B must not drop it for any reason short of overload. Inconsistent decisions across services produce traces with holes that look like bugs to the user.
- **A trace either survives whole or not at all.** If the system can only keep half of a trace's spans, throw the trace away entirely. Half-traces are worse than no traces because they create false hypotheses during incidents.

### Stage 3 — Topology the collector pipeline

A robust pipeline has three collector layers, even when implemented in the same binary:

- **Edge collector.** Sits next to the producer, usually one per host or per cluster zone. Light parsing, head-sampling enforcement, retries on the wire to the next layer.
- **Sampling collector.** A pool of stateful collectors that buffer traces long enough to apply tail sampling. Sharded so all spans of a trace land on the same instance; sharding is by trace ID, never by service.
- **Storage-facing collector.** Receives sampled traces, applies the final transformations (PII scrubbing, attribute normalisation, tenant routing) and writes to the trace store.

Failure modes to design for explicitly:

- The sampling collector's memory limit must be enforced. When memory pressure rises, drop the oldest in-flight trace buffers rather than the newest spans, and never block ingest. A blocked collector backs pressure all the way to the producing service and causes outage cascades.
- The wire between layers must support retries with bounded queue depth at the sender and a clear "discard with metric" policy when the queue overflows. Silent loss is not acceptable; metricked, named loss is.
- A failover storage destination (a write-only object bucket) lets the storage-facing collector preserve traces during a trace-store outage. Replay tooling reads from this destination when the store recovers.

### Stage 4 — Span attribute discipline

The other dominant cost in a tracing stack is attribute volume. Define an attribute schema with three classes:

| Class | Examples | Indexing policy | Storage policy |
| --- | --- | --- | --- |
| **Indexed attributes** | `service.name`, `service.tier`, `http.route`, `rpc.method`, `db.system`, `tenant.id`, `error` (boolean), `status.code` | Always indexed for filter and group-by | Always stored |
| **Searchable attributes** | `http.target` (path with route templated out), `db.statement.summary`, `queue.name` | Tokenised text search, scoped to the recent retention window | Always stored |
| **Body attributes** | Raw payloads, full SQL statements, request bodies | Not indexed | Stored if and only if explicit policy allows; PII-scrubbed at the storage-facing collector |

Three rules that prevent classic mistakes:

- **Never index attributes whose value space is unbounded.** Request IDs, user IDs, full URLs, full SQL statements, and free-form error messages belong outside the index. They go into searchable or body classes and are recovered by scan at query time.
- **Templated routes are an indexed attribute; raw URLs are not.** A route is `/users/:id/orders`; a URL is `/users/8c1f.../orders`. The first is bounded; the second is not.
- **PII must be scrubbed at the storage-facing collector, not at query time.** Once data is at rest, you cannot reliably enforce who sees it. The scrub list is a versioned configuration file and changes are auditable.

### Stage 5 — Retention tiering by service tier, not uniformly

Trace retention is rarely uniform. A typical structure:

| Service tier | Hot tier (full attributes) | Warm tier (indexed plus body, slower query) | Cold tier (archive only) |
| --- | --- | --- | --- |
| **Tier 0** — customer-facing critical | 7 days | 30 days | 90 days |
| **Tier 1** — customer-facing non-critical | 3 days | 14 days | 30 days |
| **Tier 2** — internal | 24 hours | 7 days | None (deleted after warm) |
| **Tier 3** — batch and background | 24 hours | None | None |

Two implementation rules:

- **The retention tier is set per trace at the storage-facing collector**, derived from the producing service's tier label. Do not let individual spans within a trace claim different retention; that produces incoherent traces.
- **Error traces escalate.** Any trace with an error span is promoted to the next-higher tier's retention, capped at the hot-tier maximum. The most important traces are the ones with errors; truncating their retention because they came from a Tier 2 service is the wrong economy.

### Stage 5b — PII and payload handling

Traces routinely carry the worst-case data: real request payloads, real SQL with real user data, real error messages with real customer details. Decide PII handling once, at the right layer.

- **Scrub at the storage-facing collector, never at query.** A scrub list maintained in version control names attributes and patterns to redact before write. Examples: bearer tokens in headers, email addresses in SQL, free-form `user_input` fields. The scrub list is reviewed quarterly with the security team.
- **Differentiate "redact" from "drop".** A redacted attribute keeps its key with a placeholder value; the trace remains useful for shape analysis. A dropped attribute is removed entirely; the trace loses information about its presence. Most fields should be redacted; only the most sensitive should be dropped.
- **Bodies require an explicit opt-in.** Storing request or response bodies is a separate decision from storing spans, and it should be made per service tier. Tier 0 services that handle payments should default to no-body retention; an internal service can be more permissive.
- **The scrub list is auditable.** Changes to the list go through code review, are tagged with a ticket reference, and produce a runtime metric so the collector can prove it is enforcing the current version.

### Stage 6 — Build the incident-time query playbook

A trace store that no on-caller knows how to query is wasted spend. Document a small set of canonical queries that every on-caller is expected to run, in this order, during an incident.

1. **Trace by ID.** The fastest path. Surface trace IDs in logs and in error dashboards so the on-caller has a stack of IDs to paste in.
2. **Recent error traces for the service, last 15 minutes.** Filtered by `service.name` and `error=true`; sorted by duration descending. Use this when you know the service is in trouble but do not yet have a specific trace ID.
3. **Slow traces by route, last 30 minutes.** Filtered by `http.route` (or `rpc.method`) with duration above the route's tail-sampling threshold. Use this when latency is the symptom.
4. **Recent traces touching a specific dependency.** Filtered by `db.system` or by an outbound `rpc.service`. Use this when a downstream is suspected.
5. **Recent traces by tenant.** Filtered by `tenant.id`. Use this when a customer is reporting an issue and you have their tenant identifier.

For each query, capture three properties: the maximum time window allowed before the query is split or refused; the maximum number of traces returned; the linked dashboards opened when a result is selected.

The query playbook is the trace store's contract with on-call. If a query is missing from the playbook because the storage layer cannot answer it in seconds, that is a design defect, not an operator problem.

### Stage 7 — Operational checklist before traffic ramps

Before the pipeline carries production traffic, walk through this checklist with the owning team.

1. The edge collector survives an unavailability of the sampling tier by buffering on local disk with a bounded ceiling and dropping with a named counter. Verified by a fault-injection test.
2. The sampling tier's memory limit is enforced and verified under synthetic load at twice the design peak. Verified by a load test that simulates a crash-loop burst.
3. Sharding consistency: a deliberately misrouted span (a trace whose spans land on two sampling shards) produces a metric named for the inconsistency. Verified by a synthetic test injected weekly.
4. Tail-sampling rules are documented in a versioned configuration. A change to the rules is reviewed and produces an audit event.
5. The PII scrub list has been reviewed by the security team within the last quarter. A diff since the last review is attached to the launch ticket.
6. Per-tenant ingest caps are configured. A synthetic tenant exceeding its cap is rejected with a clear error and the platform records the event.
7. Retention tiers are configured per service tier. A span tagged with the wrong tier is rejected with a clear error, not silently accepted.
8. The query playbook is published in the on-call documentation, with screenshots, and at least two on-call engineers have run each query in a drill.
9. A trace deliberately seeded with an error is verifiable to land in storage within the platform's documented end-to-end latency target.
10. A trace seeded into a non-error path and not exceeding the per-route latency threshold is statistically expected to be dropped, and the dropped-spans metric reflects it.

### Stage 8 — Anti-patterns that look attractive and are not

Refuse these requests, with reasoning.

- **"Let us keep 100% of traces for a few days."** It sounds simple and is the most expensive thing the system can do. Tail sampling exists because storage is the binding constraint; 100% retention even briefly disables every cost control.
- **"Let us index the request body for search."** Body content is unbounded, customer-influenced, and the largest privacy surface. If body search is genuinely needed, it belongs in a logging stack with the appropriate redaction, not in a trace store.
- **"Let us merge traces from different services with a stitched trace ID."** Stitching produces half-truth traces that hide bugs and create new ones. Propagate the original trace ID end-to-end; if a service cannot propagate, fix that service.
- **"Let us sample more aggressively to save money — drop everything below p50."** This drops exactly the traces that establish the baseline against which p99 incidents are diagnosed. Keep a small probabilistic floor of normal traces; reduce by tuning the per-route latency thresholds and retention tiers, not by killing the baseline.
- **"Let us cap span attributes at five per span to control cost."** The cost is not in attribute count; it is in attribute cardinality. A span with twenty bounded attributes is cheaper than a span with three unbounded ones. Address cardinality, not count.

## Inputs

- **Required:** spans-per-second at steady state and peak, number of services, average spans per trace, fraction with errors.
- **Recommended:** representative investigation queries with frequency and latency targets; current sampling rates and miss rates; cost ceiling.
- **Optional:** existing collector and storage components; PII attribute lists; per-service tier classification.

## Outputs

A markdown design with these sections, in order:

1. **Workload profile** — the quantified table from stage 1.
2. **Sampling policy** — edge, collector, and storage-gate decisions with explicit rules and overrides.
3. **Collector topology** — three layers with sharding, failure modes, and failover destination.
4. **Attribute schema** — three classes with index, search, and storage policy; PII scrub list.
5. **Retention tiers** — per service tier with error escalation rule.
6. **Query playbook** — five canonical queries with windows, limits, and linked dashboards.
7. **Migration plan** — if applicable, the order in which services adopt the new pipeline.

## Examples

### Example 1 — Adding tail sampling to an existing 1% head-sampled pipeline

User says: *"We sample 1% of traces at the edge. During incidents we never have the trace we need. Adding tail sampling — what do we do?"*

Recommended response shape:

- Keep edge sampling at 1% as the floor for routine traces, but propagate the decision faithfully.
- Add a sampling collector tier with a 60-second decision window — assume the long-tail trace is under 30 seconds.
- Tail-keep rules: every trace with `error=true`; every trace exceeding a per-route p99 threshold computed from the previous 24 hours; 5% of the remainder.
- Sharding by trace ID. Three replicas minimum; failover-tolerant to one replica loss.
- Storage gate caps per tenant; tier 2 services downsampled an additional 50% post-tail.
- Validation: re-walk the user's last five incidents and confirm the new pipeline would have kept the traces involved.

### Example 2 — Multi-tenant platform launch

User says: *"We are standing up a tracing platform for ten product teams. Two of them ship critical customer-facing services; the rest are internal."*

Recommended response shape:

- One tenant per on-call rotation. Two critical tenants get Tier 0 retention defaults; the rest get Tier 2.
- Edge collector runs as a daemon per cluster node. Sampling collector pool sized for the worst-minute peak across all tenants combined plus 30% headroom.
- Attribute schema published as a contract: tenants who want a non-standard attribute indexed file a request that is reviewed for cardinality.
- Query playbook included in the tenant onboarding documentation. On-call shadowing across teams uses the same five queries so an incident commander from one team can help another.
- Cost ceiling per tenant published; soft alert at 80%, hard cap at 100% with a paging escalation.

## Common review findings

When reviewing an existing tracing stack against this methodology, the following findings recur with standard remediations.

1. **Edge sampling at 1% with no propagation.** Traces are fragmented because services in the same trace make independent decisions. Implement decision propagation in the standard instrumentation library and revisit miss rates a month later.
2. **No tail sampling.** All interesting traces are statistically missed. Add a sampling collector tier with the rules in stage 2.
3. **High-cardinality attributes in the index.** Request IDs, full URLs, full SQL statements. Move to body class with redaction; rebuild the index.
4. **PII scrub at the query layer.** Once at rest, controls do not hold. Scrub at the storage-facing collector and version the scrub list.
5. **Uniform retention across service tiers.** Tier 0 critical services share the budget with Tier 3 background jobs. Differentiate retention per tier and promote error traces.
6. **Collector memory limit unenforced.** A burst will OOM the collector and back pressure all the way to applications. Enforce limits and verify under load.
7. **Sharding by service rather than by trace ID.** Spans for one trace land on multiple shards; tail sampling cannot decide. Reshard by trace ID.
8. **No incident-time query playbook.** On-callers improvise queries and time them out. Publish five canonical queries with bounds and rehearse them in drills.
9. **One tenant with no quotas.** A bad rollout consumes everyone's budget. Establish per-tenant quotas before the platform onboards a second team.

## Limitations

- **Not an instrumentation guide.** The skill assumes spans are emitted; it does not specify how to instrument a codebase.
- **Not for log-driven tracing systems.** Some teams reconstruct traces from logs; that architecture has different cost shapes and is not modelled here.
- **Not a flamegraph or continuous-profiling design.** Traces explain calls; profiles explain where time burns. They are siblings, not substitutes.
- **Tail-sampling thresholds are starting points.** Per-route latency thresholds need at least 14 days of production data to be calibrated; expect to revisit them.
- **Retention tier defaults are illustrative.** Regulatory and contractual obligations override; pair this skill with a compliance review when relevant.
- **The two-stage sampling model assumes a controllable collector tier.** Fully managed tracing services may not expose tail-sampling configuration; the design then reduces to edge-only sampling, with the trade-offs the user must accept.
- **Cross-system trace correlation is out of scope.** Traces that span an internal service and an external SaaS provider need bridging at the trust boundary; that is a separate design exercise.

## Tail-sampling rule design — a worked example

A user asks: "How do we tail-sample for a service with 50 routes, 90% of traffic on three of them, and a tail latency that varies between routes?"

The recommended approach:

1. **Compute per-route latency thresholds** from the previous fourteen days. Use the route's own p95 or p99, not a fleet-wide number. Three high-traffic routes will have stable thresholds; the long tail will have noisy thresholds and is acceptable to bucket under a single fallback threshold.
2. **Express the rules as a small set of policy clauses**, evaluated in order: keep if `error=true`; keep if `duration > route_threshold`; keep with probability 5% otherwise. Add a debug-keep clause for traces flagged at the edge.
3. **Allocate a fixed budget** of traces-per-second to the collector tier. Probability adjusts to fit; when budget is tight, the floor shrinks first, the latency rule never compromises.
4. **Refresh thresholds on a cadence**, weekly is enough for most services. Hold thresholds steady during an active incident — a service in an outage will shift its distribution and the rule should not chase it.
5. **Surface the kept rate per rule** as a metric. A drop in error-kept rate is a leading indicator that error spans are being dropped — sometimes because the error attribute changed name in a deploy.

The output of this process is a configuration file under version control with clauses, thresholds, and the date the thresholds were last refreshed. Anyone reading the file should be able to reproduce the kept rate in production from the rules.

## Cost levers, ranked

When asked "how do we spend less on tracing without going blind", apply the levers in this order. The order is calibrated for typical workloads; reorder only with measured data.

1. **Tighten span attribute hygiene.** High-cardinality attributes are usually the largest contributor to storage cost and the easiest to remove. Audit, move unbounded attributes to body or remove them, and re-measure.
2. **Adjust tail-sampling thresholds per route.** A route whose threshold is set too low keeps too many traces; one set too high keeps none. Calibrate with the previous fourteen days of data.
3. **Differentiate retention by service tier.** Tier 3 background services rarely need the same retention as Tier 0. Differentiating cuts storage by a meaningful fraction without affecting incident response.
4. **Reduce body storage to a per-tier opt-in.** Bodies are the largest per-trace cost. Most teams do not need them by default.
5. **Reduce the probabilistic floor for normal traces.** A 5% floor can become a 2% floor with minimal loss of baseline signal; only reduce after the previous levers are exhausted.
6. **Reduce native retention.** Less aggressive than reducing what is sampled; preserves recent-incident debug at the cost of older trace availability.
7. **Move to a cheaper storage substrate.** Object-storage class changes and archival tiers save money at the cost of query latency. Only after the structural levers above are exhausted.

The lever order matters. Teams that start at step 7 (storage substrate) and skip steps 1-3 spend the same money to keep less useful traces.

## Glossary used in this skill

- **Span.** A single timed operation in a service: a request handler, a downstream call, a database query.
- **Trace.** A directed acyclic graph of spans sharing a trace identifier; usually rooted in a request received at the edge.
- **Head sampling.** A decision made at the producing service before the outcome of the trace is known.
- **Tail sampling.** A decision made by a collector after the full trace (or enough of it) has been observed.
- **Decision window.** The time the sampling collector waits for spans of the same trace before deciding to keep or drop.
- **Propagation.** Carrying the sampling decision and trace context across service boundaries so all participating services agree.
- **Tenant.** A logical isolation boundary, typically aligned with an on-call rotation.
- **Service tier.** A classification of services (Tier 0 critical, Tier 1, Tier 2, Tier 3) used to drive retention and quota defaults.

## Handoff to neighbouring designs

A tracing stack design composes with the broader observability practice. Coordinate handoffs.

- **To logging.** Every log line should carry the trace ID and span ID of the span that produced it. This is the property that makes trace-to-log drill-down work; without it, the trace store is a separate ecosystem from logs. Verify the structured-logging contract before signing off.
- **To metrics.** Span-derived metrics (request rate, error rate, latency histograms) emitted by a metrics generator must use the same `service.name` and `http.route` attributes as the metric collection path; mismatched labels break dashboards. Verify in joint review.
- **To incident response.** The query playbook from stage 6 should be referenced in the incident-commander runbook with screenshots. On-callers should not be inventing queries during an incident.
- **To compliance and privacy.** The PII scrub list is reviewed by security and compliance owners on a documented cadence. Changes to the list are visible to those owners.
- **To capacity and cost owners.** Per-tenant ingest caps and storage tier choices have a cost shape; surface it to whichever team owns the bill. A surprised finance partner is the leading cause of a design being rolled back.

## Span structure — guidance an architect should expect to enforce

A trace store can only be as useful as the spans that arrive in it. The architect's job is to enforce a small set of structural rules across services, even though the rules are enforced in instrumentation libraries elsewhere.

- **Every span has a `service.name` and a `service.tier` attribute.** Without these, retention tiering and cardinality reviews cannot operate.
- **Every span has a `status` attribute, set to ok or error, distinct from the `http.status_code` or any RPC-specific status.** Tail-sampling rules read `status`; depending on `http.status_code` alone produces inconsistent decisions across protocols.
- **Every span uses route templates as attributes, not raw URLs.** A span with `http.route="/users/:id"` is indexable; one with `http.target="/users/8c1f..."` is not.
- **Every span has bounded names.** An unbounded span name produced from a customer string explodes attribute cardinality even when no attribute is unbounded. Span names belong on a closed list per service.
- **Every trace has a single root span.** A trace with multiple roots is the result of broken propagation upstream; surface it as a metric so the producer can fix it.

These rules sit in the instrumentation library and in the storage-facing collector's validation. The architect publishes them and expects every onboarding service to comply; non-compliant services are visible in a dashboard and ticketed against their owning team.

## Drill notes for on-call readiness

Before the trace store is on-call's first stop during an incident, run two drills.

- **Synthetic-incident drill.** Inject a controlled error into a non-production environment with the same instrumentation. An on-caller runs the five canonical queries against the live trace store and reports time-to-first-useful-trace. The target is under two minutes from notification.
- **Outage drill.** Simulate a sampling collector partial outage. Confirm that edge buffering survives the duration, that the dropped-spans counter reflects the loss, and that incident commanders are alerted to the platform issue distinct from the original incident.

Drills surface problems no design review catches: a query that times out at the volume the production store actually carries, an attribute that was supposed to be indexed and is not, a runbook screenshot that was taken before a UI change. Run drills quarterly at minimum.
