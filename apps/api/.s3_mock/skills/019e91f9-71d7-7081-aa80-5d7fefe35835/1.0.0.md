# Prompt Management Strategy

## When to use

Use this skill when a team has shipped one or more LLM features and the prompts have become a liability rather than an asset. The symptoms are familiar: prompts are scattered across the codebase, the product wiki, and a Notion page; nobody knows which version is in production; A/B test results are anecdotal; localised variants drift apart; rolling back a regression means a code deploy; and changes ship without re-running the evals.

The skill produces a strategy document, not a tool selection or an implementation. It names the source of truth, the versioning scheme, the promotion pipeline, the A/B testing strategy, the deprecation policy, the multi-locale plan, the ownership model, the observability requirements, and the migration steps from wherever the team is today.

The skill is not for designing a single prompt — that lives in the prompt-engineering practice. It is not for designing the evaluation harness that gates promotion — that lives in the harness-design skill. It is not for choosing a SaaS prompt-management vendor — it produces requirements a vendor or homegrown stack must meet. It is the missing layer between "we have prompts" and "we operate prompts".

## How to apply

The skill walks a deterministic ten-stage pipeline.

### Stage 1 — Inventory the current state

1. Read `current_state` and list every place a prompt currently lives. Typical answers: hard-coded strings in source files, environment variables, a database table, a SaaS prompt platform, a Notion or Confluence page, a Google Doc, a JSON file in a config repository. List all of them; missing one is what produces "the bug is in a prompt that nobody can find".
2. For each location, record: who can edit, how a change reaches production (deploy, migration, runtime fetch), whether changes are reviewed, whether changes are logged.
3. List every LLM feature from `feature_inventory` and the prompts each uses. A feature that calls the model more than once per invocation (router, planner, summariser) has more than one prompt; record each.
4. Mark which prompts are user-visible (because they affect outputs the user reads) and which are internal (because they only affect routing or extraction). Both need management; user-visible prompts need stricter review.
5. End the inventory with a one-line honesty check: where would a regression today most likely originate, and how would the team find it? If the answer is "we would not", every subsequent stage is justified.

### Stage 2 — Pick a single source of truth

6. The strategy designates one source of truth per prompt. Acceptable choices include a versioned file in a code repository, a row in a database with an append-only history table, or a SaaS prompt registry that exposes a fetch API. The choice depends on `team_shape` and `constraints`.
7. **Code repository as source of truth.** Best when only engineers edit prompts, when prompts change at deploy cadence, when audit comes for free from git, and when the codebase already has good review practices. The prompt is a string constant or a templated file; it ships with the binary.
8. **Database with history table as source of truth.** Best when prompts change faster than code deploys, when non-engineers edit, and when the team can build or buy a small admin UI. The history table is append-only with `prompt_id`, `version`, `body`, `author`, `created_at`, `notes`, `status`. The production code fetches the active version by `prompt_id`.
9. **SaaS prompt registry as source of truth.** Best when the team values an off-the-shelf editing UX, when versioning and rollback need to be a click, when the vendor's evaluation and observability features are wanted. Beware vendor lock-in; the strategy must include an export path and the ability to fall back to local copies if the vendor is unreachable.
10. Whatever the choice, the rule is *exactly one source of truth per prompt*. Copies elsewhere (in slides, docs, screenshots) are read-only mirrors. If the copy disagrees with the source of truth, the source of truth wins by definition.

### Stage 3 — Versioning scheme

11. Every prompt has a stable identifier (`prompt_id`) and a version. The identifier is immutable; the version increments.
12. Choose semver or a monotonically increasing integer. Semver is useful when prompt schemas (input variables) can change in breaking ways and consumers must opt in. Integer versions are simpler when prompts are always invoked by a single consumer that updates in lockstep.
13. A prompt version captures, at minimum: the prompt body, the variable schema, the target model (or `model-agnostic`), the temperature and other inference parameters, the author, the change notes, and the status (`draft`, `staging`, `production`, `deprecated`, `retired`).
14. Treat the variable schema as a contract. Adding a required variable is a breaking change; renaming a variable is a breaking change; adding an optional variable with a default is not. The strategy spells out the rule because consumers will rely on it.
15. Pin the inference parameters at the prompt-version level, not in the calling code. A prompt that reads well at temperature 0.2 and behaves randomly at 0.9 is two different prompts; combining them masks regressions.
16. Forbid in-place edits to a published version. A change is a new version. The previous version remains queryable for as long as it has callers or as long as the audit retention window requires.

### Stage 4 — Promotion pipeline

17. A new prompt version moves through staged statuses: `draft` (the author is iterating), `staging` (eval-gated, runnable against the eval harness, available to internal testers), `production` (a percentage of traffic, ramping), `deprecated` (still served to callers that have not migrated), `retired` (no longer served, retained for audit).
18. The transition from `draft` to `staging` requires: the eval harness runs against the new version, all gate metrics pass, axis metrics meet or beat the current production version on the regression test set, and the diff against the production version is reviewed.
19. The transition from `staging` to `production` requires: the staging run is reproducible (same inputs, same model, same parameters), the diff against production was approved by an additional reviewer, the rollout plan (Stage 5) has been chosen, and the kill switch is verified to work.
20. The transition from `production` to `deprecated` requires: the new version is at one hundred percent traffic on the production callers, no incident has occurred in the canary window, and the deprecation notice has been recorded with a target retirement date.
21. The transition from `deprecated` to `retired` requires: zero callers in the last N days (default thirty), the audit window has elapsed, and the retirement is logged.
22. Block any transition that skips a stage. Skipping `staging` because "the change is small" is how prompt regressions reach users.

### Stage 5 — A/B testing strategy

23. Prompt A/B tests are how the team decides between candidate versions in the wild after the eval harness says they are both acceptable.
24. Pick the unit of randomisation. Per-request randomisation gives the fastest convergence and is appropriate for stateless features. Per-user randomisation is required when the feature is conversational, when the user might compare answers across sessions, or when consistency matters more than statistical power.
25. Decide which metrics decide the test. The strategy ties the A/B test to the success metrics from the feature spec (acceptance rate, edit distance, conversion). Eval-harness metrics are not enough to win an A/B test; they are necessary to *enter* one.
26. Decide the minimum sample size and the maximum duration. Define both before starting; stopping early on a favourable trend is how teams ship prompts that look good for a week and regress in the second.
27. Run a calibration period. For at least the first few hours of any A/B test, both arms must serve the same prompt; the resulting metrics must be statistically indistinguishable. If they are not, the test infrastructure is broken before any prompt change is judged.
28. Require a counter-metric guard. If a chosen metric improves but the counter-metric degrades beyond a threshold, the test does not promote even if statistical significance is reached on the headline.
29. Record every test in a registry: the prompt versions in each arm, the cohort definition, the start and end timestamps, the metrics, the outcome, and the post-mortem if any. A pattern of "we tested this, we shipped it, we cannot find the test" is how prompt drift becomes invisible.

### Stage 6 — Deprecation and rollback

30. Every promotion creates a rollback obligation. The strategy specifies the rollback mechanism: a config flip that points callers back to the previous version, executable without a code deploy and without a database migration.
31. The rollback path is tested on the day the kill switch is built, not the day of the first incident. The strategy specifies a quarterly rollback drill where the team rolls back a non-critical prompt in staging and confirms the system behaves.
32. Deprecation has a published timeline. When a version is moved to `deprecated`, every caller is notified with the target retirement date. Callers are given a migration period proportional to integration complexity (a week for internal callers, a quarter for external API consumers).
33. During the deprecation window, the deprecated version is monitored: any new caller against a deprecated version triggers a warning. A version that picks up new callers after deprecation indicates a missed migration.
34. Retirement removes the version from active serving but not from the audit store. Retained copies must be sufficient to reconstruct a model output produced in the past, including the prompt, the inference parameters, the model, and the retrieved context if any.

### Stage 7 — Multi-locale strategy

35. If the feature serves more than one locale, decide the localisation pattern. The strategy names exactly one pattern as the default and the conditions under which exceptions are allowed.
36. **Translation pattern.** A canonical prompt is authored in one language; locale variants are translations reviewed by speakers of each target language. Best when the structure of the prompt is identical across locales and only the surface language varies.
37. **Locale-specific authoring pattern.** Each locale has its own prompt, authored from scratch by a speaker. Best when the user-visible behaviour must differ across locales beyond surface language — for example, different politeness levels, different examples, different refusal phrasings.
38. **Conditional pattern.** A single prompt with locale-conditioned sections, controlled by a variable. Best when most of the prompt is locale-agnostic and only a few sections vary.
39. Whatever the pattern, every locale variant is its own prompt version with its own eval set. A locale that ships without a localised eval is a locale that ships without quality measurement.
40. Plan the bottleneck. Most teams have more locales than reviewers; the strategy names a default response when a reviewer is not available: hold the rollout, ship to the unblocked locales first, or accept a known-degraded locale with a banner. Choose ahead of time.
41. Watch for model-capability drift across languages. A prompt that scores ninety on English may score sixty on a low-resource language with the same model. The strategy requires per-locale tracking of headline metrics and slice-level gate metrics.

### Stage 8 — Ownership and review

42. Pin ownership per prompt: a directly-responsible individual (DRI) and a backup. The DRI approves changes; the backup approves when the DRI is unavailable. The audit trail captures both names.
43. Decide who may author drafts. A widely-permissive answer is fine for `draft` status (PMs, designers, and engineers can all propose changes); permissions tighten at each subsequent status.
44. Require code-review-style review for every promotion to `staging` and `production`. The reviewer is a different person from the author. The review checklist is small: variable-schema diff, behaviour diff on the eval set, latency and cost delta, any new guardrail implications.
45. Require an out-of-team review for prompts that touch regulated content, that change refusal behaviour, or that change tool-use authorisation. Out-of-team reviewers include legal, compliance, or a designated safety reviewer depending on the change.
46. Log every change with author, reviewer, status transition, and timestamp. The log is append-only and queryable. "Who changed this and when" is the most-asked question during an incident.

### Stage 9 — Observability

47. Production logs capture, per invocation: the prompt id, the prompt version, the model, the inference parameters, the input variables, the output, the latency, the token counts, and any guardrail or judge scores recorded inline.
48. The team's analytics has a "by prompt version" pivot. Every metric that matters can be sliced by prompt version, locale, model, and tenant. Without this pivot, A/B tests degrade to anecdote.
49. The pipeline emits a daily report per prompt: call volume, headline quality metrics, latency p50 and p95, cost, error rate, and the status (draft, staging, production, deprecated). The DRI for the prompt reads the report.
50. Anomaly detection runs on the report. A sudden drop in a quality metric, a sudden spike in latency, or a sudden spike in refusals triggers a page to the DRI. The threshold is calibrated against the rolling baseline, not against an absolute number that goes stale.

### Stage 10 — Migration from the current state

51. The strategy ends with a sequenced migration plan from today's mess to the target architecture.
52. **Week one.** Inventory complete and frozen. Source of truth chosen. A single pilot feature picks one prompt and runs end-to-end through the new pipeline (draft, eval, stage, promote, observe). The pilot proves the pipeline is real.
53. **Weeks two through four.** Top three prompts by call volume migrate. Each migration includes building the eval harness if missing, defining the success metrics, and recording the baseline.
54. **Month two.** Remaining production prompts migrate. Deprecation timelines for any legacy locations are published. Ownership is assigned for every prompt.
55. **Month three.** A/B testing is enabled. The first promotion-by-A/B-test runs end-to-end. The observability pivot is verified across at least two prompts.
56. **Quarter two.** Multi-locale rollouts under the new strategy. Rollback drill executed. Retrospective on the migration with adjustments to the strategy.
57. The migration plan includes a "stop-the-bleed" rule for the period before migration is complete: until a prompt is migrated, no in-place edits in production; any change requires migrating that prompt first. The rule keeps the chaos from growing while the strategy lands.

## Outputs

The `strategy_doc` markdown is the full strategy in the order above. The `strategy_summary` JSON mirrors the sections for tooling consumption — the registry schema, the promotion-pipeline statuses, the A/B test fields, the locale pattern, the ownership map, and the migration milestones.

## Examples

A team running a single English chatbot with prompts hard-coded in their backend repository will land on "code repo as source of truth, integer versioning, eval-gated promotion via CI, A/B testing per-user, single locale, engineering DRI per prompt". Their migration is short: extract prompts into a single `prompts/` directory, wire the eval harness into CI, build a feature flag for prompt selection, and run the first A/B test on the smallest prompt.

A team running a multi-tenant SaaS with five locales and prompts edited by a mix of PMs and engineers will land on "database with history table as source of truth, semver, eval-gated promotion via admin UI, A/B testing per-user with locale-stratified analysis, translation pattern with per-locale eval sets, mixed ownership with engineering as backup DRI". Their migration is longer: build the admin UI, define the variable-schema contract, get the translation pipeline online, set up the per-locale eval, train the PMs and designers on the new flow.

## Limitations

The skill produces a strategy, not an implementation. It assumes the team has or can build the components it names (an eval harness, a feature flag system, an analytics pivot). For teams without those, the migration plan calls them out as prerequisites with explicit ownership.

The skill does not select between SaaS prompt-management vendors or open-source equivalents. It produces the requirements a vendor must meet so the team can evaluate options on a level playing field.

The skill assumes prompts are the primary lever. Teams whose primary lever is fine-tuning will find the principles transfer, but the concrete pipeline shape — what constitutes a version, how A/B testing works, what a rollback looks like — differs and is out of scope here.
