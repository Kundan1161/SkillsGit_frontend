# Feature Spec Audit

## When to use

Use this skill when a feature spec is about to enter engineering kickoff — the moment when ambiguity converts directly into rework — and the asker wants to find the gaps before the team does. The output is a gap report with specific fixes, a kickoff-readiness assessment, and drafted patches for the spec.

Engage when the spec is at least a draft. The skill cannot audit a one-line idea; the input must be a written document with at least some sections.

Decline or push back when:

- The spec is a vision document, not a build document. Vision documents lack the structure the audit needs and are *supposed* to lack acceptance criteria. Recommend the PRD drafter skill first.
- The work is genuinely simple and the spec is intentionally short (a minor copy change, a configuration update). Heavy audits inflict process on small work. Confirm and proceed lightly, or decline.
- The team has explicitly chosen a lighter spec format (one-paragraph briefs, a ticket only). The audit should adapt rather than impose; mark items as "n/a for this format" rather than flag them as gaps.
- The spec is already approved and shipping. Audit becomes retrospective. Useful for post-mortem learning, but mark the framing.

The skill is at its best when the asker is the PM or the tech lead trying to harden a doc before it gets ten engineers' attention. The hidden value is not catching the bug; it's preventing the meeting where ten people discover the spec is missing the same field.

## How to apply

Run the methodology in seven phases. Each phase fires a category of checks.

### Phase 1 — Frame and parse

1. **Identify the document type.** PRD, engineering RFC, design doc, ticket-scale brief, technical proposal. Different types have different completeness bars; do not flag missing sections that the format does not call for.
2. **Identify the surface area.** Use `surface_area` if supplied; otherwise infer from the spec. UI features need different sections than batch jobs need different sections than API endpoints.
3. **Find the explicit sections.** Scope, goals, requirements, acceptance criteria, rollout, observability, security, accessibility, error states, edge cases. Note which exist and which are missing.
4. **Find the implicit content.** A spec without an "Edge cases" header may still address edge cases inside the requirements section. Audit content, not headers.

### Phase 2 — Audit the goals and scope

5. **Is the goal an outcome?** "Reduce time-to-first-value for trial users" is an outcome; "Ship the new onboarding screen" is an output. Output-shaped goals are a yellow flag; they leave the team room to ship something that does not move the metric.
6. **Is the scope bounded?** Does the spec say what is *not* in scope? If not, that is the single highest-leverage gap. Add it.
7. **Is the success metric named?** A spec without a success metric will ship and then orbit forever — the team cannot know when to stop investing.
8. **Is the success metric measurable from the data the system will produce?** If the metric is "user satisfaction" but the system collects no satisfaction signal, the metric is fictional. Flag.

### Phase 3 — Audit the requirements and acceptance criteria

9. **Are requirements testable?** Each functional requirement should be either binary (does/does not happen) or measurable (above/below a threshold). Wishy-washy verbs ("supports", "enables") are usually trouble.
10. **Are acceptance criteria written?** Acceptance criteria are the spec's contract with QA and engineering. If absent, every requirement is a gap. If present, check they cover the happy path *and* at least one error path *and* at least one edge case.
11. **Are inputs and outputs specified per requirement?** For each requirement, what does the user/system do, and what does the user/system see or receive? A requirement with implicit inputs invites incompatible implementations.
12. **Are non-functional requirements covered?** Performance (latency, throughput, scale), reliability (SLO/availability), security, accessibility, internationalization, audit. Each gets its own subsection or is consciously marked "covered by default platform behavior."
13. **Are dependencies named?** Other services, vendor APIs, internal teams, data sources. A spec that depends on a team not in the kickoff is a launch blocker disguised as a feature.

### Phase 4 — Audit the edge cases, error states, and empty states

14. **Empty states.** First use, zero data, unauthenticated, no permissions, no entitlement. Each gets either a description in the spec or an explicit note "use platform empty state."
15. **Error states.** For every action that can fail, what does the user see, what does the system log, and what triggers a retry? Failures to specify: backend timeouts, validation errors, partial successes (some items saved, some not), permission denials mid-action.
16. **Edge cases the surface area implies.** For an API: large payloads, malformed inputs, rate-limited callers, idempotency for repeated requests, missing optional fields. For a UI: small viewport, slow network, accessibility tooling (screen reader, keyboard-only), copy-paste from other tools, language switch mid-flow. For a batch job: empty input set, single-item input, mid-run failure, restart-from-checkpoint. For a data pipeline: schema drift, late-arriving data, duplicates, deletes, time-zone boundaries. For a mobile feature: backgrounding, low memory, offline, region/locale switch.
17. **Concurrency.** Two users editing the same thing; the same user from two devices; the system reading while the user is writing. If the spec has multi-user surface area and is silent on concurrency, flag.
18. **State machines.** If the feature has named states (draft, pending, approved, rejected), all transitions must be specified. A state diagram in the spec or a transition table is the standard.
19. **Off-the-happy-path inputs.** Special characters, RTL languages, emoji, very long strings, very short strings, leading/trailing whitespace, mixed scripts, names that look like SQL. Specs that only test "Alice" miss "O'Brien" and "李娜" and "Bobby Tables".
20. **Time and locale.** DST transitions, leap years, leap seconds, midnight boundaries, time zones for users in flight, dates before 1970 or after 2038. Most teams need none of this; some teams need all of it. The spec should declare which.

### Phase 5 — Audit observability and operability

21. **Are events specified?** What signals does the feature emit — clicks, requests, errors, business events? Without specified events, the success metric cannot be computed.
22. **Are dashboards specified?** What does the team look at after launch to know it is working? "Existing dashboard X plus new tile Y" beats "we'll set up dashboards later."
23. **Are alerts specified?** What triggers an alert and what does the on-call engineer do? An alert without a runbook is noise.
24. **Is logging specified?** What gets logged at what level, what does not get logged (e.g., PII), what is the retention. Specs that hand-wave logging produce log floods or log droughts.
25. **Are SLOs/SLIs named?** For features that participate in user-facing reliability, what is the target? Without it, the team will not know when the feature is in regression.
26. **Is debugging documented?** When a user reports the feature is broken, how does support reproduce, what data do they need, who do they escalate to? Specs that ignore the support path produce support-hostile features.

### Phase 6 — Audit rollout and kill switch

27. **Is the rollout strategy specified?** Behind a flag? Percent ramp? Geo-cohort? Internal first? Specs that say "we will ship it" leave a lot of risk on the table.
28. **Is the flag system named?** Which feature-flag tool, what is the flag name, who can flip it. Without a named flag, the team will improvise.
29. **Is the kill switch explicit?** A kill switch is a fast, reversible way to disable the feature in production without a code deploy. For any change with user-facing impact, a kill switch should exist. The audit fires a high-severity flag if missing.
30. **Are rollback criteria specified?** What metric drop, error rate, or signal triggers a rollback? Without explicit criteria, every regression becomes a debate.
31. **Are launch criteria specified?** What must be true on the day of GA — instrumentation green, docs published, support trained, comms approved. Specs that skip this section enable the "we'll launch and figure it out" antipattern.
32. **Is the migration plan named (if applicable)?** Data migrations, customer migrations, deprecation of the prior path. Each migration is a project of its own; the spec must either name it or carve it out.

### Phase 7 — Audit security, privacy, accessibility, and compliance

33. **Auth and authz.** Who can do this, who cannot, how the system checks. Specs that say "the user can…" without specifying the role often leak permissions.
34. **PII and data handling.** What personal data is touched, where it goes, who can read it, how long it lives. If the spec touches PII and is silent, flag at high severity.
35. **Threat model snapshot.** For features that touch sensitive surface area (payments, auth, data export, ingestion of external content), a short threat model paragraph: top three threats and mitigations. A spec that lacks this is rolling the dice.
36. **Accessibility.** Keyboard navigation, screen-reader labels, color-contrast, focus management, motion preferences. For UI features, fire a high-severity flag if missing.
37. **Internationalization.** Strings extracted, dates/numbers/currencies localized, RTL support. For UI features in i18n-capable products, flag if missing.
38. **Compliance.** GDPR (data export, deletion), HIPAA, SOC 2 controls, SOX, regional rules. The spec does not need to embed the regulation, but it must name which regimes apply and how the feature complies.

### Phase 8 — Compose the outputs

39. **Score severity per gap.** Use a 3-tier scale: **blocking** (do not kick off until fixed — e.g., no acceptance criteria, no rollout plan, no kill switch on a risky change), **important** (fix before code freeze — e.g., missing edge cases, unspecified observability), **nice-to-have** (fix when convenient — e.g., glossary terms, formatting). Use `severity_threshold` to calibrate — `permissive` collapses important and nice-to-have, `strict` promotes nice-to-have to important.
40. **Group gaps by section.** The asker will edit the spec by section; presenting gaps grouped by section makes the edits efficient.
41. **For each gap, write a one-sentence fix.** Not "edge cases missing" but "Add an edge case: behavior when the user has zero permitted projects (display the empty state and disable the create button)."
42. **Compose the kickoff-readiness verdict.** Three states: **ready** (no blockers), **conditional** (blockers exist but are addressable in <1 day), **not-ready** (blockers require materially more work; recommend a follow-up review before kickoff).
43. **Compose the patches.** For each gap, draft the specific text the asker can paste into the spec. Patches are short, in the voice of the surrounding doc, and ready to copy. This is the single most-leveraged output — a list of gaps without patches puts the work back on the PM; patches let them merge and move.
44. **Confidence-tag the audit.** "High confidence: spec is detailed and the surface area is well-defined." "Medium: spec is sparse, audit catches the form but not the substance." "Low: spec is too thin to audit substantively; recommend more drafting before another audit."

## Inputs

- **`spec`** — required. The document to audit.
- **`surface_area`** — optional. `api-endpoint`, `ui-feature`, `batch-job`, `infra-service`, `mobile-feature`, `integration`, `data-pipeline`, `generic`. Defaults to `generic`.
- **`severity_threshold`** — optional. `permissive`, `standard`, `strict`. Defaults to `standard`.
- **`team_context`** — optional. Team size, on-call structure, observability stack, deployment cadence, regulatory context.

## Outputs

- **`gap_report`** — the list of gaps with severity, location, and recommended fix.
- **`kickoff_readiness`** — overall verdict, blocking gaps, fix order, next-step.
- **`spec_patches`** — drafted text per gap.

## Examples

### Example 1 — A UI feature spec missing edge cases and rollout

**Source.** A 2,000-word PRD for a new dashboard feature. Goals and requirements are crisp. Acceptance criteria exist for the happy path. No section on empty/error states, no rollout plan, no kill switch.

**Output highlights.**

- **Gap report.** 11 gaps total. 3 blocking: (a) no rollout strategy, (b) no kill switch for a feature that touches the dashboard data layer, (c) acceptance criteria absent for error paths. 5 important: empty states for new accounts, accessibility (keyboard, screen-reader), observability events for the new feature, alert thresholds, support-debugging path. 3 nice-to-have: glossary terms for two acronyms used inconsistently.
- **Kickoff readiness.** Conditional — blockers are addressable in half a day; the spec author can fix them before the kickoff.
- **Patches.** For the kill-switch gap: "Rollout & Kill Switch — The feature ships behind feature flag `dashboard-v2-tiles` (managed in LaunchDarkly). The flag defaults to off in production. The kill switch is the same flag, flipped to off; flag changes propagate within 30 seconds. Rollback criterion: if dashboard-load p95 latency rises above 800ms for more than 10 minutes, flip the flag off and triage." (Similar patches for the other 10 gaps.)

### Example 2 — A thin API spec for an integration

**Source.** A one-page brief for a new webhook integration. Surface area: `integration`. Requirements are crisp; observability and security are silent.

**Output highlights.**

- **Gap report.** 8 gaps. 2 blocking: (a) no auth specification for the webhook receiver, (b) no rate-limit / idempotency specification. 4 important: observability events, error responses (4xx/5xx codes the receiver should return), retry behavior expectations, debugging path for failed deliveries. 2 nice-to-have: a worked example payload.
- **Kickoff readiness.** Not ready — auth and idempotency are non-negotiable before engineers start.
- **Patches.** For auth: "Each webhook request includes header `X-Signature: hmac-sha256=<hex>`, computed over the raw body using a shared secret per integration. Receivers MUST validate before processing. Validation failures return 401 and are not retried."

### Example 3 — A mature spec with light gaps

**Source.** A 4,000-word PRD that has been through two review cycles. Surface area: `mobile-feature`.

**Output highlights.**

- **Gap report.** 4 gaps. 0 blocking. 2 important: backgrounding behavior for the new feature is not specified; offline behavior is not specified. 2 nice-to-have: copy is not extracted for translation; one acronym is not in the glossary.
- **Kickoff readiness.** Ready — the spec can ship to kickoff as-is, with the 2 important gaps tracked as work items to close during sprint 1.
- **Patches.** Drafted backgrounding and offline behavior text, ready to paste.

## Limitations

- The skill audits *for* completeness. It does not validate whether the *design* is right; a perfectly complete spec for the wrong feature is still the wrong feature.
- The skill assumes the asker can fix the gaps. If the gaps are blocked by missing inputs from a team not in the asker's chain, the patches will be templates rather than usable text.
- The skill may flag gaps that the team has intentionally decided to leave open. Mark such items as "intentional gap, see [link]" in the spec and the audit will respect the marker.
- Some checks are surface-area specific; using `generic` will produce a less targeted audit. When in doubt, pass the right `surface_area`.
- Compliance checks are non-exhaustive. The skill names the most-common regimes; it does not perform legal review.
- The skill produces a doc-quality verdict, not a delivery-risk verdict. Delivery risk depends on team capacity, dependencies, and execution — those need a separate conversation.
