# Detector Evaluation Rig Designer

## When to use

Use this skill when an engineering team needs an evaluation regime that tells them whether a real-time object detector is good enough to ship and stays good enough after it ships. The output is a written plan that covers how the test sets are built, which metrics are computed, how cohorts and slices are designed, how false positives are explored, how drift is monitored once the detector is live, and which gates a release must clear before it is promoted. The skill produces a plan and a structured artifact, not the evaluation code itself.

Use this skill at four moments: setting up a first evaluation rig for a new detector that has only had training-side metrics so far; replanning an evaluation when a model expands its class taxonomy or its operating envelope; debugging a regression where aggregate metrics look fine but field complaints suggest a hidden cohort is broken; and adapting an evaluation to a new deployment context, where the previously trusted offline metrics no longer correlate with field outcomes. It is not the right skill for designing the data pipeline that produces training data (see the data-pipeline skill), nor for the deployment architecture that runs the detector (see the deployment-architect skill), nor for choosing model weights for a fresh training run.

**Mandatory safety disclaimer.** This skill produces methodology guidance. Real-time detection failures in safety-critical contexts can cause physical harm, financial loss, or violations of individual rights. Every recommendation must be validated in the target operating envelope; never accept a detector for production on aggregate metrics alone — slice-stratified evaluation, edge-case coverage, and live drift monitoring are required, with documented stop-the-line triggers and a human-review path for ambiguous cases.

## How to apply

The skill walks a fourteen-stage pipeline. The early stages establish what is being measured and why; the middle stages build the test sets and metrics; the late stages design the gates and the post-deployment monitoring.

### Stage 1 — Restate the evaluation question

1. Read `detector_under_test` and rewrite the evaluation question as a sentence in the form: "Decide whether <detector identifier> meets <acceptance criteria> across <operating envelope> well enough to <promotion decision>." If any clause is missing or vague, ask before continuing. An evaluation that does not name the promotion decision it serves becomes vanity metrics.
2. Distinguish between *acceptance evaluation* (does this version meet the bar?), *comparative evaluation* (which of these versions wins?), *diagnostic evaluation* (where is the model weak?), and *monitoring evaluation* (is the deployed model still good?). The same dataset can serve more than one purpose but the rig must declare which.
3. Identify the *audience* for each evaluation report: engineering, product, safety, regulatory, executive. Different audiences need different views of the same evidence; the rig publishes the underlying data once and renders multiple views.

### Stage 2 — Define the taxonomy and the unit of judgement

4. Pin the class taxonomy: full list, definitions, mutually-exclusive boundaries, super-categories. Many evaluation surprises trace to a class definition that subtly changed between training and evaluation (an "open door" became a "door"; "person" silently included "person on bike").
5. Pin the *unit of judgement*. Detection metrics evaluate per-object decisions, but the decision the consumer cares about may be per-frame (was there a person in this frame at all?), per-event (was there a perimeter breach in this minute?), or per-track (did the system correctly identify this object across frames?). Build the rig to compute both the per-object metric and the per-decision metric that matches the consumer.
6. Pin the *match criterion*. The default is intersection-over-union above a threshold; alternatives include centre-point distance, generalized intersection-over-union, or bounding-box-corners distance. For rotated boxes, segmentation masks, or three-dimensional outputs the match criterion is different and must be specified. The same criterion must be used training-side and evaluation-side or trends will not be comparable.

### Stage 3 — Build the test-set portfolio

7. Build at least three test sets with different purposes. A *primary acceptance set* is large, stratified across the operating envelope, and treated as the canonical "what does mean precision look like" set. A *regression set* is smaller, hand-curated, includes every historical failure that has been root-caused, and is the set the release blocks on. A *diagnostic set* covers edge conditions deliberately oversampled to detect weakness — this is where small-object, occluded, crowded, and adversarial cases live.
8. Build optional sets that match deployment realities: a *temporal-novelty set* of recent data the model has not seen, used to detect distribution shift; a *negative-only set* of images with no instances of any target class, used to bound the false-positive rate independently of recall; a *paired-precision set* where every image has both positive and negative regions to exercise the post-processing layer.
9. Stratify each test set by the dimensions of the operating envelope: illumination, weather, scene type, camera type, distance from camera, occlusion level, object size, demographic factors where relevant and lawful. Each stratum gets a minimum cell size so per-stratum metrics are statistically meaningful.
10. Decide the *label authority* for each set. Acceptance sets need majority-vote labels from multiple annotators with adjudication; regression sets need gold labels with named curators; diagnostic sets often need expert labels. Document the inter-annotator agreement floor below which a sample is dropped or re-labelled.
11. Specify the *split discipline*. Training, validation, and test must not share any source sequence, location, or session — temporally and geographically adjacent frames leak. Document the split key (camera id, session id, location id, time window) and the audit that verifies no leakage occurs.
12. Specify the *refresh policy*. Acceptance sets that never change become stale; sets that change every release lose comparability. A common pattern is to freeze the acceptance set at major versions and add new edge cases to the diagnostic set on a continuous basis.

### Stage 4 — Define the metric set

13. Pin the *primary detection metrics*. Mean average precision over a range of intersection-over-union thresholds is the field default; average recall at small/medium/large object sizes captures recall behaviour the average-precision number can hide; per-class average precision exposes per-class weakness; precision and recall at a chosen operating point (typically the deployment score threshold) translates the model to the consumer's number.
14. Pin the *latency metrics*: median, 90th, 99th percentiles, maximum, jitter (the variance of consecutive-frame latencies), and warm-up duration. Aggregate latency without percentiles hides tail behaviour that breaks streaming workloads.
15. Pin the *combined latency-accuracy metric* if one exists for the deployment context. Many real-time systems care about a Pareto front more than a single point; the rig should publish that front, not pretend a single number is the answer.
16. Pin the *robustness metrics*: accuracy under common corruptions (motion blur, defocus, noise, jpeg compression, weather-style augmentations), accuracy across cohorts compared to aggregate (the gap between worst cohort and aggregate is a fairness and reliability signal), accuracy on the temporal-novelty set compared to the acceptance set.
17. Pin the *post-processing metrics*: average number of detections per image at different score thresholds (a sudden drop indicates a saturation problem), NMS suppression rate, count of low-confidence detections in known-empty regions.
18. State explicitly that the rig does not compute a single number. Every release report carries a vector of metrics across cohorts and test sets, plus a rendered summary.

### Stage 5 — Design slice and cohort analyses

19. List the slices that matter for the deployment: scene types, illumination bins, weather bins, camera bins, object-size bins, occlusion bins, time-of-day bins, demographic bins where relevant and lawful. Each slice gets its own per-class precision-recall report.
20. Apply *minimum-cell-size discipline*. A cell with too few objects produces noisy metrics that mislead decisions; the rig either pools small cells, flags them as low-confidence, or excludes them from gates.
21. Apply *intersectional slicing* for the highest-risk dimensions. For some deployments the worst cohort is at the intersection of two conditions (small-object plus low-illumination, for instance), and one-dimensional slicing hides it.
22. Build *worst-cohort tracking* into every report. The gap between aggregate metric and worst-cohort metric is often a more decision-relevant number than the aggregate alone.

### Stage 6 — False-positive sweeps

23. Design a *negative-region scan*: a corpus of images known to contain no target objects, with the detector run at a low score threshold to surface every spurious detection. The false-positive density is a deployment-critical number that is often invisible in average-precision metrics.
24. Design a *score-threshold sweep* that publishes precision-recall curves not just averages. The chosen deployment threshold is then a documented operating point on that curve, with stated trade-offs.
25. Design a *class-confusion analysis*. When two classes are visually similar, false positives appear as confusions; the rig publishes a confusion matrix even though detection is not classification, because per-class precision behaviour depends on it.
26. Design a *hard-case mining* loop. After each evaluation, samples with the highest residual loss or the highest disagreement among ensemble members feed back into the diagnostic test set on the next iteration.

### Stage 7 — Latency and throughput measurement

27. Specify the *measurement harness*. End-to-end latency is what the consumer sees; module-level latency tells the engineering team where to look. Both belong in the report.
28. Specify the *load profile* under which latency is measured: idle, steady-state at expected load, burst above expected load, cold-start. Latency at idle is a misleading number for a multi-tenant deployment.
29. Specify the *hardware profile*: the exact accelerator, driver, runtime, and build identifier. Latency numbers without those become apocrypha.
30. Specify the *repeat count* and outlier policy. A handful of measurements is not enough; hundreds-to-thousands of samples are typical, with the worst few percent reported as the tail.

### Stage 8 — Edge-case curation

31. Build the edge-case library deliberately. Useful categories include: very small objects, very large objects, heavily occluded objects, crowded scenes, motion-blurred objects, near-camera and far-camera objects, atypical poses, atypical viewpoints, adversarial physical artefacts (reflective surfaces, retro-reflective signs, repeating patterns), known-look-alike negatives (a sticker that resembles a target class).
32. Tag each edge case with its provenance: synthetically generated, field-captured, hand-curated, derived from a regression incident. Provenance affects the weight the rig assigns to a metric drop on that case.
33. Maintain a *previously broken* set: every time a field issue is traced to a specific image or sequence, that artefact is added to the regression set with an explanatory comment and a linked incident. The set grows as the deployment matures.

### Stage 9 — Synthetic and simulated data policy

34. Decide whether synthetic data participates in evaluation. Synthetic images can fill rare-condition cells but risk over-stating performance because the model also has not seen any real version. The rig either uses synthetic data only for diagnostic and regression sets (not for acceptance gates) or labels synthetic-derived metrics explicitly.
35. Decide whether augmented data participates. Robustness-under-corruption metrics are derived by augmenting clean images; the augmentation policy must be documented and pinned, because changes to it silently change the metrics.
36. Document the *sim-to-real gap*. If simulated data is used for cohort exploration, the rig periodically validates that the gap between simulated and real performance on the same cohort is bounded and not drifting.

### Stage 10 — Release gates

37. Pin the *aggregate gate*: the top-line metric over the acceptance set must meet a floor. Aggregate gates alone are insufficient but they are the floor.
38. Pin the *per-class gate*: every class with safety-critical status must meet its per-class floor; non-safety-critical classes have a no-regression rule (the new version cannot lose more than a stated delta).
39. Pin the *cohort gate*: every cohort with a designated minimum must meet it; no cohort may regress beyond a stated delta from the previous release.
40. Pin the *regression gate*: every artefact in the regression set must be detected correctly; a failure here blocks the release regardless of aggregate gain.
41. Pin the *latency gate*: P95 and P99 latencies must meet their floors; warm-up time and cold-start recovery must meet their floors.
42. Pin the *false-positive gate*: false-positive density on the negative-only set must not exceed the floor.
43. Document the *waiver process*. Some failures are knowingly accepted (a regression in a low-priority class to gain in a high-priority class). Waivers are signed, time-bounded, and tracked.

### Stage 11 — Drift monitoring once deployed

44. Pin *input-side drift signals*: distributional moments of the input stream (brightness, edge density, scene-class distribution if a classifier is available) compared to the training distribution. A persistent drift triggers an offline evaluation.
45. Pin *output-side drift signals*: rolling detection rate per class, rolling NMS suppression rate, rolling distribution of score values. These detect both performance regressions and input shifts.
46. Pin *agreement-with-verifier signals* if a secondary model runs on a fraction of traffic. Disagreement above a baseline is a high-value early-warning signal because both models failing in the same way is unlikely.
47. Pin *feedback-loop signals*: rate of overrides by a downstream human reviewer, rate of corrections from a label-feedback loop, rate of escalations to manual review.
48. Specify the *cadence*. Some signals are evaluated continuously, some at a daily rollup, some weekly. The rig documents the cadence and the on-call ownership.
49. Specify the *trigger conditions*. A drift signal exceeding a threshold for a sustained window triggers a structured response: re-evaluate on the regression suite, snapshot inputs for analysis, alert the model owner.

### Stage 12 — Reporting

50. Build a *release report* template. Each release publishes the same set of tables and plots so trends across releases are legible: aggregate metric trend, per-class trend, per-cohort heatmap, regression-set pass-fail, latency histogram comparison, false-positive sweep, drift dashboard snapshot.
51. Build an *executive summary* layer that translates the technical numbers into the decisions they support: ship-no-ship, on-call-confidence, risk-changes-vs-previous-release.
52. Build a *forensic capability*: given any deployed detection, the rig can trace which build produced it, which version of the post-processing applied, and the per-stage metrics that were current at release.

### Stage 13 — Risks, limitations, and acceptance

53. Enumerate the risks of the rig itself: test-set staleness, label noise, leakage between train and test, overfitting to the acceptance set across releases, cohort definitions that miss the population the consumer cares about, latency measurements that do not reflect production load. Each risk has an owner and a periodic audit.
54. Document *what the rig cannot tell you*. A passed evaluation does not prove field safety; it proves that on the artefacts the rig knows about, the detector behaves at the agreed level. The deployment must still carry drift monitoring and a human-review path.

### Stage 14 — Compose the deliverable

55. Open with the evaluation question, the promotion decision it supports, and the audience for the report.
56. Render the plan as a markdown document organized by the stages above, with at least one example slice table, one example release report skeleton, and the drift dashboard outline.
57. Emit `plan_json` with structured fields: `test_sets[]`, `metrics`, `cohorts[]`, `gates`, `drift_signals[]`, `cadence`, `risks[]`.
58. Close with the mandatory safety disclaimer restated, an "open issues" list (cohorts known to be under-covered, label-quality concerns, latency-measurement gaps), and pointers to the deployment-architect and data-pipeline skills.

### Cross-cutting evaluation concerns

59. *Label-noise accounting*. Every test-set metric is upper-bounded by label correctness. The rig estimates label noise per set by sampling a small fraction for re-labelling under a more rigorous protocol and computing per-class disagreement. Metrics carry an explicit "label-noise floor" so a stakeholder reading a 0.97 mean-precision number knows whether the residual gap is the model or the labels.
59. *Multiple-comparison discipline*. A rig that compares two builds across ten cohorts and three metrics produces thirty comparisons; some will look significant by chance. The plan documents which comparisons are pre-registered (and therefore acceptable as gates) and which are exploratory (and therefore reported but not gating).
60. *Operating-point honesty*. The deployment score threshold is a single number on a precision-recall curve; reporting precision-recall as a curve and the chosen operating point as a flagged dot is more honest than a single mean value, which can hide threshold-sensitive behaviour.
61. *Test-set hygiene*. Each test set has a written charter (purpose, refresh policy, owner), a versioned label manifest, a hash of the underlying images, and an audit log of every change. A test set that has silently mutated is not a test set; it is a moving target.
62. *Reviewer load*. Some metrics require human adjudication (ambiguous match cases, occluded objects, boundary regions). The rig estimates the human-hours per release report and either budgets for them or designs the metric to be machine-decidable.
63. *Cross-team contract*. The evaluation rig is the contract between training, deployment, product, and safety. Once the contract is signed, both training-side and deployment-side teams optimize against it; changes to the contract are co-signed by the same set of stakeholders.
64. *Statistical floors*. Per-class metrics on small classes need a stated minimum sample count before they enter a gate; below that count the metric is reported with explicit "low-confidence" markers and is excluded from no-regression rules.
65. *Adversarial probing*. A periodic adversarial pass — synthetic perturbations, known-look-alike negatives, or red-team curated cases — exercises the model on inputs the operating envelope does not naturally produce. The rig owns the schedule and the response.

### Stage 14.4 — Match-criterion precision

The choice of matching algorithm between predicted and ground-truth boxes is more consequential than it appears. Standard intersection-over-union at a single threshold biases toward bounding-box overlap and away from centre accuracy; a generalized variant that penalizes both overlap and enclosing-area mismatch reports differently. For rotated boxes the match criterion is rotated intersection-over-union, which itself has multiple algorithmic implementations that disagree at the boundary. For masks the match criterion is mask-level intersection-over-union, which can be computed at pixel level (rigorous) or at polygon level (approximate but cheaper). The rig picks one and locks it; the lock survives across releases. Comparing a 0.78 mean-precision number computed with one match criterion against a 0.80 number computed with another is the kind of release-day disaster the lock prevents.

A. Document the match criterion in the `metrics` section of the plan with its parameters and a reference to the implementation that backs it.
B. Re-evaluate the rig if the criterion ever changes; do not retrofit old reports against a new criterion.
C. Surface match-criterion choices in the executive summary so non-technical stakeholders can ask whether a metric change reflects a model change or a measurement change.

### Stage 14.5 — Pipeline-level evaluation versus model-level evaluation

66. The deployed pipeline is more than the model. Preprocessing, post-processing, NMS thresholds, tracker association, and uncertainty fallback all influence the consumer's number. The rig evaluates the *end-to-end pipeline* on a set of held-out raw inputs at least once per release, in addition to the model-level evaluation that compares a new checkpoint to the previous one in isolation.
67. Pipeline-level evaluation requires raw inputs (video, image streams) and the full inference stack assembled as it will run in production. The dataset for this is smaller than the model-level acceptance set because raw inputs are heavier and the evaluation is slower; the test set is chosen for breadth across operating modes rather than statistical depth on any one slice.
68. The gap between model-level and pipeline-level numbers is itself a quality signal. A model that gains a point of mean precision in isolation but loses ground at the pipeline level has had its gain absorbed by a misconfigured threshold downstream; the rig must surface this gap explicitly.
69. Pipeline-level regression tests anchored to historical incidents are run as smoke tests on every change to any pipeline component, not only on model changes. A change to the NMS threshold, the preprocessing resampler, or the post-processing decode is a release-eligible change and is evaluated as one.

### Stage 14.6 — Long-tail and rare-class measurement

70. Rare classes are under-represented by definition. A test set sized for the dominant classes has cells too small to detect a regression on a class that appears in one of a thousand frames. The rig either *over-samples* rare classes in dedicated cohorts, *up-weights* them in the aggregate metric, or reports them with explicit "small-cell" caveats.
71. Synthetic augmentation can fill rare-class cells but the rig labels synthetic-derived metrics so a reader can distinguish from a metric earned on field data.
72. Long-tail recall is often the difference between a deployable detector and one that surprises in the field. The rig publishes a separate long-tail recall report at every release cadence and gates on it for safety-critical classes.

### Worked second example

Beyond the first example above, the rig is portable to other contexts. As a second worked example, consider a wildlife-monitoring detector on remote trail cameras where bandwidth, label cost, and class imbalance dominate the design:

- Test sets: an acceptance set drawn from a multi-year archive stratified by species, season, time-of-day, weather, and trail. A regression set anchored to historical mis-identifications between visually similar species. A negative-only set of empty-trigger images, which often outnumber positives by an order of magnitude in real deployments.
- Metrics: per-species average precision, but reported alongside count-stratified results because rare species have noisy metrics; false-trigger rate on the negative-only set, because every false trigger costs reviewer time downstream; per-trail and per-season slice analysis to surface camera-specific drift.
- Gates: per-species recall floors for the highest-priority species; aggregate false-trigger ceiling; no-regression rule on the regression set; reviewer-load ceiling computed from the predicted detection count at the deployment threshold.
- Drift monitoring: rolling per-species rate by trail; reviewer override rate; cadence is daily aggregation and weekly cohort report. A species that vanishes from a trail's detections is investigated as a possible model failure before it is accepted as a true ecological signal.
- Out-of-distribution behaviour: the rig includes a feature-space distance score for each detection and tracks the distribution of distances over time; a sudden shift indicates either a new species, a new camera, or a model failure, and the response policy documents who investigates first.

## Examples

**Input (placeholder):**

`detector_under_test`: "Multi-class detector for people, vehicles, and unattended packages on outdoor fixed cameras."

`operating_envelope`: "Day, night with artificial illumination, rain, fog; urban and suburban scenes; mounted at 3–5 metres."

`data_assets`: "About 200k labelled frames across 18 months; per-class counts are imbalanced — packages are about 2 percent of objects."

`acceptance_floor`: "People recall at least 0.95 at precision 0.85; vehicles mean precision at least 0.6; packages recall at least 0.8 at precision 0.7; P99 latency at most 80 ms."

`deployment_context`: "Single-server multi-camera streaming; alerts go to a control room; rollback within five minutes."

**Plan (abbreviated):**

- Test sets: an acceptance set of 20k frames stratified across illumination, weather, scene type, mounting height; a regression set of 1,500 hand-curated frames anchored to historical incidents; a diagnostic set of 5k frames over-sampling small-object, heavy-occlusion, and reflective-surface conditions; a negative-only set of 10k frames containing no target objects.
- Metrics: per-class mean average precision over IoU 0.5–0.95, average recall at small/medium/large, precision-recall curves at the deployment threshold, false-positive density on the negative-only set, P50/P90/P99 latency.
- Slices: illumination quartiles, weather bins (clear/rain/fog), scene types, distance bins, occlusion-level bins, plus a small-object-plus-low-illumination intersectional cell.
- Gates: aggregate mAP floor; per-class floors; no-regression rule per cohort beyond 0.5 percentage points; regression set must pass at 100 percent; latency floors; false-positive-density ceiling.
- Drift monitoring: rolling input-brightness drift, rolling detection rate per class, agreement-with-verifier on a 1-percent sample, on-call alert if any signal sustains an excursion for thirty minutes.
- Cadence: continuous drift signals, weekly cohort report, per-release full evaluation.

**Output excerpt:** the markdown plan plus a JSON object whose `gates` field carries `{aggregate, per_class, per_cohort, regression, latency, false_positive_density}` and whose `drift_signals` is a list of `{signal, definition, threshold, cadence, action}` records.

### Worked third example

As a third example, consider an evaluation rig for a real-time biometric-presence detector deployed in retail environments where the regulatory and demographic-fairness constraints dominate the design. The consumer is a store-traffic analytics dashboard that counts unique visits and reports occupancy; the system must not retain biometric templates, must perform demographic-parity audits, and must satisfy a documented retention policy.

- Test sets: an acceptance set stratified across demographic dimensions (age range, perceived gender, perceived skin tone) using a vendor-curated public dataset plus a smaller in-store sample collected under consent; a regression set of historical mis-counts traced to specific store layouts; a negative-only set of empty-store frames at all times of day; an adversarial set with mannequins, posters, and reflections.
- Metrics: per-cohort recall and precision at the chosen operating point; demographic-parity gap as the difference between the worst cohort and the aggregate, reported on every release; false-positive rate on the negative-only set; latency histogram across cameras.
- Slices: demographic cohorts, store-format bins, lighting bins, camera-mount-height bins, time-of-day bins, and an intersectional cell for the demographic-by-lighting interaction that is the historical weak point.
- Gates: aggregate precision and recall floors; demographic-parity gap below a documented threshold; no regression on the regression set; latency floors; false-positive density ceiling.
- Drift monitoring: rolling per-camera and per-cohort detection rate; consent-tracking signal; weekly demographic-parity report shared with the compliance team.
- Cadence: continuous drift signals, daily privacy-and-retention compliance check, weekly demographic-parity report, per-release full evaluation.
- Audit: every cohort metric and every gate evaluation is logged with a hash of the test set and a hash of the build, so a regulator can reconstruct any past decision.

The third example exists to make a point: the same rig structure adapts across domains. The stages do not change; the *cohort definitions*, the *gate thresholds*, and the *audit obligations* change. A rig is portable when its structure is decoupled from any one deployment's specifics.

### Stage 14.7 — Threshold calibration as a release artifact

The deployment score threshold is not a model property; it is a release artifact computed from the model and the test set together. Two builds with the same architecture and the same training data but slightly different score distributions can have very different deployment thresholds. The rig publishes the threshold as part of the release artifact, alongside the precision-recall curve that earned it, and binds the threshold to the model checksum. Changes to the threshold without a model change are a documented release event in their own right.

A. The rig publishes a *threshold-vs-target* table: for each candidate threshold, the per-class precision and recall on the acceptance set. The chosen threshold is the row that meets the gate; the rationale is recorded with the build.
B. The rig recomputes the threshold on every release; it is never inherited silently.
C. Threshold changes between releases that exceed a documented sensitivity are flagged for review — a large threshold drift can be a symptom of score-distribution drift in the model that mean precision did not reveal.

### Stage 14.8 — Federated and per-tenant evaluation

When the deployment serves multiple tenants — a multi-camera enterprise, a multi-customer SaaS, a multi-region rollout — aggregate metrics across tenants hide the worst tenant. The rig supports *per-tenant* evaluation as an additional axis: each tenant has its own acceptance and regression slice; aggregate metrics are reported with worst-tenant alongside, and gates apply per tenant. Tenants with insufficient data fall back to the aggregate gates plus an inheritance rule that documents the assumption.

A. The plan documents the *tenant-onboarding* evaluation: when a new tenant joins the service, a structured assessment runs on a small sample of their data to predict cohort behaviour and surface foreseeable issues before live traffic.
B. The plan documents the *tenant-offboarding* policy: when a tenant leaves, their evaluation slice is archived under a retention rule, not deleted, so historical regression analyses remain reproducible.

### Stage 14.9 — Evaluation infrastructure as code

The rig is itself an engineering artifact and must be maintained as one. The plan documents the version control for the test sets (set manifests in a repository, image blobs in a content-addressed store), the version control for the evaluation code (the same review and release discipline as the inference code), and the audit trail for every report (input hashes, code commit, parameters, environment). An evaluation that cannot be reproduced from its inputs is not an evaluation; it is an anecdote.

A. The rig publishes a *re-run* command: given a release identifier, anyone can reproduce the report from the manifest. The command works months later because the manifest pins every input.
B. The rig publishes a *diff* command: given two release identifiers, the report names every difference between the two evaluations — different test-set version, different code, different parameters — so the reader knows what changed in the measurement as well as what changed in the model.
C. The rig protects the test sets from leakage into training. The acceptance set in particular is never used as training data, and a leakage check runs on every training run.

### Stage 14.10 — Human-review integration

For deployments that route uncertain or contested detections to humans (the deployment-architect skill's fallback path), the evaluation rig integrates with the human-review pipeline. The corrected labels from review become a labelled stream that flows back into the diagnostic and regression test sets with explicit provenance. The agreement rate between the deployed model and the human reviewers is itself a metric — high agreement on easy cases and disagreement on hard cases is the healthy pattern; high disagreement on easy cases indicates a deployed-model regression.

A. The rig publishes the *review agreement* metric per cohort.
B. The rig pins the *review-derived label policy*: a human-corrected label is treated as gold for the diagnostic set but is only promoted to the acceptance set after a second independent review confirms it.
C. The rig pins the *time-to-include* policy: a corrected label is available in the diagnostic set within a stated window so future releases can be evaluated against the most recent field failures.

### Stage 14.11 — Privacy, consent, and regulatory framing

When the test sets contain images of identifiable people, the rig is also a privacy artifact. Many regulatory frameworks restrict the storage of biometric data, the retention of identifiable images, and the cross-border transfer of personal data. The plan documents the privacy provenance of every test set: where the images came from, what consent governed their collection, where they may be stored, and who may view them.

A. *Consent provenance*. Each test image is tied to a consent record or to a documented public-data licence; images without a clear provenance are excluded.
B. *Retention*. The plan sets a retention horizon; images past their horizon are deleted; deletion is audited.
C. *Access*. Reviewers and auditors are named; access is logged.
D. *Cross-border transfer*. Where applicable, the plan documents which test sets may flow across which jurisdictional boundaries; sets that may not are pinned to in-region infrastructure.
E. *Right-to-erasure*. If a data subject exercises a deletion right, the rig has a procedure to remove the affected images and re-baseline the dependent reports without invalidating the historical audit trail.

### Stage 14.11.5 — Fairness audit cadence

For deployments that touch human subjects, demographic-parity and equalized-odds analyses are first-class evaluation outputs. The plan documents the cadence, the protected attributes considered (and the legal basis for considering them), and the action policy when a parity gap exceeds the documented threshold.

A. Parity audits are released on a fixed cadence regardless of model changes; drift in field demographics is itself an audit-worthy event.
B. Audit results are reviewed jointly by engineering, product, and compliance.
C. A failing audit triggers a stop-the-line on the next release until the gap is investigated and either closed or formally accepted with sign-off.

### Stage 14.12 — Tooling boundaries

The rig sits in an ecosystem that includes a dataset-management system, an experiment tracker, a CI runner, a dashboarding plane, and a deployment release plane. The plan identifies the boundary between the rig and each neighbour: what the rig owns, what it consumes from neighbours, what it produces for them. Clear boundaries prevent the rig from becoming the place where every related concern lives.

A. The rig owns: test-set manifests, metric definitions, gate definitions, drift signals, the per-release report.
B. The rig consumes: training-side manifests, deployment artifacts, the production telemetry stream.
C. The rig produces: pass/fail signals to the release plane, cohort drift summaries to the dashboarding plane, labelled feedback to the dataset-management system.

A rig with clean boundaries is testable, replaceable, and explainable. A rig that owns every related concern is none of those.

### Acceptance criteria for the rig itself

An evaluation plan produced by this skill is acceptable when it satisfies the following checks:

1. *Promotion decisions named*. Every gate ties to a decision a person actually makes; gates that do not decide anything are removed.
2. *Cohorts cover the operating envelope*. Every dimension in the operating envelope has a stratification; intersectional cells exist for known-risky pairs; minimum cell sizes are stated.
3. *Metrics defined precisely*. Match criterion, score threshold, sample size, and confidence floor are documented; the report carries those numbers alongside the metric so a reader can verify.
4. *Drift signals operational*. Every drift signal has a definition, a threshold, a cadence, and an owner; orphan signals are removed.
5. *Test-set hygiene*. Every test set has a charter, a version manifest, an owner, and a refresh policy; leakage audit has run.
6. *Reproducibility*. Every report can be re-run from inputs months later; the diff command works.
7. *Human-review integration*. If the deployment uses human fallback, the rig integrates with it; review-corrected labels feed back with provenance.
8. *Cross-skill pointers*. The rig names the deployment-architect and edge-deployment skills explicitly and identifies the inputs each one needs from this plan and provides back for it.

A plan that passes all eight is ready for stakeholder sign-off. A plan that fails any one returns to the relevant stage.

## Limitations

- The plan is methodology, not infrastructure. Picking a specific dataset-management tool, label-store, or experiment-tracking system is outside the scope.
- The numeric floors and thresholds in any example are illustrative. Real floors must be set jointly with product, safety, and legal stakeholders.
- The skill assumes labelled data exists. Cold-start regimes where no labels are available need a separate plan that starts with weak labels, active learning, and bootstrapping.
- Statistical significance under small per-cohort cell sizes is a real risk; the plan flags it but does not specify the confidence-interval method, which depends on the metric and the workflow.
- High-regulation contexts (medical, biometric identification, demographic decisions) impose additional cohort and reporting obligations that this plan flags but does not encode in full.
