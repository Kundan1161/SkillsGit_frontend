## When to use

Invoke this skill when a VFX supervisor, producer, or lead compositor must package a shot (or a sequence of shots) for handoff to another team — an external vendor, a freelancer, a parallel studio, or even a future version of themselves. Typical situations:

- A shot is leaving the originating studio for an external vendor and must arrive with everything the vendor needs to start work, with no back-and-forth queries.
- A sequence of related shots needs a consistent breakdown so each shot inherits the sequence-level conventions and only its per-shot specifics differ.
- An internal handoff is needed between departments (matchmove to layout, layout to lighting, lighting to comp) and the boundary must be unambiguous about what is finished and what is provisional.
- A shot is being archived for future revisits and must be self-contained enough that someone in a year can rebuild from the package alone.

Do not invoke this skill for purely creative briefs that have not yet been broken down — the motion-graphics shot architect skill applies. Do not invoke it for matte extraction or compositing methodology — those have dedicated skills. Do not use it as a substitute for production tracking; it produces the contents of a handoff, not the project-management system that tracks them.

## How to apply

The methodology produces a self-contained, versioned package for each shot that respects sequence-level conventions, carries every piece of upstream data the receiver needs, and defines an explicit review and approval loop.

### Phase overview

- Phase 1 establishes sequence-level conventions so per-shot work inherits them.
- Phase 2 builds the shot brief that travels with the package.
- Phase 3 prepares the plate at the highest available precision with full metadata.
- Phase 4 assembles tracking, camera, and survey data.
- Phase 5 gathers on-set reference (HDRI, color charts, witness cam, set photos).
- Phase 6 lists and versions every asset the shot needs.
- Phase 7 prepares the edit-locked cut reference and audio stems.
- Phase 8 packages everything with manifest, README, and checksums.
- Phase 9 defines the review and approval loop.
- Phase 10 self-checks the package before handoff.

The defining principle of a handoff: the package must be self-sufficient. A receiver with no other context, no access to the studio's internal servers, and no relationship with the originator should be able to start work using only the package.

### 1. Establish sequence-level conventions before shot-by-shot work

1. **Lock the sequence-level frame rate, resolution, and aspect ratio.** Per-shot conventions must inherit these; never let a shot drift in frame rate without flagging.
2. **Lock the working color space and view transform.** Distribute an OCIO configuration version pinned to the project; the receiver uses the same version. Inconsistent OCIO configs are one of the most common cross-studio defects.
3. **Adopt a single file-naming pattern.** Recommended: `<show>_<seq>_<shot>_<task>_<descriptor>_v<NNN>.<ext>`. Numbered versioning is mandatory; date-stamped names alone do not survive parallel iteration.
4. **Adopt a directory structure pattern.** Each shot directory contains the same subdirectories in the same order: `plates/`, `reference/`, `camera/`, `assets/`, `comp/`, `renders/`, `notes/`, `delivery/`. Predictable structure cuts onboarding for the receiver from days to minutes.
5. **Define what "edit-locked" means.** A handoff against an unlocked edit will require rework on every cut change. Insist on an edit lock for the relevant cut before shipping; flag explicitly when a shot is handed off against a soft edit so the receiver builds with handles.
6. **Define handles.** Plate handles of at least 12 frames at head and tail are standard; some sequences need more if the cut is still in flux. Receivers should always work to handles, not the cut frame range, and trim only on final delivery.

### 2. Build the shot brief

7. **State the shot's identity and timing.** Sequence and shot number, total frame count including handles, frame rate, working resolution, working color space, view transform.
8. **State the creative ask in one paragraph.** What the shot must communicate. Avoid jargon; the brief should read clearly to a new artist who has not seen the rushes.
9. **List the elements that change.** Replace (existing element swapped), add (new element introduced), remove (element erased), modify (existing element altered). Each element gets a short description and an approximate screen location and timing window.
10. **Identify the look reference.** A still or moving reference for the look the shot must hit. If reference comes from an internal master shot, name the master and its version.
11. **List approval gates.** Three to five gates is typical: matte lock, layout lock, lighting lock, comp lock, final. Each gate has a named approver and a target date.
12. **Surface known risks.** Plate problems (motion blur on a hard edge, sky blown out, mistaken focus), missing data (no clean plate, no HDRI), or creative ambiguities (two competing references). The brief is the right place to surface these; do not bury them in a side conversation.

### 3. Plate preparation for handoff

13. **Hand off plates at their highest available bit depth.** A 16-bit half-float EXR sequence is the standard. If the original camera negative is in a raw format, decode to scene-linear half-float EXR before handoff, with the decode parameters documented.
14. **Hand off both the cut range and the handles.** Two read ranges: `plate_handles_NNNN-MMMM.exr` containing the full handle range, and metadata noting the cut-in and cut-out frame numbers.
15. **Hand off the clean plate(s).** A region with no actor or no removable element, captured on set, used for fill and screen cleanup. If a clean plate was not captured, document this and propose a fix (paint-fix from neighboring frames, or a stabilization-based fill).
16. **Hand off the un-distorted and the distortion-removed plate as a pair.** If a lens-distortion model is part of the pipeline, both the original-distortion plate and the un-distorted plate ship together, with the distortion parameters documented so the receiver can redistort at output.
17. **Hand off any per-frame metadata.** Camera frame rate, shutter angle, ISO, lens focal length, and aperture per frame if the lens was being adjusted. Sidecar files (CSV, JSON, or studio-specific formats) accompany the plates.
18. **Document the plate's color encoding.** Camera color space, transfer function, and the transform applied to reach the handoff encoding. Do not assume the receiver will guess correctly.

### 4. Tracking and camera-match data

19. **Hand off the solved camera.** A camera animation matched to the plate, expressed in the show's units (typically meters), in a format the receiver's 3D tool can consume. Common interchange formats are FBX, Alembic, USD, or the studio's internal format.
20. **Document the camera's intrinsic parameters.** Focal length per frame (or a constant if locked), sensor size, principal point offset, and any non-linear distortion model parameters not already baked into the un-distort.
21. **Hand off tracking markers and their solved positions.** Even when a camera is solved, the markers themselves are useful as anchors for placement and as a sanity check on the solve.
22. **Hand off the matchmove scene.** The matchmove-tool scene used to derive the camera, so the receiver can re-solve or extend the track if needed.
23. **Hand off any object tracks.** If a prop, a vehicle, or a body region was tracked, ship its track with named animation matching the camera's animation interval.
24. **Hand off the survey data.** If the set was surveyed (lidar scan, photogrammetry, witness photographs), the survey data accompanies the camera so receivers can place elements correctly in 3D space.

### 5. On-set reference data

25. **HDRI captures.** Light-probe imagery from the set, ideally with three exposures captured back-to-back to build a high-dynamic-range environment. Document the position relative to the survey origin.
26. **Color charts and gray ball.** A frame of a color chart and a gray ball shot at the same lighting conditions as the plate; the matchmove or lighting team uses these to calibrate.
27. **Lens grid.** A frame of a lens grid (or several at different focus distances) used to derive the lens-distortion model.
28. **Witness-cam footage.** A secondary angle on the same scene aids 3D reconstruction and tracker placement.
29. **Set photographs.** Reference stills of the set, props, and costumes the shot will need. Annotate which frames were captured before and after the take.
30. **Talent reference.** If a digital double, hair simulation, or costume CG asset is needed, capture cyclorama photography and turn-around video before talent leaves the set.

### 6. Assets

31. **List every asset the shot uses.** A line per asset: name, version, source, the role in the shot, and whether the asset is hero (visible foreground) or context (background dressing).
32. **Use a published-asset versioning scheme.** Asset versions are immutable once published; a fix bumps the version, never edits the published asset in place.
33. **Hand off only the assets the shot needs.** A full library handoff pollutes the package and slows ingest. Hand off the specific versions referenced by the shot.
34. **Document any asset substitutions.** If a lower-resolution stand-in is shipping for review and the hero version will arrive later, name the substitution and the date the hero is expected.
35. **Hand off rigs only when animation is being authored.** A rigged character ships when the receiver will animate; a posed or baked asset suffices when only placement is needed.

### 7. Edit-locked timing and audio reference

36. **Ship the cut reference.** The cut as currently locked, with handles, encoded to a watchable codec (a ProRes or H.264 family proxy) showing the shot's place in the sequence.
37. **Ship the audio stem if relevant.** Audio that informs timing (foley hits, dialogue beats, music transients) ships as a sidecar. Mark whether audio is locked or temporary.
38. **Mark the cut-in and cut-out frames.** Inside the handle range, identify the final cut points so the receiver can avoid building hero detail outside them when budgeting effort.
39. **Identify any temp effects in the cut.** Temp shots, slug frames, animatics, or placeholder titles. The receiver must know what to ignore and what to match.

### 8. Package the handoff

40. **Adopt one packaging convention per project.** A directory tree (rsync or cloud sync), a tar or zip archive, a studio-specific package format (USD or an internal manifest). Choose one and use it everywhere on the project.
41. **Include a manifest at the package root.** A text or JSON file listing every file, its role, its version, and its checksum. The receiver verifies the manifest on ingest.
42. **Include a README at the package root.** A short human-readable orientation: which file is the brief, which is the cut reference, where the plates live, how to load the camera. Five minutes spent on a README saves a day of receiver questions.
43. **Verify checksums on both ends.** A transfer that drops a few bytes silently is rare but catastrophic. Verify a checksum after extraction.
44. **Track package versions.** Every handoff is a numbered version. A second handoff incorporating a notes pass is a new package, not an in-place update.

### 9. Review loop and QC

45. **Set a review cadence.** Dailies (daily review of work in progress) is the default. Weekly is common for slow-burn sequences; twice-daily for crunch.
46. **Define the review format.** A specific codec (a ProRes or DNxHR family file), a specific resolution, a specific color tag, with a slate and a burn-in carrying shot number, version, and date.
47. **Define the review tool.** A shared review platform (frame-accurate web review, internal screening room) is the default. Notes are time-coded; verbal notes alone do not survive.
48. **Define approval gates with named approvers.** Each gate from the brief has a named approver (VFX supervisor, director, client). Skipping a gate without explicit approval invites rework.
49. **Define the QC checks the deliverable must pass.** Edge integrity, alpha sanity, color tag and codec correctness, frame range and frame rate match, file naming and packaging match the convention. The receiver runs QC before submitting; the originator runs QC on receipt.
50. **Define the change-request process.** A standardized notes form ensures notes are actionable: shot number, frame number, what to change, reference. Free-form prose notes are a leading cause of misunderstood revisions.

### 10. Self-check before responding

51. **Is the brief self-contained?** A receiver with no prior context should be able to start work from the brief alone.
52. **Are all source materials in the package, not referenced by URL?** A handoff that relies on a server the receiver cannot reach is a defective handoff.
53. **Is every version number explicit?** Asset versions, plate versions, camera versions, brief versions. Implicit "the latest" fails the moment another version is published.
54. **Are tracking and camera data in a form the receiver's tool consumes?** Verify the interchange format before shipping; do not ship a format the receiver must translate.
55. **Is the review loop defined or assumed?** A handoff without a defined loop turns into informal back-channel reviews that drop notes.

## Directory structure (reference)

A predictable per-shot directory layout speeds receiver ingest. The following layout is a working reference; adopt it or a documented variant, and use it identically across every shot in the project:

```
<show>/<seq>/<shot>/
  README.md                        — orientation and how-to-load notes
  manifest.json                    — every file with role, version, checksum
  brief/
    <show>_<seq>_<shot>_brief_v<NNN>.md
  plates/
    <show>_<seq>_<shot>_plate_handles_<in>-<out>_v<NNN>.<frame>.exr
    <show>_<seq>_<shot>_clean_handles_<in>-<out>_v<NNN>.<frame>.exr
    <show>_<seq>_<shot>_plate_undistort_v<NNN>.<frame>.exr
  camera/
    <show>_<seq>_<shot>_cam_v<NNN>.abc
    <show>_<seq>_<shot>_cam_v<NNN>.fbx
    <show>_<seq>_<shot>_matchmove_v<NNN>.<tool-format>
    <show>_<seq>_<shot>_lens_distortion_v<NNN>.json
    <show>_<seq>_<shot>_trackers_v<NNN>.txt
  reference/
    cut_proxy_v<NNN>.mov
    look_ref_v<NNN>.<format>
    on_set_photos/
    set_hdri_v<NNN>.exr
    set_color_chart_v<NNN>.exr
    set_gray_ball_v<NNN>.exr
    set_lens_grid_v<NNN>.exr
    witness_cam_v<NNN>.mov
  assets/
    <asset_name>_v<NNN>/
  audio/
    <show>_<seq>_<shot>_audio_v<NNN>.wav
  notes/
    notes_log.md
  delivery/                        — empty; reserved for receiver outputs
```

Receivers create their working directories under the shot's `delivery/` so all submissions land in a known location.

## Naming convention details

A small set of rules covers most cases:

- **Token order is fixed.** Show, sequence, shot, task, descriptor, version, frame, extension. Never reorder.
- **Versions use a fixed-width number.** `v001` through `v999`; pad to three digits even when bumping past `v009` so directory listings sort correctly.
- **Frame numbers use a fixed-width number.** Five digits (`00001` through `99999`) is standard for a project that fits in that range; six digits for longer projects. Padding ensures correct sort order.
- **Avoid spaces, accented characters, and special characters.** Use only letters, digits, hyphens, and underscores.
- **No "final" in any file name.** Versions are mathematical; `v007` is final until v008 exists.
- **Date stamps are not version numbers.** A file with both a version number and a date is acceptable; a file with only a date is not (two artists working in parallel will produce identically dated files).

## Manifest file structure

The manifest is the single source of truth for what is in the package. A JSON structure that the receiver can validate programmatically:

```
{
  "package_version": "1",
  "show": "<show>",
  "sequence": "<seq>",
  "shot": "<shot>",
  "handoff_target": "<vendor name or internal team>",
  "handoff_date": "<ISO date>",
  "originator": "<artist or team>",
  "frame_rate": 24,
  "resolution": [1920, 1080],
  "pixel_aspect": 1.0,
  "working_color_space": "ACEScg",
  "view_transform": "ACES Rec.709",
  "cut_in_frame": 1025,
  "cut_out_frame": 1168,
  "files": [
    {
      "path": "plates/...",
      "role": "plate",
      "version": "v001",
      "checksum_sha256": "<hex>"
    },
    ...
  ]
}
```

The receiver runs a manifest verification on ingest to confirm no file was lost in transit.

## Receiver onboarding checklist

A handoff that delivers a perfect package but no onboarding documentation still loses days to receiver questions. Include in the README:

- The working color space and view transform; the OCIO config version and a link or attached copy.
- The frame rate, resolution, pixel aspect.
- The cut range and the handle range.
- How to load the camera into the receiver's 3D tool of choice.
- How to load the comp template into the receiver's compositor of choice.
- The review platform link, the cadence, and the credential or invitation flow.
- The point of contact for each approval gate.
- The expected dailies time and the timezone.
- The submission directory pattern the receiver should use.

A README of one page that hits these points is the difference between a one-week ingest and a one-day ingest.

## Examples

**Example invocation**

> "Helicopter-replacement shot, 6 seconds plus 24-frame handles each side. Source plate is log-encoded at 24p. We have a witness cam, lens grid, on-set HDRI, gray ball reference, lidar scan of the rooftop. Going to an external compositing vendor. Working space is ACEScg. Six-shot sequence; this is shot 03."

**Expected high-level output**

Brief: shot is `proj_seqA_shot030`, frames 1001–1192 with handles 1001–1024 and 1169–1192. Working space ACEScg with Rec.709 view transform. Replace stock helicopter in plate with a hero helicopter CG model authorized at version v007. Look reference: shot 01 of the same sequence at its v012 lock. Approval gates: matchmove lock (date), layout lock (date+3), lighting lock (date+7), comp lock (date+10), final (date+12). Known risks: motion blur on rotor edges crosses screen-right; clean plate captured on set, but the actor's hand briefly intersects the rotor disc.

Package manifest: `proj_seqA_shot030_brief_v001.md`, `plates/proj_seqA_shot030_plate_handles_1001-1192_v001.<frame>.exr`, `plates/proj_seqA_shot030_clean_handles_1001-1192_v001.<frame>.exr`, `reference/cut_proxy_v003.mov`, `reference/look_ref_shot01_v012.mov`, `camera/proj_seqA_shot030_cam_v002.abc`, `camera/proj_seqA_shot030_matchmove_v002.<tool-format>`, `camera/lens_distortion_v001.json`, `reference/hdri_rooftop_v001.exr`, `reference/lidar_rooftop_v001.<format>`, `assets/helicopter_hero_v007/`, `notes/README.md`, `notes/manifest.json`.

Tracking and camera data: solved camera at 24 fps, FBX and Alembic versions. Focal length animated per frame (lens was being pulled). Sensor 35.0×18.6mm. Principal point offset (-2.1, 0.4) pixels. Lens distortion model and parameters in `lens_distortion_v001.json` with both forward and inverse coefficients. Tracking markers as locators parented to the world; matchmove scene in the matchmove tool's native format.

Review loop: dailies daily at 18:00. Deliverables for review: 1920×1080 ProRes 4444 at 24p, Rec.709 view transform baked, with slate and burn-in (shot number, version, date, frame counter). Notes via the shared review platform; time-coded. QC before each submission: alpha integrity check, color tag verification (Rec.709 on the review file), frame range check (1001–1192), file naming check, checksum manifest verification. On receipt at the originator: same checks plus a comp QC pass against the look reference.

## Limitations

- This skill produces a handoff structure; it does not perform the upstream tasks (matchmove, lighting, FX) that populate the package.
- It assumes a single shot at a time. A sequence-wide handoff with many shots benefits from the same conventions but adds a sequence-level brief on top that this skill does not detail.
- It does not address contract, NDA, watermarking, or rights-management aspects of an external vendor handoff. Those belong to a legal-and-business workflow.
- It does not handle real-time and interactive deliverables (game cinematics, immersive walkthrough), which carry per-frame budget and engine-specific asset constraints beyond this scope.
- For very high-secrecy projects, additional encryption-at-rest and chain-of-custody requirements supplement (and do not replace) the conventions described here.
