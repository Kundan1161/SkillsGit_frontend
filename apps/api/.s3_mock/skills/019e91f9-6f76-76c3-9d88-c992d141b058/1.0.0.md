# Mobile Performance Tuner

## When to use

Reach for this skill when an app is slow, heavy, hot, or fat and the team needs a structured way to fix it rather than a guess-and-patch cycle. Mobile performance work has a high false-fix rate because the symptoms (a janky scroll, a long cold start) are downstream of many causes, and changing the wrong one is invisible to users. The tuner imposes a measurement-first discipline so the change you ship is the change that mattered.

Common triggers:

- An analytics dashboard or store vitals report shows a regression in startup time, ANR rate, or frozen frames.
- Users in field testing complain about "the app feeling slow" on a specific device.
- App size grew past a threshold and download conversion dropped.
- Battery consumption complaints arrive after a release that introduced location, background fetch, or a new SDK.
- The product team is shipping a new device tier (low-end, foldable, tablet) and wants the app to clear the bar before launch.

Do not use it for:

- Pure code style or architectural cleanup unrelated to runtime behaviour.
- Server-side performance (API latency, slow queries) — fix those at the API.
- Visual design or perceived performance work that does not change measurable metrics; the tuner focuses on measurements.

## Inputs

- `symptom` (required) — Picks which playbook to load. "Mixed" runs an abbreviated triage across all categories.
- `platform` (required) — Determines which tools and tactics apply.
- `device_class` — Where you are aiming the optimisation. A flagship-only target wastes effort; a low-end target imposes harder discipline.
- `current_metric` — Without a number, the report is qualitative. Strongly encourage the user to supply at least one measured value before tactics are proposed.
- `target_metric` — The bar to clear. Defaults to platform vitals thresholds when absent.
- `code_or_trace` — A profile capture massively improves the diagnosis quality; without it, ranking root-cause hypotheses is informed guesswork.
- `notes` — Constraints. A team that cannot adopt new dependencies needs different tactics than a team that can.

## How to apply

This is an inverted process: measure, diagnose, then change. Resist the urge to propose tactics before the measurement plan exists.

### 1. Pin down the metric and the workload

A performance complaint without a metric and a workload is unactionable. Convert vague language to numbers.

- "Cold start is slow" becomes "time to interactive (TTI) from icon tap on a Pixel 5a with a clean process is 3,800 ms, p50; we want 1,800 ms."
- "Feed is janky" becomes "while scrolling the home feed on iPhone SE 2 at 60 Hz, the average frozen frame rate over a 30 s session is 18%, with 12 frames at >700 ms; the target is < 0.5% frozen and zero frames > 700 ms."
- "App is fat" becomes "the production AAB on Android is 86 MB; the install size for a Pixel 7 is 122 MB; the target is < 50 MB install size."

If `current_metric` is missing, the diagnosis report's first action item is to capture the metric, with a recipe (see step 2). Do not skip ahead to tactics.

Define the workload: which screen, which device, which connectivity, cold or warm process, light or heavy data. Two runs of the same scenario with different workloads can disagree by 5×.

### 2. Build the measurement plan

The plan picks an authoritative measurement and a way to attribute it.

**Cold and warm start**

- iOS: Xcode Instruments → App Launch template, captures pre-main and main thread time. Or `MetricKit`'s `MXAppLaunchMetric` for field data. Cold start = process not in memory; warm start = process suspended in memory; resume = foreground transition.
- Android: Macrobenchmark with the Jetpack Benchmark library produces TTID (time to initial display) and TTFD (time to full display). For field data, use Play Console Android Vitals or Firebase Performance Monitoring's `_app_start` trace.
- React Native and Flutter sit on top of the native start cost; measure the native cold start first, then add the framework warmup. RN reports `setupTime` via the `Performance` API on the new architecture; Flutter exposes `Timeline.startSync` and `WidgetsBinding.instance.firstFrameRasterized` callbacks.

**Scroll and frame performance**

- iOS: Instruments → Time Profiler and Hangs Detection. SwiftUI on iOS 17+: `Instruments` Animation Hitches profile. Frame metrics from `MXAnimationMetric`.
- Android: Macrobenchmark frame timing, `JankStats` library in app, Perfetto traces for deep dives. Field data: Play Console "Slow rendering" vitals (any frame > 16 ms is "slow", > 700 ms is "frozen").
- React Native: profile under New Architecture's Fabric renderer with the JS thread + UI thread + Render thread timeline; the legacy "JS FPS / UI FPS" overlay is no longer accurate on Fabric.
- Flutter: `flutter analyze --build` and Flutter DevTools timeline. The build/layout/paint/raster phases are visible; raster jank usually means too many shaders being compiled at runtime.

**Memory**

- iOS: Instruments → Allocations and Leaks. `os_signpost` for custom region tagging. Memory warnings are visible in `MetricKit`.
- Android: Android Studio Profiler memory tab, LeakCanary for activity/fragment leaks, `dumpsys meminfo` for process-level views.
- Native heap, Java heap, graphics memory, and code memory are different budgets; report each separately.

**Battery and network**

- iOS: Xcode Energy Log, `MXEnergyMetric`. Network cost via `os_signpost` and Instruments Network template.
- Android: Battery Historian for `bugreport` analysis, Play Console "Excessive Wake Locks" and "Excessive Wi-Fi scans" vitals.

**App size**

- iOS: App thinning report from App Store Connect (per-device size), `Showing Package Contents` of the IPA, Xcode's "Show Build Folder" for raw asset weight.
- Android: Android Studio APK Analyzer; `bundletool build-apks` to inspect per-device size from the AAB.

The plan also names the **target device**. A measurement on a developer's M3 MacBook simulator does not reflect a Pixel 4a in the wild; insist on a real, representative device or a cloud device farm (Firebase Test Lab, AWS Device Farm).

### 3. Generate the root-cause hypothesis list

With a measurement in hand, rank likely causes. Each category has a default ordered list of causes that explains a large fraction of cases.

**Cold start**, descending likelihood:

1. Too many dependencies initialised eagerly at process start (analytics, crash reporting, ads, push). On Android, anything declared in `androidx.startup` or initialised in `Application.onCreate`. On iOS, anything in `@main App` body or pre-main side effects.
2. Large `Application` / `AppDelegate` doing synchronous work on the main thread.
3. Dex / classpath cost on Android pre-Profile-Guided builds. Solution: ship Baseline Profiles.
4. iOS: dynamic frameworks loaded at launch beyond what is needed.
5. React Native: JS bundle size and first-render work on the JS thread. Hermes byte-compiled bundles, RAM bundles, and inline requires reduce this.
6. Flutter: shader compilation jank on first run; use SkSL warmup or Impeller on iOS / Vulkan on Android.
7. Disk reads on the main thread (reading caches, settings, encrypted storage).
8. Network request on the splash screen that blocks the first frame.

**Scroll jank**, descending likelihood:

1. Recomposition or rebuild storms — Compose recomposing entire trees, SwiftUI invalidating large `Group`s, RN re-rendering large `FlatList` rows, Flutter rebuilding large widget subtrees because the state object is high in the tree.
2. Image decoding on the main thread; large bitmaps without downsampling.
3. List virtualisation missing or misconfigured: `LazyColumn` items without keys, `FlatList` without `keyExtractor` and stable keys, `ListView` without `itemExtent`, `UITableView` with autosizing rows and no estimated height.
4. Layout passes triggered per frame by mutable state (e.g. animated values driving layout instead of paint).
5. Background work on the same thread as rendering (still possible on RN's legacy architecture; rare on Fabric/Flutter raster thread).
6. Shadow / blur / clip effects that force expensive offscreen rendering.

**Memory pressure**, descending likelihood:

1. Image cache unbounded. Default Glide / Coil / SDWebImage / Kingfisher / FastImage caches are bounded; custom caches frequently are not.
2. Activity / ViewController leaks — singletons holding views, closures capturing self strongly, observers not removed.
3. Bitmap / `UIImage` retained at full resolution; downsample to display size.
4. Large `WebView` instances kept alive across navigation.
5. Native heap allocations from a third-party SDK without a public knob.

**Battery drain**, descending likelihood:

1. Background location with high accuracy + short interval.
2. Continuous Bluetooth scanning.
3. Wake locks held longer than needed; misuse of `WorkManager` constraints.
4. Network polling on a tight interval instead of push or long-polling.
5. CPU-heavy work in a foreground service without throttling.

**App size**, descending likelihood:

1. Uncompressed image assets shipped at full resolution; switch to AVIF or HEIC or downsize.
2. Multiple icon sets bundled when one suffices.
3. Native libraries for ABIs that the device cannot use; per-ABI App Bundles fix this on Android.
4. Vendored debug or test code in the release build.
5. Multiple HTTP client libraries shipped together.
6. Localised strings for languages never installed; per-language App Bundles fix this on Android.
7. Animation files (Lottie, Rive) at high frame counts when fewer suffice.

For each candidate, write the evidence the trace would show if this were the cause. This is the falsification step: the next measurement should distinguish between hypotheses.

### 4. Propose tactics with effort, impact, and platform notes

Once the top hypotheses are picked, list tactics. Each tactic has four columns:

- **Tactic** — what to change.
- **Expected impact** — quantified where possible ("expect 200–400 ms reduction in TTI"). If the impact is unknown, say so.
- **Effort** — engineer-days, with a range.
- **Risk** — what could regress (perceived quality, other metrics, code complexity).

### 4a. Cold start tactics

- **iOS**: defer non-critical SDK init to after the first frame using `Task { @MainActor in ... }` post-`onAppear` or `DispatchQueue.main.asyncAfter`. Move file I/O off the main thread. Audit `AppDelegate` and split into actor-based initialisers. Remove `+load` and `+initialize` in Objective-C dependencies if any. Audit dynamic frameworks (`otool -L` on the binary) and statically link where possible.
- **Android**: adopt Baseline Profiles via the Macrobenchmark library; expect 15–30% TTID improvement on first launches. Move SDK initialisation out of `Application.onCreate` into `androidx.startup` Initializers with `dependencies()` that defer non-critical ones; use `AppInitializer.getInstance(context).initializeComponent(...)` on demand. Replace `MultiDex` if still present (it is rarely needed at minSdk 21+). Consider `App Startup Library`'s lazy mode.
- **React Native**: enable Hermes (default on 0.70+); turn on inline requires for the bundler so unused modules do not parse at launch. Adopt RAM bundles on Android. Move JS work that runs before the first scene to a worker; use `InteractionManager.runAfterInteractions` on legacy or `useEffect` after first paint on Fabric.
- **Flutter**: precompile shaders with SkSL on Skia, or switch to Impeller (iOS default on 3.10+, Android on opt-in). Pre-warm common routes by using `precacheImage` and resolving `ImageProvider`s during splash. Defer plugin registration when the plugin supports it.

### 4b. Scroll jank tactics

- **iOS**: in SwiftUI, factor list rows into their own `View`s with `@StateObject` rather than recomputing them from the parent; use `@Observable` (iOS 17+) for cheaper invalidations. In UIKit, ensure `UICollectionView` uses prefetching and self-sizing cells with estimated sizes set. Avoid `AnyView` in lists.
- **Android**: in Compose, profile recomposition with the Layout Inspector; mark stable types with `@Stable`/`@Immutable`; use `key()` on `LazyColumn` items; avoid `derivedStateOf` misuse. In View System, use `RecyclerView` with `setHasFixedSize(true)` where applicable and a `DiffUtil`-based adapter.
- **React Native**: replace `FlatList` with `FlashList` (Shopify) on the new architecture for >2× scroll perf in long lists; provide `estimatedItemSize`. Avoid `onScroll` handlers that setState every frame.
- **Flutter**: use `ListView.builder` with `itemExtent` when items are uniform; `const` widgets where possible; avoid `Opacity` for static fades — use `AnimatedOpacity` only where needed; do not call `setState` on the entire screen from list items.

### 4c. Memory tactics

- Downsample images to displayed size at decode time (`UIImage.preparingThumbnail`, `BitmapFactory.Options.inSampleSize`, `ResizeImage` in Flutter, `resizeMode` and proper `width`/`height` on RN `Image`).
- Bound caches explicitly; periodically purge on memory warnings (`didReceiveMemoryWarning`, `onTrimMemory`).
- Find leaks with LeakCanary (Android) or Instruments Leaks (iOS) and fix the strong references.

### 4d. Battery tactics

- Replace polling with push.
- Increase location accuracy only when needed; release wake locks promptly.
- Batch background work with `WorkManager` or `BGProcessingTask` and respect the system's deferral.

### 4e. App size tactics

- Adopt App Bundles (AAB) on Android; enable per-ABI and per-language splits.
- Adopt App Thinning on iOS (it is on by default; ensure asset catalogs are used).
- Use vector assets where rasters are not required.
- Strip debug symbols from release; upload them to the crash reporter instead of shipping.
- Tree-shake JS and remove unused locales in RN; use `flutter build --tree-shake-icons` for Flutter.
- Compress with `zopfli` or modern image formats; HEIC for iOS, WebP/AVIF for Android, AVIF where supported on Flutter via plugins.

### 5. Verification protocol

Every tactic ships with a before/after measurement on the same device with the same workload. The protocol specifies:

- Device model and OS version.
- Build configuration (release, profile, debug — only release is honest).
- Workload: cold or warm, network condition (offline, 3G, LTE, Wi-Fi), user state (signed in, freshly installed, with cache).
- Sample size (at least five runs, report median and p95; one-run measurements are noise).
- Confidence: if p95 changed but median did not, the tactic helped the bad tail; report that.

If the post-tactic measurement does not show the expected improvement, do not ship the tactic. Roll it back and revisit the hypothesis. Shipping a change that did not move the metric is how performance debt accumulates.

### 6. Avoiding the regression treadmill

Once metrics are at target, lock them down with continuous measurement so they do not drift back.

- Wire benchmark runs into CI. Macrobenchmark on Android and a custom XCTest with `XCTOSSignpostMetric` on iOS. Flutter has `integration_test` with `WidgetsBinding.instance.endOfFrame` instrumentation. RN has Flashlight or Reassure.
- Track field metrics: Firebase Performance Monitoring, Play Vitals, MetricKit, Sentry Performance, or in-house. Alert on regressions of more than 10% week-over-week.
- Treat performance budgets like API contracts — review every PR for changes to a budgeted screen.

## Outputs

`diagnosis_report` is the structured narrative with measurement plan and ranked hypotheses.

`tactics_plan` is the ordered tactic list with impact/effort/risk.

`verification_protocol` is the runbook for measuring each tactic before and after.

## Examples

### Example: Android cold start, Pixel 5a, currently 3.8 s, target 1.8 s

Excerpt from `diagnosis_report`:

```
Workload: cold start, clean process, Wi-Fi, signed-in user, default home screen.
Measurement tool: Macrobenchmark TTID, 10 runs, median.
Current: 3,820 ms (p50), 4,510 ms (p95). Target: ≤ 1,800 ms (p50).

Ranked hypotheses:
1. (High) Eager SDK init in Application.onCreate. Application.onCreate trace
   shows 1,540 ms attributable to Crashlytics, Analytics, A/B testing init,
   and DI graph warm-up.
2. (High) No Baseline Profile in the AAB. First-launch ART JIT cost
   typically adds 400–800 ms on devices without cached compiled code.
3. (Medium) Splash screen waits on a remote-config fetch with a 3 s timeout.
4. (Low) Disk read of encrypted SharedPreferences for feature flags on
   the main thread (~50 ms).
```

Excerpt from `tactics_plan`:

```
| # | Tactic | Expected impact | Effort | Risk |
|---|---|---|---|---|
| 1 | Move Crashlytics + Analytics + A/B init to androidx.startup with WorkManager-deferred non-critical components | 600–900 ms | 3 d | Crash report loss for first ~1 s window |
| 2 | Generate Baseline Profile via Macrobenchmark, include in AAB | 400–700 ms | 2 d | None |
| 3 | Make remote-config fetch non-blocking; render with cached values | 200–400 ms | 1 d | First-launch users see prior flag set |
| 4 | Move flag read to a background coroutine; render skeleton | 30–60 ms | 0.5 d | Brief skeleton flash on slow devices |
```

Excerpt from `verification_protocol`:

```
Device: Pixel 5a, Android 14, factory image, battery 50–80%, screen on, no
other foreground apps. Network: home Wi-Fi, 2.4 GHz.
Builds: release, R8 full mode, AAB installed via `bundletool install-apks`.
Runs: 10 cold starts; uninstall and reinstall between runs to ensure cold.
Metric: TTID via Macrobenchmark; report median, p95, and min.
Acceptance: median ≤ 1,800 ms and p95 ≤ 2,400 ms across two consecutive
sessions of 10 runs.
```

## Limitations

- The tuner cannot diagnose without a measurement. If the user resists capturing one, the report stays qualitative and explicitly says so.
- Field performance varies by device, OS version, and connectivity. Targets met on three test devices may miss the long tail; complement with field telemetry.
- Some tactics require breaking changes (Baseline Profiles need a fresh install; Hermes requires a clean RN setup); the tuner notes when a tactic is non-trivial to revert.
- Performance is a property of the whole app, not a single screen. Optimising one screen aggressively can regress another by sharing the same global state or initialiser; verify with a broader workload, not just the screen under test.
- Battery measurements are noisy; expect to need long captures or aggregated field data rather than a single run.
