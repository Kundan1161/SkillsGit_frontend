# Sentry Prompt Optimizer

## When to use

Use this skill when creating or refining prompts across different AI model families — especially when you need a repeatable, evidence-based process rather than vibes-based prompt tweaking.

## How to apply

Walk the six-step workflow below in order. Define success criteria before editing the prompt. Keep instructions causal. Stop optimizing on plateau, oscillation, overfit, excessive cost, or non-prompt bottleneck.

## Six-Step Workflow

### 1. Capture Contract

Document before editing:

- Task type
- Target model
- Prompt surfaces (system, developer, user, tools)
- Success criteria
- Constraints (latency, cost, safety)

### 2. Inventory External Context

List stable references by path rather than copying content wholesale. Keep prompts small; the model can fetch context if you tell it where.

### 3. Choose Model Strategy

Consult model-family notes to decide between:

- **Family-specific optimization** — handcrafted for one target model.
- **Portable base with adapters** — shared core plus small per-family adapters.

### 4. Shape Prompt

- Put stable policy in `system` or `developer`.
- Put task variables in user-facing sections.
- Avoid repetition and filler.

### 5. Optimize

- Baseline current performance on a held set.
- Cluster failures.
- Generate 2–4 candidate edits.
- Compare on the same cases.
- Validate on holdout data.

### 6. Return Package

Deliver:

- Target & success criteria
- Context references
- Optimized prompt
- Adapter notes (if portable)
- Eval set
- Optimization log
- Residual risks

## Stop Rules

Stop optimization when you hit any of:

- **Plateau** — no further gains across multiple iterations.
- **Oscillation** — fixes break previously-passing cases.
- **Overfit** — training set improves, holdout regresses.
- **Excessive cost** — token cost per win exceeds threshold.
- **Non-prompt bottleneck** — the failure is in tooling, retrieval, or model capability, not the prompt.

## Common Pitfalls

- Editing before defining success criteria.
- Optimizing on the same cases you measure on.
- Adding more instructions instead of removing weak ones.
- Treating model output style preferences as bugs.
