# Kubernetes Manifest Reviewer

## When to use

Use this skill when an engineer hands you Kubernetes manifests (raw YAML, kustomize bases and overlays, or `helm template` output) and asks for a pre-merge or pre-deploy review. Triggers include: a Deployment is about to ship to production for the first time; a Helm chart is being submitted to a chart repository; a team is migrating from one cluster distribution to another and wants a posture check; a security or platform team is auditing workloads for Pod Security Standards (PSS) compliance or for CIS benchmark conformance; an engineer is taking over an unfamiliar service and wants a tour with notes.

The skill applies whether the workload runs on EKS, AKS, GKE, OpenShift, k3s, or self-managed Kubernetes. It applies whether manifests are authored directly, generated by kustomize, rendered from Helm, or produced by an operator's CRD. The check is the same; the platform-specific nuance is layered on top.

It does not apply to: CRD authoring (that's a controller-design task); cluster bootstrapping or platform-team responsibilities (autoscaler choice, control-plane configuration); or live debugging of a failing pod (that's a triage task and needs logs, not manifests). For those, prefer dedicated tools.

The bar the skill applies is "would this run safely under the Pod Security Standards `restricted` profile, would the on-call know what to do when it pages, and would the platform team be comfortable inheriting it?"

## Inputs

| Input | Required | Purpose |
| --- | --- | --- |
| `manifests` | yes | The YAML under review. |
| `cluster_context` | no | Cluster details that change which checks apply. |
| `workload_type` | no | What runs in the pods — used for idiom-specific checks. |
| `tier` | no | Environment tier — production and regulated bias toward stricter findings. |

## How to apply

The agent walks the manifests deterministically. Each stage produces structured findings; the final stages rank and render them.

### Stage 1 — Inventory

1. Parse the input as YAML. Group documents by `apiVersion` and `kind`. Build a resource inventory: how many Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, Services, Ingresses, ConfigMaps, Secrets, ServiceAccounts, NetworkPolicies, HorizontalPodAutoscalers, PodDisruptionBudgets, and CRDs are present.
2. Identify the *namespaces*. A manifest set with no namespace declared is ambiguous; record it and call it out as a Minor (or a Blocker if the workload is multi-tenant).
3. Identify the *labels and annotations*. Check for the recommended Kubernetes labels (`app.kubernetes.io/name`, `app.kubernetes.io/instance`, `app.kubernetes.io/version`, `app.kubernetes.io/component`, `app.kubernetes.io/part-of`, `app.kubernetes.io/managed-by`). Missing labels are Minor; inconsistent labels across related resources are a Major.
4. Identify the *image references*. Pin to digest is best (`image@sha256:...`); pin to immutable tag is acceptable; `:latest` is a Blocker for any non-dev environment.
5. Note the *workload type* if not provided. Stateless API, stateful database, batch job, daemonset, model-serving inference — each has a different review weighting.

### Stage 2 — Container security context

6. Every container has `securityContext.runAsNonRoot: true`. Missing is a Major; explicitly `runAsNonRoot: false` in production is a Blocker.
7. Every container sets `securityContext.runAsUser` to a non-zero UID and `runAsGroup` to a non-zero GID. Missing is a Major.
8. Every container has `readOnlyRootFilesystem: true`. Where the application needs to write, a `emptyDir` volume mounted at the right path is the pattern. Missing is a Major.
9. Every container drops capabilities by default: `securityContext.capabilities.drop: ["ALL"]`. Add only what's needed and document why. Missing drop is a Major; any `add` without comment is a Major.
10. `allowPrivilegeEscalation: false` is set on every container. Missing is a Major; `true` is a Blocker.
11. `privileged: true` is a Blocker unless the workload is genuinely a privileged DaemonSet (CNI plugin, storage driver, GPU node setup) and the manifest documents why.
12. Pod-level `securityContext` sets `seccompProfile.type: RuntimeDefault` (or `Localhost` with a profile). Missing is a Major in production.
13. AppArmor or SELinux profile annotations are present where the distribution supports them. Missing is a Minor in dev, Major in regulated tiers.

### Stage 3 — Pod Security Standards profile mapping

14. Map every container against the **baseline** PSS controls (no host namespaces, no host ports, no host paths in volumes, no privileged, no hostProcess, drop `NET_RAW`, restrict capabilities, no `/proc` mount, seccomp not `Unconfined`).
15. Map every container against the **restricted** PSS controls (in addition to baseline: no privilege escalation, runAsNonRoot, capabilities drop `ALL`, restricted volume types, seccomp `RuntimeDefault` or `Localhost`).
16. Produce a one-line verdict per workload: `restricted-compliant`, `baseline-compliant`, or `privileged`. Resources that fail `baseline` in a production tier are Blockers.
17. The namespace-level `pod-security.kubernetes.io/enforce` label is set to the target profile. Missing in a multi-tenant cluster is a Major.

### Stage 4 — Resources and quality of service

18. Every container has both `resources.requests` and `resources.limits` for `cpu` and `memory`. Missing CPU requests on a production pod is a Major; missing memory limits is a Blocker (OOMKill predictably).
19. CPU limits are scrutinized. For latency-sensitive workloads, omit CPU limits and rely on requests + cluster autoscaler — CPU limits cause throttling under load. Note this with the workload type; flag mismatches.
20. Memory request equals memory limit for predictable QoS (Guaranteed class) on critical workloads. Sloppy ratios are a Minor.
21. The pod's QoS class (Guaranteed / Burstable / BestEffort) is appropriate for the workload. BestEffort in production is a Major.
22. `terminationGracePeriodSeconds` is set deliberately. Default 30s is appropriate for stateless; longer for stateful, with the application's `preStop` hook draining cleanly.
23. `topologySpreadConstraints` are present for workloads with replicas > 1 to avoid single-node failures. Missing is a Major in production.
24. `affinity` / `antiAffinity` rules avoid co-locating replicas on the same node when availability matters. Missing is a Major for tier=production.

### Stage 5 — Probes

25. Every container has a `livenessProbe`. Missing is a Major.
26. Every container has a `readinessProbe`. Missing is a Major (worse than missing liveness — traffic flows during startup).
27. Every container has a `startupProbe` if startup is slow (> initialDelaySeconds the liveness probe can stomach). Missing is a Major when applicable.
28. Probes use a sensible endpoint. Hitting `/` returns 200 even when the app is broken; use a real health endpoint. Hitting the same endpoint for liveness, readiness, and startup hides the distinction.
29. `failureThreshold` and `timeoutSeconds` are calibrated to the application. Default 1s timeout is too aggressive for many JVM apps; default 3-failure threshold is too lax for cascading dependency loss. Note when defaults look uncalibrated.
30. Exec probes that fork heavy commands every few seconds are a Major (they cost CPU). HTTP probes are preferred where possible.
31. Probes do not include authentication that depends on side effects (a probe that logs in to the DB to check liveness causes a thundering herd on dependency recovery).

### Stage 6 — Rollout strategy

32. `Deployment.spec.strategy` is set deliberately. `RollingUpdate` with explicit `maxSurge` and `maxUnavailable` is the default; `Recreate` is appropriate for non-redundant workloads. Implicit defaults in production are a Minor.
33. `maxUnavailable: 0` for workloads where every replica matters; `maxSurge: 1` to cap blast radius. Numbers chosen for replica count > 10 are different from numbers for replica count = 2.
34. StatefulSet `updateStrategy` is `RollingUpdate` with a `partition` value used deliberately during canary; default `OnDelete` is a code smell unless an operator manages updates.
35. `progressDeadlineSeconds` is set so a wedged rollout fails fast instead of stalling indefinitely. Missing is a Minor.
36. `revisionHistoryLimit` is bounded (default 10, often lowered to 5). High values bloat etcd; missing is a Nit.
37. PodDisruptionBudget (PDB) exists for workloads with replicas > 1 in production. Missing PDB is a Major. PDB `minAvailable` (or `maxUnavailable`) is configured to allow node maintenance — `minAvailable: 100%` is a deadlock and is a Blocker.

### Stage 7 — Networking

38. Every namespace has a default-deny NetworkPolicy (ingress and egress) and explicit allow rules for the traffic the workload needs. Missing default-deny in a multi-tenant cluster is a Major.
39. NetworkPolicies are scoped narrowly. `from: []` (allow from anywhere) defeats the purpose. Wide allow rules are a Major.
40. Services use the correct type. `LoadBalancer` accidentally provisions cloud LBs; `NodePort` exposes on every node; `ClusterIP` (the default) is what most internal workloads want. Mismatches are a Major.
41. `externalTrafficPolicy: Local` for LoadBalancer Services that need to preserve client source IP and where the workload can tolerate per-node traffic skew. Defaults to `Cluster`; the right choice depends on the workload.
42. Ingress objects use TLS. Plaintext Ingress in production is a Blocker.
43. Ingress class is specified explicitly. Implicit ingress controller selection is a Minor and breaks on multi-controller clusters.
44. Ingress annotations are specific to the chosen controller and not copy-pasted from another controller's documentation. Mismatch is a Major (silent failure).
45. Service mesh annotations (Istio sidecar injection, Linkerd, etc.) are present when the cluster has a mesh and the workload is in the mesh's namespace. Missing is a Major in mesh-enabled clusters.

### Stage 8 — Identity, secrets, and configuration

46. Every pod has an explicit `serviceAccountName`. The default service account inherits broad permissions; named SAs scope intent. Missing is a Major.
47. The ServiceAccount has only the roles it needs. RoleBindings/ClusterRoleBindings to `cluster-admin` for a workload are a Blocker unless the workload is genuinely a cluster operator and the manifest justifies it.
48. `automountServiceAccountToken` is `false` on pods that do not call the Kubernetes API. Missing is a Major; defaults to `true`.
49. Secrets are not embedded in ConfigMaps. Sensitive ConfigMap values are a Blocker.
50. Secrets are sourced from a real secret manager (External Secrets, Sealed Secrets, CSI Secrets Store, Vault) when the cluster supports it. Plain `Secret` objects in Git are a Major unless GitOps-encrypted.
51. Environment variables sourced from Secrets use `valueFrom.secretKeyRef`, not literal values. Literal secrets in env are a Blocker.
52. ConfigMaps separate per-environment configuration from immutable defaults. Mixing causes drift between environments.
53. Image pull secrets are scoped to the namespace and to the workload's ServiceAccount; not attached cluster-wide.

### Stage 9 — Storage

54. Every PersistentVolumeClaim has a `storageClassName` set explicitly. Default storage classes change across clusters; implicit selection is a Major for production.
55. PVCs request appropriate sizes; don't ship a 1Gi claim for a production database.
56. `accessModes` are minimal (`ReadWriteOnce` for most workloads); `ReadWriteMany` only when the workload is genuinely multi-writer.
57. Stateful workloads have a backup plan documented (a CronJob, an operator, or an out-of-band tool). A StatefulSet without backup posture is a Major in production.
58. `volumeBindingMode: WaitForFirstConsumer` is preferred for topology-aware scheduling. Note when it's missing.

### Stage 10 — Observability hooks

59. Containers expose metrics on a documented port and the pod is annotated for the cluster's scrape mechanism (`prometheus.io/scrape: "true"` and `prometheus.io/port`, or a ServiceMonitor for Prometheus Operator). Missing is a Major in clusters that scrape.
60. Containers emit logs to stdout/stderr, not to files inside the container. File logging is a Major.
61. Pods set the OpenTelemetry resource attributes via downward-API environment variables (`OTEL_RESOURCE_ATTRIBUTES` with pod name, namespace, node name) so traces are tagged. Missing is a Minor.
62. Liveness/readiness endpoints are documented in the chart README or manifest comments. Undocumented endpoints get broken silently.

### Stage 11 — Rollout safety extras

63. Each Deployment has at least one PodDisruptionBudget if replicas > 1.
64. HorizontalPodAutoscaler (HPA), if present, has `minReplicas` >= 2 for production stateless workloads. `minReplicas: 1` in production is a Major.
65. HPA metrics are calibrated. CPU-only HPA on a workload that's memory-bound is a Major.
66. VerticalPodAutoscaler (VPA), if used, is set to `recommender`-only or `auto` based on the workload's tolerance for restart. `auto` on stateful workloads is a Major.
67. PriorityClass is set deliberately. Critical workloads should have a high-priority class; batch jobs a low-priority class.

### Stage 12 — Helm chart-specific checks

If the input is a Helm chart (not just rendered manifests), the agent layers the following.

68. `Chart.yaml` declares `apiVersion: v2`, a valid `version` (semver), an `appVersion`, a `description`, a `maintainers` block, and a `kubeVersion` constraint. Missing fields are Minor.
69. `values.yaml` is documented. Every value has at least a one-line comment with the property name. `helm-docs` (or equivalent) keeps the README in sync.
70. `values.yaml` uses flat structures where possible; nested maps require deep `--set` paths that bite users.
71. Templates use `include` for repeated blocks (labels, selectors, environment) rather than copy-paste.
72. Templates use the standard label helpers (`{{ include "chart.labels" . }}`) so labels stay consistent across resources.
73. Templates respect `nameOverride` and `fullnameOverride` so callers can rename.
74. Templates do not embed secret values in plain text; they reference Secret resources or external sources.
75. Templates produce valid YAML when default `values.yaml` is applied. Missing values that would cause `helm template` to emit broken YAML are a Major.
76. Templates produce predictable output across Kubernetes minor versions in the supported range (no API kinds at versions outside the constraint).
77. Subcharts are pinned by version; `*` is a Major.
78. The chart includes at least one rendered example or a CI step that runs `helm template` and lints the output.

### Stage 13 — Severity assignment

79. Assign every finding one severity:
    - **Blocker** — the workload is unsafe to merge: privileged container, plaintext secret, public exposure without TLS, no memory limit on a production workload, missing namespace pod-security label, `:latest` tag in production, RoleBinding to cluster-admin.
    - **Major** — likely to cause a real incident in the next 90 days: missing readiness probe, missing PDB, missing NetworkPolicy, BestEffort QoS, default service account in use, missing rollout strategy.
    - **Minor** — small defect: missing recommended labels, repetition that should be templated, missing `revisionHistoryLimit`.
    - **Nit** — style: ordering, key casing, comment grammar.
80. When in doubt, pick the lower severity.
81. Cap nits at 8 in the rendered output; summarize the tail.

### Stage 14 — Compose the report

82. Lead with a one-paragraph summary: what the manifests deploy (as the agent understood), the headline counts (`2 blockers, 6 majors, 9 minors, 4 nits`), and a PSS verdict (`restricted-compliant` / `baseline-compliant` / `privileged`).
83. Render a per-resource scorecard: a small table listing each Deployment / StatefulSet / DaemonSet / Job and a one-letter grade for security, resources, probes, rollout, networking. The grade is heuristic; it focuses attention.
84. Group findings by severity. Within each severity, group by resource kind, then resource name, then field path.
85. For each finding, emit a fenced block with: severity tag, category, resource ref (kind/name + field path), "Why it matters" (one sentence), "Suggested fix" (a small concrete change).
86. End with a "What I did not check" section: anything the cluster context omitted (e.g., "no service mesh declared, so sidecar-injection annotations were not validated").
87. Produce `findings_json` in parallel.

### Stage 15 — Self-check

88. Verify every "Blocker" is genuinely a blocker by the standard in step 79. Tighten if unsure.
89. Verify every "Suggested fix" is small, concrete, and reversible.
90. Re-read the report; if it has more than 30 findings, consolidate or downgrade.
91. Verify the PSS verdict matches the per-resource detail; mismatches are inconsistencies and erode trust.
92. Verify resource references are accurate. A finding on a non-existent field is worse than no finding.

### Stage 16 — Workload-type weightings

The agent re-weights findings based on the input workload type.

93. **Stateless API.** Emphasize HPA, PDB, readiness probe, graceful shutdown, NetworkPolicy. CPU-limits-off may be acceptable.
94. **Stateful database.** Emphasize StorageClass, PVC sizing, backup posture, anti-affinity to avoid co-located replicas, careful update strategy, drainage on terminationGracePeriod. HPA usually inappropriate.
95. **Batch job.** Emphasize `restartPolicy` (`OnFailure` or `Never`), `backoffLimit`, `ttlSecondsAfterFinished`, resource limits to avoid noisy neighbors. PDB usually not needed.
96. **DaemonSet.** Privileged is sometimes legitimate (CNI, storage); document why. Tolerations for node taints are required; rolling-update strategy with sensible `maxUnavailable`.
97. **ML training.** Resource limits are often skipped intentionally for elastic burst; document the policy. NodeAffinity to GPU pools is required.
98. **ML serving.** Treat as stateless API but with attention to startup probes (model loads are slow) and memory bursts.
99. **CronJob.** `concurrencyPolicy: Forbid` is usually right; `startingDeadlineSeconds` set so missed runs do not pile up; history limits set.

### Stage 17 — Distribution-specific notes

Layer the following when the cluster context names a distribution.

100. **EKS.** IAM Roles for Service Accounts (IRSA) preferred over static AWS keys. Use `eks.amazonaws.com/role-arn` annotation on the ServiceAccount. Default VPC CNI gives every pod an IP; mind subnet sizing.
101. **AKS.** Use Azure AD Workload Identity (federated tokens) rather than service principal secrets. Use Azure CSI for managed disk classes.
102. **GKE.** Workload Identity for GCP access; do not embed service-account keys. Use Autopilot-incompatible features deliberately if running Autopilot.
103. **OpenShift.** SecurityContextConstraints (SCC) replace PSP/PSA semantics; routes replace many Ingress patterns. RunAsAnyUser is rare; OpenShift assigns UIDs.
104. **k3s / on-prem.** Mind the default storage class (local-path) — not appropriate for production replicated workloads.

### Stage 18 — Anti-patterns catalog

Watch for these recurring smells.

A. **The kitchen-sink Deployment.** A single Deployment running multiple unrelated processes (app server, log shipper, sidecar, build helper). Split.
B. **The default-everything pod.** No probes, no resources, no security context, default ServiceAccount, default namespace. Triple-check before flagging — sometimes this is template-rendered output from an older chart.
C. **The leaky sidecar.** A sidecar container with `privileged: true` "to read logs" — almost never necessary; use shared `emptyDir`.
D. **The init-container that lasts forever.** An init container that polls in a loop; should be a sidecar or a real readiness gate.
E. **The `:latest` time bomb.** Image tags floating in production.
F. **The hostPath mount.** Host path mounted RW from a non-platform workload; almost always a misuse.
G. **The catch-all ingress.** One Ingress with wildcard host and broad path rules across unrelated workloads.
H. **The unbounded job.** A `Job` with no `backoffLimit`, no `activeDeadlineSeconds`, no `ttlSecondsAfterFinished`.
I. **The HPA on memory only.** Memory is rarely the right scale signal alone; combine with CPU or custom metrics.
J. **The cluster-wide ClusterRole.** A workload binding to `cluster-admin` "to make it work." Almost always over-privileged.

## Outputs

The skill returns two artifacts:

1. `review_report` (markdown) — triaged review with PSS verdict, per-resource scorecard, and ranked findings.
2. `findings_json` (JSON) — structured findings for admission preview tooling.

## Examples

**Input (placeholder):**

A `helm template` output for a Node.js API: one Deployment with 3 replicas, one Service, one Ingress (TLS), one ConfigMap, one Secret (Vault-injected via annotations), one HorizontalPodAutoscaler. No NetworkPolicy, no PDB. Image is pinned by digest. Namespace `webshop` has no PSS label.

**Agent reasoning (abbreviated):**

- Stage 1: 1 Deployment, 1 Service, 1 Ingress, 1 ConfigMap, 1 Secret, 1 HPA; image pinned by digest — good.
- Stage 2: securityContext present at pod level only, container lacks `runAsNonRoot`. Major.
- Stage 3: PSS — baseline OK, restricted fails on missing seccomp. Major.
- Stage 4: requests + limits present, memory request != limit (Burstable QoS) — fine for stateless API; CPU limit set, may throttle — note.
- Stage 5: readiness probe present, liveness probe missing — Major.
- Stage 6: rollout strategy uses defaults; `progressDeadlineSeconds` not set. Minor. No PDB. Major.
- Stage 7: no NetworkPolicy. Major. Ingress has TLS — good. Ingress class is implicit. Minor.
- Stage 8: explicit ServiceAccount, `automountServiceAccountToken: true` (default). Major.
- Stage 11: HPA `minReplicas: 1`. Major.
- Stage 12: chart not provided; skip.

**Output (abbreviated):**

```
**Summary:** Node.js API; 3 replicas; TLS Ingress; HPA enabled.
**PSS verdict:** baseline-compliant; not restricted-compliant.
**Headline:** 0 blockers, 7 majors, 4 minors, 2 nits.

### [MAJOR] probes: missing livenessProbe on the api container
Resource: Deployment/webshop-api  spec.template.spec.containers[0].livenessProbe
Why it matters: Without liveness probes Kubernetes cannot restart a stuck pod automatically; a deadlocked Node event loop will keep serving stale responses until the readiness probe also fails or until manual intervention.
Suggested fix: Add an HTTP livenessProbe pointing at a dedicated `/live` endpoint with timeoutSeconds: 3 and failureThreshold: 6.
```

## Limitations

- The skill reasons over manifest text; runtime behavior under load is inferred, not observed.
- Distribution-specific behaviors (admission controllers, mutating webhooks, OPA Gatekeeper / Kyverno policies installed on the cluster) are not visible from manifests alone. The skill says so.
- Helm chart review without the `templates/` directory and `values.yaml` is partial; rendered output cannot reveal templating mistakes.
- The skill cannot run a live admission controller; PSS evaluation is static and may diverge from the cluster's exact enforcement.
- Custom resources from operators are checked only structurally unless the agent has knowledge of the CRD's schema.
- The skill does not generate a NetworkPolicy or a PodSecurityPolicy automatically; it identifies absence and suggests a starting shape.
