# Eventing Architect

## When to use

Use this skill when a team is deciding how to move information between services and the answer is not obviously "call an HTTP endpoint". The skill helps choose among messaging styles, designs the resulting topology, and writes down the contract rules that keep the system maintainable as event count grows.

The skill is calibrated for teams that have at least two cooperating services and a workload that does not fit clean synchronous request/response. It handles greenfield decisions, migration decisions (queue to log, single-broker to multi-broker), and contract redesigns (event taxonomy gone wrong).

Common triggers:

- An order-management system needs to inform billing, analytics, and search; doing three synchronous calls in series is fragile.
- A team uses HTTP everywhere and is now seeing cascading outages whenever any downstream slows; introducing async decoupling is on the table.
- Two services share a database table; one team wants to publish changes instead.
- The event topology grew organically and now nobody can tell who consumes what.
- A regulator or auditor needs a replayable history of changes; the team wonders whether event sourcing applies.

Do not use this skill for:

- The decision of whether to split a monolith. Use a service-decomposition skill first.
- Single-process pub/sub within one runtime. Use in-process event buses; full messaging design is overkill.
- Real-time low-latency edge cases like trading or game state replication; those have specialized stacks beyond this skill.

## Inputs

- `workload` (required) — Producers, consumers, throughput, average and max message size, retention needs, idempotency status, expected fan-out.
- `business_consistency` — Constraints between database writes and publishes. The outbox pattern is only necessary if there is a constraint to preserve.
- `ordering_requirements` — Most workloads need per-entity order, not global order. Stating the scope is critical because per-entity is far cheaper.
- `existing_infrastructure` — Picking a broker the team already runs is usually better than picking a theoretically superior one nobody operates.
- `latency_profile` — Decides whether to optimize for throughput or for tail latency.

## How to apply

The steps build a design document section by section. Apply them in order.

### 1. Frame the workload

1.1. Restate the workload in one paragraph using the skill's vocabulary: producers, consumers, fan-out, throughput, message size, retention, ordering scope, idempotency status, business-consistency constraint, latency profile.

1.2. Identify the **dominant message style** the workload looks like:

- **Command** — a request for a specific recipient to do specific work (e.g. "send this email"). Implies a queue with one logical consumer group.
- **Event** — a fact about something that happened in the world (e.g. "order placed"). Implies a topic with any number of consumer groups.
- **Document** — a representation of a state for downstream caches (e.g. "current user profile"). Implies compacted topic or change-data-capture.

1.3. A single workload often contains more than one style. Separate them. Mixing command and event semantics in the same topic destroys clarity later.

### 2. Pick the messaging style

2.1. **Request/response over HTTP or gRPC** still wins when the caller needs the result inline and the downstream is fast and reliable. Do not adopt eventing just because it is fashionable.

2.2. **Work queue** (SQS-like or RabbitMQ-like) fits commands and best-effort fan-out. One consumer group, competing consumers, ack-based delivery, simple semantics. Use when:

- The fan-out is one-to-one or one-to-few with stable consumers.
- Retention beyond a few days is unnecessary.
- Replay is not a feature you need.

2.3. **Event bus** (pub/sub with subscriptions, e.g. cloud pub/sub or topic exchanges) fits events with unknown future consumers. Use when:

- The number of consumers will grow but each one is independent.
- You want logical separation per consumer without coordinating them.
- Replay is not a hard requirement but durability of unconsumed messages is.

2.4. **Log-based broker** (Kafka-like or Pulsar-like) fits high-volume events with replay needs and per-key ordering. Use when:

- The same stream of events feeds multiple consumer groups that re-process independently.
- You need ordered delivery per entity (key).
- You need to retain events for days, weeks, or longer for analytics or rebuild.
- The team can run a stateful broker.

2.5. **Hybrid** — pick the style per topic, not per system. It is normal to have an HTTP front door, a work queue for jobs, and a log for events in the same system.

### 3. Pick the broker family fit

3.1. Reduce broker choice to **operational fit, throughput fit, semantic fit**. Operational fit dominates: a team that already runs broker X should generally pick broker X for a new use case unless throughput or semantic fit forces otherwise.

3.2. Throughput fit is rarely the bottleneck for first-year workloads; most reasonable brokers handle the loads of most services. Discount throughput as a deciding factor unless the workload exceeds 10k messages per second per topic.

3.3. Semantic fit drives the choice for advanced use cases:

- Per-key ordering and replay over weeks: log-based broker.
- Delayed messages and scheduled retries: queue with native delays.
- Fan-out subscriptions with per-consumer offsets and long retention: log-based broker or pub/sub with replay.
- Priorities, multi-tenant isolation per queue, fine-grained ack: classic queue broker.

3.4. Pick **one broker family** for the system unless you have a strong reason for two. Cross-broker eventing is an operational tax.

### 4. Design the topic / queue taxonomy

4.1. The taxonomy is the most consequential design decision in eventing. Names rot less if they come from the business language, not the technology.

4.2. Use a **noun + verb-past-tense** naming convention for events: `order.placed`, `payment.captured`, `shipment.dispatched`. Avoid `update`, `change`, `event` as suffixes; they are noise.

4.3. Use **imperative verbs** for commands: `email.send`, `invoice.generate`. Commands live on separate queues from events; never share a topic.

4.4. Decide **topic granularity**:

- One topic per aggregate type (e.g. `order.*`) — easier governance, easier per-key ordering.
- One topic per event type (e.g. `order.placed`, `order.cancelled`) — easier consumer filtering, more topics to manage.

Default: one topic per aggregate type, with the event type carried in a payload field. Switch to per-event topics only when the consumer set per event type diverges sharply.

4.5. Reserve a **system namespace prefix** to separate domain events from internal infrastructure events (e.g. `audit.*`, `metrics.*`, `tracing.*`). Keep the namespaces small.

4.6. Avoid encoding tenants, regions, or environments in topic names unless the broker semantics require it. Use payload fields or broker-level isolation features instead; topic names should not change when an account moves region.

### 5. Design the event schema

5.1. Use a schema language with backward-compatibility tooling: Protobuf, Avro, or JSON Schema with a registry. Free-text JSON without schemas does not survive past a year.

5.2. Pick a **payload shape**:

- **Full state** — payload contains the entire entity state. Pros: consumers do not need to call back. Cons: large messages, sensitive data on the wire.
- **Delta** — payload contains only the changed fields. Pros: small, focused. Cons: consumers reconstruct state, hard to consume in isolation.
- **Notification + lookup** — payload contains only the id and event type; consumer calls back for the state. Pros: small, payloads do not carry PII. Cons: callback load on the producer.

Default for domain events: a notification with the key fields needed to route (entity id, tenant id, event type, occurred-at, schema version), plus a state snapshot when the snapshot is small and stable.

5.3. Reserve **envelope fields** common to every event: `event_id` (UUID, idempotency anchor), `event_type` (string), `event_version` (semver string), `aggregate_id`, `tenant_id` if applicable, `occurred_at` (ISO 8601 with timezone), `producer` (service name), `trace_id` (for tracing propagation), `schema_uri` if using a registry.

5.4. Keep PII out of payloads when you can. Carry an id and let consumers look up sensitive fields on demand with proper authorization. Encryption-at-rest in the broker is not a substitute.

5.5. Document the contract in the registry. Generate consumer code from the schema; do not handwrite serialization in each consumer.

### 6. Plan schema versioning

6.1. Versioning rules that work across years:

- **Adding optional fields**: minor version bump, no consumer changes required.
- **Removing or renaming fields**: major version bump, requires a coordinated migration.
- **Changing field semantics with same name**: major version bump, treated as breaking even if the type is the same.
- **Changing the topic taxonomy**: never; create a new topic and migrate.

6.2. Run **dual publishing** during major version transitions. Producers publish both v1 and v2 to separate topics; consumers migrate one at a time; the v1 topic retires after all consumers move.

6.3. Set a published **deprecation policy**: any non-current major version is supported for at least N months (default: 6) with announced sunset dates.

6.4. Use the schema registry's compatibility mode to block incompatible changes at publish time. Manual compatibility review does not scale.

### 7. Decide ordering

7.1. State the **ordering scope** explicitly: global, per-aggregate, per-tenant, none.

7.2. Most domain events need only **per-aggregate ordering** ("all events for order 12345 in order"). Achieve this by using the aggregate id as the partition key. The broker delivers the same key to the same partition, preserving order within the key.

7.3. Global ordering is expensive. Avoid it unless you can articulate why. If you cannot route messages to a single partition globally, you cannot have global order from the broker; you need a downstream sequencer.

7.4. **Consumers must tolerate disorder**. Even with per-key ordering, retries and rebalances can deliver out-of-order. Make consumers idempotent on `event_id` and use `occurred_at` for sequencing, not arrival time.

7.5. Document the ordering guarantee in the contract. Consumers will assume their broker's strongest setting unless told otherwise.

### 8. Decide delivery semantics

8.1. The realistic options are **at-most-once**, **at-least-once**, and **effectively-once**. True exactly-once across a broker plus an external store does not exist; effectively-once is at-least-once plus consumer idempotency.

8.2. Default to **at-least-once** for both producer and consumer. Then build idempotency on the consumer side:

- Deduplicate on `event_id`.
- Use unique constraints on side effects when the database supports them.
- For external side effects, carry an idempotency key into the downstream call.

8.3. At-most-once is acceptable for low-value telemetry. Never use at-most-once for money or fulfillment.

8.4. Exactly-once-within-broker features (Kafka transactions, broker-level idempotent producers) help for read-process-write loops inside one broker but do not cover external side effects. Use them where they apply; do not rely on them outside their scope.

8.5. Tie producer durability to **the outbox pattern** when the producer also writes to a database. The producer writes the event row and the business row in the same database transaction; an outbox relay publishes from the database to the broker. This eliminates the "wrote to database, failed to publish" failure mode.

### 9. Design retention and replay

9.1. Set retention per topic, not per system:

- Commands on queues: retain until acknowledged plus a short DLQ window.
- Domain events on log brokers: retain 7–30 days by default; longer if a downstream rebuilds from history.
- Audit events: retain per the audit policy, often 1 year or more, possibly archived to cold storage.

9.2. Plan **replay tooling** before you need it. A replay tool should let an operator reset a consumer group's offset to a wall-clock time or a specific event id and resume. Cowboy replays via direct broker commands are dangerous.

9.3. For long retention, separate **hot retention** (broker) from **cold retention** (object storage). Hot retention is for replay; cold retention is for audit.

9.4. Document the replay guarantees on each consumer: which consumers are safe to replay, which are not, what side effects are produced. A consumer that emails users on event arrival is not replay-safe without further work.

### 10. Plan failure handling per consumer

10.1. Every consumer needs three policies stated in advance: retry, dead-letter, alerting.

10.2. **Retry within the consumer** is for transient errors. Default: 5 attempts with exponential backoff. Permanent errors (deserialization, schema mismatch, missing required field) skip retry and go directly to the dead-letter destination.

10.3. **Dead-letter destination** is a separate topic or queue per consumer. Include the original message, the failure reason, the timestamp, and the attempt count. Build a replay tool for the dead-letter store as part of shipping.

10.4. **Alerting** on consumer lag and DLQ growth. Lag growing past a threshold means the consumer cannot keep up; DLQ growth means messages are failing permanently. Both deserve pages; both need runbooks.

### 11. Build the rollout plan

11.1. For greenfield, stand up the broker, schema registry, and producer first. Add consumers one at a time. Ship the first consumer end-to-end before adding the second.

11.2. For migration from synchronous calls to events, dual-write first: the producer continues the synchronous call and also publishes the event. Stand up the new consumer reading the event. Verify equivalence for a week. Remove the synchronous call when the new path is proven.

11.3. For a broker-family change (queue to log), keep both running. New events go to the new broker; old consumers migrate one at a time. Retire the old broker only when nothing reads from it.

11.4. Each step has a reversibility checkpoint: a feature flag that routes back to the previous path. Test the flag on day one, not on the day of trouble.

### 12. Emit the design

12.1. Lead with a one-paragraph summary: chosen messaging style, broker family, headline taxonomy decision, ordering scope, delivery semantics.

12.2. Include the topic taxonomy as a list, with one line per topic: name, payload shape, partition key, retention, producer, consumers.

12.3. Include the schema-evolution rules verbatim. They will be re-read for years.

12.4. Include the rollout plan with checkpoints and reversibility.

12.5. Include open questions the design did not resolve and what the team needs to find out.

### Decision rules and heuristics

- **Async is a tax, not a free lunch.** Eventing adds operational and reasoning overhead. Adopt it for a concrete reason, not because microservices are trendy.
- **Per-key ordering is enough for almost everyone.** Global ordering claims usually fall apart when scrutinized.
- **Idempotency is the consumer's job.** Trying to enforce it at the broker layer eventually breaks.
- **Schema before code.** A registry plus generated clients prevents the "free-text JSON" decay that kills events systems.
- **One broker family unless forced.** Two brokers is twice the operational cost; three is unbearable.
- **The outbox pattern is the default.** Whenever a write and a publish must agree, the outbox is the simplest correct answer.
- **Replay tooling ships on day one.** Replay built later is built under duress.
- **Names from the business, never from the implementation.** Topic names like `kafka_orders_topic_v3_new` survive nobody.

### Edge cases

- **Mixed in-region and cross-region consumers.** Cross-region adds latency and broker-mirroring concerns; consider regional topics with a mirror to a global topic.
- **PII-heavy payloads.** Prefer notification-plus-lookup; mask or redact on the wire; encrypt the cold archive separately.
- **Very small system (one producer, two consumers).** Eventing may be overkill; an in-process or in-database queue can be fine.
- **Existing event sourcing.** If the application is built on event sourcing, the broker is downstream of the event store. Treat the event store as the source of truth and the broker as a fan-out layer.
- **High-cardinality keys.** Per-key ordering with extreme key cardinality may not improve consumer locality. Consider hashing keys to a fixed partition set.
- **Late-arriving consumers with full-history needs.** Log-based broker with long retention is the cheapest answer; CDC from a database snapshot can bridge older history.
- **Cross-tenant isolation requirements.** Use broker-level isolation features (topic ACLs, separate partitions, per-tenant subscriptions); do not rely on payload filtering alone.

## Outputs

- `messaging_design` — A markdown design document with the headline summary, taxonomy, schema-evolution rules, ordering plan, delivery-semantics plan, retention plan, and consumer failure-handling plan.
- `event_catalog_seed` — A short list of named events with payload sketches, producer, consumers, schema version, retention, partition key, intended downstream side effects. Suitable for seeding a future event catalog.
- `rollout_plan` — Phased steps with reversibility checkpoints, ownership assignments, and pre-launch verification gates.

## Examples

### Worked example

Input excerpt:

> Order management service writes orders to Postgres. Need to inform: billing (creates invoice), analytics (aggregates daily), search (re-indexes), notifications (emails the user). Throughput: 50 orders per second sustained, 500 per second peak. Order events must be processed in order per order. Late delivery up to one hour is acceptable for analytics; billing must be near-real-time. Team runs Kafka in production already.

Expected output sketch:

- Messaging style: event-driven on a log-based broker.
- Broker: Kafka, already operated, no second broker introduced.
- Topic taxonomy: `order.events` (per-aggregate, per-order partition key), `order.commands.notifications` (commands for the notifications service).
- Payload: envelope plus a notification body with order id, customer id, total, status; full state lookup remains on the order service.
- Ordering: per-order ordering via order id as the partition key; global ordering not required.
- Schema: Avro in a schema registry; envelope fields standardized.
- Delivery semantics: at-least-once producer with outbox-pattern relay from Postgres; consumers idempotent on `event_id`.
- Retention: 14 days on `order.events`; 7 days on commands; analytics rebuilds within 14 days if needed.
- Consumer plan: billing critical (alert on lag > 30s), search and analytics best-effort (alert on lag > 1h), notifications uses a separate command topic to keep order-event consumers idempotent.
- Rollout: dual-publish for 14 days; cut billing first, then notifications, then search and analytics.

## Limitations

- The skill does not benchmark brokers. It picks a family and assumes operational competence; capacity planning happens elsewhere.
- It does not generate concrete Kafka or Pulsar configuration files; it produces a design, not a deployment.
- It assumes a schema registry is available or can be introduced. Without one, the schema-evolution rules cannot be enforced and the design degrades.
- It cannot decide for an organization whether to operate a broker in-house or use a managed service; both work with the same design.
- For pure batch workloads that look like ETL more than messaging, the skill will recommend not adopting eventing. That is the right answer, but some teams want a different one.
