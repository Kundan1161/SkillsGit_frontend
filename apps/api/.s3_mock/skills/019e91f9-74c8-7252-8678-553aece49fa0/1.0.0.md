# Template And Paved Road Author

## When to use

Use this skill when a platform team is designing — or rescuing — a **software template** (a.k.a. scaffolder template, golden-path template, paved-road repo). The goal of a template is "a new service reaches production in **one hour or less** with all the must-haves wired in", and the failure modes are well known: templates that are over-prescriptive, templates that can't be upgraded, templates that diverge into snowflakes within months.

This skill is the **template authoring** skill. It complements `internal-platform-strategy-author` (which decides *which* paths to pave) and `service-catalog-architect` (which integrates the template's output into the catalog). Use this skill when the strategic question is settled and you're ready to design the actual template.

Trigger on phrases like:

- "software template" / "scaffolder template" / "Backstage template"
- "paved road" / "golden path template"
- "new service in one hour"
- "service template upgrade story"
- "templates diverged"
- "cookiecutter"/"copier" for internal services

Do **not** trigger when the user wants a single-shot code generation (use code-generation skills). This skill produces a **template design**, not a generated service.

## How to apply

Walk the user through six design steps.

### 1. Pick the workload type and scope tightly

One template = one workload type. Resist "the universal service template" — every dimension you parameterize is a future bug. Common workload types worth their own template:

- **Stateless HTTP service** (the most common starter).
- **Scheduled job / batch worker** (cron, Argo Workflows, Kubernetes Job).
- **Event-driven worker** (Kafka/SQS/Pub-Sub consumer).
- **Frontend / SSR app** (Next.js, Remix).
- **ML model serving endpoint** (GPU-aware, model-registry-aware).
- **Data pipeline** (Airflow/Dagster DAG with lineage).

If the user wants one template to handle two workload types, push back: split.

### 2. Decide the template's "minimum viable production"

The template's job is to deliver **production-ready by default**, not "hello world plus a Dockerfile". The minimum that must be wired in:

- **Source control hygiene** — repo with branch protections, CODEOWNERS pointing at the owning team Group, license file, security policy link.
- **CI pipeline** — lint, test (with coverage threshold), build, SBOM, vulnerability scan, container build with reproducible base image, sign artifact, publish on tag/merge.
- **Deploy mechanism** — declarative manifest (Helm chart, Kustomize overlay, Score workload, Crossplane composition) consumed by the org's deployer (Argo CD or Flux), pre-wired to dev / staging / prod environments with required approval policies.
- **Observability** — RED metrics or USE metrics endpoint, structured logs in the org's standard format, traces with the org's tracer (OpenTelemetry SDK preferred), correlation IDs propagated.
- **Health and lifecycle** — readiness probe, liveness probe, graceful shutdown, configuration via env vars or the org's config service.
- **SLOs and dashboards** — at least one default SLO (availability + latency for HTTP services) with the SLI query pre-wired; a default dashboard reference linked from the catalog page.
- **Security baseline** — non-root container, read-only filesystem, distroless base, secrets via the org's secret manager (not env-var-in-YAML), TLS-everywhere, dependency-update bot enabled.
- **Catalog registration** — a fully-filled `catalog-info.yaml` so the service appears in the catalog at creation with owner, system, tier, and links.
- **On-call linkage** — link to the team's rotation; if the team doesn't have one, the template's post-create hook opens an issue saying "register a rotation before going to prod".

If any of these is missing from the template, file an issue in the platform backlog before shipping it.

### 3. Parameterize sparingly

Each input prompt is a place a developer can answer wrong. Hard limits:

- **Required inputs**: name, owning team (validated against Groups), system (validated against Systems), tier, language variant (only if the template supports more than one).
- **Optional inputs (with strong defaults)**: deploy regions, public-vs-private endpoint, base resource requests.
- **No inputs for things the platform mandates**: container base image, log shipper, secret manager. These are choices, not options.
- **Total prompts target**: ≤ 7. If you need more, you're trying to do two workload types in one template.

Validate every input at scaffold time:

- Owner is an existing Group.
- System is an existing System.
- Tier is one of the three documented values.
- Service name is unique in the catalog and matches the org's naming convention.

A scaffold that produces an entity with `owner: TODO` is a future orphan. Fail closed.

### 4. Design the upgrade story (this is what kills templates)

The #1 cause of template death is **no upgrade path**. The day after a service is generated, the template moves on; six months later 200 services have diverged in 200 ways.

Design choices that preserve upgradeability:

- **Embed a `.platform/manifest.yaml`** in every generated service that records: template name, template version, generation timestamp, opt-out flags.
- **Make the template a thin shell over reusable components.** Prefer composition over copy-paste:
  - CI workflows: extend a shared reusable workflow (GitHub Actions `uses: org/.github/.github/workflows/service-ci.yaml@v3`) — the service repo only declares parameters; the actual workflow lives in a versioned shared repo.
  - Helm chart: depend on a shared chart (`charts/service-base@v4`); the service only ships values.
  - Container base image: pin via tag from the platform's image registry; updates flow through tag bumps.
  - Standard libraries (logging, metrics, tracing): single internal SDK pinned via dependency, updated by Renovate/Dependabot.
- **Renovate (or equivalent) is enabled by default** with auto-merge for green minor/patch updates of platform-owned dependencies.
- **Drift detector** runs nightly: scans repos for divergence from the latest template baseline (e.g. workflow file edited, base chart pinned old, base image old). Files a low-severity issue if drift exists beyond an agreed threshold.
- **Major bumps follow a documented playbook**: notice in N-1 quarter, automated migration PRs in N, drift threshold tightens in N+1.

The platform team's measure: **median age of platform-owned dependencies across all services**. If it's older than three months, your upgrade story is broken.

### 5. Choose escape hatches deliberately

Templates that forbid escape hatches get forked. Templates with too many escape hatches stop being golden. Design the seams:

- **First-class escape hatches** (supported off-path moves): customize the Helm `values.yaml`, add additional CI jobs, override resource requests, opt out of the default SLO with a written rationale.
- **Second-class escape hatches** (allowed but flagged in scorecard): replace the standard log format, replace the standard metric library, use a non-standard base image.
- **Disallowed without exception** (security or compliance non-negotiables): bypass SBOM, deploy without secret manager, run as root, disable the deployer's approval gate for prod.

Document the escape hatches in the template README; track second-class usage in the scorecard so it stays visible.

### 6. Distribution, discovery, and adoption metrics

A template no one uses is a museum piece.

- **Discovery**: list the template in the developer portal's scaffolder UI (Backstage, Port, or homegrown), with: when to use, what it produces, who maintains it, the support SLA, links to similar/related templates.
- **Self-serve scaffold**: one click → repo created, catalog registered, default branch protected, on-call check triggered. Wall-clock target: under 5 minutes from "click" to "repo URL".
- **Adoption metric**: percentage of new services in the last 90 days that started from this template (the **golden-path adoption rate**). Below 70% means the path is not golden.
- **Drift metric**: count of services that started from this template and now diverge on platform-owned bits. Trends matter more than absolute counts.
- **Owner and SLA**: every template has a named maintaining team (a Group in the catalog) and a documented response SLA for bugs and upgrade questions.

If a template doesn't have an owner, kill it. Unowned templates poison trust faster than no templates at all.

### Bonus: Score-style workload abstractions

For multi-runtime fleets, consider a **workload spec** layer (Score, Acorn, etc.) where the developer authors a small platform-neutral spec and the platform composes it into Kubernetes, Compose, or serverless manifests. Tradeoffs:

- Pro: real portability, smaller author surface, easier to upgrade the platform side.
- Con: another abstraction; debugging the generated YAML is a skill; not all engines support all primitives.

Recommend only when you have multiple deploy targets (e.g. local Compose for dev, K8s for prod) or when you genuinely expect to swap runtime in the next 18 months. Otherwise it's overhead.

## Inputs

- **target_workload** (required): one workload type (stateless service, scheduled job, etc.). Refuse to scope two in one template.
- **runtime_stack** (required): languages, deploy target, CI tool, deployer, observability backend, secrets mechanism.
- **must_haves** (optional): non-negotiables the security/compliance/SRE org imposes — auth pattern, base image, region rules, encryption-in-transit, SBOM tool.
- **previous_templates** (optional): prior templates and what failed (drift, no upgrade path, too prescriptive, ignored).

## Outputs

A markdown template spec with this shape:

1. **Workload scope** — one sentence describing exactly what this template produces and what it explicitly does not.
2. **Generated layout** — directory tree of the scaffolded repo, every file annotated with "platform-owned (shared/upgrade automatically)" vs "service-owned (developer maintains)".
3. **Parameter list** — required + optional inputs with validation rules and defaults.
4. **Embedded defaults table** — the must-haves wired in: CI steps, deploy mechanism, observability, SLOs, security baseline, catalog registration, on-call linkage.
5. **Upgrade story** — how the template's pieces are kept fresh (reusable workflow, shared chart, base image, SDKs, Renovate config, drift detector, major-bump playbook).
6. **Escape hatches** — first-class, second-class, and disallowed, with rationales.
7. **Adoption metrics** — what you'll measure (golden-path adoption rate, drift count, median platform-dep age) and the targets.
8. **Owner and SLA** — named maintaining team, response SLA, deprecation rules.

## Examples

> "Design a Backstage template for a new Go HTTP service deploying to EKS via Argo CD, with Datadog observability and Vault secrets."

Workload scope: stateless HTTP services in Go 1.22+, prod target = EKS via Argo CD. Layout: `cmd/`, `internal/`, `Dockerfile` (distroless), `chart/` (depending on `org-charts/service-base@v4`), `.github/workflows/ci.yaml` (one-line `uses:` pointing at the shared reusable workflow), `catalog-info.yaml`, `.platform/manifest.yaml`, `SLO.yaml`. Parameters: name, owning team, system, tier, public-endpoint-yes/no, region (default: us-east-1). Embedded defaults: Datadog APM auto-injected via the shared chart, Vault Agent sidecar via the chart, default SLO 99.9% availability + p95 latency < 300ms wired into Datadog SLO API. Upgrade story: reusable workflow + shared chart + base image, all versioned independently, Renovate auto-merges patches. Escape hatch: override chart values via `chart/values.yaml`. Disallowed: bypass SBOM, run as root.

> "Our 6 service templates have diverged. Half don't have working SLOs. New services take 4 days to deploy."

Diagnosis: templates were one-shot copy-paste, no shared upstream. Recommendation: (1) freeze new templates; (2) build one **service-base** Helm chart, one reusable CI workflow, one base image — replace the 6 templates with **2 thin shells** (HTTP service, scheduled job) that consume the shared pieces; (3) generate `.platform/manifest.yaml` retroactively for existing services via a one-shot migration tool; (4) stand up the drift detector so the next quarter shows the divergence curve flattening. Expect time-to-first-deploy to drop from 4 days to under 4 hours within two quarters of adoption.

> "Score-spec for a multi-runtime fleet (Compose locally, K8s in prod)."

Workload scope: developer authors `score.yaml` with workload + dependencies (`postgres`, `s3`, etc.). Local: `score-compose generate` produces `compose.yaml`. Prod: a platform-owned converter (or `score-k8s`) emits Helm values consumed by the standard chart. Parameters and defaults live in `score.yaml`; the developer never edits raw K8s. Upgrade story is **strong** here: the converter version bumps and re-renders manifests in CI; services don't need to be touched. Watch out: Score's `resources` abstraction is leaky when a team needs a CRD-specific field — document the escape hatch to inline annotations.

## Limitations

- This skill is opinionated against monolith templates ("one template, many workload types"). If your org needs that, you'll need to extend with conditional logic and accept higher long-term maintenance.
- The skill assumes you have a deployer (Argo CD, Flux, or equivalent) and a CI provider that supports reusable workflows. Without them, the upgrade story collapses; build those primitives first.
- It does not pick the scaffolder engine (Backstage's scaffolder vs Cookiecutter vs Copier vs Backstage + Crossplane). Use the engine your portal already mandates.
- For greenfield orgs with < 10 services, this is overkill — a templated git-repo and a checklist will outperform a scaffolder. Revisit at ~20 services.
- Generated SLO defaults are starting points; tune per service after week-1 production observation.
