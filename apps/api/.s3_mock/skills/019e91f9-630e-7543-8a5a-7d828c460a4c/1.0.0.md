## When to use

Reach for this skill when an agent is asked to write, restructure, or plan a brand guidelines document. Typical situations:

- A brand system has been designed and now needs a document that lets others use it without asking the designer.
- A brand has rules in people's heads and an outdated PDF and needs a refreshed canonical artifact.
- A company is opening partner programs and needs partner-facing usage terms in addition to internal guidelines.
- A scale-up is replacing a PDF with a documentation site and needs a structure that supports versioning and search.
- A brand owner is moving from a single guidelines document to a living one with a public changelog.

Skip this skill when the request is to design the brand system itself (use a brand-system architect skill instead), when the request is to audit existing guidelines for compliance with a regulation, or when the deliverable is a finished marketing piece rather than a reference document.

## How to apply

Work through the document plan in this order. The first six steps are structural decisions that drive everything else; do not start writing prose until they are settled.

1. Identify the audiences.
   The four common audiences are the internal designer (deep technical detail, downloadable source files), the internal non-designer (templates, shortcuts, what-not-to-do), the external partner or vendor (usage rules, license terms, branded asset downloads), and the press or analyst (logos, headshots, fact sheet).
   Smaller programs may collapse these; larger programs may add a developer audience (token feeds, embed snippets) and an executive audience (positioning summary).
   For each audience, name the one outcome they should be able to achieve without further help.

2. Decide the canonical format.
   A documentation site is recommended when the brand evolves more than once a year, when the audience uses the brand in digital media, and when assets benefit from search.
   A PDF is recommended when the audience is offline, when distribution is controlled, or when the document is itself a brand artifact.
   Site-and-PDF is common at maturity, with the site as canonical and the PDF generated from it.
   A README-in-repo is appropriate for open-source projects whose brand is small.

3. Decide where the canonical lives.
   One location wins when sources disagree.
   Common patterns are a public site with versioned routes, a partner portal behind a signed terms gate, a Figma library that is the source of truth for visuals with a docs site for prose, or a repository whose README is the canonical artifact.
   State the rule explicitly in the document so future contributors do not re-litigate.

4. Decide the versioning model.
   Use semver-style versioning (major for breaking changes such as new wordmark, minor for additions such as a new icon set, patch for clarifications) and keep a public changelog.
   Tag releases.
   Note that brand guidelines, unlike software, are usually backward-compatible — old assets need to keep working even when new ones supersede them.
   Distinguish what is canonical (the current version, in force on new work) from what is permitted (older versions still in circulation under their retirement schedule).

5. Decide the asset repository conventions.
   Source files live in a tracked repository (a Git repo, a DAM, a tracked Figma file) with a documented folder layout, a naming convention, and a generation pipeline that produces derivative files (SVG, PNG, PDF, ICO, favicon set).
   The naming convention should encode mark variant, color theme, and aspect ratio in the filename so a downloader can pick the right file by inspection.
   Refer to the asset-pipeline skill for the operational detail; the guidelines document references the conventions but does not implement them.

6. Decide the license model for external use.
   Three common models are no-license (assets are public but use is governed by the trademark holder), a permissive license with restrictions (assets may be used in narrowly defined contexts such as "to indicate compatibility with this product"), and a partner program license (signed agreement, time-bounded, limited use cases).
   The model determines who sees which sections of the guidelines and which assets are gated.

7. Plan the top-level structure.
   A common structure is: Introduction, Brand essentials, Logo, Color, Type, Iconography, Imagery, Motion, Voice, Accessibility, Applications, Templates, Assets, Usage terms, Changelog, Contact.
   Adjust to the audiences chosen in step 1.
   Avoid clever or theme-named sections; readers search for the obvious word.

8. Author the introduction.
   Open with the brand idea in one sentence and the personality words.
   State who the guidelines are for and how to use them.
   Identify the owning team and the contact path.
   Do not lead with the wordmark — lead with the why.
   Keep the introduction under five hundred words; longer ones are skipped.

9. Author brand essentials.
   Capture the mission and positioning in plain prose, the audiences the brand speaks to, and the personality words.
   Keep this short.
   Long essentials sections are skipped; short ones are absorbed.
   Where the company has separate corporate mission and product positioning statements, name both and explain how they relate.

10. Document the logo.
    State each mark variant, the case for each, the clear-space rule expressed as a multiple of an internal unit, the minimum size per medium, the dark and light variants, the responsive sizing rules, and a don't-use catalog with labeled negative examples.
    Link to source files in the asset repository.
    Show the construction grid on a separate page for designers who need to extend the system.

11. Document color.
    List primitives and semantic roles separately.
    Show every text-on-surface pair with its computed contrast ratio in both themes and the WCAG result.
    Document the role each color plays, not just its hex.
    Forbid use of primitives in product surfaces and explain why — a primitive-only system makes every reskin a search-and-replace project.

12. Document typography.
    Show the families, the scale, weights, line heights, letter spacing, the fallback stack, the license terms, and the licensed surfaces.
    Show worked examples in each role (display, h1 through h6, body, caption, code).
    Include the responsive behavior rule and any rule on long-form line length.

13. Document iconography.
    Show the grid, the stroke weight, the size set, and the source-or-commission rule for icons outside the core set.
    Include a downloadable icon-set link with a documented version.
    State the rule for requesting new icons so contributions stay coherent rather than mixed-in third-party packs.

14. Document imagery and illustration.
    Show on-brand and off-brand examples side by side.
    State the rules on subject framing, lighting, color treatment, human representation, and use of stock.
    State any rules on AI-generated imagery — disclosure expectations, licensing, prohibited uses, and contexts where it is forbidden outright.

15. Document motion.
    State the personality of motion, the duration and easing tokens, and the reduced-motion alternative.
    Include a short clip or storyboard for each signature animation if the format supports it.
    State the rule that motion never carries information by motion alone; the static state must convey the same meaning.

16. Document voice.
    State the voice in three to five sentences.
    Provide a preferred-words list and an avoid-words list.
    State capitalization, contractions, numerals, oxford-comma, and product-name rules.
    Show one on-voice paragraph and one off-voice paragraph for contrast.
    Voice is learned by example; budget pages for the examples.

17. Document accessibility.
    State the WCAG level the brand commits to, the contrast floors, the focus-indicator rules, alt-text discipline, caption expectations for motion, reading-level targets, and the policy for color-only information.
    Note any commitments above the floor for regulated products or accessibility-sensitive markets.

18. Document applications.
    Show the brand applied to real surfaces — a marketing page, a product UI, an email, a social post, an event signage panel, a partner co-brand.
    Each application should call out which rules are in force and where exceptions are permitted.
    Use real applications rather than mockups whenever possible; mockups read as aspirational and are followed loosely.

19. Document templates.
    Where templates exist (decks, social posts, email signatures, document covers), link to them and state the rules for editing them.
    State which fields are editable and which are locked.
    Templates that allow everything are not templates; they are blank canvases.

20. Document the asset repository.
    Show the folder layout, the naming convention, and the file-format matrix (SVG for digital scaling, PNG for raster fallback, PDF-X or EPS for print, ICO and PNG sets for favicons, color-profile-tagged TIFF for special print).
    Show how to choose the right file by filename.
    Link to the canonical asset repository; do not duplicate files into the guidelines document.

21. Author usage terms.
    State who may use the brand, in which contexts, with what restrictions.
    Distinguish nominative use (referring to the brand factually) from suggestive use (implying endorsement).
    Forbid uses that imply false partnership, alter the marks, or attach the brand to political, religious, or adult content unless those are part of the brand.
    Note any trademark notices required on use.

22. Author the partner license if a partner program exists.
    Spell out the scope, the time bound, the renewal mechanism, the permitted asset variants, and the audit rights of the brand owner.
    Refer to legal counsel; the document is not a substitute for a signed agreement.
    The partner license section is the part of the document that is most often litigated; budget time for legal review.

23. Author the changelog.
    The changelog lives at a stable URL and lists each release with version, date, and notes.
    Distinguish breaking changes (require partner action) from additions (no action required).
    Keep entries in reverse chronological order.
    Link from each entry to the migration steps where any apply.

24. Define the contact and escalation path.
    State the team that owns the brand, the channel to request a review (a partner co-brand, an unusual application, an exception), and the typical turnaround.
    Without a contact path, the guidelines are read as either permissive or forbidding and both outcomes are wrong.
    Where the team has on-call hours or a request form, link them.

25. Plan the maintenance cadence.
    Quarterly is a reasonable default for review of usage in the wild, accumulation of new patterns into the document, and decision on retirements.
    Annual is reasonable for a major release.
    State the cadence in the document so partners know what to expect.

26. Set up the publishing pipeline.
    If the canonical is a site, decide the hosting, the editor experience, the review and approval flow, and the URL versioning scheme (for example `/v1`, `/v2` or content-negotiated).
    If the canonical is a PDF, decide who generates it, from what source, and how it is distributed and retracted.
    Confirm previous versions remain accessible at stable URLs for citation and audit.

27. Stage the rollout.
    Internal first, partner next, public last.
    Announce the launch in the channels each audience listens to.
    Sunset the previous artifact with a public note rather than silently replacing it.
    A silent replacement breaks every external link and erases the citation record.

## Inputs

- The brand system being documented.
- The audiences served.
- The canonical format and distribution channel.
- Any existing guidelines or assets that the new document supersedes.

## Outputs

- A complete outline of the guidelines.
- Draft prose for the foundational sections (introduction, voice, usage terms).
- Stubs for the technical sections (logo, color, type) that the brand owner fills in with the source spec.
- A changelog template and a maintenance plan.
- A list of decisions still required.

## Examples

A request like "author a guidelines site for a developer-tools brand whose audiences are internal designers, internal engineers, external partners, and press" should produce:
- A four-audience information architecture with sections labeled by audience.
- Only the partner-license section gated behind sign-in and an accepted terms agreement.
- A public changelog at a stable URL with semver-style versioning.
- An asset section that links to a Git repository rather than duplicating files.
- A voice section grounded in plain technical writing with example paragraphs.
- A token-feed section for developers with snippets and a versioned reference.
- A contact path with a request form and a documented turnaround time.

A request like "draft the usage terms for a consumer brand that licenses its mark to retailers" should produce:
- A partner-only section spelling out the permitted asset variants and the contexts in which the mark may appear.
- A prohibited-contexts list including unrelated political or adult content and uses that imply false partnership.
- An audit-rights paragraph reserving the brand owner's right to review usage in-market.
- A renewal and termination mechanism with notice periods.
- A public section permitting nominative use by reviewers and journalists with no sign-in required.
- A reference to counsel for the signed agreement that accompanies the license.

## Anti-patterns to avoid

The methodology fails when any of these creep in. Flag them explicitly when reviewing a guidelines document.

- A single-audience document trying to serve four audiences. The internal designer gets bored, the partner cannot find the license, and the press leaves with no facts.
- A document that opens with the wordmark and goes straight to clear space. The reader has not been told what the brand is or who the document is for.
- A voice section that names adjectives without examples. Voice cannot be transferred by descriptor lists; example paragraphs are mandatory.
- A guidelines PDF with no changelog and no version tag. Readers cannot tell whether they are looking at the current rules.
- A document that forbids everything and permits nothing. The result is partners who either ignore the document or stop using the brand at all.
- A document that permits everything and forbids nothing. The result is brand drift within months.
- Usage terms drafted without legal review. The partner license is the part most often litigated; an unreviewed term is a future problem.
- A canonical that exists in two places (a site and a Figma library) with no rule for which wins. Both sources drift apart and the team loses trust in either.

## Migration guidance

Most guidelines authoring is a migration from a previous artifact rather than a green-field draft. The methodology handles migration:

- Inventory the previous artifact. List every page or section and decide whether it survives, merges, or retires.
- Preserve the previous artifact at a stable URL. External links and citations depend on it.
- Map the previous structure onto the new one and publish a side-by-side correspondence for the first quarter after launch.
- Notify partners and vendors with enough lead time to update their downstream artifacts.
- Track which surfaces have moved to the new guidelines and which are still on the old, and report progress to the brand owner monthly until migration completes.

## Limitations

- The skill produces a document plan and draft prose; it does not replace legal review of usage terms or partner licenses.
- The skill assumes the brand system itself is settled. A document built on an unstable system will need to be rewritten section by section as the system stabilizes.
- Trademark notices, registered-mark symbols, and required attributions are jurisdiction-specific and must be verified by qualified counsel.
- The skill does not handle distribution platform configuration or DAM tool setup; it specifies the conventions those platforms should enforce.
- The skill does not translate the document into other languages. Translation must be coordinated with the brand owner, with attention to voice rules that may not transfer directly across languages.
- Accessibility commitments stated in the document must be verified by a qualified accessibility reviewer; the skill states the commitment but does not confirm conformance.
- Output should be reviewed by a brand owner and, for usage terms and partner licenses, by legal counsel before publication.

## What this skill does not do

To keep scope clear, the skill explicitly does not:

- Design the brand system the document describes. Use the brand-system-architect skill for that.
- Construct the logo system. Use the logo-system-construction-methodology skill for that.
- Operate the asset pipeline. Use the brand-asset-pipeline skill for that.
- Author a legally binding contract. The partner license section of the document references the agreement; the agreement itself is counsel's work.
- Perform a brand audit of existing usage. A separate audit pass against the canonical document is required; the document defines the rules, the audit measures conformance.
