## When to use

Use this skill when an analytics team needs to organize data delivery into a domain-aligned mart, not a sprawl of ad-hoc dbt models. Specifically:

- A team is exiting the "one giant model" stage and needs proper marts before the analytics surface becomes unowned and unsupported.
- A new domain (e.g., a freshly-acquired company, a new product line, a new geography) needs a mart from scratch.
- Marketing, finance, product, and support each have their own copy of the customer table and you want to consolidate.
- A reverse-ETL job, a BI tool, or an AI agent is being introduced and the data surface needs to be defined as a contract, not a moving target.
- A migration from a legacy warehouse or a hand-rolled SQL stack to a modern dbt / semantic-layer setup is underway.

Do not use this skill to redesign the staging layer — that is upstream. Do not use it to define metrics — pair with the metric definition designer. Do not use it to do dimensional modeling (star schemas) at the warehouse-engine level; pair with the star schema designer, which is the input the mart designer consumes.

## How to apply

The mart is the boundary between analytics-engineering work and business consumption. It is a contract: producers maintain it, consumers depend on it, and changes are coordinated. Work the steps in order.

### 1. Bound the domain

1. **Name the domain in one phrase.** "Revenue", "marketing", "product analytics", "support performance", "subscription operations". The name controls scope; ambiguous names ("data") produce sprawling marts.
2. **Write the one-paragraph mart charter.** What questions does it answer, who reads it, what is outside its scope. The charter goes in the mart README and is the first thing future contributors read.
3. **List the domain owners.** A mart has one accountable owner (a team lead, an analytics-engineering lead, or a domain analyst) and a list of stakeholders. Decisions are made by the owner; stakeholders are informed.
4. **List the consumers concretely.** "The CFO's monthly board pack", "the growth dashboard in Lightdash", "the Stripe-to-Salesforce reverse-ETL", "the AI agent that answers questions in Slack". Vague consumers ("the business") are not consumers; they are an evasion. The consumer list determines the grain.
5. **Reject domain overlap upfront.** Revenue and marketing both touch "customer" and "deal"; product and support both touch "user" and "session". Define which mart owns each conformed entity (see step 5) and which mart consumes it from the owner. Co-ownership is no ownership.

### 2. Inventory the inputs

6. **List every staging model in scope** with its grain, refresh cadence, primary keys, and known data-quality issues. A mart built over unreliable staging will inherit the unreliability and surface it to consumers.
7. **List every intermediate model in scope.** Intermediates that exist for one mart are mart-private; intermediates shared across marts are part of the project's common layer and should be governed there.
8. **Identify sources missing from staging.** A mart that requires a Salesforce table but the staging layer does not include one is a request to extend staging, not an excuse to bypass it with a direct source reference. Flag and require staging be built first.
9. **Identify duplicated upstream logic.** Two staging models reading the same source, or two intermediates computing the same join, will produce divergent marts. Resolve before mart design begins.
10. **Note adapter-specific patterns.** BigQuery STRUCT, Snowflake VARIANT, Databricks Delta, Redshift compound sortkeys — the mart will use whatever the engine provides. Document the engine upfront so design decisions (clustering keys, partitioning, materialized views) align.

### 3. Decide the fact tables

11. **A fact table records events or states with explicit grain.** Pick the grain first, the columns second. "One row per order line, with order timestamp", not "all the order columns".
12. **Identify the candidate facts for this domain.** Revenue: invoices, transactions, refunds, subscriptions, renewals. Marketing: ad-impressions, ad-clicks, leads, attributed-touches. Product: events, sessions, feature-uses. Support: tickets, ticket-events, CSAT-responses, agent-actions.
13. **For each fact, pick exactly one grain.** Mixed-grain facts (a single table holding both order-level and order-line-level rows) produce wrong answers under almost every aggregation. Split.
14. **Choose grain at the lowest meaningful level.** Aggregating up is cheap; aggregating down is impossible. A daily-grain product-usage fact is more flexible than a monthly-grain one, even if today's only consumer is the monthly executive dashboard.
15. **Name facts by the noun and the grain.** `fct_orders` (one row per order), `fct_order_lines` (one row per line), `fct_subscription_events` (one row per state-transition), `fct_ad_clicks_daily` (one row per ad x day). The name tells the consumer the grain; they should not have to look it up.
16. **Identify additive, semi-additive, and non-additive measures** on each fact. Additive measures (revenue, click count) sum across all dimensions. Semi-additive (account balance) sum across some dimensions but not time. Non-additive (ratios, distinct counts, ranks) need careful handling at the aggregation layer or, preferably, expression in the semantic layer rather than as a stored column.
17. **Reject mart facts that hold unaggregated raw events** unless raw events are the genuine consumer surface. A mart `fct_pageviews` with the raw event payload is fine for product analytics; a mart `fct_revenue_clicks_pageviews_ticketsalljoined` is a sign of model fatigue, not design.

### 4. Decide the dimension tables

18. **A dimension is who, what, where, when.** Customer, product, channel, geography, date. Dimensions are typically slowly changing; facts are typically immutable.
19. **For each fact, list the dimensions it is sliced by.** Every dimension reference becomes a foreign-key column on the fact. Surface keys (`customer_sk`, `product_sk`) plus a natural key alongside for joins back to operational systems.
20. **Build dim tables at the project's "as-of" model for the entity.** `dim_customers` typically holds one row per customer with the current values. If history matters (and for marts it usually does), add a Type 2 SCD via dbt snapshots and a separate `dim_customers_history` model.
21. **Be ruthless about Type 2 history.** Only attributes that are referenced for historical analysis need Type 2 treatment. Customer name change rarely matters; plan tier change usually does; assigned account executive sometimes does. Track only what is needed; the cost in storage and complexity is real.
22. **Document the SCD strategy on every dim column.** Even simple `dim_customers` should annotate each column with Type 1 (overwrite), Type 2 (track history), or Type 0 (never changes). This is the audit trail that prevents the next analyst from "fixing" a Type 2 column to a Type 1.
23. **Reject dim tables with thousands of columns.** A 400-column dim is the result of every team adding fields they want. Split by domain (`dim_customers_billing`, `dim_customers_growth`) or use a structured column for rarely-queried attributes.

### 5. Conform dimensions across marts

24. **A conformed dimension is one shared across marts** with identical grain and identical surrogate keys. Customer in the revenue mart must equal customer in the marketing mart — same `customer_sk`, same `customer_id`, same canonical name. Without conformance, cross-domain queries are impossible.
25. **Establish a single owning mart per conformed dimension.** Revenue typically owns customer (it has the most rigorous matching); product typically owns user (it has the most events); marketing typically owns channel and campaign; support typically owns agent.
26. **Other marts consume the conformed dim by reference** (`ref()`-ing the canonical model), never by rebuilding their own copy. Drift between two versions of the same conformed dim is the single largest source of cross-domain reporting bugs.
27. **For date dimensions, use a single project-wide `dim_date`.** Every mart joins to it. Build with rich attributes (fiscal periods, holidays, day-of-week, ISO week, quarter-end flag) once; reuse everywhere.
28. **For currency, exchange rates, and time zones, use a single project-wide reference table** or set of macros. Multiple inconsistent conversion approaches produce reporting bugs that take quarters to find.
29. **Document conformed dimensions in a project-wide doc.** A reviewer should be able to see at a glance which marts depend on which conformed dims.

### 6. Materialization and refresh

30. **Default mart materialization is `table`.** Views are too slow for BI consumption at any scale; ephemeral models cannot be queried directly and are a pain to debug; tables are predictable.
31. **Use `incremental` for facts that grow append-only** and exceed roughly 10M rows. Specify `unique_key`, `incremental_strategy` (`merge` for warehouses that support it; `append` for pure event streams), and the `is_incremental()` filter on the high-water-mark column.
32. **Use `materialized_view`** (Snowflake dynamic tables, BigQuery materialized views, Databricks streaming tables) for facts that require sub-minute freshness and the engine supports it. Document the constraint.
33. **Match the refresh cadence to the consumer.** A finance mart consumed in monthly close needs daily refresh at most; a product mart consumed for real-time experimentation may need hourly or sub-hourly. Over-refreshing is a cost mistake; under-refreshing is a trust mistake.
34. **Document the freshness SLA per model.** "fct_orders refreshes hourly; expected lag from source < 90 min." Consumers need to know what they can rely on.
35. **Plan for backfill.** Every incremental model needs a `--full-refresh` path that completes within an acceptable window. If the full-refresh takes a day on a 10TB table, partition and refresh segment-by-segment, not the whole table.

### 7. Tests and contracts

36. **Every fact has a `unique` and `not_null` test on its grain key.** A `fct_order_lines` without a `unique` test on `order_line_sk` is a fact that will silently double-count under future refactoring.
37. **Every foreign key on a fact has a `relationships` test** to its dimension. Orphan keys are an early warning that staging is broken.
38. **Every dim has a `unique` test on its surrogate key** and a `not_null` test on its natural key. SCD Type 2 dims add a `unique_combination_of_columns` test on (natural_key, valid_from).
39. **Use `accepted_values` for every enum-style column** in both facts and dims. A status column that silently gains a new value should fail the build, not propagate quietly.
40. **Use freshness tests on every staging source the mart depends on.** A mart whose upstream is two days stale should warn; one whose upstream is a week stale should error.
41. **Use dbt contracts (or equivalent) for marts consumed by external systems.** A reverse-ETL job that consumes `fct_orders` should fail the dbt build, not silently break in production, when the contract changes.
42. **Add custom singular tests for domain-specific invariants.** "Refund amounts never exceed original transaction amount", "no customer has two active subscriptions in the same product line", "no negative quantities on a shipped order". These tests embed business knowledge that schema-level tests cannot express.

### 8. Documentation and exposure

43. **Every mart model has a `description` in schema.yml** stating the grain in plain English and the domain owner.
44. **Every column on a mart model has a description.** No exceptions. Mart columns are the consumer surface; undocumented columns produce questions that should have been answered in advance.
45. **Use `doc()` blocks for shared definitions** (e.g., what "active customer" means, where the canonical churn definition lives). Reference the metric definition in the mart docs; never redefine.
46. **Every consumer is an `exposure`.** Dashboards, BI tools, reverse-ETL syncs, AI agents. Without exposures, lineage stops at the mart and the data team has no idea who will break.
47. **Tag exposures by criticality.** A board-pack dashboard is critical; an exploratory analyst dashboard is not. The tag drives the deprecation cadence and the on-call response when the mart breaks.
48. **Use `meta` blocks for owners, refresh SLAs, PII flags, and certification level.** A standardized meta schema across the project makes governance tooling possible.
49. **Publish a mart README.** It lives in the dbt repo, explains the charter from step 2, and lists the canonical entry points (the five-or-so models a consumer should start from).

### 9. Domain-specific guidance

Each domain has its own canonical shape. Apply these as defaults; deviate when the business justifies it.

50. **Revenue mart.** Facts: `fct_invoices`, `fct_transactions`, `fct_refunds`, `fct_subscriptions` (one row per subscription per state), `fct_subscription_events` (one row per transition), `fct_arr_daily` (snapshot of ARR per customer per day). Dims: `dim_customers` (owns conformed customer), `dim_products`, `dim_plans`, `dim_contracts`. Watch for: multi-currency, refund timing, deferred-revenue recognition, contract amendments.
51. **Marketing mart.** Facts: `fct_ad_spend_daily`, `fct_ad_impressions` (often aggregated to channel x day x audience), `fct_ad_clicks`, `fct_leads`, `fct_marketing_touches` (multi-touch attribution model output). Dims: `dim_channels`, `dim_campaigns`, `dim_audiences`, `dim_creatives`. Watch for: attribution-model versioning, last-touch vs multi-touch reconciliation, UTM-parameter normalization, ad-platform de-duplication.
52. **Product mart.** Facts: `fct_events` (one row per raw event, optionally), `fct_sessions` (one row per session), `fct_feature_usage_daily` (one row per user x feature x day), `fct_funnels` (one row per user x funnel-stage). Dims: `dim_users` (owns conformed user), `dim_features`, `dim_devices`, `dim_app_versions`. Watch for: event-schema drift, anonymous-to-identified user stitching, time-zone normalization, bot traffic.
53. **Support mart.** Facts: `fct_tickets`, `fct_ticket_events`, `fct_csat_responses`, `fct_agent_time`. Dims: `dim_agents`, `dim_ticket_types`, `dim_priorities`, `dim_customers` (consumed from revenue mart). Watch for: ticket-merge events, status-history modeling, SLA-clock pauses, response-time vs resolution-time distinctions.
54. **Custom domain marts.** Follow the same fact/dim split. Resist building a mart that is "everything in one place" — that is the symptom the team came to fix.

### 10. The rollout plan

55. **Ship facts before reports.** A new fact model with no consumer is harmless; a new dashboard with no fact is broken. Build the pipeline bottom-up.
56. **Dual-publish during migration.** When a mart replaces existing models, run both side-by-side for one full reporting cycle. Compare numbers. Investigate every divergence. Cut over only when explained.
57. **Communicate the cutover.** Email every consumer with a date, the new model names, and the test queries they can run to validate their own dashboards. Silent cutovers produce incident postmortems.
58. **Deprecate aggressively.** Once a mart has replaced its predecessors and one reporting cycle has passed cleanly, mark the predecessors as deprecated and set a removal date. Models marked deprecated for more than two quarters should be removed; otherwise they accumulate.
59. **Track adoption.** Count downstream queries against the new mart and the old one. When the old one drops to zero, remove. When it stays nonzero, find out who is still using it and either migrate them or document the exception.
60. **Plan for v2.** No mart is perfect at launch. Schedule the first review at 90 days and the second at 180 days. The mart that does not get revised within a year is either perfect (unlikely) or unloved (likely).

### 11. Anti-patterns to surface

61. **The "everything" mart.** One model joining all upstream tables. Split.
62. **The mart with no grain stated.** Unrecoverable until grain is named.
63. **The mart with five owners.** Pick one.
64. **The mart that bypasses staging** to pull a "convenient" raw source directly. Forces the bypass into every future audit; refactor.
65. **The mart whose columns evolve faster than its consumers.** Add columns liberally; rename or drop columns only under contract.
66. **The mart that imports its own redefinition of customer.** Conformed dims must be consumed, not rebuilt.
67. **The mart with no tests on its grain key.** Every other test is moot if the grain is not what it claims to be.
68. **The mart that materializes a 200-line SQL into a view.** Views over views in marts produce query trees that explode at run time. Materialize.
69. **The mart consumed by an executive dashboard with no exposure declared.** When the mart breaks, no one knows the dashboard is downstream.
70. **The mart designed in isolation from its consumers.** A mart designed without a consumer interview is a mart that will be reshaped within a quarter.

### 12. Output discipline

71. **Open with the charter.** Two sentences: what the mart is, who reads it.
72. **Then list facts and dims** in two flat lists. Each entry: name, grain (for facts) or natural key (for dims), short description, owner, refresh cadence.
73. **Then the conformed dimensions section** naming the mart that owns each shared dim and the marts that consume it.
74. **Then dependency map.** A flat list of upstream staging and intermediate models per mart model, and downstream consumers per mart model.
75. **Then rollout plan.** Phases with named exit criteria.
76. **End with a one-paragraph "what this mart will not do".** Constraining negative space prevents the next-quarter scope creep that produces "everything" marts.

## Inputs

- The domain (revenue, marketing, product, support, custom).
- Source inventory (staging, intermediate, raw).
- Consumers (teams, tools, dashboards, downstream syncs).
- Optional scale signals (row counts, warehouse engine, refresh expectations).
- Optional existing models to merge, replace, or keep.

## Outputs

- Mart design (facts, dims, conformed dimensions, columns, tests, materialization).
- Dependency map (upstream → mart model → downstream consumer).
- Phased rollout plan with dual-publishing and deprecation steps.
- "What this mart will not do" boundary statement.

## Examples

**Example 1 — Revenue mart from scratch**

> Input: A Stripe-based subscription business. Staging has `stg_stripe__invoices`, `stg_stripe__charges`, `stg_stripe__customers`, `stg_stripe__subscriptions`, `stg_salesforce__opportunities`. Consumers are the CFO's monthly board pack, the AE compensation system, and the in-app billing page.
>
> Expected output: Facts — `fct_invoices` (one per invoice), `fct_transactions` (one per charge or refund), `fct_subscription_states` (one per subscription per state-transition), `fct_arr_daily` (one per customer per day, snapshot). Dims — `dim_customers` (Type 2 on plan tier, AE owner, contract status), `dim_plans`, `dim_products`. Conformed customer dim owned by this mart; consumed by marketing and support. Materialization: `fct_arr_daily` incremental, partitioned by snapshot_date; everything else table, refreshed daily at 04:00 UTC. Exposures: three named consumers. Rollout: ship `fct_invoices` and `dim_customers` first, dual-publish against the legacy `customer_revenue_report` model for one month, cut over after CFO sign-off.

**Example 2 — Product mart on a warehouse-native event stream**

> Input: A consumer product on Snowflake with ~500M events/month. Staging has `stg_events__raw` (one per event), `stg_users` (current state), `stg_app_versions`. Consumers are the growth team's weekly review, the product manager dashboards, and an AI-powered "where did users drop" diagnostic tool.
>
> Expected output: Facts — `fct_events` (incremental, partitioned by event_date), `fct_sessions` (incremental, daily roll-up), `fct_user_feature_daily` (one per user x feature x day), `fct_funnels` (one per user x funnel x highest-stage-reached x cohort-week). Dims — `dim_users` (Type 1 with separate Type 2 history), `dim_features`, `dim_app_versions`, `dim_devices`. Conformed user dim owned by this mart; consumed by support. Materialization: `fct_events` incremental with 7-day late-arriving window; `fct_sessions` incremental; aggregate facts table-materialized. Refresh hourly. Watch for: anonymous-to-identified stitching adds rows retroactively — `fct_events` includes a `stitched_at` timestamp and downstream models filter on `event_at`, not `inserted_at`.

**Example 3 — Marketing mart consolidating ad platforms**

> Input: Three ad platforms (Google, Meta, LinkedIn) with their own staging models, a marketing-automation tool, and a Salesforce link. Consumers are the marketing leadership weekly review and the CFO's CAC calculation.
>
> Expected output: Facts — `fct_ad_spend_daily` (one per channel x campaign x day), `fct_ad_clicks` (one per click, with UTM-normalized fields), `fct_leads` (one per lead, with attributed first-touch and last-touch channel), `fct_marketing_touches` (one per touch per lead, for multi-touch model). Dims — `dim_channels` (owned here), `dim_campaigns` (owned here), `dim_creatives`. Customer dim consumed from revenue mart. Watch for: ad-platform self-reported metrics differ from in-house tracking — document the discrepancy and pick one source per metric; UTM-parameter casing is inconsistent and must be lowercased in staging; attribution-model version is metadata on `fct_marketing_touches` so historical changes can be re-run without overwriting prior assignments.

## Limitations

- The skill produces a design, not running SQL. A subsequent dbt build is required to land the models.
- It does not size compute or storage costs. Use the warehouse engine's planner for that.
- For very high-cardinality dimensions (millions of distinct products, hundreds of millions of users), some materialization recommendations need to be tuned per engine; the skill flags the cardinality but does not produce engine-specific tuning.
- It assumes the staging layer exists and is reliable. If staging is missing or untrusted, fix staging first; pair with the dbt review skill.
- It does not specify the semantic-layer wiring on top of the mart. Pair with the metric definition designer to bridge mart columns to metrics.
- For data-mesh organizations with strong domain autonomy, the mart-per-domain pattern still applies but conformed-dimension ownership negotiations are political, not technical; the skill flags conformance gaps but cannot resolve them.
