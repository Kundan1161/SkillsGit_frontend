# ROS 1 to ROS 2 Migration Planner

## When to use

Use this skill when a team must plan a migration from ROS 1 to ROS 2. Triggers include: ROS 1 Noetic's end-of-life is approaching and the team needs a credible plan; a new robot generation is being designed and the team is debating whether to stay on ROS 1 or jump; a fleet exists half on ROS 1 and half on ROS 2 and the operational pain of supporting both is mounting; a third-party dependency (Gazebo, MoveIt, Nav stack, a sensor driver) has moved to ROS 2 and is dragging the rest of the stack along; or leadership wants a cost and risk estimate before approving the migration.

The skill produces a *plan* — staging, dependencies, interface mappings, bridge strategy, testing approach — not a code conversion. Actual code migration is per-package work that uses the plan as a guide.

It does not apply to: small in-place code edits (the team should consult ROS 2 porting tutorials directly); ROS 2 to ROS 2 distribution upgrades (e.g., Humble to Jazzy — that is a smaller exercise); or fresh ROS 2 system design (use the architecture-reviewer skill instead).

**This skill produces methodology guidance for robot software architecture. Outputs must be reviewed by qualified robotics engineers and validated in simulation and bench tests before any deployment on hardware that interacts with people or property. Bad robot software causes physical harm — treat all advice as a starting point, not a deployment-ready specification.**

The bar the skill applies is "can the team migrate without grounding the fleet, without losing safety-critical behaviors, and without spending more than the budget allows?"

## How to apply

The planner walks through a structured set of decisions and produces a staged plan.

### Stage 1 — Inventory and triage

1. Enumerate every package in the current ROS 1 stack. For each, record: language (C++ / Python / mixed), third-party dependencies, whether it owns hardware, whether it is safety-critical, lines of code (rough proxy for effort), test coverage (rough proxy for confidence).
2. Classify each package into one of: *trivial port* (small Python or C++ utility, few external dependencies), *moderate port* (mid-sized node with several pub/sub topics and one or two services), *complex port* (large node, action servers, dynamic_reconfigure, plugin interfaces), *third-party port* (the team does not own the source — they wait or pay).
3. Identify *hard blockers*: packages whose third-party dependency has no ROS 2 port and no realistic path to one. Hard blockers either delay the migration, get bridged, or get reimplemented.
4. Identify *soft blockers*: packages whose ROS 2 port exists but lags in features or stability. These ship after the rest.
5. Identify *load-bearing packages* — the ones every other package depends on (an internal message-definitions package, a core driver, a custom transform library). These are migration-critical and go first.
6. Produce the *package migration table* with columns: package, language, complexity, third-party readiness, recommended phase, blockers, owner.

### Stage 2 — Distribution choice

7. Target a *long-term-support* distribution. Humble is the current canonical LTS for many teams; Jazzy is the newer LTS; choosing a non-LTS distribution forces another migration within a year and is usually a mistake.
8. Confirm the target distribution supports the team's *operating system* — each ROS 2 distro has a tier-1 Ubuntu version, and using anything else is on-your-own.
9. Confirm the target distribution has *binary releases* of the team's third-party dependencies (Nav2, MoveIt2, sensor drivers). Source-only builds work but increase friction.
10. Decide whether to target a *single distribution* across the fleet or to permit a rolling distribution upgrade later. Single-distribution is simpler; rolling is harder but reduces customer-visible churn.

### Stage 3 — Interface mapping

11. For every ROS 1 topic, decide the ROS 2 *topic name* and *QoS profile*. Topic names usually port directly; QoS must be designed (see the architecture-reviewer skill for the QoS framework).
12. For every ROS 1 service, decide whether it becomes a ROS 2 service or — if it is long-running with cancellation needs — a ROS 2 action.
13. For every ROS 1 *actionlib server*, port to a *ROS 2 action server*. The semantics are similar but the API differs significantly. Plan to rewrite the action server, not translate it line-by-line.
14. For every ROS 1 *dynamic_reconfigure* server, port to ROS 2 *parameters with callbacks*. ROS 2 parameters subsume dynamic_reconfigure; the migration is conceptual as well as syntactic.
15. For every ROS 1 *nodelet*, port to a ROS 2 *composable node* (component). The intra-process zero-copy semantics carry over with cleaner ergonomics.
16. For every ROS 1 *message definition*, decide whether to port as-is, modernize, or deprecate.
    - As-is is fastest and supports bridging.
    - Modernization is the chance to fix field units, add headers, add frame_id, and version interfaces.
    - Deprecation is for messages that should not have existed in ROS 1.
17. Standard ROS messages (`std_msgs`, `geometry_msgs`, `sensor_msgs`, `nav_msgs`) have ROS 2 equivalents with very similar shapes; most port trivially. Note the few that changed (`Header` has lost `seq` in ROS 2; `tf::Transform` semantics differ).

### Stage 4 — Lifecycle and composition redesign

18. ROS 2's lifecycle nodes are a feature ROS 1 did not have. Identify packages that *should become lifecycle nodes* during migration — drivers, planners, controllers, anything that owns resources, anything safety-critical.
19. Identify which nodes will be *composable* (loaded into a component container) for performance. Re-introducing nodelet equivalents in ROS 2 as components is one of the migration's net wins; plan for it.
20. Identify the *executor strategy* per process. ROS 1's single global spinner is gone; each ROS 2 process picks an executor. Plan for the architecture-reviewer skill's executor recommendations.

### Stage 5 — Bridge strategy

21. The *ros1_bridge* package allows a ROS 1 system and a ROS 2 system to coexist with bidirectional topic/service translation. It is essential for any phased migration with a live fleet.
22. Identify which interfaces need to cross the bridge in each direction during the transition. Bridging everything is expensive in CPU and adds latency; bridging only what is needed is the discipline.
23. *Caveat*: the bridge needs both ROS 1 and ROS 2 runtimes on the same machine, with compatible OS support. Older OSes may not host both.
24. *Caveat*: custom messages require special handling in the bridge — both sides need the type information, which means building the message definitions for both distros.
25. *Caveat*: bridged QoS defaults are conservative. High-rate sensor topics flowing through the bridge with `RELIABLE` will starve. Tune QoS on the ROS 2 side.
26. For multi-machine fleets, decide whether the bridge runs on every robot or only on a central machine — the bandwidth and latency implications differ.
27. Plan the *bridge sunset* — the date by which the last bridged interface is migrated and the bridge is removed. Without a sunset, the bridge becomes permanent technical debt.

### Stage 6 — Parameter and launch migration

28. ROS 1 `.launch` (XML) files do not run on ROS 2. ROS 2 supports Python, XML, and YAML launch — the team chooses one or mixes.
29. Python launch is the most expressive and the most common new-project choice. XML launch is simpler and closer to ROS 1's mental model. YAML launch is the most static.
30. ROS 1's parameter server is gone. Each ROS 2 node owns its parameters; parameter YAMLs are loaded per-node at launch.
31. Plan the *parameter file reorganization*. A monolithic ROS 1 `params.yaml` typically becomes several per-node YAMLs in ROS 2, or one YAML organized by node name.
32. Plan the *namespace strategy*. ROS 2's per-node namespaces are stricter than ROS 1's loose handling — get the namespace plan right before mass migration.
33. Plan the *environment variables*. `ROS_MASTER_URI` is gone (no master in ROS 2). `ROS_DOMAIN_ID`, `ROS_LOCALHOST_ONLY`, and RMW selection take its place.

### Stage 7 — Action server migration

34. ROS 1 actionlib and ROS 2 actions look similar but differ in details — ROS 2 actions are first-class and use the underlying middleware, not a wrapper of topics.
35. Plan to *rewrite* action servers, not port. Goal handles, feedback publishing, cancellation, and result reporting are different.
36. Audit each ROS 1 actionlib server for *cancellation correctness*. If the ROS 1 server ignored preempts or had race conditions, the ROS 2 rewrite is the chance to fix them.
37. Audit each ROS 1 actionlib *client*. ROS 2 action clients have a different API; calling code needs adjustment too.

### Stage 8 — Rosbag and tooling migration

38. ROS 1 `.bag` files and ROS 2 `.db3` / `.mcap` rosbag2 files are different. There are tools to convert (`rosbags` Python library and others); plan whether to keep historical bags as ROS 1 (preserved as artifact) or convert them to ROS 2 for replay.
39. Plan tooling: `rqt` plugins, `rviz`, `tf` ecosystem. RViz2 is largely API-compatible with RViz; `rqt` plugins often need porting. List the tools the team relies on and check ROS 2 status of each.
40. Plan CI. ROS 1 colcon vs catkin matters. ROS 2 builds on colcon; if the team is on `catkin_make` in ROS 1, the migration also shifts build tooling.

### Stage 9 — Testing strategy

41. Treat the migration as an opportunity to *raise test coverage*. A passing ROS 2 test suite is the migration's exit gate.
42. Plan *unit tests* for each migrated package — `pytest` or `gtest` depending on language.
43. Plan *integration tests* using `launch_testing` — bring up the node, send messages, assert outputs. ROS 2's test infrastructure is meaningfully better than ROS 1's; use it.
44. Plan *simulation regression tests*. A canonical mission run in Gazebo (or Ignition/Gz) on the ROS 1 stack and the ROS 2 stack should produce comparable trajectories. Diff them.
45. Plan *hardware regression tests*. A bench-rig version of the robot, with the wheels off the floor, runs the same canonical mission. Diff sensor traces.
46. Plan a *phased rollout to the fleet*: dev robots first, internal staging, customer pilot, broader fleet. Define rollback criteria for each phase.

### Stage 10 — Risk and mitigation

47. *Hidden interface drift*: ROS 1 stacks accumulate undocumented topic dependencies. A package that mysteriously consumed `/diagnostics_agg` for behavior will break silently. Mitigation: full graph audit before and after.
48. *Performance regression*: ROS 2 with the wrong executor, the wrong QoS, and process-per-node instead of composition is *slower* than ROS 1. Mitigation: composition plan, QoS plan, profiling baseline.
49. *Driver dropouts*: third-party drivers ported by their maintainers may have subtle behavior differences. Mitigation: side-by-side test with ROS 1 reference and ROS 2 candidate against the same hardware.
50. *Fleet downtime*: a botched migration can ground robots. Mitigation: bridge-then-cut-over phasing, not big-bang; ability to roll back per robot.
51. *Lost institutional knowledge*: engineers who knew the ROS 1 system retire or move on mid-migration. Mitigation: documentation of the migration plan itself, including the design rationale for QoS and lifecycle choices.

### Stage 11 — Phased plan

52. Produce a phased migration plan tuned to the timeline input. A representative shape for a 12-month phased migration:
    - *Phase 0 (weeks 1-4)*: build infrastructure — ROS 2 CI green, ros1_bridge integrated, message-definitions package ported, training for the team.
    - *Phase 1 (weeks 5-12)*: port the load-bearing infrastructure packages — internal libraries, robot description, message-only packages.
    - *Phase 2 (weeks 13-24)*: port drivers and perception, with bridge keeping them visible to remaining ROS 1 consumers.
    - *Phase 3 (weeks 25-36)*: port planners, controllers, mission logic. Run the full stack in simulation on ROS 2.
    - *Phase 4 (weeks 37-44)*: dev-robot hardware bring-up. Internal staging fleet.
    - *Phase 5 (weeks 45-52)*: customer pilot, fleet rollout, bridge sunset.
53. For *immediate-cutover*, the plan compresses Phase 1 through Phase 5 into 4-8 weeks and accepts higher risk; reserve only for small stacks with no live fleet.
54. For *gradual-bridged-multi-year*, the plan budgets explicit bridge-maintenance work and sets a hard sunset date — without it the bridge becomes permanent.

### Stage 12 — Render

55. Produce a `migration_plan` with: executive summary, package inventory and triage table, distribution choice rationale, interface-mapping summary, bridge strategy, lifecycle and composition redesign, parameter and launch migration, action and dynamic-reconfigure migration, testing strategy, risk register, and phased rollout schedule.
56. Produce a `package_migration_table` as the tracking artifact for the migration team.

## Decision frameworks

Several recurring decisions show up in every migration. The planner walks through each.

### Port vs rewrite

For each package, the team decides whether to *port* (preserve the design, change the API) or *rewrite* (re-do the design in ROS 2 idioms). The planner applies this rubric:

- **Port** when the ROS 1 design is good and the team understands it. The team will save time by translating rather than redesigning.
- **Rewrite** when the ROS 1 design was constrained by ROS 1 idioms that ROS 2 fixes (no lifecycle, no actions in some flows, parameter server as a global blackboard). The team wins by leaning into ROS 2.
- **Rewrite** when the ROS 1 implementation was the source of recurring bugs. Migration is a license to fix.
- **Rewrite** when the ROS 1 implementation has minimal test coverage. Porting an untested package gives untested ROS 2 code — bring tests with the rewrite.
- **Port** when the package is small and stable and the team is short on time.

For each package on the migration table, the planner emits a port-or-rewrite recommendation with a one-line rationale.

### When to bridge a package vs migrate it

The ros1_bridge lets a ROS 1 package and a ROS 2 package coexist. The planner applies this rubric:

- **Bridge** when the package has no urgent need to be on ROS 2 and the third-party ports are not ready yet.
- **Bridge** when the team lacks bandwidth for the migration but needs the system to keep working.
- **Migrate** when the package is on the critical path of another migration (e.g., the planner depends on the localization being on ROS 2).
- **Migrate** when the bridge cost is high (large messages crossing the bridge multiple times per second).
- **Bridge** for packages owned by external teams or vendors who control the migration schedule.

Bridged packages get a *sunset deadline* in the plan. Bridge-forever is not a plan.

### When to wait for a third-party port vs go independent

For each third-party dependency without a ROS 2 port, the planner choices are:

- **Wait** for the upstream port. Best when the upstream is responsive and the team can use the bridge in the meantime.
- **Contribute** to the upstream port. Best when the team has expertise and the upstream welcomes contribution.
- **Fork and port** internally. Best when the upstream is stale and the team needs to own the result.
- **Replace** with a ROS 2-native alternative. Best when a ROS 2-native alternative exists with comparable quality.
- **Build internally**. Worst case; only when the dependency is small and the team can absorb maintenance.

Each third-party dependency on the migration table gets a recommendation here.

### When to upgrade interfaces during migration

The migration is a one-time chance to fix message designs without a separate breaking change. The planner applies this rubric:

- **Fix** when the field has a units bug (`angle` without a unit), a frame bug (no `frame_id`), or a timestamp bug (no `stamp`). These are cheap to fix at the migration point.
- **Fix** when the message conflates unrelated data and was a bottleneck.
- **Preserve** when the message has a large surface area across the codebase and the fix would multiply the migration work by 10x.
- **Preserve** when the message is on a customer integration surface — breaking it cascades to the customer migration.
- **Version** when the team needs both old and new shapes coexisting; ROS 2 supports multiple message types so a `*V2` suffix on the new shape works.

## Examples

A representative example: a 14-package mobile-robot stack on ROS 1 Noetic with a custom navigation pipeline (not the ROS 1 navigation stack), a custom MoveIt configuration for a manipulator arm, and three custom sensor drivers. The planner would likely recommend: target Humble, phased over 9-12 months with ros1_bridge for live demos; port message-definitions and the robot-description package in Phase 1; port sensor drivers (drivers first, because everything downstream depends on them) in Phase 2; rewrite the navigation pipeline as a Nav2-based stack rather than literal port; migrate to MoveIt2 in parallel with a planning team-of-one; sunset the bridge by month 10. The plan would flag that ROS 1 Noetic's Ubuntu 20.04 dependency limits where ros1_bridge can run.

## Common pitfalls and mitigations

The planner names the recurring ways migrations go off the rails.

- **The "while we're at it" trap**. Mid-migration, the team decides to also redo the planner, rewrite the perception stack, and adopt a new robotics framework. The migration triples in scope and ships late. *Mitigation*: enforce that migration-phase work is migration, not new features. Capture feature ideas as follow-up work.
- **The estimation collapse**. The first three packages port in two days each; the team extrapolates to estimate the rest at two days each; the team is wrong. The complex packages take ten times as long. *Mitigation*: estimate by package complexity tier, not by historical average; multiply complex-tier estimates by 2-3x.
- **The bridge-forever drift**. The bridge "temporarily" handles a few topics. Two years later, the bridge handles thirty topics, no one remembers the original sunset date, and the system is permanently bilingual. *Mitigation*: explicit sunset date in the plan, a Jira board column for bridge-sunset work, and a quarterly check on bridge surface area.
- **The driver mismatch**. The ROS 2 driver for a sensor exists but has subtle behavior differences from the ROS 1 driver (slightly different timing, different units, different field ordering). Mission-level bugs result. *Mitigation*: side-by-side validation of every ported driver against the ROS 1 reference on the same hardware.
- **The dual-maintenance trap**. During a long phased migration, the team must patch bugs in both ROS 1 and ROS 2 versions. The team is twice as slow and twice as bug-prone. *Mitigation*: keep the migration window short, or freeze ROS 1 features and only fix safety bugs in the ROS 1 branch.
- **The launch-file translation failure**. ROS 1 `.launch` XML translates structurally to ROS 2 XML launch but the semantics differ. Teams that copy-paste-rename get launches that look right and behave wrong. *Mitigation*: rewrite launch files rather than translate; document the differences explicitly.
- **The QoS surprise**. The team ports a topic and discovers that the default QoS in ROS 2 is incompatible with the publisher's intent. Topics silently fail to deliver. *Mitigation*: as part of the migration, every topic gets a deliberate QoS choice — see the architecture-reviewer skill for the framework.
- **The lost custom-message bridge**. The bridge needs message-type information for both sides; teams forget to build their custom messages in the ROS 1 environment after migrating them to ROS 2, and the bridge stops translating them. *Mitigation*: maintain dual builds of the message-definitions package until bridge sunset.

## Cost and timeline modeling

The planner produces effort estimates per package using a complexity tier × language × test-coverage rubric:

- *Trivial Python port with good tests*: 1-3 engineer-days.
- *Trivial C++ port with good tests*: 2-5 engineer-days.
- *Moderate port (mid-sized node, some custom interfaces) with adequate tests*: 1-3 engineer-weeks.
- *Complex port (large node, action server, dynamic_reconfigure, plugin interfaces) with adequate tests*: 1-2 engineer-months.
- *Anything with bad or no tests*: add 50-100% for test-creation work.
- *Anything with hardware in the loop*: add 30-50% for bench validation.
- *Anything with customer-fleet impact*: add 25% for rollout and rollback infrastructure.

These are starting estimates that the team should refine after the first three packages are actually migrated. The first three packages always teach more than the planning estimates suggest.

The total migration cost equals the sum of per-package costs plus a fixed-overhead bucket for: ROS 2 CI setup, ros1_bridge integration, team training (1-3 weeks per engineer), regression-test infrastructure, simulation environment porting, and the post-migration stabilization window (typically 1-2 months after the last package ports).

## Outputs

The skill emits two artifacts. The first is `migration_plan`, the narrative plan covering all stages. The second is `package_migration_table`, the per-package tracking artifact.

The plan is the proposal document — the artifact taken to leadership for approval, used by engineering managers to staff the work, and referenced by engineers when they need to know why a decision was made. The table is the tracking artifact — updated weekly, owned by the migration lead, used to triage blockers and re-plan as reality diverges from estimate.

## Organizational and team-readiness considerations

Migrations are not purely technical. The planner surfaces the team-side concerns leadership must address:

- *Training*. ROS 2 idioms differ enough from ROS 1 that experienced ROS 1 engineers are not automatically experienced ROS 2 engineers. Budget 1-3 weeks of focused learning per engineer, more if they are also learning DDS for the first time.
- *Hiring*. ROS 2 expertise is increasingly required for new hires. Migration is a moment to refresh job descriptions and adjust hiring criteria.
- *Documentation*. The migration is the chance to document architecture decisions that were never written down. Refusing this chance costs the next generation of engineers months.
- *On-call burden*. During the bridge phase, on-call rotations cover two systems. Account for this in capacity planning.
- *Communication with customers*. If a customer fleet is in scope, the migration plan includes customer-facing communication: what changes, what doesn't, what to test on their side, what the rollback path is. A surprise migration is a churn event.
- *Internal demos and milestones*. Migrations are long and morale-draining. Plan demonstrable milestones (first ROS 2 node in production, first bridged subsystem, first ROS 2-only robot) and celebrate them.
- *Risk to ongoing roadmap*. Migration draws engineering capacity away from new features. Leadership must understand the trade-off explicitly; otherwise mid-migration pressure to "also ship the new gripper" derails the plan.

## Tooling and infrastructure checklist

Before Phase 1 starts, the planner verifies the following is in place:

- ROS 2 CI is green on at least one canonical package (the message-definitions package is a typical first port for this reason).
- ros1_bridge builds for both the source ROS 1 distribution and the target ROS 2 distribution on the team's CI infrastructure.
- A ROS 2 simulation environment exists — Gazebo or Gz with the robot model loaded and the standard sensors simulated.
- A bench-rig version of the robot is available for hardware-in-the-loop testing without putting motion at risk.
- Rosbag conversion tooling is selected and validated on a representative ROS 1 bag.
- A documentation home for the migration (a wiki page or doc repository) is set up, owned, and visible to all engineers.
- A Jira / Linear / equivalent project board exists with one ticket per package and per third-party dependency.
- A migration lead is named — a single accountable engineer or engineering manager who owns the plan day-to-day.

Phase 1 cannot start cleanly without these. Skipping them is the most common cause of migrations that look on track for three months and then crater.

## Communication plan

A long migration is also a communication exercise. The planner specifies the communication artifacts:

- *Kickoff document* for the engineering organization: why migrate, target distribution, expected duration, what changes for whom.
- *Weekly status* during the migration: phase progress, blockers, decisions taken, decisions deferred.
- *Customer notice* if a customer fleet is affected: what changes, what doesn't, what to test, what the rollback path is.
- *Pre-deployment notice* before each fleet rollout phase: the specific robots and environments affected, the date, the rollback window.
- *Post-migration summary* at the end: what was delivered, what was deferred, lessons learned, what the team is now able to do that it could not before.

Communication is owned by the migration lead with input from engineering management. Skipping the communication artifacts is the surest way to discover three weeks in that another team had been depending on a behavior the migration broke.

## Limitations

The planner produces a plan, not a port. It cannot:
- Estimate effort precisely — every package has surprises that emerge only during the actual port.
- Verify that a third-party dependency's ROS 2 port behaves exactly like its ROS 1 ancestor.
- Replace simulation regression and on-hardware regression testing.
- Predict subtle middleware behavior differences (DDS choice, discovery, multicast on the team's network).
- Substitute for safety review of the migrated stack before any deployment on motion-capable hardware.

Migrations are where teams discover the parts of their ROS 1 system they did not understand. Budget extra time for those discoveries, and treat the migration as a chance to leave the system in better shape than you found it.

The planner's output is most valuable when used as a living document. The first version reflects the team's understanding at the start of the migration; revisions reflect what was learned in the first weeks. A plan that does not change over the course of a migration was either trivially correct (unlikely on a large stack) or is being ignored.

Finally, every recommendation in the plan touches a robot eventually. The migration is not done when the code compiles or the tests pass; it is done when the robot has been validated in its target environment with the migrated stack. Until then, ROS 1 is still the source of truth for what the robot does.

## Rollback strategy

Every phase of the plan has an explicit rollback. The planner specifies:

- *Per-package rollback*: a package can be reverted to its ROS 1 form if the ROS 2 port misbehaves, with the ros1_bridge picking up the slack. The plan names which packages can rollback this way (most can during the bridged phase) and which cannot (typically the load-bearing infrastructure ported in Phase 1).
- *Per-robot rollback*: an individual robot in a fleet can be flashed back to a known-good ROS 1 image. The plan specifies image retention (last 3 versions minimum) and the rollback procedure.
- *Per-environment rollback*: dev, staging, and prod each maintain independent ROS 1 fallbacks until the prod fleet has been on ROS 2 long enough to retire them. Premature retirement of the ROS 1 environment is a common late-stage mistake.
- *Decision criteria for rollback*: the plan names the metrics that trigger rollback consideration (safety event, sustained reliability regression, customer-impact escalation). Without explicit triggers, rollback discussions become opinion debates in a crisis.
- *Communications for rollback*: who is told, in what order, what they are told. A rollback that catches operations and customer success by surprise is its own incident.

The agent flags any phase of the plan that lacks an explicit rollback. "Forward only" is acceptable for the final consolidation phase; it is not acceptable for any phase that touches a customer fleet.

## Post-migration consolidation

The migration is not done when the last package ports. The planner allocates a consolidation phase:

- *Re-audit the architecture* using the architecture-reviewer skill. Migrations leave compromises that should be cleaned up — QoS choices made hastily, lifecycle decisions deferred, executor configurations that "work for now."
- *Re-tune Nav2 or other major subsystems* using their respective tuning skills. Parameter values that worked on ROS 1 are rarely optimal on ROS 2; the underlying middleware and execution model differ.
- *Sunset the bridge*. Remove the ros1_bridge from the build and the runtime. Delete the dual-build infrastructure for messages. Reclaim the maintenance budget.
- *Refresh the documentation*. The pre-migration docs reference ROS 1 idioms; rewrite to reflect ROS 2 reality.
- *Hold a retrospective*. What estimate buckets were systematically wrong? Which packages took longer than expected and why? Capture the lessons for the next major upgrade.
- *Set the next milestone*. A ROS 2 LTS distribution has a finite support window; the team should set the date for the next distribution-upgrade evaluation rather than discovering it under deadline.
