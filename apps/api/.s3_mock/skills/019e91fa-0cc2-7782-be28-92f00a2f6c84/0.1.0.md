# Reproducibility Audit

> **Mandatory disclaimer.** This skill produces methodology guidance for
> lab documentation practices. Regulated environments (GLP, GMP, FDA 21
> CFR Part 11) impose specific record-keeping and electronic-signature
> requirements that this skill describes generically; compliance for any
> regulated workflow must be reviewed by qualified Quality and Regulatory
> staff.

## When to use

Use this skill when the user wants to **audit a research artifact for
reproducibility** before publication, before handing it off to another
team, or as part of a journal/repository submission. Typical asks:

- "Is this notebook reproducible?"
- "Audit the analysis behind Figure 3."
- "Give me a reproducibility scorecard for our pipeline."
- "What's missing for an external reviewer to re-run this?"

The skill produces a **scorecard plus a gap list plus a prioritised
remediation plan**. It does not re-run the artifact itself — it audits
the inputs, code, environment, and outputs as evidence of whether re-run
is *possible*.

Do **not** use this skill to:

- substitute for an actual re-run by an independent person (that
  remains the gold standard);
- assess scientific correctness or statistical validity (those are
  separate review activities);
- audit human-subjects or animal-use compliance (different governance);
- audit security or IP exposure (different specialist domain).

## How to apply

Score the artifact across the **eight dimensions below**. Each dimension
has explicit criteria for the four levels — `Strong`, `Adequate`,
`Weak`, `Missing` — and a checklist of evidence to look for. Cite
specific filenames, paths, or document sections as evidence; never
hand-wave.

Final output is the scorecard plus a gap list ranked by remediation cost
and reproducibility impact.

### Dimension 1 — Data availability

What you are scoring: can a reader obtain the *inputs* the analysis
consumed?

Levels:

- **Strong**: every input dataset is publicly available, has a stable
  identifier (DOI, accession number, archived URL), and is referenced
  by the artifact at that identifier. License is stated. Access steps
  are documented.
- **Adequate**: inputs are available on request or behind a controlled-
  access repository with a documented application process; identifiers
  exist; a frozen snapshot exists.
- **Weak**: inputs are described but live only on author hardware, lab
  fileshares, or vendor portals without versioning; "available on
  request" with no process.
- **Missing**: inputs are not described or are described only by
  semantic type ("the patient data", "the cell line images") with no
  retrieval path.

Evidence to capture: dataset identifiers, repository names, access
instructions, license, file-level hashes if present.

Special case — **human-subjects or sensitive data**: data may be
appropriately restricted; in that case `Adequate` requires a clearly
documented access process and a synthetic or shareable subset for
methods testing.

### Dimension 2 — Code availability

What you are scoring: can a reader obtain the *code* that consumed the
data?

Levels:

- **Strong**: code is in a public version-controlled repository (Git);
  a specific commit hash or tagged release pins the version used for
  the artifact; the repo has a permissive or appropriately open licence;
  README explains how to run.
- **Adequate**: code is available on request with a known release tag
  or zenodo deposit; licence is stated.
- **Weak**: code is described but only as "available from the
  corresponding author"; no version pin.
- **Missing**: code is not provided; figures/tables cannot be regenerated.

Evidence to capture: repo URL, commit/tag, licence file, README
existence and quality.

Hygiene flags to record even if a dimension scores `Strong`:

- Notebook outputs committed alongside source (good for inspection,
  but auditor must note that committed outputs may not match a re-run).
- `notebooks/` mixed with `src/` without separation.
- Hard-coded absolute paths.
- Empty or default-name notebooks (`Untitled-3.ipynb`).

### Dimension 3 — Environment capture

What you are scoring: can a reader recreate the *software environment*?

Levels:

- **Strong**: environment is fully pinned (lockfile with exact
  versions, e.g. `requirements.txt` with `==`, `renv.lock`,
  `environment.yml` with pinned builds, or a container image with a
  digest). A `Dockerfile`, `apptainer.def`, or `repo2docker`-compatible
  config exists. Hardware assumptions (GPU, specific CPU flags) are
  named.
- **Adequate**: a top-level dependency list exists with version ranges
  (`>=`, `~=`) and a tested-on stanza naming OS and Python/R version.
- **Weak**: dependencies are listed by name only ("we used scikit-learn
  and matplotlib"), no versions.
- **Missing**: no environment information at all.

Evidence to capture: presence and contents of `requirements.txt`,
`environment.yml`, `Pipfile.lock`, `poetry.lock`, `renv.lock`,
`Dockerfile`, `apptainer.def`; tested-on platform list; reliance on
system tools (samtools, bcftools, ffmpeg) and whether their versions
are pinned.

Note for biotech contexts: many bioinformatics pipelines depend on
system binaries and reference genomes outside the language package
manager. Capture the *reference data* version (genome build, gene-model
release) as part of environment.

### Dimension 4 — Parameter and configuration logging

What you are scoring: are *all* parameters that affected the result
captured?

Levels:

- **Strong**: every parameter is in a versioned config file (YAML/JSON/
  TOML) loaded by the code; the config file is committed and
  referenced by the artifact; defaults are documented; any
  command-line overrides used to produce the result are logged.
- **Adequate**: parameters appear as named constants at the top of the
  notebook/script, with comments, and the values used are visible.
- **Weak**: parameters are inline magic numbers scattered through the
  code with no documentation.
- **Missing**: parameter values are not recoverable from the artifact.

Evidence to capture: presence of `config.yaml`, `params.yml`, top-level
constants block; parameter-sweep records; logged parameter values in
output artifacts.

### Dimension 5 — Random-seed and stochastic-process control

What you are scoring: are *stochastic* steps deterministic across runs?

Levels:

- **Strong**: every stochastic operation has an explicit seed; seeds
  are set for *all relevant libraries* (Python `random`, NumPy,
  framework-specific RNGs for PyTorch / TensorFlow / JAX, R `set.seed`);
  the seed values are recorded with the result; non-deterministic GPU
  ops are flagged and bounded.
- **Adequate**: a global seed is set at the top of the analysis but
  framework-specific seeds are not addressed; deterministic *up to
  framework-version* changes.
- **Weak**: a seed is mentioned only in prose ("we used seed 42") but
  not visible in code.
- **Missing**: no seed control; results vary between runs.

Evidence to capture: `set_seed` calls, library coverage, GPU
determinism flags, recorded seed values in result outputs.

Stochastic processes to look for: train/test splits, bootstrap
resampling, cross-validation folds, MCMC chains, neural-network
initialisation, jittered plot layouts (yes, these affect figure
reproducibility).

### Dimension 6 — Execution provenance

What you are scoring: is there a *trace* of how the artifact was
produced?

Levels:

- **Strong**: a workflow tool (Snakemake, Nextflow, Make, `dvc repro`,
  `targets` for R, Quarto's render manifest, or a notebook executed
  via `papermill` / `jupyter nbconvert --execute`) declares the
  dependency graph and records execution. A log of the actual run
  exists (timestamps, hostname, runtime). A `repo2docker` /
  Binder-compatible configuration enables one-click rebuild.
- **Adequate**: an end-to-end script (`run_all.sh`) exists; manual
  steps are documented as numbered ordered steps.
- **Weak**: steps are described in prose; no executable order
  specification.
- **Missing**: no provenance — the artifact reads as a frozen output
  with no path back to the inputs.

Evidence to capture: workflow files, run logs, `papermill` output,
Quarto render manifests, hash-pinned containers.

### Dimension 7 — Result regeneration test

What you are scoring: would a re-run *produce the published result*?

Levels:

- **Strong**: a regeneration test is documented (or has been performed
  by a colleague) — re-run on the captured environment produces
  outputs that match within stated tolerances (bit-identical for
  deterministic flows; within an explicit tolerance for stochastic
  flows). Any tolerances are justified.
- **Adequate**: a key result has been spot-checked by an independent
  party; no full re-run, but a sanity check.
- **Weak**: regeneration has been claimed but not documented.
- **Missing**: no regeneration evidence at all.

Evidence to capture: test scripts, CI runs, colleague sign-off,
documented tolerance bands.

Notes:

- For stochastic results, the *seed-controlled* output should be
  bit-identical; the *substantive* result (an estimated effect, a
  selected feature set) should be within a stated tolerance.
- For wall-clock-dependent results (e.g. timing benchmarks), the
  tolerance must be explicit and the hardware described.

### Dimension 8 — Linkage to raw lab record

What you are scoring (specific to biotech): does the analysis trace
back to a **lab notebook entry, batch record, or sample-tracking
system**?

Levels:

- **Strong**: every dataset consumed by the analysis is linked to a
  lab notebook entry ID and/or sample accession; each sample's
  provenance (lot numbers, passage, batch) is traceable; the lab
  notebook references the analysis commit hash, and the analysis
  references the notebook entry ID — a **bidirectional link**.
- **Adequate**: one-way link exists (analysis → notebook entry, or
  notebook entry → analysis), with sample metadata present in a
  spreadsheet or LIMS export.
- **Weak**: samples are named but their provenance is recoverable only
  by tribal knowledge.
- **Missing**: analysis treats data as a black box; no link to the
  bench.

Evidence to capture: notebook entry IDs, sample sheets, LIMS export
filenames, the presence (or absence) of a bidirectional ID convention.

Why this dimension matters in biotech: computational reproducibility
is necessary but not sufficient; a "reproducible" analysis of a
wrongly-labelled sample is not reproducible science.

## Scorecard format

Produce a table:

| Dimension | Level | Evidence | Gaps | Remediation cost |
| --- | --- | --- | --- | --- |
| 1. Data availability | Strong / Adequate / Weak / Missing | (cite filenames, identifiers) | (bullets) | Low / Medium / High |
| 2. Code availability | … | … | … | … |
| 3. Environment capture | … | … | … | … |
| 4. Parameter logging | … | … | … | … |
| 5. Seed control | … | … | … | … |
| 6. Execution provenance | … | … | … | … |
| 7. Regeneration test | … | … | … | … |
| 8. Lab-record linkage | … | … | … | … |

Overall reproducibility level is the **minimum** across the eight
dimensions (the weakest link governs). State this explicitly; do not
average.

## Gap list and remediation plan

After the scorecard, produce a numbered list of gaps, each with:

- **Gap**: one sentence describing what is missing.
- **Dimension**: which of the eight (a gap can touch more than one).
- **Impact**: what is *not* recoverable today because of this gap.
- **Cost**: rough effort (Low / Medium / High).
- **Suggested fix**: concrete action (e.g. "add `environment.yml` with
  pinned builds and a `tested-on` stanza"; "add `set_seed(42)` plus
  framework-specific seeds at the top of `train.py`"; "deposit
  raw FASTQ to SRA under PRJ-… and reference the accession in the
  README").

Rank the list: first by impact, then by inverse cost (high-impact,
low-cost fixes float to the top — these are the "audit quick wins").

## Style rules

1. Cite evidence by **filename and line/section**, not in prose.
2. Distinguish **claims** (what the artifact says) from **evidence**
   (what is actually present). A `requirements.txt` mentioned in the
   README but absent from the repo is a `Weak`, not `Adequate`.
3. Score **what is present**, not what *should* be present.
4. Do not assess scientific correctness — only reproducibility.
5. When the artifact is partially closed (e.g. clinical data), state
   the access process and do not penalise appropriate restriction.
6. The audit report must be re-runnable by another auditor against the
   same artifact and reach the same scorecard within ± 1 level per
   dimension.
7. Never silently upgrade a dimension based on author intent
   ("they plan to release"). Score the artifact as it is.

## Inputs

- `artifact_description` — what to audit.
- `artifact_type` — selects which evidence prompts apply (e.g. R
  Markdown adds `renv.lock`; Snakemake adds `Snakefile` and `config/`
  audit).
- `target_environment` — sets the bar; "external reviewer" requires
  Strong on Dimensions 1–3; "bit-identical regeneration" requires
  Strong on 3 and 5.

## Outputs

A single markdown audit report: scorecard table, overall level, gap
list, prioritised remediation plan. The footer must contain:

> *This audit assesses reproducibility evidence as observed in the
> artifact at the time of audit. It does not assess scientific
> correctness, statistical validity, ethical approval, or regulatory
> compliance. Re-audit after remediation. For regulated workflows,
> reproducibility evidence is necessary but not sufficient; compliance
> must be confirmed by qualified Quality and Regulatory staff.*

## Examples

> **User**: "Audit the analysis behind Figure 3 of our paper. It's a
> Jupyter notebook plus a CSV of QC-passed samples; target is external
> reviewer."
>
> **Assistant**: produces the eight-dimension scorecard. Dimension 1
> scores `Adequate` (CSV cited but only on lab fileshare); Dimension 2
> `Strong` (GitHub repo + tagged release); Dimension 3 `Weak`
> (`requirements.txt` exists with `>=` ranges, no lockfile); Dimension
> 4 `Adequate` (top-of-notebook constants); Dimension 5 `Missing` (no
> seeds, despite t-SNE used in figure); Dimension 6 `Weak` (no
> workflow file); Dimension 7 `Missing` (no regeneration test);
> Dimension 8 `Weak` (samples named, no notebook entry IDs). Overall:
> **Missing** (governed by weakest links). Gap list ranks "add seeds"
> and "deposit CSV with DOI" as high-impact / low-cost quick wins.

## Limitations

This skill **does not**:

- re-run the artifact (it audits evidence of reproducibility, not
  reproducibility itself);
- assess scientific correctness, statistical power, or interpretation;
- audit ethical, regulatory, IP, or security exposure;
- substitute for a peer reviewer or a journal's reproducibility editor;
- audit compliance with a specific regulatory regime (GLP, GCP, GMP) —
  defer to Quality / Regulatory specialists.
